# InkTeach 新手开发手册

> 给不会写代码、只会对话的人。记住三件事就够：**一次一件事、说清"怎么算对"、没证据不算完。**

## 一、心法三条

1. **你负责"要什么"和"对不对"，它负责"怎么做"。** 不用懂实现，但要能说清现象和期望。
2. **一次只说一件事。** 三件事混在一句话里 = 三倍返工。
3. **没看到证据不算做完。** 它说"已通过"不算，截图 / 自检报告 / 你自己点一遍才算。

## 二、三种说法，对应三种场合

| 场合 | 怎么说 | 例子 |
|---|---|---|
| **小修**（1–2 个文件） | 直接说现象 + 期望 | "收藏弹窗标题栏的关闭按钮偏左了 4 像素，往右挪。" |
| **功能**（新面板 / 多文件） | 目标模式：只说做完是什么样 | "做一个图形库面板：能开、能搜索、点卡片就插入到画布，插入后一步撤销。" |
| **拿不准** | 先要方案，别让它动代码 | "先别改代码。给我 3 个做法 + 你推荐哪个，说理由。" |

**目标模式为什么好用**：它不会每步停下来问你"要不要继续"，会自己拆步骤、自己自检、做完汇报。
代价是——**你必须把"完成标准"写出来**，否则它不知道什么时候算完。

## 三、每次开发的固定闭环

```
1. 说目标（带验收标准）
2. 它列 3–5 步 → 开做
3. 中途扫一眼它在改哪个文件（心里有数就行）
4. 要证据：截图 / 自检结果
5. 你自己上手点一遍
6. 满意 → /new 开下一个；不满意 → /undo 退回重说
```

第 5 步不能省。AI 的"自检通过"和"人觉得好用"是两件事。

## 四、把话说清楚的模板

```
位置：图形面板 → 第二行第三个卡片
现象：点下去没反应
期望：和第一行一样选中、变蓝、能用
```

一句版：**"在哪 + 什么现象 + 应该怎样"**。

反例（会被它自由发挥）：
- ❌ "图形面板有点问题，你优化一下"
- ❌ "帮我重构一下 Engine.cs"
- ❌ "把界面做得好看点"

## 五、验收三看

| 看什么 | 怎么做 | 通过标准 |
|---|---|---|
| 看画面 | `/shot 名字` 截图 | 布局没歪、文字没裁、状态对 |
| 看自检 | `/check 图形面板` | 相关的那一条 PASS，失败项有原话 |
| 看手感 | 自己点一遍 | 能开、能关、能撤销、不卡 |

动效 / 光标 / 笔迹跟手这类，用 `/video 动作` 录 8 秒 + 抽帧，光看截图看不出来。

## 六、出问题怎么退（比"修"更重要）

| 情况 | 做法 |
|---|---|
| 改歪了 | `/undo`（撤回上一轮，提示词回到输入框可以改） |
| 越改越乱 | 说"回到上一版，换一种做法" |
| 想看看改了啥 | 说"列一下这次改了哪些文件、各改了什么" |
| 实在不行 | 说"用 git 撤回这次改动"（它会先问你要不要） |

**不要在错的版本上继续叠需求**，越叠越难退。

## 七、你真正要记的命令

项目命令（`/run` `/check` `/shot` `/video` `/release`）已于 2026-11-15 撤回，现在只剩全局的：

| 命令 | 用途 |
|---|---|
| `/guide 问题` | 忘了怎么提需求就问它 |
| `/arch 问题` | 架构意见（不出代码） |
| `/deep 难题` | Opus 做一次深度判断 |
| `/c 范围` | 验收 + 视觉审核 |

再加两个保命的：`/new` 换话题、`/undo` 退回上一轮。
截图和自检直接说也行："截个图存到 reports" / "跑一下图形面板的自检"。

## 八、防屎山的五句话（直接复制）

1. "改动最小，不要顺手改别的。"
2. "先说打算改哪几个文件、每个文件加什么，我点头再写代码。"（大功能用）
3. "新代码放新的 partial 文件，别继续往 Engine.cs 里塞。"
4. "不要新增依赖，不要改 csproj / run.ps1 / publish.ps1。"
5. "改完只跑相关的那一条自检，不要全量。"

## 九、五个新手常犯的错

1. **一次说三件事** → 它做了两件半，你分不清哪件错了。
2. **说"优化一下""重构一下"** → 没有验收标准，它自由发挥，越改越乱。
3. **不给位置让它全库找** → 慢，而且容易改到同名的另一处。
4. **它说完成就信** → 一定要自己点一遍。
5. **一个会话连做 5 个功能** → 上下文串味，它会把上一个功能的状态记错。做完一个就 `/new`。

## 十、规范在哪（你不用背）

| 文件 | 管什么 |
|---|---|
| `docs/module-map.md` | 功能 → 模块目录 → 文件 → 段落锚点（改代码先查这张） |
| `docs/test-playbook.md` | 测试分层、命令表、基线对比（L1/L2/L3） |
| `docs/feature-specs.md` | 收藏 / 图形 / 图片 / AI 的具体功能规则（按需读） |
| `AGENTS.md` | 界面硬规则：入口分级、面板尺寸、验收矩阵 |
| `docs/dev-rules.md` | 写代码硬规则：先读后写、改动最小、大文件只加一段 |
| `docs/architecture.md` | 架构决定（ADR）：为什么这么设计、否决了哪些方案 |
| `docs/app-run.md` | 怎么启动、内置自检、怎么截图录视频 |

**只有 `AGENTS.md` 每次会话自动读**；其余三个在用到时让它读（说"先看 docs/app-run.md"）。
你要做的只是——**别让它在没有规则的地方自由发挥**。

## 十一、每天开工 / 收工

- **开工**：`/new`，一句话说今天只做哪一件事。
- **收工**：让它总结"改了哪些文件 / 现在什么状态 / 下一步是什么"，大改写进 `docs/acceptance.md`。
- **发版前**：才跑全量自检（`--paneltest` / `--recoverytest` / `--keytest` 三条都跑）。
