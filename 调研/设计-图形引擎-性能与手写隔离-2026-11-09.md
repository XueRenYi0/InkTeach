# 图形引擎：性能预算与手写隔离（调研补充）

日期：2026-11-09
原则：**允许引入方便的库，但控制性能；绝对不能影响手写体验。**

---

## 0. 结论

图形引擎可以引入库，但必须遵守两条硬规则：

1. **手写路径（WM_POINTER / 笔迹采样 / 笔迹渲染）上，绝不做图形引擎的工作**：
   不解析、不布局、不栅格化、不建 D2D 资源、不等待后台、不抢锁、不分配大对象。
2. **不做新的“图形层/缓存层/脏矩形系统”**：
   - 图形就是 `Doc.Strokes` 里的普通对象，和三角形/圆/抛物线/墨迹同一套；
   - 渲染缓存复用现有 `CanvasTileCache` / `Doc.Dirty`；
   - 性能只优化“**不重复算**”：解析/采样结果挂在对象上，参数不变不重算；
   - 手写进行中：图形不重算，已画好的静态图由现有分块缓存直接画。

这样既能用成熟库/算法，又不会把手写延迟拖坏，也不增加一套新工程。

---

## 1. 手写关键路径（不能碰）

```
WM_POINTERDOWN/MOVE/UP
  → 采样/预测
  → Stroke 点写入
  → D2D 笔迹几何/湿墨渲染
  → Present
```

这条路径的目标：

- 120Hz 屏幕：每帧 **≤ 8.3ms**；60Hz：≤ 16.7ms；
- 不允许 GC gen2 / 大数组分配 / 同步 I/O；
- 不允许等待后台线程、锁、Task.Result；
- 不允许在 `PointerMove` 里做表达式解析、曲线采样、布局、字体创建、位图上传。

**图形引擎的入口只能是“空闲调度器”**，不能挂在笔迹事件上。

---

## 2. 图形引擎的分层与线程模型

```
主线程（手写/输入/呈现）
  ├─ 笔迹：最高优先级，永远不阻塞
  ├─ 图形：普通对象，由现有 CanvasTileCache 画
  └─ 活动图形（当前选中/拖参数）：矢量直画，仅一个

图形计算（BelowNormal，单线程串行，空闲才跑）
  ├─ 表达式求值 / 曲线采样
  ├─ 几何/刻度/标签布局
  └─ 结果挂回对象；不做独立图形位图缓存

空闲判定：
  最后一次笔迹/触摸后 120–200ms 才允许启动图形重算
```

### 2.1 优化策略（复用现有机制）

- 图形对象存一份**已求值的几何**（点列/布局/文字）；
- `ParamsVersion` 不变 → 直接画，不重算；
- 参数变了 → 只标记该对象，等空闲重算；
- 渲染缓存直接用现有 `CanvasTileCache`，不新增 `FigureCache`；
- 拖动参数时：当前图形低采样实时画；松手后高质量重算一次；
- 不新增 LRU/内存池/独立脏矩形。

### 2.2 手写期间

- 笔按下 → 不启动新的图形计算；
- 笔迹期间图形不重算；现有静态图由 tile cache 画；
- 抬笔 + 空闲 120–200ms → 才允许重算；
- 图形更新只标现有 `Doc.Dirty` 的对应区域，不 `InvalidateAll`。

## 3. 允许引入的库（按手写风险排序）

| 库/方案 | 许可 | 用途 | 手写风险 | 结论 |
|---|---|---|---|---|
| **D2D（现有）** | Windows | 主画布、活动图形、缓存位图/command list | 低（同线程、可控） | **主渲染** |
| **SkiaSharp** | MIT | 公式位图（已有）、静态图形快照 | 中（CPU 栅格化，放 worker） | 仅静态/公式 |
| **ScottPlot 刻度算法** | MIT | 10→5→2.5→1 刻度、标签密度 | 无（只移植算法） | **采用算法** |
| **function-plot 渐近线算法** | MIT | 函数断段、渐近线检测 | 无（只移植算法） | **采用算法** |
| **NCalc** | MIT | 表达式解析/求值 | 低（解析一次，缓存表达式；求值快） | 可选 |
| **MathEvaluator / NTDLS.ExpressionParser** | MIT | 更快的表达式求值 | 低 | 可选（新库，需验证 AOT） |
| **DynamicExpresso** | MIT | C# 表达式树 | 中（编译/JIT、AOT 风险） | 不优先 |
| **AngouriMath** | MIT | 符号化简/验证 | 中（重，放后台） | 仅后台可选 |
| **Clipper2** | BSL/MIT | 多边形布尔/偏移 | 低（按需，不在笔迹路径） | 可选 |
| **planegcs** | LGPL | 完整 2D 约束求解 | 高（WASM/C++、重） | 后置独立模块 |
| **NeoGeoSolver.NET** | **GPL-3** | C# 约束参考 | — | **不能抄** |
| **JSXGraph / WebView2** | MIT/LGPL | 整体交互几何 | **高**（独立进程/焦点/延迟） | 不采用运行时 |
| **HelixToolkit** | MIT | WPF 3D | 高（另一套 GPU/窗口） | 不采用 |

### 3.1 表达式求值的选择

函数采样典型量：每帧 500–2000 个点。

- 若每点重新解析：几十 µs～ms/点，不可接受；
- 正确做法：**解析一次，编译/缓存 AST 或 delegate**，之后每点只求值；
- NCalc 可缓存 `Expression`，支持参数更新/编译；MIT、成熟；
- MathEvaluator/NTDLS 更快，但较新，需验证 NativeAOT/数值边界；
- 第一版建议：**自研小型 AST 解释器**（+ - * / ^、sin/cos/tan/log/exp/sqrt/abs、括号、参数），
  或 NCalc；不引入符号计算。
- AngouriMath 只用于后台“AI 结果校验/化简”，不进入采样循环。

### 3.2 3D

- 不建议 HelixToolkit/WPF 3D（另一套窗口/GPU/输入）；
- 用 D2D 自己做：
  - 4×4 投影矩阵（JSXGraph `view3d.js` 同思路）；
  - 顶点→屏幕；
  - 边/面深度排序；
  - 隐藏线先不做精确消隐，用深度排序/虚线近似。
- 计算量小，主线程/worker 都可控。

## 4. 普通对象 + 现有 tile cache（不新增缓存）

| 场景 | 方案 | 理由 |
|---|---|---|
| 手写中，画布上已有图 | 静态图已在现有 tile cache 里 | 和普通墨迹一样，不额外重算 |
| 未选中、无参数变化 | 不重算 | 图形对象只存上次求值结果 |
| 选中一个图，拖参数 | 只这个图矢量实时画；其他走 tile | 只有一个活动图，成本可控 |
| 松手 | 高质量重算一次 | 拖动时可低采样 |
| 多图同屏 | 复用 CanvasTileCache 的预算/淘汰 | 不新造 LRU/缓存层 |
| 导出/打印 | 离屏高分辨率 | 不在手写路径 |

### 4.1 为什么不需要新缓存格式

- 现有 `CanvasTileCache` 已经是 D2D 分块栅格缓存，普通墨迹/图形都走它；
- 图形对象只需要缓存“求值结果”（点列/布局/文字），不是位图；
- 位图/command list 的新缓存层不引入，避免工程量和擦除语义问题。

---

## 5. 性能预算（建议）

| 项目 | 预算 |
|---|---|
| 手写帧 | 120Hz ≤ 8.3ms；60Hz ≤ 16.7ms |
| 静态图 tile 绘制 | 每块 ≤ 0.2ms（现有 tile） |
| 活动图形矢量绘制 | ≤ 2ms（简单图）；复杂图降采样 |
| 图形重算 | 每次 ≤ 10ms；串行，BelowNormal，空闲才跑 |
| 现有 tile 内存 | 沿用 `CanvasTileCache` 预算 |
| GC | 手写期间 0 gen2；图形重算不产生大垃圾 |
| 图形更新延迟 | 抬笔后 120–200ms 才启动，避免抢手写 |

## 6. 验收/测试

新增 `--figurestress`（后续实现）：

1. 画布放 20 个图（函数/圆锥/几何/立体混合）；
2. 用合成笔迹以 120Hz 连续写 5 秒；
3. 同时后台不断改一个图的参数（模拟 AI/参数变化）；
4. 记录：
   - 笔迹输入→呈现 p50/p99；
   - 丢帧数；
   - GC gen2 次数；
   - 现有 tile cache 命中率；
5. 通过标准：p99 不高于基线 +1ms，无 gen2，无输入丢失。

没有这个测试，不允许把图形引擎接到主循环。

---

## 8. 澄清：不做额外的“湿墨层/脏矩形/图形缓存系统”

用户 2026-11-09 明确：**不要为了图形再单独做一层缓存、脏矩形、湿墨层；不要把工程量做大。**

正确理解：

- 图形就是 **Doc.Strokes 里的普通对象**，和三角形/圆/抛物线/墨迹一样：
  - 橡皮擦、选中、撤销、存档、导出走同一套；
  - 现有 `CanvasTileCache` 的分块缓存只是**渲染缓存**，不是第二份图形数据；
  - 擦除时照样删对象/标脏对应分块，不会“擦不掉”。
- **不新增** `FigureVisual`、`WetInkVisual`、`FigureCache`、独立脏矩形系统。
- 手写期间图形不重算；已经画好的静态图由现有分块缓存直接画，和普通墨迹一样。
- 性能优化只做“**不重复算**”，不做“新图层”：
  1. AI/解析/采样只做一次，结果（点列/布局）挂在对象上；
  2. 参数不变就不重算；
  3. 拖参数时只更新当前对象，采样降级；松手补高质量；
  4. 复用现有 `Doc.Dirty` / `CanvasTileCache`，不另造一套。

### 8.1 为什么这样不会影响手写

- 手写路径上没有任何新代码：采样 → 笔迹 → D2D → Present 原样；
- 图形对象在笔迹期间只是“被画出来的静态对象”，不触发解析/采样；
- 图形生成/参数重算发生在空闲/松手后，不在 `WM_POINTER` 里；
- 没有第二个窗口、第二个 swap chain、第二个输入焦点。

### 8.2 什么时候才考虑分层

只有 `--figurestress` 证明“现有 tile cache + 普通对象”在 20 图/120Hz 笔迹下 p99 超标，
才考虑把湿墨/图形拆成 DComp visual；**那不是第一版，也不作为默认方案**。
现在不排期、不增加工程量。

---

## 9. 最终建议

- **主渲染/手写：D2D，不动。**
- **图形：普通对象，复用现有 tile cache / Doc.Dirty；不新增缓存层。**
- **性能：只缓存“计算结果”（点列/布局），参数不变不重算；手写期间不重算。**
- **活动图形：D2D 矢量实时；只允许一个，松手后补高质量。**
- **表达式：解析一次 + 缓存 AST；NCalc/自研，不用符号引擎进采样循环。**
- **刻度/断段：移植 ScottPlot/function-plot 算法（MIT）。**
- **3D：自研 D2D 投影，不引 Helix/WebView2。**
- **约束求解：planegcs 后置独立模块；NeoGeoSolver 只参考（GPL）。**
- **JSXGraph：只参考依赖图/状态机，不整体跑。**
