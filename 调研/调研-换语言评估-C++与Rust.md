# 调研：换 C++ / Rust 的收益评估（内存与性能）

日期：2026-10-05　　状态：**已定论：不换语言（保持 .NET）；留档**。

> **2026-10-05 决定：不换 C++/Rust，保持 .NET 路线；软渲染 POC（`tools/softpoc/`）
> 已完成使命并删除，Rust 工具链也已卸载。** 本页保留评估结论与实测数据，
> 以后"要不要换语言"再被提起时直接引用这里。

> 用户问题：现在 .NET 8 + Direct2D，空闲约 90MB，控制得不错。想进一步为
> **4GB 内存的 Win10 教室机**优化，考虑换 C++ 或 Rust。问：
> ①换了以后能不能得到好的收益？②C++ 还是 Rust？③不换效果又怎么样？

---

## 〇、三句话结论

1. **收益有上限，而且上限不大**：换语言能动的只有"运行时"那 **约 31MB**；
   GPU 栈（约 42MB）、全屏合成缓冲（约 26MB）、笔画数据都不受语言影响。
   最好最好的情况：空闲 90MB → **65~75MB**，省 20~30MB，**不到 4GB 的 1%**；
   帧率/书写延迟的收益 **约等于 0**（瓶颈在 GPU/合成器，不在语言）。
2. **非要换，选 Rust**：windows-rs 是微软首方绑定，Direct2D / DirectComposition
   （含 `IDCompositionInkTrailDevice`）都有；内存安全 + 编译器兜底。
   C++ 只在"把现有 Win32 代码尽快直译过去"这一项上占优。两者**内存/性能等价**。
3. **不换是正确选择**。真正该做的两件事：**11-10 前升 .NET 10**（.NET 8 安全支持截止），
   以及（可选）**AOT spike**——但 AOT 有一条官方门槛（"不支持内置 COM"，见 §4.2），
   要先验证 Vortice 能不能过。真正影响 4GB 机器的是**长板书后的显存/驱动池回收**，
   那和语言无关。

## 一、现状（全部来自本仓库实测，先钉死）

空闲内存（2880×1800 @200%，Iris Xe 核显):

| 构成 | 量级 | 出处 |
|---|---|---|
| .NET 运行时 + JIT + 元数据 + 程序集 | **约 31 MB** | 启动内存调研 §二 |
| Direct3D 11 + Direct2D + DirectWrite | **约 42 MB** | 同上 |
| 全屏合成缓冲（交换链/图层） | **约 26 MB** | 同上（尺寸随分辨率走） |
| 空闲提交（Trim 后 / 自然） | **93.2 / 104.2 MB**；专用工作集 76 MB | 同上 §1.1 |

性能（同一批实测）：

| 指标 | 数值 | 说明 |
|---|---|---|
| 20 分钟板书（7200 笔 / 64 万点） | 提交 **145 MB**、显存 97 MB，内存曲线基本平 | 性能-内存与卡顿实测 §4.2 |
| 每帧记录耗时 | 均值 **1.7 ms** / 最差 7.9 ms（预算 16.7 ms） | 同上 §一 |
| 空闲 CPU / GPU | **0.0%**（有东西动才画） | 三家对比 §空载 |
| 书写时输入消费速率 | **55 点/秒**，无积压 | 三家对比 |
| Present → 上屏 | **1.0 个刷新周期** | 启动内存调研 §四 |

三家横向（2026-09-13 实测，同机同屏）：

| | 本原型（C#+D2D） | InkClass（WPF） | Inkeys（C++） |
|---|---|---|---|
| 空载工作集 / 提交 | **96 / 79 MB** | 255 / 227 MB | **432 / 382 MB** |
| 书写时单核 CPU | 13.1% | 14.5% | **89~96%** |
| 每采样点 CPU | **2.0~2.2 ms** | 3.4~3.5 ms | **55~60 ms** |

**一句话**：内存大头是图形栈 + 合成缓冲 + 驱动池，不是 C#；性能瓶颈在 GPU/合成，
也不在语言。现在的 90MB 在这个品类里已经是**第一梯队**（WPF 142MB、C++ 竞品 382MB）。

> 注：以上是 2880×1800 开发机的数字。目标教室机多是 1920×1080：
> 合成缓冲按像素约小 **2.2~2.5 倍**（26 → 约 11MB），真实空闲很可能只有
> **75~85MB**。**先量真机，再谈优化**。

## 二、问题 1：换了能得到什么收益？

### 2.1 那 90MB 里，谁是由语言决定的

| 空闲构成 | 量级 | 换 C++/Rust 能省吗 | AOT 能省吗 |
|---|---|---|---|
| .NET 运行时 + JIT + 元数据 + 程序集映射页 | 约 31 MB | **能，几乎全免**（只剩 CRT/std 几个 MB） | 能省一部分（估 15~30 MB） |
| D3D/D2D/DirectWrite（含驱动分配） | 约 42 MB | **不能** | 不能 |
| 全屏合成缓冲 | 约 26 MB | **不能**（跟分辨率和图层数走） | 不能 |
| 笔画数据 / 内容块缓存 / GC 堆 | 其余 | 基本不能（数据照样要存） | 部分（堆布局不同） |

### 2.2 最好情况与性能收益

- **内存**：原生重写的最优可能约 65~75MB 空闲（省 20~30MB，= 4GB 的 0.6~0.9%）。
  Rust 和 C++ 之间差异 **<5MB**（同样的图形栈，同样的驱动）。
- **性能**：≈ 0。理由：
  1. 热路径本来就是原生代码（D2D 光栅、合成器、驱动），C# 只是"攒 D2D 命令"；
  2. JIT 早已把热路径编译成机器码，Native AOT 主要省的是**启动和内存**，不是帧率；
  3. 书写期间已开 GC 低延迟档并自检断言无第 2 代回收，没有可感知的 GC 停顿；
  4. 现在的瓶颈：1.0 个刷新周期的上屏、GPU 2.9%、每帧 1.7ms——**没有可优化的语言级空间**。
- **启动**：现在冷启动 267ms；原生可能 ~150ms、AOT ~120~170ms。产品是"一节课启动一次"，
  这段收益用户基本无感。

### 2.3 反面证据：语言不保证结果

- **Inkeys（C++）**：空载 382MB、每采样点 55~60ms、停止输入后 14~46% CPU 积压——
  它是纯 CPU 软件渲染 + GDI 重绘。**C++ 不等于轻**。
- **Rust GUI 实测**：egui/wgpu 版 135MB，换软渲染 Slint 后 30MB——
  **是渲染栈决定内存，不是语言**（来源见 §六）。
- 官方 Native AOT 只说"更小的内存足迹"，具体数值依项目；本项目自己的估计是 15~30MB。

### 2.4 结论

换语言的收益是"优化级"的（20~30MB、启动快百来毫秒），**不是"台阶级"的**；
性能上买不到任何用户能感觉到的东西。拿它去解决"4GB 机器"是**用大炮打蚊子，而且打不到蚊子**。

## 三、问题 2：C++ 还是 Rust？

假设"就是要换"，对比如下：

| 维度 | C++ | Rust |
|---|---|---|
| 内存 / 性能 | 等价（同一图形栈） | 等价（论文里 Rust 内存略高于最优 C，实际不可感） |
| Windows 图形绑定 | **最全**：WRL/ATL、C++/WinRT、官方 D2D/DComp/Ink 样例 | windows-rs 为微软首方；`windows`、`windows-canvas`（Direct2D）、`windows-composition`；**`IDCompositionInkTrailDevice` 已有绑定** |
| 生态/样例贴近本项目 | 多（D2D 分层窗口、Overlay 样例） | 少，但你们 UI 全自绘，多数用不上 |
| 内存安全 | 手工 COM 引用计数 / 生命周期，UB 与泄漏靠纪律 | 默认安全，只有 COM 边界需要 `unsafe` |
| 移植难度 | 与现有 Win32 风格可**直译**，机械、前期快 | 所有权模型会**逼一次重构**（文档模型/撤销栈/空间索引的归属），前期慢 |
| 工具链 | VS / Windows SDK（反正 AOT 也要装） | rustup + MSVC 链接器；cargo/clippy |
| 编译速度 | 快 | 慢（大项目明显） |
| 国内可用人才 | 多但贵 | 很少 |
| AI 辅助开发 | 编译器不兜 UB/泄漏 | 编译器兜住大多数低级错误 |

**判断**：

- 目标是"尽快 1:1 把现在的行为搬过去"→ C++ 门槛更低；
- 目标是"未来五年安全地持续演进"→ **Rust 更好**（本项目大量状态机、几何、撤销/历史，
  正是生命周期 bug 的高发区，编译器兜底价值最大）；
- 但两者换来的**收益完全相同且都小**（§二）。所以这张表只在"已经决定换"时才有意义。

## 四、问题 3：不换会怎么样？

**结论：不换是现在的正解。** 但有两件"正事"和一个"真正的优化方向"。

### 4.1 必做：升 .NET 10（截止 2026-11-10，约 5 周）

- .NET 8 的安全更新到 **2026-11-10**（生命周期页写 11-11，差一天）；之后无安全补丁。
  .NET 10 是 LTS（支持到 2028-11），发布已近一年，不算"刚出炉"。
- 你们是自绘 + P/Invoke + Vortice，不依赖框架特性，升级风险低；
  升完跑全量自检即可。收益：几 MB 内存 + 少量启动/CPU 改善（JIT/GC 常年优化）。
- 原决定（2026-10-03"暂缓 .NET 10"）需要改：**安全截止日就在眼前**，这次不能再缓。

### 4.2 可选：Native AOT —— 门槛比原估的高一档

官方文档明确：**Native AOT 不支持"内置 COM"**（IL3052：Built-in COM is not
supported with Native AOT compilation）。而 Vortice.Windows 3.8.3 走的就是
`[ComImport]` 这条内置 COM 路线——**直接 AOT 大概率在运行时抛异常**（trim 同理）。

所以 AOT 的前提是先把用到的 interop 层换掉，二选一：

| 方案 | 做法 | 代价 |
|---|---|---|
| GeneratedComInterface / ComWrappers | 用 .NET 8 的源生成器把用到的 COM 接口重新声明生成 | 中等，需覆盖 InkEngine 的 Gfx/DirectWrite/Ppt 接口面 |
| TerraFX.Interop.Windows | 函数指针/手工 vtable 路线，AOT 与 trim 都友好 | 中等，接口面大但机械 |

另外 `PptLink` 的 10 处 `dynamic`、`System.Drawing.Common` 的 JPEG 编码也要按原计划处理。

**建议**：做一个真正的最小 spike（半天~两天）：
装 VS C++ 工作负载 → 用 Vortice 建一个 D2D 设备画一帧 → `PublishAot=true` 发布 →
确认"内置 COM 到底死在什么调用上、要换多少接口"。拿到结论再决定值不值。
AOT 若跑通：估 **−15~30MB 提交 + 启动 <150ms**；跑不通就停在 .NET 10，不动。

### 4.3 真正的方向：针对 4GB 机器做"图形内存回收"，与语言无关

- 长板书后，**约 100MB 的驱动/显存池不还系统**（`IDXGIDevice3::Trim` 实测无效）。
  唯一的硬办法是"空闲一段时间后销毁并重建 D3D/D2D 设备"——这是你们
  《性能-内存与卡顿实测》§六第 1 项，**在 4GB 教室机上它比换语言值钱得多**。
- 1080p 目标机的合成缓冲天然小 2.2~2.5 倍，加上 iGPU 共享内存的特性，
  必须先在**真机**上量"长板书 20 分钟 + 挂机"的提交/显存/延迟，再决定做不做设备重建。
- 可选小开关：`System.GC.ConserveMemory`、`System.GC.HeapHardLimit`（.NET 9+ 运行时配置），
  量出来有收益再开；**不要碰书写延迟相关的设置**。
- 现实提醒：4GB 机器上占内存的通常不是这个 90MB 的应用，而是系统 + PPT + 浏览器。
  如果是自有机器，加一条内存条（几十块）比任何重写都便宜、都有效。

## 五、决策清单

| 时间 | 动作 | 性质 |
|---|---|---|
| 2026-11-10 前 | 升 .NET 10（net10.0-windows）+ 全量自检 + 发布回归 | **必做**（安全截止） |
| 升级后一周 | 真机（4GB / 1080p / UHD）跑 `--writetest`、`--memlife`、延迟实测 | 必做（一切优化的前提） |
| 之后 | 若真机数据支持 → 做"空闲后重建 D3D/D2D 设备" | 视数据 |
| 可选 | AOT/interop spike（半天~两天） | 可选 |
| **不做** | 换 C++/Rust 重写 | **建议否决** |

**重评触发的条件**（出现任意一条再谈换语言）：
1. 4GB 真机实测出现 OOM/明显卡顿，且定位到"运行时"而不是图形栈；
2. 要上 Mac / 移动端等非 Windows 平台；
3. 要解析大量不可信文件格式（PDF/ISF 等），需要内存安全；
4. 团队真的有了 Rust/C++ 的生产力（人、时间、测试资产都能覆盖）。

## 六、追加调研（2026-10-05）：不用 D2D / 软件渲染，能降很多吗？（"比如 Rust+？"）

**先拆账：现在 90MB 里"图形三件套"分别是多少、去掉谁能省。**

| 组件 | 实测（2880×1800 核显机） | "不用 D2D"能省吗 |
|---|---|---|
| Direct2D 设备 | **约 9 MB**（建 D2D：53.3→64.8→+9.4） | 能——但只有 9MB，**没意义** |
| Direct3D 11 设备 + 驱动 | **约 34 MB**（建 D3D：10.9→43.9） | 只有**整条 D3D 都不要**才省 |
| 交换链 / 合成缓冲 | **约 26 MB**（1080p 约 10MB） | D3D/DComp 都不要才省 |

结论：**只去掉 D2D、留着 D3D/DComp，最多省 9MB**；想省大头必须**整条 GPU 栈换掉**——
软件光栅（tiny-skia / Skia CPU / 自绘）+ GDI/多层窗口呈现。

**能省多少（按 1080p 核显 4GB 教室机估）**：

| 路线 | 空闲提交（估） | 相对现在 |
|---|---|---|
| 现在（D2D/DComp） | 约 75~85 MB | — |
| 原生 + 软件光栅 + 多层窗口 | 约 30~50 MB | **省 30~40 MB**（4GB 的 <1%） |

这是唯一的"降很多"路线，但有一串硬代价：

1. **CPU 变成瓶颈**。你们现在书写时 CPU 13% / GPU 2.9%；软件路线把光栅搬到本来就最弱的
   4 核 CPU 上。**直接反例就是 Inkeys（C++ 纯 CPU 光栅）：89~96% 单核、每采样点 55~60ms、
   停止输入后 14~46% 还在消化积压**。你们的"只补新笔画"能缓解书写路径，但擦除/撤销/
   清空/换底这类整屏结构操作会变成全屏 CPU 重画——在弱机上就是可见卡顿。
2. **失去系统湿墨通道**。`IDCompositionInkTrailDevice` 属于 DirectComposition，
   而 **DComp 必须建在 D3D 设备上**（官方初始化第一步就是建 D3D 设备）。
   现在"Present → 上屏 1.0 刷新"和书写跟手，一半靠这条通道；软件路线要自己每帧重画湿墨，
   延迟很难回到现在的量级。
3. **透明实现退化**。GDI `BitBlt` 没有逐像素 alpha；只能：
   - `WS_EX_LAYERED + UpdateLayeredWindow(Indirect)`：Vista+ 支持 `prcDirty` 脏区更新，
     但要自己维护全屏 DIB（2880p 单缓冲就 20.7MB，1080p 8.3MB），每帧上传；
     公开案例里全屏多层窗口的 CPU/延迟代价都不小；
   - 或色键透明（`ULW_COLORKEY`）：抗锯齿边缘会发脏，观感直接掉档。
4. **省的钱有一部分是"搬家"**：进程里省掉的 GPU 资源，系统里 DWM 仍要为全屏层
   保留重定向表面并做"上传 + 合成"，总内存不会同幅下降。
5. **只在核显上有意义**。核显的显存就是系统内存，省它是真省；独显机器上那些本来在 VRAM，
   对 4GB 系统内存没意义。教室机基本是核显——但核显也意味着 CPU 最弱，软渲染最吃亏。

**"Rust+？"的四种组合**（语言不是变量，渲染栈才是）：

| 组合 | 内存效果 | 结论 |
|---|---|---|
| Rust + windows-rs + D2D/DComp（照搬现有架构） | 只省 .NET 运行时 25~30MB，图形栈一分不少 | 收益 ≈ AOT，**不值一次重写** |
| Rust + 自绘软光栅（tiny-skia/femtovg CPU 等）+ 多层窗口 | 里外约省 60MB 账面、净 30~40MB | 唯一"降很多"的路线，代价见上 5 条 |
| Rust + Skia CPU 后端 | 同上一档；Skia 质量最稳、体积大 | 同上 |
| Rust + wgpu | 比 D2D **更重**（DX12/Vulkan 驱动开销） | 不要，内存不会更低 |

（C++ 同理：这些结论与语言无关。）

### 6.1 这两行到底是什么（tiny-skia / Skia CPU 细评）

**共同点**：都是 **CPU 光栅器**——你给它们路径/图像，它们把像素画进一块 RGBA 位图；
"上屏"仍要自己接**多层窗口**（`UpdateLayeredWindowIndirect`）；输入（`WM_POINTER`）不变。
也就是说：软光栅库只管"画进内存"，不管"呈现"和延迟。

**tiny-skia**（Linebender 维护，BSD-3）：

- 是什么：Skia **CPU 光栅管线**的最小移植，纯 Rust、无 C++ 依赖、二进制小、编译快。
  resvg（SVG 渲染器）就是用它。
- **有**：路径填充/描边（圆头圆角）、渐变、图案、图像、裁剪、混合模式、
  `StrokeDash` 虚线、图像 `FilterQuality`（双线性/双三次）。
- **没有**：**文字（官方明确"不做"，issue #1 "not planned"）**；模糊/滤镜类效果；
  mipmap 类高质量降采样（README 明确）；裁剪算法比 Skia 简单（更慢）。
- 性能：x86-64 上比 Skia CPU **慢 20~100%**（约为其 0.5~0.8 倍速），但仍是**最快的
  纯 Rust 软光栅**（比 raqote 快 5~7 倍）。
- 对你们：22 种图形、图标、多层圆角阴影、虚线都能画；**唯一硬缺口是文字**——
  面板/提示/角度读数/计时文字要么配 `swash`（HarfBuzz 移植 + 光栅，同作者生态）
  或 cosmic-text + 字形缓存，要么延续你们"启动时预烘 UI 位图"的做法把文字烘成图集。
  主要工作量：文字栈 + 逐项对拍观感。

**Skia CPU（skia-safe）**：

- 是什么：完整 Skia 的 Rust 绑定，Chrome/Android 同款引擎；0.25 起默认 CPU-only。
- **有**：全部——文字（HarfBuzz shaping）、虚线、模糊/阴影、色彩管理、SIMD 光栅、
  高质量图像缩放；而且绑定带 **d3d 特性（Ganesh D3D 后端）**：理论上**同一套绘制代码**
  将来可以切 GPU——"低配机走 CPU 省内存、普通机走 GPU 保性能"这条路是通的，
  但 Windows 上绑定的成熟度必须实测再信。
- 代价：C++ 构建链（首次构建 20~40 分钟，也可用预编译包）、体积大（Skia 库十几到几十 MB）、
  API 面大、进程里多几 MB 代码页与内部缓存。

**怎么选**（如果一定要软渲染）：

| 目标 | 选择 |
|---|---|
| 最小、最纯、接受自己补文字栈 | **tiny-skia** |
| 功能对齐现有 UI（文字/效果全有）、将来想留 GPU 后端退路 | **Skia CPU（skia-safe）** |
| 自己手写光栅 | **不推荐**：AA 描边、圆角连接、裁剪、虚线、混合全自己扛，顶多换"零依赖"，性能不会更好 |

（顺带：Linebender 的 vello / vello_cpu 是新一代 GPU-first 渲染器，CPU 后端刚起步，
成熟度不够，暂不进入选型。）

**但请记住**：这两个库都不是瓶颈所在。瓶颈是"CPU 光栅 + 多层窗口呈现"这两个**结构代价**——
光栅库换成谁，Inkeys 那条 89~96% 单核的曲线都可能重演（分块 + 增量更新能改善，
但要用 POC 的三个数证明）。所以结论不变：**可以做 POC，不值得直接定路线。**

**还有一个省事的对照**：现在 D2D 在没有 GPU 的机器上会自动落到 WARP/软件光栅——
"兼容无 GPU 环境"不需要另起炉灶；软件路线唯一站得住的动机只剩"省这 30~40MB"。

**建议**：

1. 依然不建议动渲染栈。省不到 4GB 的 1%，却拿产品最值钱的三样东西（1 帧跟手、
   系统湿墨、大墨量下的稳定）去赌。
2. 如果心里不踏实，做一个**最小 POC（半天~一天）**：在现有引擎里加一个
   "D2D DC 渲染目标 + 多层窗口"演示分支，只量三个数——空闲提交、书写每帧耗时、上屏延迟。
   用数据一票否决或确认，比换语言直接得多。
3. 4GB 教室机的正路仍是：升 .NET 10 → 真机量（1080p 合成缓冲天然少一半多）→
   空闲后回收图形设备（§4.3）。

### 6.2 POC 实测（2026-10-05，POC 已删除、数据留档）：软渲染到底省多少、每帧多贵

按 §6.1 的结论搭了最小 POC（`tools/softpoc/`，Rust + tiny-skia + 多层窗口，
DIB 直接当 PixmapMut 零拷贝、只更新脏区）。本机 i5-12500H / Iris Xe / 2880×1800，
同日与现有 D2D 版对照：

**内存（提交大小）**

| | 现有 D2D 版 | 软渲染 POC |
|---|---|---|
| 空闲（全屏透明层） | 93.2 MB | **21.1 MB** |
| 空闲工作集 | ~123 MB（历史） | 46.6 MB |
| dwm.exe 增量 | +17~32 MB | +20.7 MB（≈一张 2880×1800 合成表面） |
| 系统净账（进程 + dwm，粗算） | ~110~125 MB | **~42 MB** |
| 230 笔 / 4613 点书写后 | （120 笔 burst 就到 131 MB，显存 148 MB） | **21.4 MB，基本平** |

- 进程账面省了 **72MB**；其中约 21MB 是"搬给 dwm"（分层窗口也要一张合成表面，
  D2D/DComp 路线同样要付，实测它让 dwm +17~32MB），**系统净省仍有 50MB+**。
- 1080p 目标机上 DIB 和合成表面都按像素约减半（POC 侧约 8MB），现有版的
  合成缓冲同样减半——这个对照关系基本保持。
- 内存曲线平：没有 D2D 细分缓存 / 驱动池那种"涨上去不还"的机制。这是软渲染
  最硬的结构性优势。

**速度（POC 自测，200fps 逐帧遥测）**

| 场景 | 光栅 avg/max | 脏区交换 | 上传 avg/max | 每帧总 |
|---|---|---|---|---|
| 短笔画（~115fps） | 0.127 / 0.83 ms | 0.002 ms | 0.27 / 2.5 ms | **~0.4 ms** |
| 全屏横扫长笔画（~200fps） | 0.38 / 3.5 ms | 0.02 ms | 0.26 / 3.1 ms | **~0.66 ms** |
| 整屏重画（40→200 笔） | — | — | — | **10.9~15.8 ms** |
| 延迟代理（update→DwmFlush） | — | — | 0.4 ms | **14.6 ms ≈ 1 个刷新周期** |

- 书写每帧 0.4~0.7ms（i5-12500H）；就算目标机 i3-8100 按 2~3 倍慢估，
  也只有 **1~2ms/帧**，16.7ms 预算里很宽裕。
- 整屏重画 11~16ms 主要是 2880×1800 的清屏 + 交换 + 全屏上传；1080p 估 5~8ms。
  比 GPU 版慢，但属于"点撤销/清空时的一下"，可接受。
- **最大未知数**：分层窗口没有 DComp/WISP 湿墨通道，`DwmFlush` 代理约 1 个刷新周期，
  与现有"Present→上屏 1.0 刷新"同量级，但**端到端（笔尖到眼睛）必须用硬件实测**
  （见 `延时-实测与优化.md` 的方法）。

**POC 的边界（别把数字当产品数字）**

- 没有 UI / 文字 / 图形 / 截图 / PPT；全功能产品会在 21MB 上加几 MB~十几 MB
  （字体位图、图标、解码图、块缓存），但离 93MB 仍很远。
- 当前笔画按"整包围盒还原 + 重画"实现（最朴素版本，长笔画会浪费内存带宽）；
  正式版要换成你们已有的 256×256 分块增量——本 POC 的数字是**保守上限**。
- 合成笔画不是真实笔输入；CPU 数字只含光栅+上传，不含 UI/命中测试。

**它对决策意味着什么**

- 软渲染能把系统内存从 110~125MB 压到 ~40MB（本机口径），比 AOT 的 15~30MB
  **多一倍以上**——这是它唯一、但确实成立的卖点。
- 代价不变：失去湿墨/低延迟通道、要重建渲染后端（tiny-skia 无文字；Skia CPU
  更稳但重）、全功能回归成本巨大。**这是换渲染架构，不是换语言。**
- 下一步若要继续验证，只值得做一件事：**目标真机（4GB/1080p）+ 真实手写笔 +
  端到端延迟**。若手感这一关过不去，前面的内存数字都没有意义。
