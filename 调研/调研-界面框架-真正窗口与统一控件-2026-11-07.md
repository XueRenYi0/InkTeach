## 〇、结论先行

1. **要统一，但统一的是"窗口层 + 内容层 + 文字层"，不是引入一个第三方 UI 框架。**
   一套窗口管理、一套内容树、一套文字输入、一套表单/列表，所有窗口共用；
   这样"最小化/最大化/贴靠/DPI/置顶/任务栏/记忆位置"只写一次、只测一次。
2. **文档窗和对话框优先用系统标题栏；只有批注覆盖层、收藏/图形调色板、视频展台预览用无边框。**
   系统 chrome 白拿最小化/最大化/贴靠/动画/任务栏/触摸/无障碍——这是最大的 bug 削减。
   无边框不是"高级"，它是"自己接管一整套 OS 行为"，每一条都可能出 bug。
3. **一套 `WindowManager` + `WindowHost`**，支持 5 种窗口类型、2 种 chrome：
   Document（系统 chrome）/ Dialog（系统 chrome）/ Palette（无边框、置顶、无任务栏）/
   Overlay（现有批注层）/ Preview（展台预览，无边框置顶，可缩放）。
4. **不引 Avalonia / WinUI 3 / WPF。**
   它们会把 +100～250 MB 和第二个渲染器带回来；Avalonia 12.0 的自定义 chrome
   出过动画/贴靠回归（#21212，12.1 修复；#22053 是重复报告），WinUI 3 要 Windows App SDK 运行时。
   画布嵌入（NativeControlHost / SwapChainPanel）又是另一层空域与输入风险。
5. **真多文档是另一个工程。**
   现在 `InkEngine` 的 `Doc` 是单例、`_windows` 是每屏一个覆盖层；
   要同时开"白板 + PDF"两个独立文档，得先把 `Doc` 和 `View/Input` 拆开。
   窗口框架不解决这件事，先拍板"同时只开一个文档"还是"多文档/多视图"。

## 一、窗口清单与形态

| 窗口 | 用途 | 建议类型 | Chrome | 生命周期 | 输入 |
|---|---|---|---|---|---|
| 批注覆盖层 | 在桌面/PPT 上批注 | Overlay | 无边框、透明、置顶、不激活 | 常驻（每屏一个） | 笔/触摸/鼠标 |
| 白板窗口 | 真正的白板页 | Document | **系统 chrome** | 可选，可多开（看文档模型） | 笔/触摸/鼠标/键盘 |
| PDF 窗口 | 文档批注 | Document | **系统 chrome** | 可选，可多开（看文档模型） | 笔/触摸/鼠标/键盘 |
| 设置 | 分类设置 | Dialog / Document | **系统 chrome** | 模态或非模态，可记忆尺寸 | 鼠标/触摸/键盘/IME |
| 收藏 / 图形 | 调色板、拖到画布 | Palette | **无边框**、置顶、无任务栏、可缩放 | 常驻或按需 | 鼠标/触摸/拖放 |
| 视频展台 | 摄像头预览 + 批注 | Preview | **无边框**、置顶、可缩放、可锁定比例 | 按需 | 鼠标/触摸/键盘 |
| 文字输入 | 横切服务 | 无独立窗口 | —— | 跟随焦点 | IME/键盘/触摸键盘 |
| 确认/API 对话框 | 简单表单 | Dialog | **系统 chrome** | 模态 | 鼠标/键盘/IME |

**判断规则**：

- 需要**最小化/最大化/贴靠/任务栏/系统菜单/Alt+Space/动画**的 → 系统 chrome；
- 只需要**浮在画布上、随手拖动、不抢任务栏**的 → 无边框调色板；
- 需要**穿透/不激活/逐像素透明**的 → 现有覆盖层。

| 方案 | 窗口能力 | 控件/表单 | 内存 | 与画布共存 | 主要风险 | 结论 |
|---|---|---|---|---|---|---|
| **A. 自研 WindowHost + 系统 chrome + D2D 内容 + 原生文字** | 系统全给 | 自绘 + 原生文字 | **+0** | 同一套 D2D/输入 | 控件要自己写；UIA 要补 | **推荐** |
| B. 自研 WindowHost + 无边框 chrome | 自己实现 | 自绘 + 原生文字 | +0 | 同一套 | NCCALCSIZE/贴靠/动画/DPI/触摸边框，bug 多 | 只用于 Palette/Preview |
| C. Avalonia 12 做真窗口 | 系统或自绘 | **现成控件最全** | +100～200 MB | NativeControlHost 空域；画布嵌入 | 第二渲染器；12.x chrome 回归；双栈 | 备选，不做主 UI |
| D. WinUI 3 / AppWindow | 系统最好（贴靠/Mica） | 现成 Fluent 控件 | +100～250 MB + 运行时 | SwapChainPanel/XAML Islands | 部署重、启动慢、复杂度高 | 不推荐 |

| F. 纯原生控件 + 系统 chrome | 系统全给 | 原生控件 | +0 | 子窗空域 | 暗色主题/观感旧；布局手写 | 只用于文字与文件对话框 |
| G. 维持覆盖层，不做真窗口 | 无 | 无 | +0 | 无 | 不满足"最小化/并排/任务栏" | 不满足需求 |

### 4.1 为什么"系统 chrome 优先"是最大的 bug 削减

无边框窗口要自己接管这些（每一条都出过 bug）：

- `WM_NCCALCSIZE` 客户区计算；最大化时任务栏遮挡/多屏偏移；
- `WM_NCHITTEST` 的 `HTCAPTION / HTLEFT / HTRIGHT / HTTOP / HTBOTTOM / HTTOPLEFT …`；
- **Win11 贴靠**：最大化按钮必须返回 `HTMAXBUTTON`，否则悬停不弹贴靠布局
  （微软文档明确写了这一条）；
- 双击标题栏最大化/还原、`Alt+Space` 系统菜单、`WM_SYSCOMMAND`；
- 最小化/最大化/还原的 DWM 动画（genie/zoom/fade）；
- 圆角、阴影、边框、暗色标题栏；
- 触摸/笔的缩放边框（系统边框只有几像素，手指很难抓）；
- 每屏 DPI、最大化边界、`WM_GETMINMAXINFO`；
- 任务栏、Alt+Tab、`WS_EX_APPWINDOW/TOOLWINDOW`；
- 无障碍（UIA 的窗口角色、标题栏按钮）。

**系统 chrome 把这些全部白拿。** 观感上，Win11 的系统标题栏 + 暗色模式 + 圆角
并不丑；需要品牌感时，可以在客户区顶部做一条自己的工具栏，而不是把系统标题栏拆掉。

### 4.2 为什么不上 Avalonia（这次认真算了）

Avalonia 12 确实补了很多窗口能力：`WindowDrawnDecorations`、自定义标题栏、
per-monitor DPI、`NativeControlHost`、UIA、IME。但：

- **内存**：社区报告启动 100～200 MB，长时间运行还会涨；我们 4 GB 教室机
  还要装 PPT/浏览器，这笔账不划算。**以上是社区报告，未在本机实测**；
  如果 Avalonia 进入正式候选，先做 30 分钟 Hello World 内存对照再定；
- **第二渲染器**：Avalonia 用 Skia，我们的画布/覆盖层用 D2D；
  字体、DPI、命中、动画、主题都多一套；
- **画布嵌入**：`NativeControlHost` 有**空域问题**（原生子窗永远盖在
  Avalonia 内容上、只按宿主矩形裁剪，滚动/遮挡会露馅），
  把白板/PDF 画布嵌进去等于把最核心的体验押在一个边界上；
- **自定义 chrome 仍在补**：Avalonia 12.0 的 `BorderOnly` 丢失 DWM 最小化/
  最大化动画（#21212），12.1 才修复；12.2 才补 `TitleBarDecorations="None"`
  的等价能力（#21969）；#22053 是重复报告。说明"自定义 chrome + 原生窗口行为"
  这类能力是近几年才补齐的，任何框架都绕不开这些坑；
- **双栈长期成本**：设置/收藏用 Avalonia，工具条/画布用 D2D，
  以后每个交互都要问"这套在哪边"。

**结论**：Avalonia 只在"设置窗复杂到自研扛不住 + 能接受 +100 MB"时，
作为**独立进程**的备选；不做主 UI。

### 4.3 为什么不上 WinUI 3

- `AppWindow` 的窗口能力最好（系统贴靠、Mica、标题栏），但需要
  **Windows App SDK 运行时**；self-contained 官方明确写"更大、启动更慢、内存更多"；
- 画布要用 `SwapChainPanel` 或 XAML Islands；`SwapChainPanel` 是 DirectX 内容，
  但输入/DPI/层序/空域又是另一套；
- 我们的覆盖层（透明、置顶、不激活、穿透）仍然得用 Win32；
  等于同时维护 Win32 覆盖层 + WinUI 窗口两套应用模型。

**结论**：不推荐。

### 4.4 为什么不上纯原生控件

- 暗色主题下 `BUTTON/COMBOBOX/LISTVIEW` 的主题支持不完整，
  要么接受"系统灰"，要么 owner-draw（又回到自绘）；
- 我们的工具条/收藏/图形已经有统一的自绘观感，纯原生控件会割裂；
- 原生控件最适合**文字输入**（IME/撤销/剪贴板/无障碍），不适合做品牌化的按钮/滑条。

**结论**：原生只用于**文字**和**系统文件/颜色对话框**；其余自绘。

## 五、推荐架构

```
src/InkEngine/                 核心：文档、输入、渲染、工具状态（不动）
      ↕  IOverlayUi / IUiHost / IEngineCommands（现有契约）
src/InkUi/
  ├─ Window/                   新：窗口层（不引用 InkEngine）
  │    WindowManager           创建/查找/关闭/层序/owner/生命周期
  │    WindowHost              一个顶层窗口 = HWND + Chrome + Surface + 输入
  │    ChromeKind              System / Borderless
  │    WindowKind              Document / Dialog / Palette / Preview / Overlay
  │    Placement               位置/尺寸/最大化/显示器记忆
  │    Theme                   DWM 暗色/标题栏色/圆角；Win10 回退
  ├─ Content/                  新：内容层
  │    UiElement / Layout      Stack / Dock / Grid / Scroll
  │    Widgets                 Button / Toggle / Slider / Dropdown / List / Tab …
  │    TextEditHost            原生 EDIT / RichEdit 桥（IME/选区/撤销）
  │    Forms                   FormBuilder + 字段/校验/行布局
  │    Lists                   虚拟列表 / 拖放 / 多选 / 四态
  ├─ Screens/                  白板 / PDF / 设置 / 收藏 / 展台
  └─ FullUi.cs                 现有工具条（先保持，按面板迁移）
```

### 5.1 五种窗口类型的策略

| 类型 | Chrome | 任务栏 | 置顶 | 最小化/最大化 | 关闭行为 |
|---|---|---|---|---|---|
| Document | **System** | ✅ | 可选开关 | ✅ 系统 | 保存 + 可恢复 |
| Dialog | **System** | ❌ | 跟随 owner | ❌ | 取消/保存 |
| Palette | Borderless | ❌ | ✅ 常驻 | ❌ | 隐藏/记忆位置 |
| Preview | Borderless | ❌ | ✅ 常驻 | ❌ | 释放摄像头 |
| Overlay | Borderless | ❌ | ✅ 常驻 | ❌ | 常驻 |

> 全屏（白板/PDF 演示）作为 Document 的一种**窗口状态**：保存进入前的 placement，
> 全屏时铺满当前显示器工作区、隐藏系统标题栏，退出时还原；不要为全屏再写一套窗口。
> 全屏 + 置顶要单独测：不要盖住任务栏/触摸键盘/系统弹窗。

### 5.2 一个窗口的组成

```
WindowHost
  ├─ HWND            （系统或自绘 chrome）
  ├─ D2D target      （swap chain 或 DComp surface）
  ├─ RootElement     （内容树根，负责布局/绘制/命中）
  ├─ InputRouter     （指针/键盘/焦点/捕获/滚轮/IME）
  ├─ PopupLayer      （菜单/下拉/提示，裁剪在窗口内）
  └─ Placement       （位置/尺寸/DPI/最大化状态）
```

页面代码只认 `RootElement` 和 `WindowHost` 的服务，不直接碰 HWND/DWM。
这样白板、PDF、设置、收藏、展台都是"同一个窗口壳 + 不同内容"。

## 六、窗口层 Win32 必做清单（照这个写，bug 少一半）

### 6.1 样式与任务栏

| 项 | 做法 | 不做的后果 |
|---|---|---|
| 文档窗 | `WS_OVERLAPPEDWINDOW` + `WS_EX_APPWINDOW`（或 owner 为空） | 没有任务栏/贴靠/系统菜单 |
| 调色板 | `WS_EX_TOOLWINDOW` + `WS_POPUP` + 置顶 | 出现在 Alt+Tab/任务栏，老师找不到 |
| 对话框 | `WS_OVERLAPPED | WS_CAPTION | WS_SYSMENU` + owner | 模态关系乱、最小化行为怪 |
| 覆盖层 | `WS_EX_NOACTIVATE | TOOLWINDOW | TOPMOST | NOREDIRECTIONBITMAP` | 抢焦点、破坏批注 |

### 6.2 系统 chrome 的暗色与观感

| 系统 | 能给什么 | 回退 |
|---|---|---|
| Win11 22H2+ | 圆角、Mica/Acrylic、暗色标题栏、标题栏颜色、贴靠布局 | —— |
| Win11 21H2 | 圆角、暗色标题栏、贴靠布局；Mica 可能没有 | 纯色标题栏 |
| Win10 1809+ | 暗色标题栏、方角、无 Mica、无贴靠飞层（拖动贴边仍有） | 纯色/浅色标题栏 |
| Win10 早期 | 只有系统默认标题栏 | 不做暗色标题栏 |

- `DwmSetWindowAttribute(DWMWA_USE_IMMERSIVE_DARK_MODE)`：Win10 1809+ 暗色标题栏；
- `DWMWA_CAPTION_COLOR` / `DWMWA_TEXT_COLOR` / `DWMWA_BORDER_COLOR`：Win11；
- `DWMWA_WINDOW_CORNER_PREFERENCE`：Win11 圆角；Win10 自动方角；
- `DWMWA_SYSTEMBACKDROP_TYPE`：Win11 22H2 的 Mica/Acrylic；**低端机不要默认开**，
  按性能档位回退纯色；
- 不要用 `SetWindowCompositionAttribute` 这类未公开接口做毛玻璃。

### 6.3 如果必须无边框（Palette/Preview）

- `WM_NCCALCSIZE`：返回客户区 = 窗口矩形（最大化时留出任务栏）；
- `WM_NCHITTEST`：`HTCAPTION`（拖动）、`HTLEFT/HTRIGHT/HTTOP/HTBOTTOM/HTTOPLEFT…`（缩放）；
- **最大化按钮返回 `HTMAXBUTTON`**，否则 Win11 贴靠布局不弹（微软文档明确）；
- 双击标题栏：`WM_NCLBUTTONDBLCLK` → 最大化/还原；
- `WM_GETMINMAXINFO`：最大化边界、最小尺寸；
- 圆角/阴影：优先 DWM；不要自己画阴影（半透明+分层窗口会闪烁）；
- 触摸缩放边框：命中区至少 **8～12 px**（按 DPI 换算），鼠标可以窄一点；
- 关闭按钮：`HTCLOSE`；系统菜单：`Alt+Space` 要能用；
- 无边框窗口的 DWM 动画：`BorderOnly` 在 Avalonia/WPF 都出过问题，
  Win32 自己实现时也要测最小化/还原动画；
- **系统 chrome 也能加宽触摸缩放区**：在 `WM_NCHITTEST` 里先对触摸/笔坐标
  按 8～12 px 判断边框，返回 `HTLEFT/HTRIGHT/…`；其余仍交给 `DefWindowProc`，
  这样不用重画标题栏，也能让手指抓得住边框。

### 6.4 每屏 DPI

- manifest 开 **PerMonitorV2**；
- `WM_DPICHANGED`：用建议矩形 `lParam` 重排，不要自己算；
- `GetDpiForWindow` / `GetSystemMetricsForDpi` / `AdjustWindowRectExForDpi`；
- 跨屏拖动时：先按新 DPI 重排，再画；不要缓存 DPI；
- 文字/图标/边框全部按当前窗口 DPI 缩放；
- 混合 DPI（主屏 200% + 副屏 100%）必须实测。

### 6.5 置顶、owner、激活

- `HWND_TOPMOST` 只给 Palette/Preview/Overlay；Document 用开关；
- 对话框设 owner：owner 最小化时一起最小化，且永远在 owner 上面；
- 调色板不要设 owner（否则切到 PPT 就看不见），用独立置顶；
- 调色板点击不抢焦点：`WM_MOUSEACTIVATE` 返回 `MA_NOACTIVATE`；
  需要输入搜索时再显式激活；
- 不要滥用 `SetForegroundWindow`（前台锁），用 `SetWindowPos` + 激活策略。

### 6.6 位置/尺寸记忆

- `GetWindowPlacement/SetWindowPlacement` 保存 `rcNormalPosition` 和最大化状态；
- 保存前用 `MonitorFromWindow` + `GetMonitorInfo` 校验；
- 显示器拔掉/分辨率变化：`WM_DISPLAYCHANGE` 后把窗口拉回可见工作区；
- 按"窗口类型 + 显示器 ID"存，不要只存绝对坐标；
- 默认位置：主工作区居中；调色板贴主条上沿。

### 6.7 关闭/生命周期

- Document：标题栏显示文档名 + `*` 脏标记；关闭前自动保存；有未保存修改时二次确认；
- Dialog：Esc = 取消，Enter = 默认按钮；
- Palette：关闭 = 隐藏，记忆位置；
- Preview：关闭 = 停摄像头/释放设备；
- 关闭最后一个 Document 不退出进程（覆盖层还在）；
- 退出应用：先保存所有 Document，再释放 D2D/摄像头。

### 6.8 拖放

| 场景 | 做法 | 注意 |
|---|---|---|
| 从资源管理器拖 PDF/图片进窗口 | OLE `IDropTarget`（或 `DragAcceptFiles`/`WM_DROPFILES`） | 要有拖入高亮/光标反馈；大文件异步加载 |
| 收藏/图形拖到画布 | 内部拖放：捕获指针 + 全局坐标 | 跨窗口要换算屏幕坐标；落点高亮 |
| 画布对象拖到收藏 | 同上，反向 | 拖出窗口时显示"可放下"提示 |
| 触摸拖放 | 长按进入拖拽 | 不要和滚动手势打架；有震动/视觉反馈更好 |
| 拖放取消 | Esc / 松手在无效区域 | 不产生半截对象/不写存档 |

### 6.9 高对比度 / 减少动画

- 系统高对比度：`SystemParametersInfo(SPI_GETHIGHCONTRAST)`；Tokens 切换到高对比配色，
  不要用固定 `#1B1B1F`；
- 系统关闭动画：`SPI_GETCLIENTAREAANIMATION`；窗口/面板动画直接跳终态；
- 触摸键盘弹出/收起：监听 `WM_SETTINGCHANGE`/窗口客户区变化，避免输入框被盖住。

## 七、内容层：统一控件，不统一成"通用控件库"

### 7.1 控件分层

| 层 | 内容 | 做法 |
|---|---|---|
| Tier 1（先做） | Button / IconButton / Toggle / Slider / Dropdown / TextBox / List / Scroll / Tab / Dialog / Tooltip | 自绘，够设置/收藏/展台用 |
| Tier 2 | Tree / Table / ColorPicker / Expander / InfoBar / Progress / Search | 有真实界面再加 |
| Tier 3 | RichText / 视频 / 拖拽停靠 | 复用现有 TextBoxEditing / 摄像头 / 不做停靠 |

#### Tier 1 控件的行为清单（缺一项就会在某个窗口露馅）

| 控件 | 状态 | 键盘 | 触摸 | 备注 |
|---|---|---|---|---|
| Button / IconButton | normal / hover / pressed / disabled / focus | Space / Enter | ≥40 px，按下反馈 | 图标按钮必须有 Tooltip |
| Toggle / Switch | on / off / disabled / focus | Space | 点击整行 | 不做"只有小滑块可点" |
| Checkbox / Radio | checked / unchecked / indeterminate / focus | Space；Radio 用方向键 | 点击整行 | 组内互斥 |
| Slider | normal / dragging / disabled / focus | ← → / Home / End | 拖动；轨道点击 | 步进/吸附；拖出轨道不取消 |
| Dropdown | closed / open / disabled / focus | Alt+↓ / ↑↓ / Enter / Esc | 点击展开；点外关闭 | 弹层走 PopupLayer |
| TextBox | normal / focus / readonly / error / disabled | Ctrl+A/C/V/X/Z；Esc | 点按；触摸键盘 | 原生 EDIT/RichEdit |
| List / Grid | 0 / 1 / 多 / 溢出；选中 / 多选 | ↑↓ / Shift / Ctrl / Home / End | 滚动、长按多选、拖放 | 虚拟化；100+ 条目 |
| Tab / Sidebar | active / hover / disabled | Ctrl+Tab / 方向键 | 点击；滚动 | 当前项始终可见 |
| Dialog | 打开 / 关闭 / 默认按钮 / 取消 | Esc / Enter / Tab | 全屏或大按钮 | 模态时焦点陷阱 |
| Tooltip | 悬停 / 长按 | 不适用 | 长按 | 触摸不能只靠 hover |
| ScrollViewer | 可滚 / 到边 / 惯性 | PageUp/Down / Home/End | 拖动、惯性 | 滚动条自动隐藏 |
| Toast / InfoBar | info / success / warning / error | 可关闭 | 可关闭 | 不阻塞操作 |

### 7.2 自绘 vs 原生

| 元素 | 选择 | 理由 |
|---|---|---|
| 单行/多行/富文本 | **原生 EDIT / RichEdit** | IME、撤销、剪贴板、无障碍白拿 |
| 按钮/开关/滑条/下拉 | **自绘 D2D** | 观感统一、暗色可控、触摸目标可控 |
| 列表/网格 | **自绘 + 虚拟化** | 100+ 条目、拖放、多选 |
| 文件/颜色选择 | **系统对话框** | 不要重造 |
| 视频预览 | 原生/D3D 表面 | 性能与设备管理 |

> 这套组合的代价：自绘按钮没有原生 UIA。先做**键盘可达 + Name/Role/Value 最小 UIA**，
> 不做全量无障碍；表单里的文字输入仍然有原生 UIA。

### 7.3 布局与输入

- 容器只要 4 种：`Stack`（横/竖）、`Dock`、`Grid`、`Scroll`；
- `Measure/Arrange`：父给约束、子报尺寸；只在失效时重算；
- 焦点：`FocusScope` + `TabIndex`；Esc/Enter 语义写死；
- 指针：按下捕获、移动、抬起；悬停单独一条；触摸/笔/鼠标同一路；
- 滚轮：指针在滚动容器内才消费；触摸拖动滚动要跟手；
- 弹层：锚点、层序、Esc/点外关闭、焦点陷阱。

## 八、文字输入/编辑（横切服务）

### 8.1 `TextEditHost`

一个服务，三种模式：

| 模式 | 控件 | 用途 |
|---|---|---|
| 单行 | `EDIT` | 重命名、页码、计时器、搜索 |
| 多行 | `EDIT` / `RICHEDIT50W` | 备注、AI 提示词 |
| 富文本 | `RICHEDIT50W` | 画布文本框（颜色/字体/行距/选区） |

> 富文本的工具栏、颜色段、行距、选区改色继续用现有 `TextBoxEditing` 的实现；
> 本节只统一**宿主窗、定位、DPI、IME、提交/取消**，不要重写编辑器。

统一处理：

- 宿主窗：覆盖层是 `NOACTIVATE`，文字输入必须另开可激活的 `TOOLWINDOW`；
- 定位：跟随焦点矩形/光标；超出屏幕时翻转；
- DPI：按 `GetDpiForWindow` 建字体，`WM_DPICHANGED` 重建；
- IME：`ImmAssociateContextEx`、`WM_IME_*`、候选窗跟随光标；
- 提交：Enter/失焦/点击外部；Esc 取消；校验失败保持焦点；
- 剪贴板/撤销：原生控件自带；
- 暗色：`EM_SETBKGNDCOLOR` + `EM_SETCHARFORMAT`；
- 触摸键盘：需要时调 `TabTip`/`ITipInvocation`，并避免被置顶窗口盖住。

### 8.2 必测矩阵

- 微软拼音、搜狗、QQ 拼音；
- 100% / 150% / 200% DPI；
- 单行 / 多行 / 富文本；
- 鼠标 / 触摸 / 笔；
- 触摸键盘弹出/收起；
- 候选窗在屏幕边缘时翻转；
- 失焦提交、Esc 取消、Enter 换行/提交的语义。

## 九、多文档/多视图（窗口框架解决不了的部分）

现状：`InkEngine.Doc` 是 `readonly` 单例（`Engine.cs:43`），
`_windows` 是每屏覆盖层（`Engine.cs:2190`）。所以：

| 方案 | 做法 | 成本 | 适用 |
|---|---|---|---|
| A. 一个文档一个窗口 | 每个文档窗口一个 `InkEngine` 实例 | 设备/内存翻倍，覆盖层与文档窗关系要理清 | 文档少、内存够 |
| B. 一个引擎，多文档/多视图 | 拆 `InkDocument` 与 `View/Input`；窗口绑定 View | 4～8 周重构 | 真正多开白板+PDF |
| C. 同时只开一个文档 | 切文档 = 换当前 Doc；窗口只是视图 | 低 | 课堂单文档够用 |

**建议**：先按 C 验证交互；如果老师确实需要"白板 + PDF 并排"，再走 B。
不要用 A 硬凑——两个 `InkEngine` 会把 D2D 设备、分块缓存、输入定时器都翻倍，
4 GB 机器最先炸。

## 十三、需要拍板的点

1. **Chrome 策略**：Document/Dialog 用系统标题栏，Palette/Preview/Overlay 用无边框？
   建议：**是**。这是 bug 最少、开发最快的分法。
2. **窗口类型**：白板/PDF 是 Document；设置是 Dialog；收藏/图形是 Palette；展台是 Preview？
   建议：**是**。如果收藏必须贴着手写笔走，也可以先做 Palette + 吸附。
3. **文档模型**：同时只开一个文档（C），还是白板+PDF 并排（B）？
   建议：**先 C 验证，再决定 B**；不要用多引擎硬凑。
4. **控件路线**：自绘按钮/列表 + 原生文字，接受"自绘控件只做最小 UIA"？
   建议：**是**。全量 UIA 另开阶段。
5. **投入**：接受 P1～P4 + P8 约 6～9 周的分阶段投入？
   还是先用 Avalonia 做设置/展台（+100～200 MB）换时间？
