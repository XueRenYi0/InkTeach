## 〇、一句话

三家里只有 **dotnet-campus 的笔迹美化**有真实价值，但整包移植的实测代价
（单笔 1413 点分配 **187.5 MB**、p95 **3.5 ms**、最终 **11 万顶点**）和 4 GB 教室机冲突；

所以：**三家都不接，代码不进仓库，只留三条"以后可能需要"的触发条件。**

## 二、逐家结论

### 2.1 Inkeys（GPL-3.0）——能力重叠，许可不允许

它做了什么：

- 用 `IRealTimeStylus` 绑窗口，`IRealTimeStylus3` 开多点、`IRealTimeStylus2` 关 Flicks；
- 从包属性里读 `X / Y / NORMAL_PRESSURE / WIDTH / HEIGHT`，压力按
  `(raw - min) / (max - min)` 归一化；
- 用 `IInkTablet2::get_DeviceKind` 区分 `TDK_Pen` / `TDK_Touch`，
  `bIsInvertedCursor` 判橡皮端；
- GDI+ 双缓冲画布，固定笔宽，按 4 px 距离补点；橡皮单独画圆。

为什么对我们没用：

| 它有的 | 我们已有的 |
|---|---|
| 压力归一化 | `GetPointerPenInfo` 的 `pressure / 1024`，另有 `PressureWidth` 曲线 |
| WIDTH / HEIGHT（触摸面积） | `GetPointerTouchInfo` 的 `rcContact`（已用于掌拒 HUD / `Touch.cs`） |
| 笔 / 触摸 / 橡皮端区分 | `WM_POINTER` 的 `pointerType` + `penMask` |
| 高频补点 | Raw Input 补点，实测 **154～194 Hz** |
| 独立渲染线程 | 湿墨自绘 + 合成边界配速，端到端 ≈26 ms @60Hz |

更关键的是：**启用 RTS 后窗口收不到 `WM_POINTER` / `WM_TOUCH`**，而我们的输入、
手势、光标、穿透全架在 `WM_POINTER` 上。这一点在 `调研-输入栈与RTS可行性.md`
里已经用官方文档 + 实测数字论证过，本文不重复。

许可：GPL-3.0，不能拷进闭源产品。**结论：不接。**

### 2.2 希沃 EasiNote5（无许可证）——只借思路，不借代码

看到的东西与判断：

| 技术点 | 它怎么做 | 对我们的价值 | 判断 |
|---|---|---|---|
| 希沃 MCU 直读 | VID `0x1FF7`、PID `0x0F15`（触摸 PID 1）、64 字节报告；`ForbiddenAndroidPen` / `OpenAndroidPen`、切 EMR、读版本 | 只对希沃大屏有效；可绕过系统墨迹做硬件加速 | **不接**：私有协议、随固件变、可能与希沃自带驱动/白板软件抢设备，杀软/售后风险高 |
| 触摸面积当压力 | `p = clamp(max(w,h) / 140, 1e-5, 1)` | 手指书写有粗细变化 | 思路可用，但**我们自己实现**，不抄代码 |
| 笔 / 指切换冷却 | 笔优先；抬笔后 **250 ms** 才把模式交还手指 | 少一次"抬笔被手掌接管" | 思路可用，成本很低 |
| 分段渲染 | 长笔每 **20 点**切一段，只重画当前段 | 我们已有分块光栅 | 不需要 |
| 预测 | `PredictDuration = 36 ms`，硬笔/软笔两套预测器 | 我们已有 Chromium 同族线性预测，用户已判定"默认关" | 不需要 |
| 二次贝塞尔插值 | 间距 > 5 px 插点；夹角 < 4° 特殊处理 | 我们已有 Catmull 过点曲线 | 不需要 |
| 软笔压力平滑 | 18 点环形队列、压力 `/9` | 我们已有压力 EMA | 不需要 |
| 线宽随页面缩放 | `max(w/默认宽, h/默认高)` | 我们的画布坐标已统一 | 不需要 |

许可与来源风险：仓库**没有许可证**，代码是反编译产物。即使改写，也有
"接触过反编译代码"的来源污染风险。**结论：不接，连代码结构都不参考。**

### 2.3 dotnet-campus 笔迹美化（MIT）——唯一有价值，但整包不能要

它比我们多的东西：

1. **固定 43 点笔尖模板**（不随切线旋转）→ 竖粗横细、起收笔有斜切角；
2. **速度 → 宽度**：`maxW * exp(-velocityResponse * speed)`，再做 EMA 平滑；
3. **收笔状态机**：零距离抬笔外推 `0.6 ×` 上一点、尾锋角 `-155°～-35°`、
   连续窄点收尖到 `0.03`、抬笔宽度涨幅限 `1.3 ×`、点击固定 0.8 宽、两点短划凸包；
4. **凸扫掠单元**：每对相邻采样点做一个凸包，增量缓存，非零绕数一次填充——
   天然没有自交挖洞、漏填，荧光笔也只混合一次；
5. 完整规格文档 + 真实设备回放资产 + Skia 渲染回归测试。

#### 实测数据（本机，Release）

用它的算法库直接跑它自己的回放资产（`Ink3.txt`，一笔 1413 点，
时间戳按资产、压力 `raw/1024`、`VelocityResponse=2`、`PressureInfluence=0.35`）：

| 指标 | 数值 |
|---|---|
| 总耗时 | 904.31 ms |
| 平均 | 0.64 ms / 点 |
| p95 | **3.53 ms** |
| 最大 | **6.04 ms** |
| 分配 | **187.5 MB / 笔** |
| 输出 | 2475 个凸单元 / **110090 个顶点** |

其他资产（Ink0/1/2）最大 3.37～5.44 ms/点，趋势一致。

原因不复杂：它**每来一个点就整体重建完整轮廓**（O(n²)），只有凸单元是增量缓存的。
低端 4 GB 机器按 3～5 倍慢推算，p95 会到 **10～18 ms**，还有百兆级 GC——
这还没算 D2D 每帧填充 11 万顶点的代价。

#### 为什么整包不接

1. **性能 / 内存**：上面的数字，和"低端 4 GB 保持现有基线"直接冲突；
2. **架构不匹配**：我们的压感笔迹走 `ID2D1Ink`（圆头、GPU 直接铺），
   它是 CPU 生成多边形 + 自己填充；整包接等于换一条渲染路线；
3. **WIP**：PR 还没合并；6 条 review 里有真几何 bug（被过滤的 `Up` 会让轮廓停在半路、
   覆盖补丁只进 `outline` 没进 `Outlines`），演示层还有"每帧重建所有笔画路径"的问题；
4. **维护**：分支 API 会变，接进来就得自己长期维护；
5. **许可虽好但不能解决前面四条**：MIT 只说明"可以抄"，不说明"抄了划算"。

#### 留下的三条思路（不写码）

- **速度 → 宽度 + 收尖**：可以接到我们现有的 `ID2D1Ink` 半径上；
  `PressureSim` 里其实已经有 Xournal++ / perfect-freehand 两套速度压感，
  但**渲染层没接，目前是死代码**；
- **凸扫掠单元 + 非零填充**：以后真要做"美工笔 / 毛笔"笔刷时，用它做增量几何，
  只画单元、不重建完整轮廓；
- **回放资产**：以后做笔迹回归测试可以借它的输入数据（只借数据，不借代码）。

## 三、为什么不接（五条）

1. **能力重叠**：RTS、触摸面积、预测、贝塞尔、分段渲染，我们已有等价或更好的实现；
2. **性能 / 内存**：唯一有价值的笔迹美化，整包实测 187.5 MB/笔，低端机不可接受；
3. **许可**：GPL-3.0 不能进闭源；无许可证 + 反编译不能碰；MIT 也只有一家；
4. **形态冲突**：RTS 不能跨进程、启用后断 `WM_POINTER`；MCU 只对希沃、且是私有协议；
5. **维护成本**：未合并的 lab 分支、反编译代码、私有固件协议，都会变成长期负债。

| 触发条件 | 重新看什么 | 前提 |
|---|---|---|
| 希沃官方给 SDK / 合作 | MCU 硬件墨迹 | 有官方授权、能拿到固件兼容承诺 |
| 用户明确要"图里那种毛笔字"，且 `ID2D1Ink` 做不出来 | 凸单元 + 固定笔尖模板（自研） | 先做低端机预算：每点 <1 ms、单笔 <3 MB |
| 多数目标机 `rcContact` 有非零面积 | 触摸面积伪压感（自研） | 先用现有触摸 HUD 统计 |
| 我们放弃 `WM_POINTER`（基本不可能） | RTS | 整条输入链路重写 |
| TouchSuite 重新可访问 | 它的 `TouchSuite.Ink` HID 实现 | 只做思路参考，仍要看许可证 |

每条都要重新走"相关自检 + 低端机实测"，不能因为"别人用了"就接。
