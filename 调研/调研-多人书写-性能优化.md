# 多人同时书写：性能优化建议（先行）

- 日期：2026-10-24
- 状态：**只调研，不改代码**
- 前置：`调研-多人同时书写.md`（场景、单笔状态、会话重构、人数上限）
- 场景校正：用户明确 **一个触点 = 一个输入**，不考虑手掌托屏/手指搭屏；优化只面对"学生上台板演"这一种真实用法

---

## 0. 结论先行

1. **多人书写不能直接开写，先把渲染的"脏区"改掉**。现在所有每帧重画的东西（活跃笔、光标、激光、HUD…）被并成**一个矩形**；两个学生一左一右板演，这个并集就是整屏——2 个人就会把项目里"只更脏区"的优化全部吃掉。
2. **最大的性能收益不在"第二笔的几何"，而在"不要把整屏重画"**。按现有实测口径：全屏 5.2M 像素时 GPU 约 8~9%，只更脏区时 0.1~0.8%。把这一点修好，2 人板演基本就稳了。
3. **第二个收益是"每个脏区只画一次"**。现在的渲染循环是"每个脏区矩形里，把活跃笔、光标、激光、HUD、卡片全部重画一遍"；如果直接改成"每笔一个脏区"而不改循环，4 个人会变成 N×M 次重画，甚至高亮笔会因重复叠画变深。
4. **建议的落地顺序**：先做 O1（脏区/两遍渲染）→ 再做会话重构 → 再做多人模式 → 最后才谈 4 人。不要反过来"先上多人、卡了再优化"。
5. **4 人不是不能做**：按"一个点一个输入"的口径，4 人就是 4 条指针，输入层没有问题；真正要过的是帧预算。建议第一版默认 2 人，4 人作为后续开关，先用 `--multiwritetest 4` 过门禁。

---

## 1. 真实场景：学生上台板演

| 特征 | 对性能的含义 |
|---|---|
| 通常 1~2 个学生同时写，偶尔 3~4 个小组 | 2 人是主场景；4 人是低频峰值，可以按"门禁"决定是否开放 |
| 两个人常站在屏幕左右两端 | **脏区并集 = 整屏**，这是最坏、也是最常见的布局 |
| 一次板演 10~60 秒，不是连续 20 分钟 | 活跃笔几何是主要成本；撤销/存档是次要成本 |
| 学生写字大、笔画长（一个字/一行算式） | 活跃笔几何随点数线性增长，长笔画更贵 |
| 屏幕上通常已经有老师的板书/PPT | 背景分块是缓存好的，但整屏脏区会把它们全部重新贴一遍 |
| 老师可能同时在工具栏换色/翻页 | 多人模式下要禁止写字期间切页/切板；工具栏操作仍要快 |
| 不出现手掌托屏/手指搭屏 | 不做面积/间距/手掌准入，只受人数上限 |

## 2. 基线：现在一笔有多贵

来自项目内已有实测（`调研/性能-内存与卡顿实测.md`、`调研/延时-实测与优化.md`）：

| 指标 | 实测/口径 | 对多人的意义 |
|---|---|---|
| 单笔书写每帧记录 | 平均 **1.7ms**，最差 **7.9ms**（20 分钟 7200 笔） | 60Hz 预算 16.7ms，单人还有约 9~15ms 余量 |
| 单帧渲染 | 约 **1.8~2.5ms**（空白/密集页差异 <0.5ms） | 4 笔 naive 约 7~10ms，仍在预算内，但余量变薄 |
| Present 等待 | 约 **2.2ms**（waitable swapchain） | 固定开销，和人数无关 |
| 全屏脏区 | 5.2M 像素时 GPU **8~9%** | 2 人左右布局就会触发 |
| 只更脏区 | GPU **0.1~0.8%** | 单人现在的常态；多人版要保住 |
| 背景分块 | 只补画新笔画，代价与"新笔数"成正比 | 提交 2~4 笔不会重画整块，这一层已经做好 |

> 这些是单笔基线；**多人还没有实测**。下面的收益都是"按代码结构估算"，必须用 `--multiwritetest` 验证。

## 3. 现在的热点清单

| # | 热点 | 位置 | 为什么多人会放大 |
|---|---|---|---|
| 1 | 所有瞬态元素并成一个脏区 | `Overlay.ComputeTransientBounds`（`Overlay.cs:2833`） | 两笔一左一右 → 并集整屏 → 每帧全屏合成 |
| 2 | 每个脏区里重画全部瞬态 | `Overlay.RenderFrame` 的 `foreach (_frameDirty)`（`Overlay.cs:2681-2803`） | 改成每笔一个矩形后，N 个矩形会把同一笔重画 N 次 |
| 3 | HUD/卡片/提示也在脏区循环里 | `Overlay.cs:2767-2803` | 多矩形时重复画；高亮笔重复叠画会变深 |
| 4 | 活跃笔每帧重建整条几何 | `Model.BuildCenterlineCore`（`Model.cs:5562`） | 每笔 O(点数)，2 人 2×、4 人 4×；长笔画更贵 |
| 5 | 每个触点都走完整 UI/悬停/光标判断 | `OnPointerMove`（`Engine.cs:5367`） | 4 人时每帧多几百次无用判断；第二个人移动时 UI 明明没变 |
| 6 | 每笔结束都拼长日志/测量串 | `EndStroke`（`Engine.cs:7584`） | 4 人时字符串/分配 4×；诊断关掉时不该付这个钱 |
| 7 | 停手后整块板书历史序列化 | `MaybeHistorySnapshot`（`Engine.cs:212`） | 4 人写 10 分钟 = 4 倍笔数，可能一次几十毫秒停顿 |
| 8 | 撤销栈 200 步 / 3 万条 | `Doc` 撤销栈 | 4 人时"自己的上一笔"很快被挤掉；这是体验问题，不是 CPU |
| 9 | 几何对象每帧 Dispose/Create | `Stroke.BuildGeometry`（`Model.cs:4466`） | 4 笔 = 4× COM 对象 churn；长笔画更明显 |

## 4. 优化方案（按优先级）

### O1（最高优先级）：脏区从"一个并集"改成"每笔一块"

**做什么**

1. `LiveStroke` 自己维护一个 `RectF Dirty`：当前帧 `PaddedBounds` ∪ 前两帧的 `PaddedBounds`（双缓冲需要擦掉两帧前的旧像素）。
2. `ComputeTransientBounds` 不再把活跃笔并进一个大矩形；活跃笔按"每笔一块"单独加进 `_frameDirty`。光标、激光、HUD、卡片等仍可合成一块（它们通常只有一个/一小块）。
3. 一笔写完后，保留它的最后一块脏区 1~2 帧，用来擦掉抬笔那一帧的残留。
4. 矩形太多时（建议阈值 8~12 块，或总面积 > 屏幕 60%）合并成少量大矩形/整屏；阈值用实测帧时间定。

**预期收益**

- 两个学生左右板演：从"整屏 5.2M 像素"降到"两块笔迹附近"；GPU 从 8~9% 回到 1% 量级。
- 这是 2 人板演能否稳 60fps 的关键，优先于任何几何优化。

**风险/验证**

- 脏区小数边界、双缓冲"两帧前"的残留：沿用现有 `AddClipped` 的像素对齐和 `_transientHistory` 规则；自检要加"快速左右移动/抬笔后无残影"。
- 高亮笔半透明：同一块区域不能被两个脏区重复叠画（见 O2）。

### O2（最高优先级）：渲染改成"背景一遍 + 瞬态一遍"

**现状**

`RenderFrame` 对每个 `_frameDirty` 矩形都做：

```
PushAxisAlignedClip(rect)
  Clear + CompositeTiles          // 背景
  DrawActiveStroke(s)             // 瞬态
  DrawCursor / Laser / Selection  // 瞬态
  DrawHud / 卡片 / PPT 条 / 提示   // 屏幕层
PopClip
```

`_frameDirty` 本来就可能有多块（内容脏区、页面脏区、UI），所以这条循环**现在已经会重复画瞬态**；多人"每笔一块"会把它放大。

**改成两遍**

1. **背景遍**：遍历 `_frameDirty`，只做 Clear + `CompositeTiles` + 页层；把旧像素擦干净。
2. **瞬态遍**：`CanvasToWindow` 变换下，把活跃笔、光标、激光、框选、选中框等**各画一次**；每笔用自己的 `Dirty` 做裁剪（或直接不裁，反正只 Present 脏区）。
3. **屏幕层一遍**：UI 缓存位图、HUD、触点数、计时/点名卡、PPT 条、提示、截图遮罩，各画一次。
4. `Present1` 收全部脏区。

**预期收益**

- 瞬态绘制次数从"矩形数 × 元素数"降到"元素数"；高亮笔不会因重复叠画变深。
- HUD/卡片从每矩形一次降到每帧一次。

**风险/验证**

- 这是一次渲染主循环重构，必须用现有 `--latencytest` / `--paneltest` / 截图自检回归"残影、闪、重复叠色"。
- 需要保证"旧瞬态像素"仍被背景遍擦掉：活跃笔的 2 帧历史脏区必须完整。

### O3（高优先级）：活跃笔输入走快路径

**做什么**

1. `OnPointerMove` 一进来先按 `(hwnd, pointerId)` 查 `_live`；命中就直接 `ExtendLive` 并返回，跳过 UI/回放/PPT 条/计时卡/提示/光标/触摸手势判断。
2. 触摸笔迹不做悬停光标、不做 tooltip；`ApplyCursor` 对 `PT_TOUCH` 直接跳过。
3. 多人模式下，写手触点不再走 `TouchGestures.Move` 的路径统计（只需要人数表/抬起），减少每消息开销。
4. `OnPointerUp` 同样先查 `_live`，只结束对应笔，避免走界面/手势收尾链。

**预期收益**

- 4 人时每帧几百条移动消息，省掉大量命中测试/状态判断；延迟抖动更小。
- 不改变任何视觉行为，风险低。

### O4（高优先级）：多人模式关掉"贵且不需要"的东西

多人模式第一版就按下面关，不要等卡了再关：

| 功能 | 处理 | 原因 |
|---|---|---|
| 墨迹预测尾 | 关 | 单尾无法分人；每帧多一套几何 |
| 停顿成型 | 关 | 每笔一套 dwell 状态；板演不需要 |
| 运动模型/平滑（活笔） | 活笔直接用原始折线 | `RawWhileLive` 已经是折线；省掉模型重算 |
| 系统湿墨（真笔） | 只给 `PT_PEN` | 这台学校屏没有真笔；触摸不走 |
| 长按选择 / 双指手势 / 三指擦 | 关 | 第二/第三个触点就是第二/第三个人 |
| 激光 / 形状 / 框选 | 单人 | 第一版不并行 |
| 原始输入补点 / 黑匣子 / 录墨迹 | 仅诊断开关打开时 | 板演不需要，省分配 |
| 每笔长日志 `[笔画]` | 诊断关闭时不拼串 | 4 人字符串/分配 4× |

**预期收益**：每笔每帧省 0.5~2ms；4 人时是线性叠加。

### O5（中优先级）：长笔画活笔几何分块

**问题**

`BuildCenterlineCore` 每帧遍历整条笔的所有点。板演的字/算式往往很长；写到 1000 点，每帧就要重建 1000 段。

**方案（按复杂度）**

1. **先量**：如果 2 人 p95 已 ≤10ms、4 人 ≤14ms，不做这一步。
2. **笔（不透明）分块**：每 64 点把前缀冻成一个 `ID2D1PathGeometry`，只重建尾部 ≤64 点；抬笔时再重建一次完整几何做最终形状。块之间重叠 1~2 个点 + 圆帽，避免接缝。
3. **荧光笔（半透明）不要简单分块**：分块单独画会在接缝处叠色变深。要么保持整条重建，要么把前缀烘到一张透明位图再合成（复杂度更高）。
4. 不要在"点还没到齐"时按时间节流重建（会看起来一顿一顿）；按点数分块更稳。

**预期收益**：长笔画几何从 O(L) 降到 O(尾部)，4 人长笔画最明显；短笔画收益小。

**风险**：接缝、圆帽、荧光笔叠色；必须用截图/像素探针回归。

### O6（中优先级）：板书历史/自动存档降频或后台化

**现状**：`MaybeHistorySnapshot` / `MaybeAutoSave` 已经避开书写期间，但停手后会在 UI 线程整块序列化；4 人 10 分钟 = 4 倍笔数，可能出现一次几十毫秒的停顿。

**方案**

1. 多人模式使用过的会话，把 `HistoryMinGapMs` 适当拉长（例如从 10s 到 20~30s），或跳过"刚好在多人结束后"的那一次，等下一轮空闲。
2. 序列化仍在 UI 线程时，先做"只序列化白板、不含图片"（现有规则）并限制频率；如果实测仍有可见停顿，再考虑后台序列化（拷贝引用/只读快照，风险高，放最后）。
3. 自动存档同理；退出前那一份必须保留。

### O7（低优先级）：减少几何/分配 churn

1. `BuildGeometry` 每帧 Dispose/Create 路径几何；分块后自然减少。
2. `StrokeMotion` 的 `ConditionalWeakTable` 每笔一份，4 笔没问题；不要在多人模式给活笔启用。
3. `[笔画]` 长字符串、`TouchStats` 每 down 一行日志：诊断关闭时降到最低。
4. `ReadTouchSize` 每 down 分配 160 字节 HGlobal：每笔只 1 次，影响很小；如果要抠，可改栈缓冲。

### O8（可选）：自适应质量/人数

- 如果连续 N 帧超过预算（例如 20ms），**只拒绝新的写手**，不打断已经在写的笔；状态栏提示"设备性能不足，本场最多 N 人"。
- 不建议自动降低笔迹质量/抽点；那会改变手感。
- 不建议自动把 4 人降到 2 人并中断正在写的笔。

## 5. 落地顺序（和多人功能的关系）

| 阶段 | 内容 | 依赖 | 估算 |
|---|---|---|---|
| **O0** | 基线测量：用现有 `--latbench` / `--writetest` 记录单人数据；为 `--multiwritetest` 定场景 | 无 | 0.5 天 |
| **O1** | 脏区每笔一块 + 矩形合并阈值 | 无（单人也能做，行为不变） | 0.5~1 天 |
| **O2** | 两遍渲染（背景遍 + 瞬态遍 + 屏幕层一遍） | O1 | 0.5~1 天 |
| **P1** | 会话重构（`LiveStroke`、`_live`、`AnyWriting`、指针路由） | 无 | 2~3 天 |
| **O3** | 活跃笔输入快路径 | P1 | 0.5 天 |
| **O4** | 多人模式功能裁剪 | P1/P2 | 0.5 天 |
| **P2** | 多人模式设置/人数上限/日志 | P1/O3/O4 | 1~2 天 |
| **P3** | 自检 + 学校 2 人实测 | 全部 | 1~2 天 |
| **O5** | 长笔画分块（仅当 2/4 人实测不过线） | P3 数据 | 1~2 天 |
| **O6** | 存档降频/后台化（仅当实测有停顿） | P3 数据 | 0.5~2 天 |
| **P4** | 4 人开关（过门禁后） | O5 结论 | 另估 |

> O1/O2 可以**先于**会话重构做：它们不依赖多笔，单人也能验证"没有残影/没有变慢"。这样万一渲染重构出问题，能单独回退，不会和多人逻辑混在一起。

## 6. 测量：`--multiwritetest N`

实现阶段加一个合成触点压测，不靠"感觉流畅"：

| 变量 | 取值 |
|---|---|
| 人数 | 1 / 2 / 3 / 4 |
| 位置 | 同一小块 / 屏幕左右两端（专打脏区并集） |
| 笔画 | 短（每 0.5s 抬一次）/ 长（连续 10s 不抬） |
| 分辨率 | 1080p / 4K（学校实际） |
| 背景 | 空白 / 已写满一屏 |
| 工具 | 笔 / 荧光笔（高亮笔查重复叠色） |

每个场景 60 秒，输出：

- 帧记录 `avg / p95 / max`、`slow50 / slow150`、上屏脏区面积百分比；
- `LastRecordMs`、`Present` 等待、`CanvasTiles.RasterMsLastFrame`、`StrokesLastFrame`；
- 每笔几何重建耗时、提交耗时、输入到加点延迟；
- GC 次数、工作集、显存；
- 结束后自动存档/板书历史的停顿。

**建议验收线**（可按学校机器实测调整）：

| 场景 | 目标 |
|---|---|
| 2 人、4K、学校 OPS、60 秒 | p95 ≤ 10ms、max ≤ 25ms，不持续 <55fps；输入延迟比单人 +≤1 帧 |
| 4 人、同上 | p95 ≤ 14ms、max ≤ 30ms，不持续 <50fps；否则不开放 4 人 |
| 10 分钟双人后停手 | 存档/历史停顿 ≤ 30ms，内存无持续增长 |

## 7. 不建议做的事

1. **先上多人、卡了再优化**：脏区并集会让 2 人直接退回全屏重画，先把 O1/O2 做完再开功能。
2. **把渲染/输入搬到另一个线程**：D2D 设备/窗口消息的单线程约束多，收益不确定，风险远大于 O1~O5。
3. **每个写手一个独立窗口/交换链**：合成、层级、穿透、光标都会变复杂，2~4 人用不上。
4. **用面积/间距/手掌判定来"减少写手"**：用户已明确一个触点就是一个输入，不做这些。
5. **为了省性能而抽点/降采样**：会直接改变手感，板演时最容易被看出来。
6. **在多人模式保留预测尾/停顿成型**：单尾无法分人，且每帧多一套几何。
7. **用整屏重画当"简单方案"**：会把项目里已有的脏区优化全部抵消，低配 OPS + 4K 最先出问题。
