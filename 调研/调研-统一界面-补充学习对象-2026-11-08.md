# 调研补充：更多值得学习的界面管理对象

日期：2026-11-08　　状态：**调研补充，未改代码**

> 主文档：`调研-统一界面-优秀参考与先进管理方式-2026-11-08.md`
>
> 主文档覆盖了 12 个“页面 / 浮层 / 输入 / 焦点 / 滚动 / 窗口”的通用参考。
> 这一份补三个缺口：
> 1. **动作/命令系统**：工具条、菜单、快捷键、右键菜单为什么总是各写一套？
> 2. **多面板 / 停靠 / 工作区**：以后做真窗口、展台、笔记时，布局怎么管？
> 3. **键盘 / 无障碍 / 组件规范**：对话框、菜单、下拉、开关的键盘行为有没有权威标准？
>
> 结论：**最值得补的 6 个对象是 Dear ImGui、Excalidraw、tldraw、VS Code、JetBrains Platform、WAI-ARIA APG。**
> 其次是 AppKit（sheet/popover/panel）、Blender（areas/regions）、Radix/Headless UI（可访问原语）、
> Material 3 / Fluent 2 / Apple HIG（设计规范）、FlaUI（Windows UI 自动化）、Qt ADS（停靠布局）。

## 〇、结论先行

1. **我们缺的不只是“页面框架”，还缺“动作系统”。**
   现在工具条、更多、设置行、右键菜单、快捷键各自写“命中 → 执行 → 置灰 → 提示”。
   VS Code、JetBrains、Excalidraw、tldraw 都是**一个 Action 注册表**：`Id + 标题 + 图标 + 快捷键 + 可用性 + 执行`，
   菜单/工具条/快捷键只查表，不重复业务。
2. **Dear ImGui 是最接近我们渲染模型的参考。**
   它也是立即模式、每帧重建、ID 栈、Active ID、Popup 栈、捕获、键盘导航、Docking。
   我们不需要每帧重建，但它的**ID 栈 / Active ID / Popup 栈 / 捕获**可以直接借。
3. **Excalidraw / tldraw 是“画布 + UI 浮层”最直接的产品参考。**
   它们都处理了：工具条、左侧面板、对话框、Popover、菜单、快捷键、移动端、层叠。
   Excalidraw 是 MIT；tldraw 是 source-available，**只借模式，不复制代码**。
4. **VS Code / JetBrains / Blender 是“多面板工作区”的成熟参考。**
   VS Code 的 workbench 区域（标题/活动栏/侧栏/编辑组/面板/状态栏）、JetBrains 的 Tool Windows、
   Blender 的 Areas/Regions，都是“一个窗口里很多面板”的长期验证方案。
5. **AppKit 把“真窗口的三种浮层”讲得最清楚：sheet / popover / panel。**
   sheet 是贴在父窗口上的模态；popover 是锚定的小浮层；panel 是辅助窗口。
   这正是我们以后 `WindowManager` 要区分的。
6. **WAI-ARIA APG 是对话框/菜单/下拉/列表的键盘行为权威。**
   不是 Web 专属：Tab 顺序、初始焦点、Esc、方向键、typeahead、焦点恢复，桌面同样适用。
7. **Radix / Headless UI 是“可访问原语”的工程范本。**
   焦点陷阱、碰撞检测、点外关闭、受控/非受控、层级，这些都应该由底层做一次。
8. **设计规范（Material 3 / Fluent 2 / HIG）解决“看起来专业”。**
   层级、间距、圆角、阴影、动效、对话框/侧 sheet/导航栏的用法，有现成答案。
9. **FlaUI 解决“真窗口怎么自动测”。**
   基于 Windows UI Automation，能测 Win32/WinForms/WPF/Store Apps；适合测 IME、焦点、DPI、残留窗口。
10. **Qt ADS 是“以后要停靠布局”的参考，不是现在做。**
    多面板停靠、浮动组、布局持久化，等 WindowManager 立项再看。

## 二、逐个深读

### 2.1 Dear ImGui：最接近我们渲染模型的参考

#### 它解决什么问题

Dear ImGui 是“立即模式 GUI”：每帧重新声明 UI，库内部用 **ID 栈** 识别控件，
用 **Active ID** 跟踪当前交互，用 **Popup 栈** 管理弹出层，用 **Nav** 管理键盘/手柄导航。
它没有保留式控件树，和我们的 D2D 立即绘制非常接近。

#### 核心机制

1. **ID 栈**
   - 每个控件由“当前 ID 栈 + 标签”哈希出唯一 ID；
   - `PushID` / `PopID` 创建作用域，避免不同窗口/循环里的同名控件冲突；
   - ID 用于跟踪 Active ID、焦点、状态、动画；
   - 有 ID Stack Tool 可视化哈希过程。
2. **Active ID**
   - 同一时间只有一个“活动控件”（被按住/拖动/编辑）；
   - 鼠标按下时设置 Active ID，移动/抬起都发给它，不再重新命中；
   - 这就是“指针捕获”的轻量实现。
3. **Popup 栈**
   - 弹出层按栈管理：打开新 popup 时，旧的仍在栈里；
   - 关闭按 Esc/点外/显式关闭；
   - 有 `BeginPopup` / `OpenPopup` / `CloseCurrentPopup`；
   - 弹出层有层级和模态选项。
4. **Nav / 焦点**
   - 键盘/手柄导航有当前 Nav ID；
   - Tab/方向键在可导航项之间移动；
   - 与 Active ID 分离：导航焦点 ≠ 按住的活动控件。
5. **Docking**
   - Docking 分支支持窗口停靠、拆分、浮动、布局持久化；
   - 适合工具型桌面应用的多面板布局。
6. **布局**
   - 立即模式：每帧 `BeginChild` / `SameLine` / `SetNextWindowPos`；
   - 有布局栈、裁剪、滚动条；
   - 不保留控件对象，状态按 ID 存在上下文里。

#### 可照搬的逻辑

- **ID 栈**：我们的设置行/浮层/菜单项用稳定 ID，不要用下标；
  下标一旦插入/删除就串行，历史上已经出过“命中编号串段”。
- **Active ID**：一次只允许一个拖动/滑动会话；按下后捕获，Move/Up 不再重新命中。
- **Popup 栈**：菜单/下拉/确认框按栈管理，Esc 关最上面一个。
- **Nav ID 与 Active ID 分离**：键盘焦点（Tab）和被按住的控件不是一回事。
- **Docking**：WindowManager 以后可以参考，不要现在做。

#### 不照搬

- 每帧重建整个 UI（我们只在失效时重画界面位图）；
- 立即模式的文本输入（IME 仍用原生 RichEdit）；
- ImGui 的绘制/字体/后端；
- 完整 Docking（等真窗口）。

#### 我们的差异

- 我们的 UI 是“缓存位图 + 失效重绘”，不是每帧重建；
- 我们的页面/浮层是显式对象，不是每帧函数调用；
- 我们的文字输入是原生 HWND，ImGui 的输入模型不适用。

#### 来源

- Dear ImGui FAQ（ID 栈）：https://github.com/ocornut/imgui/blob/master/docs/FAQ.md
- Dear ImGui Docking：https://github.com/ocornut/imgui/wiki/Docking
- Dear ImGui 源码 `imgui.h`：https://github.com/ocornut/imgui/blob/master/imgui.h

### 2.2 Excalidraw：画布 + UI 浮层的产品范本

#### 它解决什么问题

Excalidraw 是开源白板（MIT），有完整的手绘工具条、左侧面板、对话框、Popover、菜单、快捷键、移动端。
它的 UI 不是“一个页面”，而是**画布上漂浮的一层层 UI**，和我们的场景最接近。

#### 核心机制（从源码/文档提炼）

1. **Action 注册表**
   - `actions` 目录里每个动作是一个对象：`id`、`label`、`icon`、`keyTest`、`predicate`、`perform`；
   - `ActionManager` 负责注册/执行/查询；
   - 工具条、菜单、快捷键、右键菜单都查同一张表；
   - 置灰/选中态由 `predicate` 和 `checked` 决定。
2. **UI 分层**
   - `LayerUI` 负责把不同 UI 层叠在画布上；
   - `Dialog`、`Popover`、`Island`（浮动工具条）、`Stack`（层叠）等组件；
   - 对话框/弹出层有自己的关闭/焦点行为；
   - 移动端会切换成底部/抽屉式布局。
3. **工具条 / 面板**
   - 顶部工具条、左侧属性面板、底部/浮动 Island；
   - 选中对象后出现上下文操作；
   - 面板可折叠/移动（取决于版本）。
4. **状态**
   - 画布状态与 UI 状态分离；
   - 动作执行通过 `ActionManager`，不直接改组件状态；
   - 撤销/重做是动作/历史的一部分。

#### 可照搬的逻辑

- **一套 Action 表**：工具条/菜单/快捷键/右键菜单不再各写一遍；
- **Action 的 `predicate`**：统一“什么时候可用/置灰”；
- **Action 的 `checked`**：统一开关/选中态；
- **Dialog/Popover/Island 分层**：页面、浮层、浮动工具条分开；
- **移动端/窄屏切换**：我们的窄屏/极简模式可以借“折叠/抽屉”思路。

#### 不照搬

- React/ReactDOM 状态管理；
- 画布渲染/手绘算法（我们已有自己的）；
- Excalidraw 的完整 UI 组件（许可 MIT，但技术栈不同）。

#### 我们的差异

- 我们是 C#/D2D，UI 是绘制 + 命中矩形，不是 React 组件；
- 我们的画布/墨迹引擎更重，不能把 UI 状态和画布状态混在一起；
- 我们只需要“动作表 + 分层”，不需要整套 React 组件库。

#### 来源

- Excalidraw 仓库：https://github.com/excalidraw/excalidraw
- Excalidraw 开发者文档：https://docs.excalidraw.com/
- Excalidraw+ SDK 文档：https://plus.excalidraw.com/docs/sdk
- UI Options：https://docs.excalidraw.com/docs/@excalidraw/excalidraw/api/props/ui-options

### 2.3 tldraw：画布编辑器 + UI 组件 + Actions

#### 它解决什么问题

tldraw 是无限画布 SDK，提供完整的 React UI（菜单、工具条、面板、对话框）和编辑器状态模型。
它的“Actions”设计与 Excalidraw 类似，但更强调 **Action ID 被菜单/工具条/快捷键共同引用**。

#### 核心机制

1. **Editor**
   - 画布状态、工具、选择、历史、相机；
   - 事件/状态用响应式系统驱动 UI。
2. **Actions**
   - 命名操作：`id`、`label`、`shortcut`、`onSelect`；
   - 菜单/工具条按键查 Action；
   - 支持自定义 action 注册。
3. **UI components**
   - 完整 React UI：菜单、工具条、面板、对话框；
   - 可替换/隐藏/从零构建；
   - 有 `TldrawUi` 组件和 `editor` primitives。
4. **Keyboard shortcuts**
   - 全局/工具/动作快捷键；
   - Esc 取消/退出；
   - 可自定义。
5. **Dialogs / menus**
   - 对话框、菜单、popover 由 UI 层管理；
   - 与编辑器状态解耦。

#### 可照搬的逻辑

- **Action ID 是唯一身份**：菜单/工具条/快捷键都引用同一个 ID；
- **UI 可替换**：页面只依赖 Action/Editor 接口，不依赖具体按钮；
- **Esc 分层**：先取消当前工具/选择，再关弹层/对话框；
- **快捷键可自定义**：我们的 `KeyBindings` 可以走同一张 Action 表。

#### 不照搬

- React/Signals/编辑器渲染；
- tldraw 的 source-available 许可（**不复制代码**）；
- 完整画布 SDK（我们有自己的墨迹引擎）。

#### 我们的差异

- 我们的“Action”不仅要驱动 UI，还要驱动引擎命令（`IEngineCommands`）；
- 我们的快捷键已经有 `KeyBindings`，可以复用为 Action 的快捷键字段；
- 我们的画布不是 DOM/React。

#### 来源

- tldraw UI components：https://tldraw.dev/sdk-features/ui-components
- tldraw Actions：https://tldraw.dev/sdk-features/actions
- tldraw 仓库：https://github.com/tldraw/tldraw
- tldraw Quick start：https://tldraw.dev/quick-start

### 2.4 VS Code：Workbench 区域 + Editor Groups + Quick Pick

#### 它解决什么问题

VS Code 是“一个窗口里很多区域”的成熟桌面应用：标题栏、活动栏、侧栏、编辑组、面板、状态栏；
还有命令面板、快速选择、通知、对话框、右键菜单。

#### 核心机制

1. **Workbench 区域**
   - Title Bar（标题/菜单/布局控制）；
   - Activity Bar（活动栏，图标导航）；
   - Side Bar（侧栏，视图容器）；
   - Editor Group（编辑组，可拆分/拖动标签）；
   - Panel（底部/右侧面板，终端/输出/问题）；
   - Status Bar（状态栏）。
2. **Editor Groups**
   - 编辑组可以水平/垂直拆分；
   - 标签可以在组之间拖动；
   - 组可以关闭/合并；
   - 布局是“网格 + 可调整分隔条”。
3. **Quick Pick / Command Palette**
   - 命令面板：搜索所有命令；
   - Quick Pick：列表选择、过滤、多选、输入；
   - 命令和菜单/快捷键共享同一套命令注册。
4. **Notifications**
   - 通知中心：信息/警告/错误，可操作；
   - 不阻塞主流程；
   - 有“不再提示/查看日志”等动作。
5. **Dialogs**
   - 模态对话框、确认框、输入框；
   - 与命令/动作系统集成。
6. **布局持久化**
   - 侧栏/面板宽度、编辑组布局、可见性；
   - 可保存/恢复工作区。

#### 可照搬的逻辑

- **区域化布局**：WindowManager 可以把窗口拆成 Title/Activity/Side/Content/Panel/Status 六个区域；
- **Editor Group 模型**：以后多文档/多视图（白板/PDF/笔记）可以借“组 + 标签 + 拆分”；
- **命令面板**：所有 Action 可搜索/执行，适合我们功能越来越多的工具条；
- **通知中心**：日志/更新/备份结果不要弹模态，进通知；
- **布局持久化**：窗口/面板位置按工作区保存。

#### 不照搬

- Electron/TypeScript 实现；
- VS Code 的完整扩展/工作区模型；
- 编辑组/标签的复杂拖拽（第一阶段不需要）。

#### 我们的差异

- 我们目前是单窗口覆盖层，不需要 Editor Groups；
- 但 WindowManager 以后要做多文档/多视图，可以借“组 + 标签”；
- 我们的命令要直接映射到 `IEngineCommands`，不是 VS Code 的 command service。

#### 来源

- VS Code 用户界面：https://code.visualstudio.com/docs/editing/getting-started/userinterface
- VS Code 自定义布局：https://code.visualstudio.com/docs/configure/custom-layout
- VS Code 命令面板：https://code.visualstudio.com/docs/getstarted/userinterface#_command-palette
- VS Code 通知：https://code.visualstudio.com/api/ux-guidelines/notifications

### 2.5 JetBrains Platform：Action System + Tool Windows + DialogWrapper

#### 它解决什么问题

IntelliJ 系 IDE 有大量动作、菜单、工具窗、对话框、快捷键、焦点遍历；
它把这些抽象成平台级 API，插件只注册 Action/ ToolWindow/ Dialog，不重复 UI 逻辑。

#### 核心机制

1. **Action System**
   - `AnAction`：一个可执行动作；
   - `ActionGroup`：菜单/工具条分组；
   - `ActionManager`：注册/替换/查询；
   - Action 有 `update()` 决定可见/可用/选中；
   - 菜单、工具条、快捷键、右键菜单都引用同一个 Action ID。
2. **Tool Windows**
   - `ToolWindowManager` 注册工具窗；
   - 工具窗可停靠/浮动/隐藏；
   - 有 stripe button、内容、标题栏动作；
   - 状态可持久化。
3. **DialogWrapper**
   - 标准模态对话框基类；
   - 负责：OK/Cancel、校验、焦点、Esc、默认按钮、帮助；
   - 子类只填内容/校验；
   - 有 `FocusTraversalPolicy` 控制 Tab 顺序。
4. **Popup / Chooser**
   - `PopupChooser`、`JBPopup` 等：锚定、搜索、键盘导航、点外关闭；
   - 与 Action/列表模型集成。
5. **FocusTraversalPolicy**
   - 显式定义组件之间的 Tab 顺序；
   - 对话框打开时设初始焦点；
   - 关闭时恢复焦点。

#### 可照搬的逻辑

- **Action 的 `update()`**：统一“可见/可用/选中”三态，不在每个按钮里写；
- **ToolWindow 模型**：WindowManager 的侧栏/面板可以借“注册 + 停靠 + 状态”；
- **DialogWrapper**：我们的确认框/API 表单可以有统一基类：OK/Cancel/校验/焦点/Esc；
- **FocusTraversalPolicy**：设置页/API 页的 Tab 顺序显式定义；
- **PopupChooser**：模型下拉/命令面板可借“搜索 + 键盘导航”。

#### 不照搬

- Swing/AWT/IntelliJ 平台；
- 完整插件/项目模型；
- 复杂的 Action 继承体系（我们只需要扁平表）。

#### 我们的差异

- 我们的 Action 要直接调用引擎命令，不经过 IDE 的 DataContext；
- 我们的对话框是 D2D 页面/浮层，不是 Swing Dialog；
- 我们不需要插件隔离/类加载器。

#### 来源

- IntelliJ Action System：https://plugins.jetbrains.com/docs/intellij/action-system.html
- IntelliJ Tool Windows：https://plugins.jetbrains.com/docs/intellij/tool-windows.html
- IntelliJ DialogWrapper：https://plugins.jetbrains.com/docs/intellij/dialog-wrapper.html

### 2.6 Blender：Areas / Regions / Editors / Operators

#### 它解决什么问题

Blender 是“一个窗口里大量编辑器/面板/区域”的极端案例：
3D 视图、时间线、属性、大纲、节点编辑器……每个区域可以切换编辑器类型、拆分/合并、全屏。

#### 核心机制

1. **Window / Screen / Area / Region**
   - Window 是顶层窗口；
   - Screen 是一套工作区布局；
   - Area 是屏幕上的矩形区域，每个 Area 有一个 Editor 类型；
   - Region 是 Area 内的子区域（header、toolbar、sidebar、main、footer 等）。
2. **Editor 类型**
   - 每个 Area 可以在 3D View / Timeline / Outliner / Properties / Node Editor 等之间切换；
   - 每种 Editor 有自己的绘制/输入/状态；
   - Area 可拆分/合并/全屏。
3. **Operators**
   - 操作注册表：`bpy.ops.*`；
   - 操作有 `poll()`（是否可用）、`execute()`、`invoke()`、属性；
   - 菜单/快捷键/搜索都调用同一操作；
   - 支持撤销/重做。
4. **Popover / Menu**
   - `layout.popover()` 把面板放进弹出层；
   - 菜单/弹出层有层级和关闭行为；
   - 适合属性/工具选项。
5. **Workspaces**
   - 工作区保存一套 Screen 布局；
   - 不同任务切换不同工作区。

#### 可照搬的逻辑

- **Area/Region 模型**：WindowManager 可以把窗口拆成区域，每个区域装一个 Page/Editor；
- **Editor 类型**：白板/PDF/笔记/展台可以视为不同 Editor，装进 Area；
- **Operator 的 `poll()`**：Action 的可用性判断；
- **Popover**：设置/属性浮层；
- **Workspace**：以后“上课/备课/回放”可以切换工作区布局。

#### 不照搬

- GPL 代码；
- Blender 的 3D/节点/属性系统；
- 复杂的 Area 拆分/合并交互（第一阶段不需要）。

#### 我们的差异

- 我们不需要任意拆分/合并 Area；
- 我们的“Editor”是白板/PDF/展台/笔记；
- 我们的布局可以先用固定区域 + 可折叠侧栏，不做到 Blender 那么自由。

#### 来源

- Blender Regions：https://docs.blender.org/manual/en/latest/interface/window_system/regions.html
- Blender Areas：https://docs.blender.org/manual/en/latest/interface/window_system/areas.html

### 2.7 AppKit：Sheet / Popover / Panel / 父子窗口

#### 它解决什么问题

macOS 把“浮在窗口上的东西”分成几种，语义清晰：
- **Sheet**：贴在父窗口标题栏下方，文档模态；
- **Popover**：锚定到某个控件/矩形，点外关闭；
- **Panel**：辅助窗口（工具/检查器），可浮动；
- **Window**：独立窗口。

#### 核心机制

1. **NSWindow**
   - 一个 NSWindow 对应一个屏幕窗口；
   - 有 parent/child window 关系；
   - sheet 是 document-modal，附着在父窗口。
2. **NSPanel**
   - 辅助窗口，通常不显示在 Window 菜单；
   - 可成为浮动工具/检查器；
   - 有 `becomesKeyOnlyIfNeeded` 等行为。
3. **NSPopover**
   - 锚定到 `positioningRect` / `positioningView`；
   - 有 `behavior`（transient/semitransient/applicationDefined）；
   - 点外/按 Esc 关闭；
   - 自动选择显示方向。
4. **Sheets**
   - `beginSheet` / `beginCriticalSheet`；
   - 附着父窗口，阻止父窗口交互；
   - 适合“保存/确认/登录”等短任务；
   - 关闭后回到父窗口。
5. **NSViewController**
   - 管理视图生命周期；
   - 呈现/关闭；有 `presentAsSheet` / `presentAsPopover` 等。

#### 可照搬的逻辑

- **三种浮层语义**：sheet（父窗口模态）、popover（锚定轻关闭）、panel（辅助工具窗）；
- **父子窗口**：真窗口的 owner/child 关系，任务栏/激活行为；
- **锚定 + 自动方向**：下拉/菜单的定位；
- **短任务用 sheet**：API 配置/确认框不要做独立大窗；
- **关闭回父窗口**：焦点恢复。

#### 不照搬

- AppKit/Swift/Objective-C；
- macOS 的窗口 chrome/动画；
- 完整 NSViewController 生命周期。

#### 我们的差异

- Windows 上没有 sheet 概念，但可以用“owner + 无边框子窗口/覆盖层”模拟；
- 我们的覆盖层是 NOACTIVATE，sheet 式模态更适合真窗口；
- 我们的页面/浮层在同一 HWND 内，不需要 NSPanel。

#### 来源

- NSWindow：https://developer.apple.com/documentation/appkit/nswindow
- NSPanel：https://developer.apple.com/documentation/appkit/nspanel
- NSPopover：https://developer.apple.com/documentation/appkit/nspopover
- Sheets：https://developer.apple.com/documentation/appkit/nswindow/sheets
- NSViewController：https://developer.apple.com/documentation/appkit/nsviewcontroller

### 2.8 WAI-ARIA APG：对话框/菜单/下拉的键盘权威

#### 它解决什么问题

WAI-ARIA Authoring Practices Guide（APG）定义了 Web 组件的键盘/焦点行为：
对话框、菜单按钮、Combobox、Listbox、Tabs、Accordion、Tooltip 等。
虽然是 Web，但**键盘行为是跨平台通用的**。

#### 核心机制

1. **Modal Dialog Pattern**
   - 打开时焦点进入对话框（第一个可聚焦元素或标题）；
   - Tab/Shift+Tab 在对话框内循环（焦点陷阱）；
   - Esc 关闭（除非有未保存内容需要确认）；
   - 关闭后焦点回到触发元素；
   - 背景 `aria-hidden`/inert。
2. **Menu Button Pattern**
   - 按钮有 `aria-haspopup="menu"`、`aria-expanded`；
   - 打开后焦点到第一项；
   - 上下键移动，Home/End，字母 typeahead；
   - Esc 关闭并回到按钮；
   - 点外关闭。
3. **Combobox Pattern**
   - 输入框 + 弹出列表；
   - 上下键在选项中移动，Enter 选择，Esc 关闭；
   - `aria-activedescendant` 或焦点在选项上；
   - 过滤/自动完成；
   - 关闭后焦点回输入框。
4. **Listbox Pattern**
   - 单选/多选；
   - 上下键/Home/End/Shift 选择；
   - typeahead；
   - `aria-selected`。
5. **Tabs / Accordion**
   - 左右键切换 tab；Home/End；
   - Accordion 上下键/Home/End；
   - 焦点与选中分离。

#### 可照搬的逻辑

- **对话框四件事**：初始焦点、焦点陷阱、Esc、恢复焦点；
- **菜单键盘**：上下/Home/End/typeahead/Esc；
- **下拉/Combobox**：输入 + 列表 + Enter/Esc + 过滤；
- **Tab 顺序**：视觉顺序 + 显式 tabIndex；
- **开关**：Space 切换，标签可点；
- **焦点可见**：1.5px 外框，不能被裁剪。

#### 不照搬

- ARIA 属性/角色（桌面 UI 不需要 DOM 属性）；
- Web 的屏幕阅读器实现；
- 浏览器默认行为。

#### 我们的差异

- 我们是自绘 UI，没有 DOM/ARIA；但键盘/焦点行为可以一一对应；
- 我们的无障碍支持有限，先把键盘路径做对；
- 触屏/笔也要能用，不能只做键盘。

#### 来源

- APG 首页：https://www.w3.org/WAI/ARIA/apg/
- Dialog (Modal) Pattern：https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/
- Menu Button Pattern：https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/
- Combobox Pattern：https://www.w3.org/WAI/ARIA/apg/patterns/combobox/
- Listbox Pattern：https://www.w3.org/WAI/ARIA/apg/patterns/listbox/

### 2.9 Radix UI / Headless UI：可访问原语的工程范本

#### 它解决什么问题

Radix Primitives / Headless UI 把“对话框、Popover、菜单、Combobox”的**行为**做成无样式原语：
焦点陷阱、点外关闭、碰撞检测、键盘导航、受控/非受控、层级，底层做一次，业务只写内容。

#### 核心机制

1. **Dialog**
   - 模态/非模态；
   - 焦点陷阱、初始焦点、关闭恢复；
   - 点遮罩/Esc 关闭；
   - 滚动锁定；
   - `aria-modal`/`aria-labelledby`/`aria-describedby`。
2. **Popover**
   - 锚定触发元素；
   - `side`/`align`/`sideOffset`/`alignOffset`；
   - **collision handling**：空间不够自动翻转/夹取；
   - 模态/非模态；
   - 点外关闭、Esc；
   - 焦点管理可配置。
3. **Dismissable Layer**
   - 多层嵌套时，只有最上层响应“点外关闭”；
   - Esc 逐层关闭；
   - 防止一次点击关闭多层。
4. **Menu / Dropdown**
   - 键盘导航、typeahead、焦点循环；
   - 子菜单；
   - 与触发按钮的 `aria-expanded` 同步。
5. **受控/非受控**
   - `open`/`defaultOpen`/`onOpenChange`；
   - 业务可以完全控制状态，也可以交给原语。

#### 可照搬的逻辑

- **Dismissable Layer**：多层浮层的“点外关闭”只关最上面一层；
- **碰撞检测**：下拉/菜单空间不够时翻转/夹取；
- **焦点陷阱/恢复**：对话框统一做；
- **受控/非受控**：页面可以选择自己管 open 状态，或交给宿主；
- **无障碍属性**：虽然桌面不用 ARIA，但“标签/描述/模态”语义要有。

#### 不照搬

- React/DOM；
- 完整组件样式；
- Web 的 portal/事件系统。

#### 我们的差异

- 我们的“原语”是 C# 类 + D2D 绘制 + 命中矩形；
- 我们的“碰撞检测”要按工作区/DPI/多屏计算；
- 我们的“点外关闭”要经过 OverlayLayerManager 的优先级表。

#### 来源

- Radix Dialog：https://www.radix-ui.com/primitives/docs/components/dialog
- Radix Popover：https://www.radix-ui.com/primitives/docs/components/popover
- Headless UI Dialog：https://headlessui.com/react/dialog
- Headless UI Menu：https://headlessui.com/react/menu

### 2.10 Material 3 / Fluent 2 / Apple HIG：设计规范

#### 它解决什么问题

设计规范解决“看起来专业”：层级、间距、圆角、阴影、动效、对话框/侧 sheet/导航栏的用法。
不是功能框架，但能直接提升设置页、菜单、对话框的观感。

#### 核心机制（只列与我们相关的）

1. **Material 3**
   - Dialog：模态，聚焦一个任务；有标题/内容/动作；
   - Side Sheet：侧边补充内容，标准/模态；
   - Navigation Rail：中屏导航，3–7 个目的地 + 可选 FAB；
   - List：连续纵向列表，适合设置项；
   - 层级用 tonal surface/elevation 表达，不靠重阴影。
2. **Fluent 2**
   - Dialog：重要动作/确认；保持选项简单；
   - Drawer：侧边面板，适合补充内容/导航；
   - Popover：轻量上下文；
   - Menu：动作列表；
   - 桌面密度、焦点、键盘优先。
3. **Apple HIG**
   - Modality：只在一个任务需要专注时使用；不要滥用；
   - Settings：设置项分组、即时生效、默认值；
   - Navigation：层级清晰，返回可预期；
   - Sheet/Popover：短任务/上下文。

#### 可照搬的逻辑

- **对话框只做“需要确认/短任务”**；设置不要用对话框；
- **侧 sheet/drawer**：设置左栏/详情面板；
- **Navigation Rail**：左栏折叠成图标栏；
- **层级用底色/描边**，不要重阴影；
- **动效 150–200ms**，不要弹簧；
- **开关/列表/分组**的统一间距。

#### 不照搬

- 平台专属视觉（Material 的 FAB、HIG 的 iOS 控件）；
- 完整设计系统组件；
- Web/移动端的手势。

#### 我们的差异

- 我们是 Windows 桌面 + 触屏大屏，密度介于桌面和 Pad 之间；
- 我们的品牌色/图标/字体已经有一套，不换成 Material/Fluent；
- 借“层级/间距/对话框用法”，不借皮肤。

### 2.11 NN/g 开关规范：设置页最容易犯的错

#### 它解决什么问题

设置页大量使用开关，但常见错误：标签不清、用“开/关”作为选项、切换后不立即生效、没有说明。

#### 核心机制（文章要点）

- 开关用于**立即生效**的二元设置；
- 标签要直接描述“开/关什么”，不要只写“启用”；
- 用标准开关视觉，不要自创；
- 切换后立即反馈，不要“保存”；
- 需要确认/多步骤的，不要用开关；
- 开关旁边可以有简短说明/后果。

#### 可照搬的逻辑

- 设置行：标签 + 说明 + 右侧开关；
- 开关切换立即生效（我们已经是）；
- 危险/不可逆操作不用开关，用按钮 + 二次确认；
- 禁用时说明原因。

#### 不照搬

- Web/移动端的具体视觉；
- 文章里的所有案例。

#### 来源

- NN/g Toggle-Switch Guidelines：https://www.nngroup.com/articles/toggle-switch-guidelines/

| 下拉/Combobox 键盘 | **APG Combobox** | Radix Popover | 只支持鼠标 |
| 设置页观感 | **Material 3 / Fluent 2 / HIG** | NN/g Toggle | 自创控件 |
| 设置页开关 | **NN/g Toggle** | WinUI SettingsCard | “开/关”自创 |
| 真窗口自动测 | **FlaUI** | WinAppDriver | 只测离屏 |
| 以后停靠布局 | **Qt ADS / VS Code** | ImGui Docking | 现在做 |

## 四、能直接落地的 8 个模式

### 4.1 Action 注册表（最优先）

```text
UiAction
  Id           稳定字符串（"tool.pen" / "settings.ai" / "page.back"）
  Label        中文标题
  Icon         图标 key
  Shortcut     KeyGesture?（复用 KeyBindings）
  Category     Tool / Page / Settings / Edit / View
  IsEnabled()  可用性（替代散落的置灰判断）
  IsChecked()  选中态（工具/开关）
  Perform()    执行（调 IEngineCommands 或 PageHost）
```

- 工具条、更多、设置行、右键菜单、命令面板、快捷键都查同一张表；
- `MoreHitAt` 不再返回整数，而是 `ActionId`；
- 新增功能只注册 Action，不改命中/绘制/执行三处；
- 参考：Excalidraw ActionManager、JetBrains Action System、VS Code Command、tldraw Actions。

### 4.2 稳定 ID + ID 栈

- 行/层/菜单项用 `"settings.ink.restore"` 而不是 `60 + index`；
- 循环/重复结构用 `PushId("group")` / `PopId()`；
- 自检可以断言“同一个 ID 在插入/删除后仍指向同一行”；
- 参考：Dear ImGui ID Stack。

### 4.3 Active ID / 捕获

- 全局一个 `ActivePointerId` + `CaptureLayerId`；
- `PointerDown` 设定，`PointerMove/Up` 只发给它；
- 新按下/滚轮/Esc 可以取消；
- 参考：Dear ImGui Active ID、Slate mouse capture、Flutter GestureArena。

### 4.4 Popup 栈 + Dismissable Layer

- 打开菜单/下拉/确认框时压栈；
- Esc 只关最上面；
- 点外只关最上面可轻关闭层；
- 页面关闭时清空其 popup；
- 参考：Dear ImGui Popup 栈、Radix Dismissable Layer、Web top layer。

### 4.5 区域化工作区（WindowManager）

```text
Window
├─ TitleBar
├─ ActivityBar（可选）
├─ SideBar（可折叠）
├─ EditorArea（Editor Groups / Tabs）
├─ Panel（底部/右侧，可折叠）
└─ StatusBar
```

- 白板/PDF/笔记/展台都是 Editor；
- 布局持久化；
- 参考：VS Code Workbench、Blender Areas/Regions、JetBrains Tool Windows。

### 4.6 Sheet / Popover / Panel 三分

- Sheet：贴在父窗口上的模态短任务（保存/登录/确认）；
- Popover：锚定触发控件的轻浮层（下拉/菜单/提示）；
- Panel：辅助工具窗（检查器/图层/属性）；
- 参考：AppKit NSWindow/NSPanel/NSPopover/sheets。

### 4.7 键盘/焦点规范

- Dialog：初始焦点、陷阱、Esc、恢复；
- Menu：上下/Home/End/typeahead/Esc；
- Combobox：输入 + 列表 + Enter/Esc + 过滤；
- Toggle：Space 切换，标签可点；
- 参考：WAI-ARIA APG。

### 4.8 设计规范

- 对话框只做短任务/确认；
- 设置用列表/卡片/分组，不用对话框；
- 左栏可折叠成 Navigation Rail；
- 层级用底色/描边，不重阴影；
- 动效 150–200ms；
- 参考：Material 3 / Fluent 2 / HIG / NN/g。

## 六、哪些“不要学”

- **不要学 Dear ImGui 的每帧重建**：我们缓存位图，只在失效时重绘。
- **不要学 Excalidraw/tldraw 的 React 状态管理**：我们不是 React。
- **不要复制 tldraw 的 source-available 代码**：只借 Action/UI 分层模式。
- **不要复制 Blender/Qt/Unreal/Unity 的源码**：许可/平台不兼容，只借模式。
- **不要现在做 VS Code 的 Editor Groups/Blender 的任意拆分**：WindowManager 还没立项。
- **不要照搬 Material/Fluent/HIG 的皮肤**：借层级/间距/用法，不换品牌。
- **不要把 APG 的 ARIA 属性照搬到桌面**：借键盘/焦点行为，不抄 DOM 属性。
- **不要把 FlaUI 当日常自检**：它慢，适合发布前/真窗口专项。

**主文档解决“页面/浮层/输入/焦点/滚动/窗口”的骨架；这份补充解决“动作/命令、工作区、键盘规范、设计观感、真窗口测试”。**

3. **WAI-ARIA APG**（Dialog/Menu/Combobox 键盘）
