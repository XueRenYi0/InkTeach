## 一、结论先说（按优先级）

| 级别 | 结论 | 和用户现象的关系 |
|---|---|---|
| **P0-1** | **整屏上屏兜底（`Present()`）和“只重画了脏区”不配套**。面积 >80% 或矩形 >16 时，`Present()` 会把整张后缓冲交出去，可这一帧只重画了 `_frameDirty`。后缓冲里是**两帧前**的画面，而界面层（工具条/面板）只记了**一帧**旧位置（`_uiBoundsPrev`），所以 **N-2 帧那一块界面没被擦掉**，被当成整屏内容上了屏。下一帧走 `Present1` 时，DXGI 又会把这块“非脏区”从上一缓冲**拷到新缓冲**，残影就一直留着，直到有别的东西再把那块弄脏。 | **最像“偶尔”+“拖完还留一块脏影”**：只有拖动正好碰上“这一帧脏区面积 >80%”时才会出现，出现后会一直留着 |
| **P0-2** | **多屏坐标混用**：`_frameDirty` 里一部分是**屏幕坐标**（界面、HUD、滚动条、整屏矩形），一部分是**窗口坐标**（`CanvasRectToWindow` 的结果），而且画的时候直接拿屏幕坐标当窗口坐标裁剪。主屏原点是 (0,0)，所以看不出来；**副屏（扩展模式投影仪）上原点不是 0，擦不掉旧界面、内容层也贴不上**。 | 只要把工具条拖到副屏（或者在副屏上用），就会**每帧拖一条尾巴**。本机只有一块屏，从来没有实测过 |
| P1-1 | 临时图元被合并成**一个联合包围盒**（`r.Add`），一个在左上角、一个在右下角，就会变成整屏。这正是 P0-1 那个“>80%”的主要来源，也白白多画很多像素 | 让 P0-1 出现得更频繁；同时浪费 GPU |
| P1-2 | `_frameDirty` 画之前**没有合并**（只有上屏矩形合并过），重叠的矩形每块都要把全部浮层重画一遍 | 只影响性能 |
| P2 | 反馈群二维码 `DrawFeedbackQr` 画在脏区循环**外面**、整屏半透明，静止区域会一帧比一帧更暗（疑似）；`WM_DISPLAYCHANGE` 只置脏、不整屏重画两帧；缩放手势中线性插值的块边接缝 | 小概率的“脏块 / 暗块 / 网格线” |

**排除项**：分块缓存在平移、滚动、缩放、换底色时的失效逻辑是完整的（见 3.2）；引擎自己画的浮层（选区操作条、计时卡、PPT 条、图库面板等）都有**三帧**脏区历史，在两条上屏路径下都安全；点击穿透、`WS_EX_NOREDIRECTIONBITMAP`、`UpdateLayeredWindow` 这几项和残影无关（见 2.6）。

## 二、残影成因：逐条候选机制 + 代码证据

### 2.0 先厘清上屏模型（所有判断的前提）

- 交换链：`FlipSequential`、2 个缓冲、`CreateSwapChainForComposition` + DComp 视觉树
  （`Overlay.cs:1107-1121`、`1154-1172`；`BufferCount = 2` 在 `Overlay.cs:764`）。
- 每帧：`UpdateFrameDirty` 算出 `_frameDirty` → 循环里对每块矩形 `PushAxisAlignedClip` + Copy 填底 + 贴分块 + 画所有浮层
  （`Overlay.Frame.cs:84-219`）→ 界面 `DrawUi` 不受脏区裁剪、只受自己的矩形裁剪（`Overlay.Frame.cs:222-223`，`Overlay.Ui.cs:157-183`）。
- 上屏：`Present()`（`Overlay.Capture.cs:620-722`）
  - 正常：`Present1(dirtyRects)`（`:700`）；
  - **兜底**：`FullPresent || rects==0 || rects>16 || 面积>80%` 时走 `Present()` 整屏（`:690-697`）。
- 代码的假设（注释 `Overlay.cs:480-484`、`Overlay.Frame.cs:893/908/920-925`）：**“后缓冲里是两帧前的画面”**，所以每种东西都要把“这一帧 + 上一帧（+ 上上帧）”算进脏区。
- DXGI 官方文档（[Flip model, dirty rectangles, scrolled areas](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/dxgi-1-2-presentation-improvements)）的原话：*“The runtime copies only the differences between updated areas of the previous frame and updated areas of the current frame onto the current back buffer.”*
  也就是：**用 `Present1` 带脏区时，运行时会把“上一帧的脏区减去这一帧的脏区”从上一缓冲拷进当前缓冲**；**用 `Present()` 整屏时，运行时不拷**（整屏都算脏）。

由此有两条推论（后面要用）：

1. 走 `Present1` 时，只要每帧脏区盖住“这一帧变化的像素”，画面就是对的。代码里多算的“上一帧 / 上上帧”只是保险，多花了面积，但不会出错。
2. 走 `Present()` 兜底时，运行时**不帮你拷**。整张后缓冲 = 两帧前的画面 + 这一帧重画的脏区，所以这一帧的脏区必须盖住“**N-1 和 N 两帧的所有变化**”。这是代码“两帧历史”的真正用处，也是唯一会出错的地方。

### 2.1 【P0-1，主嫌】界面层只记一帧旧位置，在整屏兜底帧上会漏掉 N-2

**证据链：**

| 步骤 | 代码 |
|---|---|
| 界面矩形每帧问一次（物理像素，含投影余量） | `Overlay.Ui.cs:96-110`（`_uiBounds`） |
| 只记**上一帧**一份 | `Overlay.Frame.cs:236-237`：`_uiBoundsPrev = uiVisible ? _uiBounds : RectF.Empty;` |
| 进脏区的只有“当前 + 上一帧” | `Overlay.Frame.cs:924-925` |
| 对比：临时图元有**三帧**（当前 + h0 + h1，而 h0/h1 本身又各自含 Prev） | `Overlay.Frame.cs:908-912`、`939-940` |
| 面积 >80% / 矩形 >16 时整屏 `Present()` | `Overlay.Capture.cs:690-697` |

**发生过程（拖工具条，第 N 帧正好触发兜底）：**

```
U(k) = 第 k 帧界面矩形
第 N 帧的后缓冲 = 第 N-2 帧画完的样子（界面在 U(N-2)）
这一帧重画： U(N) ∪ U(N-1) ∪ 其它
没重画、但内容是错的： U(N-2) − (U(N) ∪ U(N-1) ∪ 其它)   ← 拖动时就是“拖尾那一条”
Present() 整屏 → 这一条旧界面上屏
第 N+1 帧走 Present1 → 运行时把“上一帧脏区(=整屏) − 这一帧脏区”拷过来 → 这一条被**复制进另一个缓冲**
→ 两个缓冲里都有这块残影，直到有东西再把这块弄脏（悬停 / 再拖过去 / 滚动整屏两帧）
```

这和用户描述的两种现象完全对得上：“**拖动经过的地方留下旧画面**”（拖动中多次触发）和“**拖完位置还留一块脏影**”（触发一次后一直留着）。也解释了为什么是“偶尔”：必须正好碰上兜底帧。

**同类缺口（同一个根因）：**

- 界面**消失**那一帧（贴边隐藏、收起、换模式）：第 N+1 帧 `_uiBoundsPrev` 已经清空（`:237`），如果这一帧走兜底，N-1 帧的界面会“诈尸”。
- `--fullpresent`（`Overlay.cs:775`）每一帧都走兜底：按这个推理，开着它拖工具条**必然**出拖尾。这正好可以拿来做 1 分钟的验证（见 5.1）。

**为什么兜底会被触发（让它从“理论”变成“偶尔”）：**

- `ComputeTransientBounds` 把所有临时图元**合成一个包围盒**（`Overlay.Frame.cs:333-861`，每处都是 `r.Add(...)`）。例如：屏幕上方有选中框 / 操作条，同时底部有 PPT 页码条（`:533-551`），或者 HUD 开着（`:803-811`），或者激光轨迹比较长（`:378-390`），这个盒子就能占到全屏 80% 以上。
- `MergePresentRects`（`Overlay.Capture.cs:732-757`）会把有重叠的矩形取外接框，面积只会更大。
- 文档补丁 / 页脏区很碎的时候（`Overlay.Content.cs:178-201`），矩形数可能超过 16。

> 补充：如果实测证明 DComp 交换链**不做**运行时拷贝（和代码注释的模型一致），那 `Present1` 帧同样会漏 U(N-2)，拖工具条就会**一直**出拖尾。用户说的是“偶尔”，反过来说明运行时拷贝确实在工作，嫌疑落在兜底帧上。两种模型下修法相同（见 4.1）。

### 2.2 【P0-2】多屏：脏区坐标系混用，副屏上擦不掉旧界面

| 量 | 坐标系 | 证据 |
|---|---|---|
| `CanvasToWindowX/Y`、`CanvasRectToWindow` | **窗口坐标**（减了 `OriginX`） | `Overlay.cs:298-301`、`Overlay.Content.cs:549-553` |
| `ClipToWindow` 夹的范围 | **屏幕坐标** `[OriginX, OriginX+Width]` | `Overlay.Content.cs:554-562` |
| 整屏矩形 `full`、截图 / 吸管整窗、HUD、滚动条 | **屏幕坐标** | `Overlay.Frame.cs:868-872`、`488/495`、`808-809`、`845-847` |
| `_uiBounds` | **屏幕坐标**（逻辑 × k，没减原点） | `Overlay.Ui.cs:102-108` |
| 画的时候的裁剪框 | 直接把 `ClipToWindow` 的结果当**窗口坐标**用（`Transform = Identity`） | `Overlay.Frame.cs:79`、`86-90` |
| 上屏矩形 | 当**屏幕坐标**处理，减 `OriginX` | `Overlay.Capture.cs:625-628` |
| `VisibleCanvasRect` | 把屏幕坐标 `OriginX` 传给“窗口 → 画布”，原点被加了两次 | `Overlay.cs:315-321` 配 `:292` |
| `DrawUi` | 正确地减了原点 | `Overlay.Ui.cs:168-169` |

每块显示器一个覆盖窗口，副屏的原点就是显示器原点（`Engine.Host.cs:1048-1063`）。主屏原点永远是 (0,0)，上面这些差异全部抵消，所以单屏看不出问题。

**副屏（例如 `OriginX = 1920`）上会发生什么：**

- 界面画对了位置（`DrawUi` 减了原点），可擦旧位置用的是 `_uiBoundsPrev`（屏幕坐标），填底用的裁剪框落在窗口外（≥1920），**什么都没擦**；上屏矩形却减了原点、位置是对的，于是“只画不擦” → **工具条拖到哪，尾巴拖到哪**。
- 内容脏区（窗口坐标）被 `ClipToWindow` 按屏幕范围夹掉，基本都变成空；整屏矩形的裁剪框也落在窗口外。按代码推算，**副屏上内容层和浮层几乎画不出来**。这比残影严重，但和多屏未实测的记录一致（`reports/底层-分块与脏区-实测-20261110.md:295`、`调研/清单-软件完善.md:31` 都写着“本机只有一块屏”）。

> 这一条是纯读代码的结论，**必须先在双屏扩展模式下实测**（或者加一个纯数学单测，见 5.3）再动手。不过它和“教室投影仪用扩展模式”这个常见场景直接相关，所以放在 P0。

### 2.3 【已排除】`_frameDirty` 有没有覆盖引擎浮层“消失的区域”

逐项核对了脏区循环里画的东西（`Overlay.Frame.cs:137-216`）和 `ComputeTransientBounds` 里的账：

- 正在写的一笔 / 预测尾 `:351-363`；呼出盘 `:367-376`；激光 `:378-390`；落点反馈 + Prev `:397-416`；多指擦 + Prev `:421-438`；吸附短亮 + Prev `:442-473`；框选 `:475-482`；截图 / 吸管 + 收场帧 `:487-496`；图库面板 + `_libraryRectPrev` `:501-510`；收藏虚影 `:514-528`；PPT 条 / 回放条 / 计时卡 / 点名卡 / 恢复卡 / 悬停提示 / 轻提示，各自都有 Prev `:533-640`；选中框 + 操作条 + 圆钮 + 三种面板 + 菜单 + 字体下拉 + 旋转读数 + 顶点胶囊 + 角标 `:648-764`；画线读数 / 多笔胶囊 + Prev `:773-801`；HUD 三块 `:803-825`；滚动条（单独一块 + Prev，`:839-850`、`914-918`）。
- 这些都并在 `_transientNow` 里，再加上 h0/h1 两帧历史（`:908-912`），**等于三帧覆盖**。所以在两条上屏路径下都没有漏。
- 拖顶点的临时几何走的是 `Doc.Dirty`（`Engine.Selection.Vertex.cs:106-113`），会进 `_contentDirtyNow` 和 `_contentDirtyPrev`，在兜底帧下也是两帧，没问题。
- 选中操作条的“画”和“算脏区”用的是同一个函数（`Engine.cs:1131` 的 `SelectionBarCanvasRect`，绘制在 `Overlay.SelectionBar.cs:47`，脏区在 `Overlay.Frame.cs:669`），不会出现“画在这、擦在那”。

结论：**选区操作条、计时卡这些引擎浮层在主屏上不会因为脏区漏算而留残影**。用户如果在这些东西上看到残影，优先怀疑 2.2（副屏），其次是 2.1 的兜底帧（这些浮层压在界面残影上面，看起来像是它们留下的）。

### 2.4 【已排除】`PrepareUi` / `ComputeTransientBounds` / `UiVisible` 的时序

- 顺序：`UpdateUiInputWindow` 先调 `UiPrepareFrameNow()` 推进动画，再 `QueryBounds`（`Engine.Update.cs:908-917`）→ 每个窗口 `RenderFrame` 开头 `PrepareUi` 再问一次 `QueryBounds`（`Overlay.Frame.cs:54`，`Overlay.Ui.cs:96`）→ 画的时候 `Render`（`Overlay.Ui.cs:180`）。这三步之间不处理消息，读到的是同一个状态。FullUi 自己也把贴边位移做成“每帧一张快照”（`FullUi.cs:267-271`）。
- `DrawUi` 的裁剪框 = 界面矩形 + `PaintMargin`（`Overlay.Ui.cs:173-176`），和脏区里的 `_uiBounds`（`Overlay.Ui.cs:101-108`）是同一个矩形。界面画到外面的部分会被裁掉，不会留在后缓冲里。
- 剩下的风险只有一条，属于约定层面：如果某个界面在 `Render` 里改自己的位置（违反 `Ui.cs:54-64` 的契约），会出现“按新位置画、按旧位置擦”。建议加一个 Debug 断言：`Render` 前后各问一次 `QueryBounds`，两次结果必须相同。

### 2.5 【基本排除】分块缓存（SyncTiles / _tiles / _tilesVersion）漏失效

| 场景 | 处理 | 证据 |
|---|---|---|
| 平移 / 滚动 | 分块不动，相机一变就整屏重画两帧 | `Overlay.Content.cs:257-266` |
| 冻结 PDF 页 + 相机变化 | 整层重烘 | `:261-262` |
| 缩放 | 稳定 120ms 后换倍率，`Reset` 后整层重烘 + 整屏两帧 | `:279-295`，`CanvasTiles.cs:82-93` |
| 换底色 / 文档开关 / 穿透 | `MarkAllDirty` + 整屏两帧 | `Overlay.Content.cs:299-308`、`143-149` |
| 结构变化（删 / 移 / 撤销） | 作废补画清单，按脏区标块 | `:235-241`，`CanvasTiles.cs:307-311` |
| 只增不减 | 补画；不在内存里的块新建时本来就是脏的 | `CanvasTiles.cs:287-300` |
| 淘汰 | 这一帧看得见的块绝不淘汰 | `CanvasTiles.cs:454-471` |

只剩两个小风险（不是拖动残影）：

- **R-T1（防御性）**：只有 `_tilesVersion != doc.Version` 时才处理 `doc.Dirty`（`Overlay.Content.cs:228`）。如果哪天有路径改了文档（有脏区）却没加版本号，分块里就会留着旧墨。建议：版本号没变但 `doc.Dirty.Rects` 不为空时，照样 `MarkDirty`。
- **R-T2（视觉）**：缩放手势中按旧倍率拉伸贴图，用的是 `Linear` 插值（`Overlay.Content.cs:508-514`）。双线性采样在块边上拿不到相邻块的像素，会出现**淡淡的网格线**，停手 120ms 后消失。用户可能会把它说成“有脏影”。

### 2.6 【排除】点击穿透 / NOREDIRECTIONBITMAP / UpdateLayeredWindow

- 覆盖窗口是 `WS_EX_NOREDIRECTIONBITMAP` + DComp（`Overlay.cs:1041-1042`、`1154-1172`）：没有 GDI 重定向表面，也没有 `UpdateLayeredWindow`，DWM 只合成交换链视觉，不会出现“GDI 和 DComp 两份内容错位”这一类残影。
- 穿透只切 `WS_EX_TRANSPARENT|LAYERED`（`Engine.Hotkey.cs:531-539`），只影响命中测试，不影响画面。
- 接输入的小窗口是 1/255 透明度的分层窗口（`Engine.Update.cs:959-973`），肉眼看不到。它比画面晚一帧移动，只会影响“点得到点不到”，不会留下残影。
- 没有 `ResizeBuffers`，窗口尺寸固定。但 `WM_DISPLAYCHANGE` 只做了 `_dirty = true`（`Engine.Host.cs:2182-2184`），**没有请求整屏两帧**：切换分辨率或投影模式之后，可能留下一块旧画面（P2）。

### 2.7 【P2，疑似】二维码遮罩画在脏区外面

`DrawFeedbackQr` 在脏区循环**之后**整屏画 55% 黑（`Overlay.Frame.cs:226-227`、`292-294`），只在显示 / 关闭时请求整屏两帧（`:270`）。二维码开着的时候，只要还在出帧（悬停、光标），非脏区就会每帧再叠一层黑，越来越暗，而脏区那一块是亮的，看起来像一块“亮的残影”。修法：遮罩开着的时候每帧都把整屏加进脏区，或者把遮罩挪进脏区循环里画。

## 三、脏矩形 / 分块的现状数据点

- 2026-11-10 的实测报告（`reports/底层-分块与脏区-实测-20261110.md:227-277`）已经提过：`_frameDirty` 没有去重；相机变化时 trace 里面积到 103~115%，最后走整屏 `Present`。本评审补充一点：**这个“走整屏 Present”正是 2.1 残影的入口**，不只是多算几步的问题。
- 默认配置下，`Present1` 帧里的“两帧历史”是**冗余**的（推论 1）：临时图元、内容脏区、页脏区都是“当前 ∪ 上一帧（∪ 上上帧）”，上屏面积和填底 / 合成的像素数大约是实际需要的 1.5~2 倍。

## 四、改进方案（按“收益 / 风险”排序）

### 4.1 【P0，小改，先做】兜底整屏上屏之前，先真的整屏重画

- **改哪里**：`Overlay.Frame.cs` 的 `UpdateFrameDirty`（`:864-948`）末尾，加一步“预估上屏”：用和 `Overlay.Capture.cs:625-645` 同一套取整、合并，算出矩形数和面积。只要 `FullPresent || 矩形 > 16 || 面积 > 80%`，就把 `_frameDirty` 换成 `[full]`。`Present()` 里的判断保留不动，只当保险。
- **为什么**：保证“整屏上屏的帧 = 整屏重画的帧”，不管运行时拷不拷、哪一层少记了几帧历史，这条路都不会再把旧像素交出去。界面、二维码、以后新加的浮层都一起兜住。
- **同时**：把界面也改成三帧覆盖，加一个 `_uiBoundsPrev2`，或者直接把 `_uiBounds` 并进临时图元历史，这样也能防住“运行时不拷”的那种模型。代价只是多一个矩形。
- **收益**：消除 P0-1。成本：原来 >80% 的帧现在多画 ≤20% 的面积；>16 个矩形的帧很少见。
- **风险**：低。
- **自检**：新写一条 `--uidragghost`（≤10 项，见 5.1），加 `--ghosttest` 和 `--ghosttest scroll` 回归。

### 4.2 【P0，中改，先实测】统一脏区坐标系（多屏）

- **改哪里**：约定 `_frameDirty` **全部用窗口坐标**。
  - `full` → `(0,0,W,H)`（`Overlay.Frame.cs:868-872`、`488`、`495`、`Overlay.Ui.cs:1423-1427`）；
  - HUD / 触点 / 橡皮 HUD / 滚动条矩形减原点（`Overlay.Frame.cs:808-809`、`845-847`，`Overlay.Capture.cs:531-532`、`583-584`）；
  - `_uiBounds` 进脏区之前减原点（`Overlay.Frame.cs:924-925`）；
  - `ClipToWindow` 夹到 `[0,W]×[0,H]`（`Overlay.Content.cs:554-562`）；
  - `Present` 不再减原点（`Overlay.Capture.cs:625-628`）；
  - `VisibleCanvasRect` 用 `WindowToCanvasX(0)` / `(Width)`（`Overlay.cs:315-321`）；
  - 滚动条几何口径也要一起核对（`Overlay.Content.cs:718-745` 注明是“屏幕坐标”）。
- **更彻底的做法**：照 Chromium 把 `gfx::Rect`（物理像素）和 DIP 分成两种类型的思路，引入 `WinRect` / `ScreenRect` 两个只读结构，让 `AddClipped` 只收 `WinRect`，混用就编译不过。代码注释里已经反复提到“类型化坐标”（`Overlay.Frame.cs:105-107`），说明大家都知道这个坑。
- **收益**：副屏可用、副屏拖动无残影。
- **风险**：中。主屏原点是 0，理论上零行为变化，但涉及的地方很多。
- **自检**：先写纯数学单测（5.3），再用双屏实测。

### 4.3 【P1，收益最大的性能项】临时图元从“一个大包围盒”改成“分元素矩形 + 合并启发式”

- **改哪里**：`ComputeTransientBounds` 不再 `r.Add` 进一个盒子，改成往 `List<RectF>` 里加（每个元素一块）。历史从“3 个盒子”改成“3 份列表”。合并规则照 Chromium / Skia 的常见做法：两块矩形的外接框面积 ≤ 两块面积之和 × 1.3（或者间隔小于 32px）就合并，否则保持分开；最多 N 块（比如 8 块），超出就逐对合并，直到数量合格。
- **收益**：两个分散元素同时存在时（选区 + PPT 条、光标 + 计时卡、HUD + 任何东西），每帧填底、贴块、浮层重画、上屏的面积从“接近全屏”降到“几块小矩形”。核显上这就是 GPU 时间的主要来源（`Overlay.Frame.cs:81-83` 的注释已经实测过“全屏 5.2M 像素 → 8~9% GPU”）。同时 4.1 的兜底触发次数也会大幅减少。
- **风险**：中。所有“漏一块就残影”的老账要逐个对：以前靠大包围盒“顺带”盖住的东西，现在要各自算准。好在 2.3 已经核对过每个元素都有自己的矩形。
- **自检**：`--ghosttest`、`--ghosttest scroll`、`--uidragghost`、`--selftest 8`（看 HUD 里的上屏面积）。

### 4.4 【P1，小改】画之前合并 `_frameDirty`

- **改哪里**：`Overlay.Frame.cs:84` 循环前，对 `_frameDirty` 做一次和 `MergePresentRects` 同样的合并（最好用 4.3 的启发式）；如果已经有整屏矩形，就直接只留整屏（11-10 报告 P3 已经提过）。
- **收益**：重叠的 U(N) / U(N-1) / 临时图元不再各自把 25 个浮层画一遍。CPU 记录时间和 GPU 填充都能下降，界面拖动时最明显。
- **风险**：低。
- **自检**：`--selftest 8` 对比 `LastRecordMs`。

### 4.5 【P1，中改】把“上一帧矩形”的手工账收进一个 DamageTracker

- **现状**：`Overlay.cs:489-548` 一共 20 多个 `_xxxRectPrev` 字段，每个都是事后补的（注释里写着 2026-09 到 2026-11 好几轮“收起那一帧没擦”）。
- **参考**：Chromium `cc::DamageTracker`。每个 layer 记上一帧的矩形；这一帧没上报的 layer，它的旧矩形自动算作“被移除 layer 的损伤”。
- **做法**：`Damage.Report(id, rect)`，帧尾 `Damage.EndFrame()`。上一帧报过、这一帧没报的 id，旧矩形自动进脏区，历史深度统一（2 或 3）。界面、浮层、HUD 全部改走它。
- **收益**：“消失那一帧忘了擦”这一类 bug 从结构上消失；新功能接入只要加一行。
- **风险**：中，主要是迁移量大。可以先接新浮层，老代码逐步迁。

### 4.6 【P2，看实测再定】按 DXGI 语义去掉 `Present1` 帧的冗余历史

- 先用 5.2 的探针确认 DComp 交换链确实有运行时拷贝。如果有，就可以：`Present1` 帧的脏区 = 这一帧的变化（每个元素“当前 ∪ 上一帧位置”），去掉 h0/h1 和 `_contentDirtyPrev` / `_pageDirtyPrev`；兜底帧按 4.1 整屏重画；相机变化只要整屏一帧，不必两帧（`Overlay.cs:572-584`）。
- **参考**：Android HWUI / Skia 的 `EGL_EXT_buffer_age` 做法：每个缓冲记“上次是第几帧”，脏区 = 这一帧损伤 ∪ 这个缓冲没见过的那几帧损伤。Chromium viz `BufferQueue` 也是按缓冲记损伤。**照搬“按缓冲年龄算”的思路**，但我们只有 2 个缓冲，DXGI 又会帮着拷，所以实际只需要“年龄 1 = 只算这一帧”的特例。
- **收益**：移动类元素的上屏和重画面积大约减半，滚动停下少一帧整屏。
- **风险**：中高。这一步依赖驱动 / 系统行为，一定要先用探针证明，而且保留 `--nohist` 对照。

### 4.7 【P2，架构级】界面层挪到独立的 DComp 视觉（或 `IDCompositionVirtualSurface`）

- **思路**：工具条、面板、浮窗用 DComp surface 画，拖动 = `SetOffsetX/Y + Commit`，**一个像素都不用重画，也不可能留残影**（每一层由 DWM 合成，旧位置自然露出下面那层）。`IDCompositionSurface::BeginDraw(updateRect)` 本身保证更新区以外的内容保留，不需要应用自己记缓冲历史。
- **参考**：Chromium Windows 上的 DirectComposition overlay（视频、滚动层各自一个视觉）；WinUI / XAML 每个元素一个 Visual。**照搬**“静态 UI 一个视觉、只改偏移”；**不照搬** Chromium 的整套 overlay 候选策略（我们只有 3~5 层，用不着）。
- **收益**：拖面板 0 重绘，残影从机制上消失；墨迹交换链的脏区里不再有界面矩形。
- **风险**：高。DComp 的 Commit 和交换链的 Present 不是原子的，界面和墨迹可能差一帧；`--syswet` 湿墨视觉的层序（`Overlay.cs:1155-1170`）要重新安排；离屏出图的路径要另外处理。建议先只拿“工具条”做原型。

### 4.8 【P2】分块小项

| 编号 | 做法 | 收益 / 风险 |
|---|---|---|
| T-a | 块纹理留 1~2px 边（gutter，Skia / Chromium raster tile 的 border texel）：光栅时多画一圈，合成时采样不越界 | 消除 R-T2 缩放中的网格线；显存多约 1.5%；风险低 |
| T-b | `doc.Dirty` 在版本号没变的时候也处理（R-T1） | 防御；风险低 |
| T-c | `CompositeTiles` 按行列下标直接算相交块，不再遍历全部可见块（`Overlay.Content.cs:516-535`） | 小；风险低 |
| T-d | 平移时试用 `Present1` 的 `pScrollRect / pScrollOffset`：运行时搬旧像素，只重画新露出的一条和固定浮层 | 4K 核显滚动带宽减少；但界面这类固定层要额外加进脏区，风险中，必须先量 |
| T-e | 块内子脏区（11-10 报告 P4） | 维持“先量再定” |

## 六、参考做法：照搬什么、不照搬什么

| 参考 | 照搬 | 不照搬 / 原因 |
|---|---|---|
| **DXGI 1.2 文档**（Flip model + dirty rects） | 运行时拷贝的语义；“整屏 Present 的帧必须整屏有效” | 文档里自己用 `CopySubresourceRegion` 补拷的示例：运行时已经拷了，不需要 |
| **Chromium `cc::DamageTracker`** | 按 layer 记上一帧矩形，“被移除 layer 的旧矩形自动算损伤”（4.5） | 渲染表面树 / 滤镜扩张损伤：我们没有滤镜树 |
| **Chromium viz BufferQueue / Android HWUI `EGL_EXT_buffer_age`** | 按缓冲年龄累积损伤（4.6 的理论依据） | 我们是 2 个缓冲 + DXGI 拷贝，只用年龄 1 的特例 |
| **Chromium DirectComposition overlay / WinUI Visual** | 静态 UI 独立视觉、拖动只改偏移（4.7） | 完整的 overlay 候选与提升策略 |
| **Skia / Chromium raster tiles** | 块边 gutter（T-a）；按分块失效（已经在用） | GPU raster 的多线程调度：11-10 报告的 A/B 显示收益在噪声里 |
| **Windows Terminal AtlasEngine** | “失效被消费后 Present 失败 → 下一帧全量”（已经照搬，`Overlay.Capture.cs:713-720`）；“没有失效就不画” | 它只用单个脏矩形：我们的浮层分散，用单个矩形会退化成全屏（这正是 4.3 要解决的） |
| **Win2D CanvasVirtualControl / `IDCompositionVirtualSurface`** | “更新区以外由系统保留”的语义（4.7） | 不把墨迹层搬过去：低延迟湿墨还是要交换链 + 等待对象 |

## 七、建议的落地顺序

1. **4.1**（兜底先整屏重画 + 界面三帧）+ **5.1** 专项：半天以内，直接针对用户报的问题。
2. **5.3** 单测 + 双屏实测，确认 **4.2** 后再改坐标系。
3. **4.4** 合并 → **4.3** 分元素脏区：性能收益最大，需要带着 `--ghosttest` 系列改。
4. **5.2** 探针有结论之后，再决定 **4.6**；**4.5 / 4.7** 进中期架构计划。
