# 设计：统一界面 / 窗口 / 控件框架（自建薄框架）

日期：2026-11-07　　状态：**设计调研，不改代码**

> **2026-11-07 拍板（用户）：不自建通用框架——工程量太大，除非 AI 再进步，否则不值得。**
> 本文保留为设计参考，不再作为施工单。落地改走"最小路线"：
> - 覆盖层 / 墨迹 / 画布 / 现有更多/设置/收藏继续原生 D2D，不重写；
> - 只抽一个可复用的 `BarControl`（翻页条 + 播放条），不做通用控件库；
> - 真窗口先用 **WinForms + 原生画布子窗**（标准白、工程量最小）；
>   要现代/触摸再考虑 Avalonia（买框架，不自建）；
> - 窗口先用系统标题栏；"按钮内缩/全屏无边框"后置；
> - 笔记（类 OneNote）单独立项，后置。

> 用户目标（2026-11-07 整理）：
> - 自己写一套**可复用的界面框架**，把现有「更多 / 设置 / 收藏 / 图形」和后续
>   「白板窗口 / PDF 批注窗口 / 视频展台 / 笔记（类 OneNote）」统一起来；
> - 统一控件：PPT 翻页、PDF 翻页、白板翻页、播放条这类"很窄的小界面"，
>   移动 / 点击 / 命中 / 焦点都用同一套逻辑；
> - 窗口要像 Windows 真窗口：最大 / 最小 / 关闭、可拖动；按钮**不要贴屏幕最右上角**，
>   往内往下一点（学校大屏老师够不着）；全屏时无边框；
> - 页码点击 = 快速跳页；旁边加「三条杠」打开菜单（左右位置待定）；
> - 文字输入以后想做成"只有光标在闪、背景透明、没有框"；
> - 桌面快捷方式作为各功能入口，但仍是同一个程序；
> - 先研究框架原理，不改代码；评估工程量；评估 Avalonia 开源能不能直接照搬/借鉴。

## 〇、结论先行

1. **思路可行，而且值得做。** 但要把它定位成"**应用薄框架**"，不是"通用 UI 框架"：
   只覆盖我们真实需要的窗口、屏幕、面板、控件和输入；不做 XAML、绑定、设计器、跨平台。
2. **推荐三层模型：Window（真窗口）→ Screen（整页界面）→ Widget（小控件）。**
   `更多 / 设置 / 收藏 / 图形` 是 **Screen**；`白板 / PDF / 展台 / 笔记` 是 **Window**；
   `翻页条 / 播放条 / 按钮 / 列表` 是 **Widget**。Screen 不绑定宿主，
   既能在覆盖层里当模态页，也能以后装进真窗口。
3. **翻页条建议：页码点击 = 快速跳页；三条杠放在最右端、用分隔线隔开。**
   这样"◀ 页码 ▶"仍是一组，三条杠是独立的"更多动作"；条在左下角时，
   右端更靠屏幕中心，老师更好按。若条贴右边，则整体镜像到左端（锚点感知）。
4. **窗口建议：自绘标题栏 + 内缩按钮。**
   标题栏 48 高，最小化 / 最大化 / 关闭按钮 44×44，距上/右各 12～16 逻辑像素；
   非全屏可拖、可缩放、可最大化；全屏无边框，按钮浮在内容右上角、自动淡出；
   底层仍用 Win32 的 `WM_NCCALCSIZE / WM_NCHITTEST / HTMAXBUTTON` 保住贴靠和系统行为。
5. **文字输入独立成 `TextEditService`，不要塞进控件框架。**
   现有原生 RichEdit 给不了真透明（代码注释已写明），先做"无边框 + 板色/近白底"，
   "真透明 + 只有光标"需要自绘文本 + TSF 或分层色键，单独评估，不阻塞框架。
6. **Avalonia 开源不能整包照搬。** MIT 允许复制，但它是 Skia + 属性系统 + XAML + 绑定 +
   完整控件库的通用框架，和我们的 D2D/墨迹/覆盖层架构不匹配；照搬等于 fork 一个框架。
   **正确做法：借它的架构模式（Measure/Arrange、InputElement、FocusManager、
   ControlTheme、虚拟化、WindowDrawnDecorations），不搬它的运行时。**
7. **工程量：中等偏大。**
   框架核心 + 现有四个界面迁移 + 翻页/播放条 ≈ **4～6 个月**；
   再加白板 / PDF / 展台真窗口 ≈ **7～10 个月**；
   笔记 MVP 再 **6～10 周**（全套笔记功能 9～14 个月，1 人粗估）。
   建议分阶段，先做"框架核心 + 设置/收藏试点 + PageBar"，约 **3～4 个月**看到第一版。

## 一、术语与分层（先把"界面 / 窗口 / 控件"分开）

| 名词 | 是什么 | 例子 | 归谁管 |
|---|---|---|---|
| **Window** | 真正的顶层窗口（HWND） | 白板窗、PDF 窗、展台窗、笔记窗、设置窗 | `WindowHost` / `WindowFrame` |
| **Screen** | 一整页内容（可滚动、可导航） | 更多、设置、收藏、图形、笔记页、PDF 页 | `ScreenHost` / `Screen` |
| **Panel** | 页面里的分区 | 设置左栏、收藏分类栏、笔记页列表 | `Panel` 容器 |
| **Widget** | 小控件 | 按钮、开关、滑条、翻页条、播放条、标签页、列表项 | `Widget` |
| **Popup** | 临时浮层 | 菜单、快速跳页、下拉、提示、确认框 | `PopupLayer` |
| **Surface** | 绘制目标 | 覆盖层 / 普通窗口 / 子区域 | `UiSurface` |
| **Overlay** | 现有批注覆盖层 | 透明、置顶、不激活、穿透 | 现有 `OverlayWindow`（特殊） |

### 1.1 关系图

```
WindowHost（顶层窗口 / 覆盖层）
  ├─ WindowFrame（标题栏、边框、窗口按钮、拖动/缩放）
  ├─ ScreenHost
  │    └─ Screen（更多 / 设置 / 收藏 / 图形 / 白板 / PDF / 笔记）
  │         └─ Layout
  │              ├─ Panel
  │              │    └─ Widget（按钮 / 列表 / 翻页条 / 播放条 …）
  │              └─ Widget
  └─ PopupLayer（菜单 / 快速跳页 / 下拉 / 提示）
```

**关键：Screen 不认识宿主。**
同一份 `SettingsScreen` 今天可以放在覆盖层里当模态页，明天可以装进一个真窗口；
`More/Favorites/Shapes` 也一样。这样"界面"和"窗口"不会各写一套。

## 三、统一控件模型（框架核心）

### 3.1 一个节点只回答四个问题

```text
UiNode
  Measure(available) -> desiredSize
  Arrange(finalRect)
  Render(ctx)
  HitTest(point) -> HitResult
```

`HitResult` 只包含：

```text
HitResult
  Node        命中的节点
  LocalPoint  节点内坐标
  Cursor      光标形状
  Capture     是否需要捕获（拖动/滑条）
  Consume     是否吃掉这一次输入
```

**硬规矩：绘制和命中必须读同一份几何。**
现有 `PptBar` 的注释写得很对："绘制和命中读同一个，各算一遍迟早差几个像素"。
框架里每个 Widget 只存一份 `Bounds`，绘制/命中/提示/自检都从它来。

### 3.2 布局只用四种容器

| 容器 | 用途 |
|---|---|
| `Stack` | 横/竖排列（按钮组、表单项） |
| `Dock` | 上/下/左/右贴边（标题栏、底栏、侧栏） |
| `Grid` | 行列（设置行、卡片网格） |
| `Scroll` | 裁剪 + 滚动（长页面、列表） |

- `Measure/Arrange` 只在失效时重算；`Render` 不改布局；
- 文字用 `TextLayout` 量一次、缓存；
- 列表一律虚拟化（只建可见项）。

### 3.3 一条输入管线

```
指针/笔/触摸
  → WindowHost 收消息
  → HitTest（从顶层到子节点）
  → 捕获（按下即捕获，抬起释放）
  → Gesture（tap / double / long / drag / flick）
  → Widget 回调
  → 命令（IEngineCommands / 本地状态）
```

必须统一的判定：

| 手势 | 规则 |
|---|---|
| 单击 | 按下/抬起在同一节点，移动 < 阈值 |
| 双击 | 两次单击间隔 < 系统双击时间 |
| 长按 | 按住 > 500ms 且移动 < 阈值；触摸/笔优先 |
| 拖动 | 移动 > 4～8px；进入拖动后不再触发单击 |
| 滑条/滚动 | 捕获后只走拖动，不触发父级点击 |
| 取消 | Esc / 指针离开 / 捕获丢失 → 回滚视觉状态 |

**所有控件共用同一套阈值**（`DragThreshold`、`LongPressMs`、`DoubleClickMs`），
不许每个控件自己写一套。

### 3.4 焦点 / 键盘 / IME

- `FocusManager`：一个焦点、Tab 顺序、FocusScope（弹窗内焦点陷阱）；
- 键盘：Esc / Enter / Space / 方向键 / Tab / Shift+Tab 统一；
- 文字：所有输入走 `TextEditService`，Widget 只给"矩形 + 初始值 + 校验 + 提交/取消"；
- 弹窗：打开时记住原焦点，关闭时还原。

### 3.5 弹层

`PopupLayer` 统一：

- 锚点（上/下/左/右自动翻转）；
- 层序（在窗口内最高；覆盖层上的原生画布另开小窗）；
- 关闭规则（Esc / 点外 / 选择项 / 滚动）；
- 焦点陷阱（菜单/对话框）；
- 裁剪（不超出窗口/屏幕）。

### 3.6 主题 / 动画 / 持久化

- 颜色/圆角/字号/间距只用 `Tokens` 一份；
- 动画统一时钟、缓动、系统"减少动画"降级；
- 窗口位置/大小、面板位置/尺寸、滚动位置、分类选择都有 `PlacementStore`；
- 每个界面必须有 0 / 1 / 多 / 溢出四态（项目硬规则）。

### 3.7 自检

- 每个 Widget：命中/状态/键盘/触摸的微型用例；
- 每个 Screen：0/1/多/溢出 + 截图；
- 每个 Window：最小化/最大化/还原/贴靠/DPI/位置记忆；
- **无窗口后台自检**优先（像 `--settingsaudit`），不抢用户前台；
- 需要真窗口时用隐藏窗口 + 离屏渲染，不弹到用户面前。

## 五、PageBar：翻页条 + 快速跳页 + 三条杠

### 5.1 现状与问题

现在 `PptBar` 是 `[◀] [页码] [▶]`，点页码弹菜单（第一项才是跳页）。
问题：

- 点页码的语义不直观：用户以为只是跳页，结果弹菜单；
- 菜单没有独立入口，老师不知道还有"自动保存/回放/清空/关闭"；
- 页码格同时承担"显示 + 菜单"，点击区域大但语义混。

### 5.2 新布局（推荐）

```text
[◀] [ 3 / 12 ] [▶] │ [☰]
```

- `◀ / ▶`：上一页 / 下一页；
- 页码格：**单击 = 快速跳页**（弹出页号网格）；
- 分隔线：8px 间距 + 1px 线；
- `☰`：**菜单**（跳转、自动保存、回放、清空、关闭/适应宽度等，按来源变）。

**三条杠放右边**的理由：

1. `◀ 页码 ▶` 保持一组，不被菜单劈开；
2. 条默认在屏幕左下角，右端更靠屏幕中心，触摸更好按；
3. 菜单/更多动作在右端是桌面惯例；
4. 如果条贴右边，整体镜像：`[☰] │ [◀] [页码] [▶]`，由锚点感知决定，不写死。

### 5.3 尺寸与命中

| 项 | 值 |
|---|---|
| 条高 | 48 逻辑像素 |
| 箭头 | 40×48 |
| 页码格 | 78×48（黄金矩形，视觉主体） |
| 三条杠 | 40×48 |
| 分隔 | 8 + 1px + 8 |
| 总宽 | 约 40+78+40 + 17 + 40 ≈ 215 |
| 触摸目标 | ≥40；条整体可拖 |
| 拖动阈值 | 8px（手指会抖，比界面 4px 松一点） |
| 默认位置 | 屏幕左下角，离边 16 |
| 记忆 | `pptBarX/Y`（现有），统一成 `pageBarX/Y` |

### 5.4 快速跳页（点页码）

```text
        ┌ 跳转到页 ─────────────┐
        │ 1  2  3  4  5  6 ... │
        │ 11 12 13 ...         │
        └──────────────────────┘
              ▲
        [◀] [3/12] [▶] │ [☰]
```

- 页号网格：10 列、44×44、6px 间距；当前页高亮；
- 页数多时面板内部滚动；
- 面板从条上方长出来；上方放不下就翻到下方；
- 点页号 → 跳转 → 关闭面板；Esc / 点外关闭；
- 键盘：输入数字 + Enter 也可跳。

### 5.5 三条杠菜单

```text
        ┌──────────────────────┐
        │ 跳转到页…            │
        │ 自动保存      开     │
        │ 回放本页             │
        │ 清空本页             │
        │ 关闭                 │
        └──────────────────────┘
              ▲
        [◀] [3/12] [▶] │ [☰]
```

- 菜单宽度 = 条宽（从条上长出来，像一套）；
- 菜单项按来源适配：
  - PPT：跳转 / 自动保存 / 回放 / 清空 / 结束放映；
  - PDF：跳转 / 自动保存 / 回放 / 清空 / 适应宽度 / 旋转 / 关闭；
  - 白板：跳转 / 新建页 / 删除页 / 清空 / 关闭（如果做分页）；
  - 笔记：跳转 / 新建页 / 删除页 / 导出 / 关闭。
- 菜单项 40 高；危险项（清空/删除）二次确认，不贴常用项。

### 5.6 统一模型：PageBar 不认识 PPT/PDF

```text
PageBarModel
  SourceKind      Ppt / Pdf / Board / Notes
  Index           当前页（1 起）
  Count           总页数
  CanPrev/CanNext
  MenuItems       由 Source 提供
  OnGoto(i)
  OnMenu(id)
```

宿主只实现 `IPageSource`：

```text
IPageSource
  int Count
  int Index
  bool CanPrev / CanNext
  void Prev() / Next() / Goto(int)
  IReadOnlyList<PageBarMenuItem> MenuItems
```

这样 PPT/PDF/白板/笔记共用同一套翻页条，不再各写一份几何/命中/菜单。

### 5.7 播放条 / TransportBar

播放条不是翻页条，但共用 `BarShell`：

```text
[▶/⏸] [━━━━●━━━━] 01:23 / 05:00  [1.0×] │ [☰]
```

- 用于墨迹回放、视频展台、录音/录课；
- 控件：播放/暂停、进度、时间、速度、菜单/关闭；
- 与 PageBar 共用：圆角条、拖动、夹取、置顶、触摸目标、PopupLayer、主题。

## 六、Window：真窗口 + 内缩按钮 + 全屏无边框

### 6.1 窗口类型

| 类型 | 例子 | 标题栏 | 任务栏 | 置顶 | 最小化/最大化 |
|---|---|---|---|---|---|
| Document | 白板 / PDF / 笔记 | **自绘** | 有 | 可选 | 有 |
| Dialog | 设置 / 确认 / API | 自绘或系统 | 无 | 跟随 owner | 无（或仅关闭） |
| Palette | 收藏 / 图形 | 无边框 | 无 | 常驻 | 无 |
| Preview | 视频展台 | 无边框 | 无 | 常驻 | 无 |
| Overlay | 批注层 | 无 | 无 | 常驻 | 无 |

### 6.2 标题栏与按钮（用户要求：往内往下）

```text
┌──────────────────────────────────────────────┐
│  白板 1                                  ─ □ ✕│  ← 按钮距上/右各 12～16
│                                              │
│  ┌────────────────────────────────────────┐  │
│  │                                        │  │
│  │              画布 / 页面                │  │
│  │                                        │  │
│  └────────────────────────────────────────┘  │
│        [◀] [3/12] [▶] │ [☰]                  │
└──────────────────────────────────────────────┘
```

- 标题栏高 48；按钮 44×44；图标 18～20；
- 按钮组**不贴屏幕最右上角**：距窗口上/右各 12～16 逻辑像素，
  学校大屏上老师不用踮脚够；
- 按钮顺序：最小化 / 最大化（还原）/ 关闭；关闭用红色悬停；
- 标题栏空白区可拖动；双击最大化/还原；
- 全屏：隐藏标题栏，画布铺满；按钮浮在右上角内缩位置，
  2 秒后淡出，碰屏幕顶边/右上角再出现；Esc 退出全屏；
- 全屏时无边框；非全屏可拖、可缩放、可最大化；
- 贴靠/系统菜单/动画：自绘标题栏仍要处理 `WM_NCCALCSIZE`、
  `WM_NCHITTEST`（`HTMAXBUTTON`）、`WM_GETMINMAXINFO`，否则 Win11 贴靠不弹。

### 6.3 窗口状态机

```text
Normal ──最大化──> Maximized ──还原──> Normal
  │                    │
  └──全屏──────────────┴──> Fullscreen ──Esc──> 之前状态
  │
  └──最小化──> Minimized ──任务栏──> 之前状态
```

- 记住每个窗口的 `Normal` 位置/大小/显示器；
- 最大化/全屏不改 `Normal` 记忆；
- 关显示器/改分辨率后，窗口必须回到可见工作区；
- 关闭：保存/确认；最小化：进任务栏；
- 多窗口：每个 Document 独立；Dialog 跟随 owner；Palette/Preview 置顶。

### 6.4 拖动与缩放

- 标题栏拖动：移动超过阈值才进入拖动，避免点按钮时误拖；
- 触摸/笔拖动同样有效；
- 边缘缩放：8～12px 命中区（按 DPI），鼠标可窄、触摸加宽；
- 夹进工作区，不允许拖出屏幕后找不回来；
- 多屏：跨屏拖动按目标屏 DPI 重排；
- 全屏下不拖动；用 Esc / 手势退出。

### 6.5 文档模型（窗口框架绕不开）

- 一个窗口 = 一个 `DocumentView`；当前 `InkEngine.Doc` 是单例；
- 第一版：**同时只开一个文档**（白板或 PDF），切文档 = 换当前 Doc；
- 要"白板 + PDF 并排"必须先拆 `InkDocument` 与 `View/Input`，
  不要用多个 `InkEngine` 实例硬凑（设备/缓存/定时器翻倍，4 GB 先炸）；
- 笔记是另一套文档模型（见第十节），不要硬塞进白板页。

## 七、Screen：现有四个大界面怎么统一

### 7.1 ScreenHost

```text
ScreenHost
  ├─ Header（返回 / 标题 / 关闭）
  ├─ Content（当前 Screen）
  ├─ ScreenStack（push / pop）
  └─ PopupLayer
```

- 覆盖层里的「更多 / 设置 / 收藏 / 图形」都是 Screen；
- 一次只显示一个模态 Screen；返回/关闭回上一个；
- 打开时记住来源，关闭时还原焦点；
- Screen 自己管滚动位置/分类/页签，`ScreenHost` 不管业务；
- 以后要装进真窗口，只换宿主，不重写 Screen。

### 7.2 四个界面的统一结构

```text
┌──────────────────────────────────────────────┐
│ ←  设置                                   ✕  │
├──────────┬───────────────────────────────────┤
│ 工具栏   │  工具栏                            │
│ 常规     │  [极简] [自定义] [完整]            │
│ 书写     │  ...                              │
│ 墨迹     │  常规                              │
│ AI 服务  │  深色主题            [开关]        │
│ 备份     │  ...                              │
│ 关于     │                                   │
└──────────┴───────────────────────────────────┘
```

- 左栏固定，右栏连续滚动；
- 左栏当前项高亮；滚到哪段高亮哪段；
- 0/1/多/溢出：分类多时左栏滚动；内容多时右栏滚动；
- 收藏/图形：顶部页签 `图形 | 我的收藏`，下面虚拟网格；
- 更多：启动器网格，0/1/多/溢出，底栏固定动作。

### 7.3 Screen 的四种状态（项目硬规则）

每个 Screen 必须写清：

- **0 个**：空态文案 + 下一步；
- **1 个**：不拉伸、不居中到奇怪位置；
- **很多**：滚动/分页 + 总数；
- **溢出**：分类/动作收进「更多 ▾」，当前项始终可见。

## 八、文字输入（独立服务，不进控件框架）

### 8.1 现状事实

- 画布文本框用原生 `RICHEDIT50W` + 独立宿主窗；
- 编辑底色：白板 = 当前板色；文档/图片 = 很淡的近白；
- **原生 RichEdit 给不了真透明**（`TextBoxEditing.cs` 注释已写明）；
- 有边框/底色是为了在 PPT/图片上能看清。

### 8.2 目标形态

```text
点击画布 → 只有一竖光标在闪（没有框/没有底色） → 直接打字
```

- 编辑时不出现边框、不出现背景块；
- 光标/选区/IME 候选窗正常；
- 失焦/Enter/Esc 提交/取消；
- 富文本（颜色段/字体/行距）仍要支持。

### 8.3 技术路线（分阶段）

| 阶段 | 做法 | 透明 | 成本 |
|---|---|---|---|
| A（先做） | 无边框 RichEdit；背景 = 板色/近白；去掉边框 | 否（但白板上看不见） | 1～2 天 |
| B | 分层宿主 + `LWA_COLORKEY` 色键 | 近似透明，抗锯齿边缘可能带色边 | 3～5 天，需实测 |
| C | 自绘 DirectWrite 文本 + TSF/IME + 光标/选区 | 真透明 | 2～4 周，风险高 |
| D | 保持原生 RichEdit，PDF/图片上用半透明浅底 | 半透明 | 1 周 |

**建议：先 A（无边框 + 板色），再 D（文档页半透明浅底），C 等框架稳定后再评估。**
不要为了"真透明"把文本编辑/IME 重写一遍——这是最容易出 bug 的地方。

### 8.4 `TextEditService`

```text
TextEditService
  Begin(rect, initial, mode, options, onCommit, onCancel)
  UpdateRect(rect)        跟随滚动/缩放
  Commit() / Cancel()
  IsEditing
```

模式：单行 / 多行 / 富文本 / 光标直入。
所有界面（设置、重命名、页码、笔记、画布文本框）都走这个服务，不再各写宿主。

### 9.1 一个 exe，多个入口

| 快捷方式 | 参数 | 打开 | 关闭 |
|---|---|---|---|
| InkTeach 批注 | 无 | 覆盖层 + 工具条 | 回托盘/退出 |

  Key           board / pdf / visualizer / notes / settings / favorites

所有入口共用同一套 `WindowHost` / `ScreenHost`，不写七套启动逻辑。

## 十、笔记（类 OneNote）：单独一个文档模型

### 10.1 定位

- 白板 = **无限画布 + 墨迹优先**；
- 笔记 = **分页 + 文本优先 + 墨迹批注**；
- 两者不要共用"页"的实现，否则会互相拖累。

### 10.2 最小模型

```text
Notebook（笔记本）
  └─ Section（分区）
       └─ Page（页）
            ├─ TextBlocks（富文本块）
            ├─ InkLayer（墨迹批注）
            └─ Images（图片）
```

- 页列表在左侧/顶部；当前页编辑区；
- 文本块用 `TextEditService`（富文本）；
- 墨迹层复用画布笔迹，但坐标绑在页内；
- 保存：页 = 文本块 + 墨迹 + 图片；先本地，不做同步；
- 搜索：先标题/纯文本，后全文索引；
- 导出：PDF/图片/HTML 后做。

### 10.3 工程量

- MVP（页/分区/文本块/墨迹/保存/页列表）：**6～10 周**；
- 全文搜索/模板/导出/表格：再加 4～8 周；
- 不建议第一版就做 OneNote 全功能；先做"能记、能翻、能存"。

## 十一、Avalonia 开源：能借什么、不能借什么

### 11.1 法律上

- Avalonia 核心是 **MIT**：可以复制、修改、商用，但必须保留版权声明；
- 部分 Pro 组件（RichTextEditor/PDF/TreeDataGrid/VirtualKeyboard 等）是订阅制，
  不能当开源直接搬；
- 我们只考虑 MIT 核心的**架构/模式**，不复制 Pro 组件。

### 11.2 为什么不能整包照搬

- Avalonia 是 **Skia + 属性系统 + XAML + 绑定 + 完整控件库 + 平台窗口层** 的通用框架；
- 我们的核心是 **Win32 覆盖层 + D2D + 湿墨 + 分块 + 原生输入**；
  两套渲染/输入/窗口模型接在一起，等于同时维护两个框架；
- 代码量巨大，依赖 Skia/HarfBuzz/Angle 等；直接 fork 会被上游版本拖着走；
- 照搬它的控件，仍然要自己写：窗口 chrome、翻页条、播放条、白板/PDF/笔记业务。

### 11.3 值得借的模式

| Avalonia 的模式 | 我们怎么用 |
|---|---|
| `Layoutable.Measure/Arrange` + 失效重算 | 自己的 `UiNode` 布局 |
| `InputElement` 路由事件 / Pointer 捕获 | 统一输入管线 |
| `FocusManager` / FocusScope | 焦点/键盘/弹窗 |
| `ControlTheme` / 伪类 | 自己的 Tokens/状态样式 |
| `ItemsControl` 虚拟化 | 收藏/图形/笔记页列表 |
| `WindowDrawnDecorations` / `TopLevel` | 自绘标题栏/窗口状态 |
| `TextBox` IME 桥 | 只参考，不搬；文字仍用原生 RichEdit |

### 11.4 可以直接用 Avalonia 吗？

- 可以，但只建议用于**非画布的窗口/表单**；
- 画布/覆盖层仍原生 D2D；
- 代价：+100～200 MB、第二渲染器、`NativeControlHost` 空域、触屏键盘要手动调；
- 如果选择这条，翻页条/窗口 chrome/笔记仍然要自己写，Avalonia 只省"通用控件/布局"。

**结论：借架构，不搬框架；先用薄框架，Avalonia 留作备选。**

## 十五、对用户几个具体问题的直接回答

**1. 思路可不可行？**
可行。你的需求本质是"一套应用框架 + 一套控件 + 一套窗口壳"，不是通用 UI 框架；
范围可控，先做核心再铺界面。

**2. 自己写框架性价比高吗？**
如果后面确实有 10+ 个界面/窗口、且要统一翻页/播放/窗口/触摸行为，**值得**；
如果只做几个设置框，Avalonia/WinForms 更快。你的路线（白板/PDF/展台/笔记）
界面数量足够多，自建薄框架的复用价值能回本。

**3. Avalonia 开源直接照搬不是更好吗？**
法律上可以（MIT，保留声明），但架构不匹配：它整套是 Skia + XAML + 绑定 + 控件库，
和我们的 D2D/墨迹/覆盖层接起来等于维护两个框架。**借它的设计模式，别搬运行时。**

**4. 工程量大不大？**
中等偏大：框架 + 现有界面 + 翻页条 ≈ **4～6 个月**；再加白板/PDF/展台 ≈ **7～10 个月**；
笔记 MVP 再 6～10 周（全套 9～14 个月）。建议先做 P1（约 3～4 个月）看效果。

**5. 页码和三条杠怎么放？**
页码点击 = 快速跳页；三条杠放**右端**，用分隔线隔开；
条贴右边时镜像到左端。理由：不劈开 `◀ 页码 ▶`，右端更靠屏幕中心、好按，
菜单在右端也符合习惯。

**6. 窗口按钮内缩可以吗？**
可以。标题栏 48，按钮 44×44，距上/右 12～16；全屏无边框、按钮浮层自动淡出；
非全屏可拖/缩放/最大化；底层保留 Win32 贴靠/系统行为。

**7. 文字输入只有光标、背景透明？**
方向可行，但原生 RichEdit 给不了真透明（现有代码注释已说明）。
先做"无边框 + 板色/近白底"，文档页用半透明浅底；真透明要自绘文本 + TSF，
单独评估，不放进第一版框架。
