### 从 WintabDN 学到的（**直接省掉我们踩坑**）

1. **必须 `lcOptions |= CXO_MESSAGES`**
   （我们自己探针第一版就是漏了这个 → "上下文开得起来却收不到包"。
   标准姿势：`lc.lcOptions |= CXO_MESSAGES; lc.lcPktData = ...; lc.lcMoveMask = lc.lcBtnDnMask = lc.lcBtnUpMask = lc.lcPktData;`）

2. **⚠ 内存泄漏坑（aledelgo 的 PERFORMANCE FIX）**
   原文：*"without this line, the memory consume of .NET apps increase exponentially
   when the PEN is used for long time (or worse when the pen is leaved alone on the
   tablet screen) causing the app to crash now or later"*
   → 每次 `WTPacket` / `WTPacketsGet` 用完的**非托管缓冲必须释放**。
   我们目前是"开一次缓冲、`finally` 释放"，没有这个风险，但要保持。

3. **`WTInfo()` 查静态信息是标准做法**
   Wacom 官方原话：*"Use WTInfo() to get static information about the tablet, such as
   tablet dimensions, coordinate resolution, **the presence of tilt, pressure range**"*
   → 我探针里"枚举设备属性问压力范围"就是对的做法 ✓

4. **压力的语义**（Wacom 官方）：
   *"the minimum value of the range indicates the resting, unpressed state, and the
   maximum value indicates the fully pressed state"*
   → 所以 **悬停时压力必须 = 0**，这就是我认出偏移 36 的判据 ✓

## 二、🔴 重大线索：「偶尔缺墨」很可能就是 **PHRC**

**Wacom 官方文档原话**（developer-support.wacom.com）：

> Operations in graphics applications that require very small dots of ink, so called
> "stippling," may not work correctly because of **user system settings for
> Press-And-Hold-To-Right-Click (PHRC)** causing the system to misinterpret stippling
> operations as trying to activate PHRC. One solution is to disable PHRC.
> **Another good solution is to use Wintab as an ink source in your app, as it does not
> use system ink.**

**用户症状对照**（Microsoft Q&A 里有人描述得一模一样）：

> "If I want to draw any line, **I have to drag it out of the circle, about 4mm, before
> it creates a line**."

→ 即：**笔停住不动约 1 秒 → Windows 开始判"长按右键手势" → 接下来约 4mm 的移动被吞掉**
→ 表现就是「**偶尔缺一小段墨**」。

**这条能同时解释**：为什么是"偶尔"（要停住才触发）、为什么很快就消失（手势判完就恢复）、
为什么自检复现不出来（合成输入不带 PHRC）。

**验证方法（30 秒）**：
> 在 InkTeach 上画一条线，**画到一半故意停住约 1 秒**（笔尖别抬），然后再继续画。
> 如果停住之后紧跟着**缺一小段（约 4mm）**→ **PHRC 确认**。

**两个解法**：
- **A. 用 Wintab 当输入源** ← Wacom 官方推荐的解法，且我们**已经实测这条路通了**
- **B. 让用户关掉 PHRC**（控制面板 → 笔和触控 → 笔选项 → 按住 → 取消勾选"启用按住右键单击"）
  ⚠ 但 Win11 上很多机器关不掉/会被重置（论坛里一堆人关不掉），**不能只靠这个**

## 五、我们属于什么水平（对照业界，2026-10-07 查）

### 业界的数（端到端，玻璃到玻璃）

| 设备 | 端到端延时 |
|---|---|
| Apple Pencil + iPad Pro 120Hz | **20 ms**（2017 首发时）；2026 年实测 **22.3 ms**（中位） |
| Surface Pen + Surface Pro | **21 ms** |
| 安卓系触控笔 | 41 ~ 69 ms |
| Mac Sidecar（iPad 当副屏） | 43.8 ms |

**行业经验线：30 ms 以内算"优秀、几乎察觉不到"**（15ms vs 25ms 的差别普通人分不出）。
**而 60Hz 屏幕一帧就是 16.7 ms** —— 这是物理地板。

### 我们的数（本机 `--latbench`，**软件那一段**）

| 场景 | 笔尖动→收到消息（中位） | 合计 记录→上屏（中位） | P95 | 掉帧 |
|---|---|---|---|---|
| 空板·慢写 140Hz | 0.09 ms | **1.10 ms** | 2.42 | 0/146 |
| 空板·快写 200Hz | 0.09 ms | **0.99 ms** | 2.59 | 0/121 |
| 密集页 3000 笔 | 0.09 ms | **1.35 ms** | 2.64 | 0/145 |

### 怎么读这两个数

- **30 ms 的"优秀线"里，60Hz 屏幕刷新就吃掉 16.7 ms**，剩约 13 ms 给"输入栈 + 软件"
- **我们占 1.0~1.4 ms ≈ 那 13 ms 的 10%**，占整条 30 ms 预算的 **3~5%**
- **画布上多少墨几乎不影响**：空板 1.10 ms → 3000 笔密集页 1.35 ms
- **掉帧 0**（三个场景全 0）

**⚠ 诚实的边界**：端到端（玻璃到玻璃）**我们量不了** ——
那需要高速摄像机 + 机械臂（评测机构就是这么做的）。
我们能负责的是"**软件这段不拖后腿**"，而这个数摆在这儿。

**→ 结论：我们软件这一段不是瓶颈，而且离瓶颈很远。**
"跟不跟手"主要取决于板子 / 驱动 / 屏幕刷新率。用户真机反馈"试着挺好的"和这个数是一致的。

## 六、驱动里那个 "Ink" 开关，对我们有影响吗？

**没有负面影响 —— 两条路我们都覆盖。** 那个开关是"**笔按哪条路上报**"的总闸：

| 驱动里的 Ink 开关 | 笔怎么上报 | 我们走哪条路 | 压感 |
|---|---|---|---|
| **开** | Windows Ink 笔消息（`PT_PEN`） | 指针路径（原有那条） | ✅ 有，1024 级 |
| **关** | 鼠标消息（`PT_MOUSE`） | 鼠标路径 + **Wintab 补压力** | ✅ 有，**16383 级** |

而且**不会重复**：Wintab 只在"这条输入不是 `PT_PEN`"时才接手。

⚠ **要分清两个不同的开关**（很多人混）：
- **系统设置里的「笔和 Windows Ink」**：管笔快捷键、手写、忽略触摸 —— **不改变笔的上报方式**
- **驱动面板里的 "Windows Ink" 勾选框**：**这个才决定"按 Windows Ink 报还是按鼠标报"**

## 七、换一块没有 Wintab 的板子会怎样？

**全自动，不会更糟**：

1. 没装厂商驱动 → `WTOpen` 打不开 → 启动时打一行
   「`[wintab] 未启用：…（关 ink 时就没有压力，行为与以前一致）`」→ **安静退回老路**
2. **Windows Ink 那条路（`PT_PEN`）完全不依赖 Wintab** ✓ 所以"开 ink 有压感"照样成立
3. 有 Wintab 就白赚（关 ink 也有压感）；没有就退回原来的样子

⚠ **唯一要注意的**：Wintab 是**单一提供者** ——
装了两家的驱动时，**后装的会把 Wintab 提供者顶掉**，可能"上下文开得起来却收不到包"。
判据：日志里 `包0`。处理：卸掉不用的那家驱动。

## 八、我们的实测数据（本机高漫表）

```
驱动          : GaomonTablet 16.0.0.218，System32\wintab32.dll 16.0.0.11
上下文        : lcOptions 默认 0x0003（**没有 CXO_MESSAGES**，必须自己补）
                lcPktData 默认 0x15F7（含 X Y 正压力 倾斜 按键 笔类型 时间戳 状态 上下文 序列号）
包率          : 168 Hz（lcPktRate 声明上限 400）
轴量程        : X 0~50800、Y 0~31750、Z 0~1024、**正压力 0~16383**、切向压力 0~16383、倾斜 0~3600
压力实测      : **0 ~ 16383**（1156 个包，用力敲 14 下）

⚠ 包体布局与规范**不一致**（这是本条最重要的发现）：
   规范顺序：context(0) status(4) time(8) ... X(24) Y(28) normalPressure(32)
   **实测  ：context(0) status(4) ???(8)  time(12) ... X(28) Y(32) normalPressure(36)**
   驱动在 offset 8 多占了一个字 → 从它往后**所有字段整体挪 4 字节**。
   （所以我按规范算的偏移把 Y 当成了压力，报出"压力 593~1162"这种错结论。）
```

**→ 结论：任何偏移都必须用真机数据实测钉一遍，规范 ≠ 驱动的实现。**
