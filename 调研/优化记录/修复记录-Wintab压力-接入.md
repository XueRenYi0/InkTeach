# 修复记录：接入 Wintab（第一阶段：只借压力）

**时间**：2026-10-07　　**分支**：`opt/d2d-memory`　　**开关**：默认开，`--nowintab` 关

---

## 一、做了什么

关掉 Windows Ink 之后，笔会被系统当成**鼠标**上报（`PT_MOUSE`），
而鼠标这条路上**永远没有压力**（非笔设备没有 `penMask`）——
所以关 ink 时所有笔迹都是等宽的，和开 ink 的手感是两样东西。

Wintab 是**驱动自己的通道**，与 Windows Ink 开关无关。接入后：

| | 开 ink（Windows Ink 路） | 关 ink（原来是鼠标路） | 关 ink（接 Wintab 后） |
|---|---|---|---|
| 压力 | 有，**1024 级** | ❌ 没有 | ✅ 有，**16383 级** |
| 包率 | 165 Hz | 60~80 Hz + Raw Input 补点 | 不变 + 真实压力 |

**第一阶段刻意只借"压力"、不借坐标**：坐标仍旧走既有的指针/鼠标那条路（含 Raw Input 补点），
所以**几何一个字都没动** —— 万一 Wintab 有问题，症状只会是"压力不对"，
不会把笔画画歪，`--nowintab` 一行退回。

## 二、三个坑：都是查同行资料查到的，不是我试出来的

> **这就是"凡事先查同行经验"那条铁律的价值。** 三次里没有一次是我自己想到的。

1. **补 `CXO_MESSAGES`**（Wacom 官方 WintabDN 的第一步）
   —— 我们自己的探针第一版漏了它，表现是"上下文开得起来却收不到包"。
   **但产品里我们反而故意不用它**，见下条。
2. **不用包消息，改主动轮询**（某个 Python Wintab 库的做法：`lcOptions &= ~CXO_MESSAGES`）
   —— 对我们**尤其重要**：我们在 Raw Input 上吃过的亏是
   "空闲时也持续被唤醒 → 主循环被顶成 46fps、单核 26%"。
   轮询没有这个问题：不写一笔时一次都不去取。**实测空闲 0.04~0.17%** ✓
3. **不要 `WTOpen(..., fEnable:true)`**（同一个 Python 库的记录：
   *"某些 Wacom 驱动版本在重度初始化过的进程里用 fEnable=1 打开会破坏进程堆"*）
   → 我们先 `fEnable:false` 打开、再单独 `WTEnable(true)`。

另外清掉了默认上下文里的 **`CXO_SYSTEM`**：它是"让驱动去移动系统光标"，
而笔移动光标是 Windows 通过"笔当鼠标"已经做好的事，再让 Wintab 插一脚只会打架。

## 三、包体布局：**规范 ≠ 驱动的实现**（本轮最贵的教训）

按规范算：时间戳@8、X@24、Y@28、压力@32。
**这个高漫驱动实测是：时间戳@12、X@28、Y@32、压力@36** ——
驱动在 offset 8 多占了一个字，从它往后**所有字段整体挪 4 字节**。

这个错让探针报过"压力范围 593~1162"这种**假结论**（那其实读的是 Y 坐标）。

**所以产品里不写死偏移**：用 **`pkSerialNumber` 每包 +1** 这条铁律现场钉正
（"每包 +1"骗不了人；光看"值在合理范围内"查不出来，因为坐标也在 0~65535 里）。
没钉正就如实报"**按规范值 压力@32（没能现场钉正）**"，并且——

**还有一道合理性断言**：压力必须落在驱动自报的 `DVC_NPRESSURE` 区间内
（问驱动要的，不是猜的：`DVC_NPRESSURE = 15`，已用 Wine 的 wintab.h、
Wacom 官方 WINTAB.H、Rust wintab_lite 三处独立印证；本机实测 0~16383 一致）。
越界就**一个数都不信**、只记 `越界N` 计数。

## 四、一个自己发现、并主动堵掉的回归

**笔只是悬停在板上时，压力也是 0**（Wacom 官方口径："区间最小值表示静止/未按下"）。
要是把 0 当有效压力补进去，用户"笔搁在板上、手上用鼠标画"时，
**鼠标线条会莫名其妙变细**。

→ 只认 **> 0**；并且沿用代码里现成的「缺压回填」口径
（`Input/PenInput.cs` 的 `_lastValidPressure`）：这一笔见过一次真实压力之后，
后面偶尔缺一下就沿用上一个值，而不是掉回中点让笔画中间凹一下。
基准**每笔归零**。

## 五、真机抓到的两个 bug（2026-10-07 用户日志）

用户贴的日志一眼看出问题：

```
压感=无                                                  ← 这一笔没压感
[wintab 包221 补压89点 实测钉正 压力@36（偏规范 +4 字节）]  ← 看着像成功了
```

**这两栏自相矛盾**，一查是两个 bug 叠在一起：

### bug① 只有第一笔有压力

```csharp
if (!WintabEnabled || _wintabTried || ...) return;              // 打过一次就再也不打
if (_wintab.IsOpen && ActiveStroke == null) _wintab.Close();    // 空闲时关掉
```

第一笔写完 → 空闲 → 上下文被关；下一笔又被 `_wintabTried` 挡住 →
**上下文永久关闭，后面每一笔都没有压力**。

**修**：开一次就留着。轮询没有包消息，空闲时一次都不去取 → 不留着也不产生唤醒；
起笔前先 `Flush` 倒掉积压，也不会吃到过期样本。
**实测（上下文开着）空闲 CPU 0.01%** —— 留着的代价是零。

### bug② 三个计数一直累加 → 日志会骗人

`包221 / 补压89点` 是前几笔攒下来的。**我一开始真以为压力补上了**，
直到发现"压感=无"和它对不上。日志数字必须是"**这一笔**"的，否则它就不是证据。
→ 起笔时三个计数归零，差值基线一起归零。

### 顺带加的一栏：让这类 bug 一眼可见

`[笔画]` 里现在**直说状态**：

- 开着 → `[wintab 包N 补压N点 实测钉正 压力@36（偏规范 +4 字节）]`
- 没开 → `[wintab **未开**（这一笔没有压力）]`

> **教训：状态要直说，别让人（包括我自己）去推断。**
> 上次就是因为只报累计数字，看着像成功，白查了一轮。

### 验证
- 连画 3 笔 → 三笔全部正常，**没有一笔出现"未开"**
- 空闲 CPU（上下文开着）**0.01%**
- inputtest / appendertest / cornertest 全通过

### bug③ raw 补点的压力被写死 0.5（真机会看出粗细一跳一跳）

真机日志：一笔 393 个点里 **raw 补了 214 个（占 55%）**。

```csharp
// 压力沿用"这一笔到目前为止的值"：鼠标模式下本来就没有压力，
// 传 0.5 与既有路径一致
ActiveStroke.AddPoint(cx, cy, 0.5f, NowMs);   // ← 注释说"沿用"，代码写死 0.5
```

以前无所谓（鼠标那条路全笔都是 0.5，传什么都一样），
接了 Wintab 之后后果很明显：**一半的点是真实压力、一半被拉到中线** → 粗细一跳一跳。

**修**：`WtSeenPressure` 时用当前真实压力，否则仍是 0.5 ——
**没开 Wintab、或开 ink 走真笔那条路时，老行为逐字不变。**

### 附带：`WtPressurePoints` 数的不是"点"

那一栏写的是"补压N点"，我却写成每次调用 +1（一条合并消息可能带好几个点）。
**日志数字必须是它字面说的东西**，否则它就不是证据 ——
这个毛病今天已犯过一次（把累计值当成了本笔值）。

### ⚠ `widthtest` 的说明（重要，别误判）

细档（逻辑 1.0 = 物理 2 像素）覆盖率实测 **0.68~0.70**，判据线 0.75。

**用原始代码（`pristine` = ba38272，未改动的 GitHub 快照）编译后跑，一样失败（0.68/0.70/0.69）。**
→ **与本轮任何改动无关，是这台机器当前的环境状态。**

排除过程（都做了）：
- `--nowintab` / `--norawinput` 对照 → 一样失败
- 把 `settings.json` 挪开用默认值 → 一样失败
- CPU 降到 0.1% 再跑 → **三次都是同一个数 2189**（确定性，不是负载）
- 历史：同一份代码 `10:07` 失败(2147)、`10:18` 通过(2441)

特征：**各档粗细都少一样的绝对面积（~250~370 像素²）**，不是按比例缩小
→ 是**抗锯齿/亚像素**层面的差异，不是逻辑差异。

**结论：这是既有的、环境相关的测试抖动。**
以后看到它失败，先别怀疑自己的改动 —— 用上面这套对照方法确认。
