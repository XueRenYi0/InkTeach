# 多人同时书写：可行性调研与落地设计

- 日期：2026-10-24
- 状态：**只调研，不改代码**
- 目标：两个人在同一块大屏上**同时各写各的**，互不断笔、互不抢笔
- 关联：`调研-触摸手势-学校大屏.md`（第 9.3 节 InkClass/ULTRA 的多人书写蓝本）、`调研-触摸手势-滑动书写与轮盘呼出.md`

---

## 0. 结论先行

1. **技术上可行**：Windows 的 `WM_POINTER` 本来就是每个触点一条指针、每条指针有独立 id；引擎现在只是自己把"同时只能有一笔"写死了。
2. **最大改动不在输入，而在"单笔状态"**：`ActiveStroke`、`_drawing`、`_activePointer`、停顿成型、预测、湿墨、测量、日志等一大批状态都是"全局只有一笔"。要支持两个人，先把这些状态收进"每笔一个会话"。
3. **建议做成独立第三档「多人书写」**（手势 / 单指 / 多人），而不是在手势模式里再加一个开关。原因：第二个触点一落下，现有触摸层会把它判成双指手势或"蹭到的手指"，和"第二个人开始写"在语义上直接冲突；一个模式开关比一堆启发式更可解释。
4. **第一版只支持 2 人、只支持笔/荧光笔**：形状、框选、截图、橡皮、激光仍保持"一次一个人"；双指手势、三指擦、长按选择在多人模式下全部停用（擦除用工具）。4 人不是不能做，但先过两道门禁：脏区不能是整屏、帧预算够；详见 1.1。
5. **性能的第一坎是脏区，不是第二笔**：现在两笔的脏区取并集，左右两边写会退化成整屏重画；O1/O2 必须先改成"每笔一个矩形"，否则 2 人就会把现有的脏区优化吃掉。
6. **不做手掌/面积/间距判定**：按用户口径，**一个触点就是一个输入**——学校里不会出现手掌托屏、手指搭在屏上的情况。多人模式只受"人数上限"约束；`TouchStats` 仍然记录触点数/面积，但只用于诊断和性能，不参与准入。
7. 工作量粗估：**会话重构 2~3 天 + 脏区/渲染多笔化 0.5~1 天 + 多人模式 1~2 天 + 自检/真机验证 1~2 天**（按当前代码量，不含发版）。

## 1. 产品口径（需要先定）

| 问题 | 建议 | 理由 |
|---|---|---|
| 最多几个人 | **2 人（第一版）** | 教室最常见的是两个学生上台；红外同时触点数、撤销/存档、课堂空间都随人数变差。4 人不是不能做，但必须先过性能门禁，见 1.1 |
| 两个人用什么工具 | **笔 / 荧光笔** | 这两种是"各写各的"；形状/框选/截图/橡皮是"抢同一个上下文" |
| 颜色 | 两人共用当前颜色 | 现有工具是全局的；按人分颜色要改工具状态模型，第一版不做 |
| 手势 | 多人模式下**全关**（双指翻页/缩放、三指擦、长按选择、两指轮盘） | 第二根手指到底是"第二个人"还是"手势"，没有可靠判据；模式隔离最稳 |
| **写手准入** | **每个触点都算一个输入，只受人数上限** | 用户明确：学校大屏书写不会出现手掌托屏/手指搭屏；不做面积、间距、手掌判定 |
| 擦除 | 用工具栏橡皮（一次一个人擦） | 三指擦在多人模式下会把第三个人误擦；面积橡皮已取消 |
| 撤销 | 每写完一笔 = 一步撤销 | 和现在一致；两个人同时写时，Ctrl+Z 撤的是"最后完成的那一笔" |
| 翻页/白板/PPT | 多人模式下照常可用，但**写字期间禁止切页/切板** | 否则一笔会跨页提交 |
| 是否记忆 | 记住上次选择（`touch.mode=multi`） | 和现有单指模式一致 |

> 如果用户的实际场景是"老师 + 一个学生"或"两个学生"，上面的口径都成立；如果是要"一整个小组 4~6 人同时写"，需要另议上限。

### 1.1 人多了会怎样（重点：流畅度与性能）

先给结论：

- **2 人：可控，但必须先改"脏区"**。现在两笔的脏区是**一个并集**；两个人站在屏幕左右两边写，并集会覆盖整屏，等于每帧全屏重画——这是多人版第一个性能坎，不是第二笔本身。
- **4 人：CPU/渲染大约比 2 人再翻一倍，但脏区已经饱和**，不会再次翻倍。主要风险从"帧率"转成：红外多点是否可靠、撤销与存档、课堂拥挤。
- **6 人以上：不建议**。先不说 CPU，红外屏的同时触点数、遮挡和课堂空间都会先撑不住。

#### 逐项会变多少

| 维度 | 1 人 | 2 人 | 4 人 | 依据/说明 |
|---|---|---|---|---|
| 活跃笔几何/帧 | 1× | 2× | 4× | 每帧每笔重建一次；`BuildCenterlineCore` 会遍历这一笔的**全部点**（`Model.cs:5562`） |
| 活跃笔渲染/帧 | 1× | 2× | 4× | `DrawStroke` 每笔一次 |
| 上屏脏区 | 笔周围一小块 | **常退化为整屏** | 整屏 | `ComputeTransientBounds` 把活跃笔并成一个 `RectF`（`Overlay.cs:2833/2851`） |
| 输入消息 | 1× | 2× | 4× | 同一条 UI 线程串行处理 |
| 提交/分块光栅 | 1× | 2× | 4× | 每笔 `AddStroke` + 相关瓦片重光栅 |
| 撤销栈消耗 | 1× | 2× | 4× | 200 步 / 3 万条上限；4 人时"自己刚写的"很快被挤掉 |
| 板书历史序列化 | 1× | 2× | 4× | 停手后整块序列化，仍在 UI 线程；4 倍笔数就是 4 倍停顿 |
| 红外同时触点 | 1 | 2 | 4 | 按"一个触点 = 一个输入"算；面板实际报多少以现场 `TouchStats` 为准 |
| 课堂空间 | 宽松 | 合适 | 拥挤 | 65~86 寸屏站 4 个人，手和身体会互相挡 |

> 关键不是"4 = 4 倍慢"。几何/渲染是线性，但**脏区在 2 人时就已经到顶**；4 人是在"整屏重画"的基础上再把活跃笔的几何翻一倍。

#### 为什么 2 人就会整屏重画

`Overlay.ComputeTransientBounds`（`Overlay.cs:2833`）把所有"每帧重画"的东西（活跃笔、橡皮光标、框选、激光、HUD…）**并成一个矩形**：

```csharp
var r = RectF.Empty;
if (app.ActiveStroke != null)
    r.Add(CanvasRectToWindow(app.ActiveStroke.PaddedBounds));   // 并集
```

两个写手一个在左、一个在右时，这个并集就是整屏。接着：

- `RenderFrame` 按这个矩形 `PushAxisAlignedClip`（`Overlay.cs:2681-2687`）；
- `CompositeTiles` 会把整屏的分块都贴一遍；
- `Present1` 也按整屏矩形上屏。

项目里已有的实测口径：全屏 5.2M 像素时 GPU 占用约 **8~9%**，改成只更脏区后降到 **0.1~0.8%**（`Overlay.cs:2678` 的注释）。也就是说，**多人版如果不动脏区，2 个人就会把这条优化吃掉**。

> 这不是"第二笔的计算量"问题，而是"两笔的并集"问题。人数从 2 到 4，脏区不会更糟（已经整屏），但活跃笔和提交量继续线性增长。

#### 4 人真正会先卡在哪

按风险从高到低：

1. **红外屏本身**：同时触点上限、扫描率随触点数下降。按"一个触点 = 一个输入"的口径，2 人就是 2 个触点、4 人就是 4 个；如果面板额外报出触点（鬼点/硬件抖动），只能现场记录、按硬件问题排查，**不打算用软件判定去猜**。
2. **脏区/整屏重绘**：2 人就已经触发；4 人只是在这之上再叠几何。低配 OPS + 4K 时最可能先掉帧。
3. **硬件多报的触点会变成"多出来的一笔"**：不设计手掌/间距判定；如果现场出现，先记 `TouchStats`，确认是面板问题还是驱动问题。
4. **撤销/历史**：4 人写满 200 步只要每人 50 笔；板书历史序列化在停手后可能带来一次几十毫秒的停顿。
5. **课堂使用**：4 个人挤在一块屏前，工具/颜色是全局的，一个人换色/换工具会影响所有人；老师也难判断"这一笔是谁的"。

#### 性能预算（建议验收线）

当前单笔基线（项目内实测）：20 分钟 7200 笔，每帧记录平均 **1.7ms**、最差 **7.9ms**；60Hz 预算是 16.7ms。

建议给多人版定三条线（可按学校机器实测调整）：

| 场景 | 目标 |
|---|---|
| 2 人、4K、学校 OPS、连续 60 秒 | 帧记录 p95 ≤ 10ms、最大 ≤ 25ms，不持续低于 55fps；输入延迟比单笔多不超过 1 帧 |
| 4 人、同上 | p95 ≤ 14ms、最大 ≤ 30ms，不持续低于 50fps；否则不开放 4 人 |
| 10 分钟双人板书后停手 | 板书历史/自动存档的停顿 ≤ 30ms，内存无持续增长 |

> 这些数字是"门禁"，不是承诺。**2 人先实测；4 人只有过了这条线才考虑开放。**

#### 不管 2 人还是 4 人，先做哪几件事

按性价比排序：

1. **脏区从"一个并集"改成"每笔一个矩形"**：`_transientHistory` 从 `RectF[2]` 改成"每帧一组矩形"，`Present1` 收多个矩形；同时把渲染改成"背景一遍 + 瞬态一遍"，避免 N 个矩形把同一笔重画 N 次（半透明荧光笔还会叠深）。这是 2 人阶段就该做的基础设施。
2. **活跃笔不走运动模型/预测**：多人模式已经关了预测；活笔直接用原始折线（`RawWhileLive` 已经是折线），把 `StrokeMotion` 的重计算省掉。
3. **增量几何**：现在每个新点都会重建整条中心线；改成"已提交部分不变，只画新增段"，把 O(L²) 压成 O(L)。这一条工作量最大，只有 4 人实测不够时才做。
4. **降低提交/存档频率**：4 人时板书历史间隔拉长，或改成后台序列化（现在序列化在主线程）。
5. **人数上限做成常量**：`MaxWriters = 2`，4 人作为后续开关；不要第一版就暴露。

> 完整的优化顺序、两遍渲染、输入快路径、`--multiwritetest` 基准和验收线见 **`调研-多人书写-性能优化.md`**。建议 O1/O2 先于多人功能完成。

## 2. 现在的引擎为什么只能写一笔

### 2.1 入口只认一条指针

`Engine.OnPointerDown`（`Engine.cs:4357`）在触摸手势层之后有一道硬闸：

```
if (_drawing) return;          // Engine.cs:4558
_activePointer = id;           // Engine.cs:4560
```

`OnPointerMove` 只处理 `_drawing && id == _activePointer`（`Engine.cs:5488`），
`OnPointerUp` 只处理 `id == _activePointer`（`Engine.cs:5685`）。

所以第二个人落指时：

- 如果第一笔已经在写 → 第二下被 `_drawing` 挡掉；
- 如果第一笔还没真正画出去 → 触摸层会把它判成双指手势（见 2.2）。

### 2.2 触摸层会把"第二个人"判成手势

`TouchGestures.Down`（`Touch.cs:184`）的判定：

| 条件 | 现在的结果 |
|---|---|
| 1 个触点、干净开始 | `Write` |
| 2 个触点、都在 150ms 内、第一根还没动 | **`Gesture2`**（双指翻页/缩放） |
| 2 个触点、第一根已经动了 | **`Ignore`**（当成写字中途蹭到的手指） |
| ≥3 个触点、干净开始 | **`Erase`**（三指擦） |
| 长按 500ms 没动 | 选择 |
| 两指长按 400ms | 呼出盘 |

也就是说：**第二个人只要在第一笔起手 150ms 内落指，就一定会被当成双指手势；晚一点落指，就一定被当成蹭到的第二根手指。** 这不是参数问题，是角色模型只设计了"一个人 + 手势"。

`Touch.cs:222` 的 `clean` 判据、`Touch.cs:225-226` 的 2/3 指分支，是多人书写必须改的第一处。

### 2.3 单笔状态的清单

| 状态 | 位置 | 多人后会怎样 |
|---|---|---|
| `ActiveStroke` | `Engine.cs:349` | 第二笔会覆盖第一笔；第一笔还没进文档就丢了 |
| `_drawing` | `Engine.cs` 多处 | 一个 bool 表示"有没有人在写"，第二个人进不来 |
| `_activePointer` / `_activePointerType` | `Engine.cs:2038` | 只有一个"当前指针"，第二根会抢走 |
| `Doc.BeginErase/EndErase` | `Model.cs:7379/7384` | 一个文档只有一个擦除批次；两个人同时擦会并成一步撤销 |
| `ActiveStrokeHasPressure` | `Engine.cs:2118` | 整笔属性，按人分要进会话 |
| `_pen` / `_ptr` 采样缓冲 | `Engine.cs` / `Input/PenInput.cs` | 共用缓冲；只要同步 `Read(id)` 还能用，但净化/回填要按会话 |
| `_cleanBuf` | `Engine.cs:1241` | `--clean` 的滑动平均是全局的，两个会话会互相污染 |
| `_predictor` / `_tailCanvas` | `Engine.cs:1284/1294` | 预测尾只有一条；多人时应直接关预测 |
| `_dwell` / `_dwellInk` / `_stepPlan` | `Engine.cs` | 停顿成型/多笔图形只有一套；多人时停用 |
| `_systemWetStroke` | `Engine.cs` | 系统湿墨只跟一条笔；触摸本来不走它，笔+手指同写时再说 |
| `InputBlackBox` / `_recordPts` / 测量 | `Engine.cs` | 诊断是"一笔一份"，多人要按会话记 |
| `Laser` | `Model.cs:8316` | 激光已经有"多条轨迹"的结构，但 `Writing` 仍只有一条 |
| `_activePointer` 的捕获 | `Engine.cs:4582/5686` | `SetCapture`/`ReleaseCapture` 是窗口级，见 3.1 |

### 2.4 渲染与脏区

- `Overlay.cs:2734` 只画 `app.ActiveStroke`；
- `Overlay.cs:2851` 脏区只加 `app.ActiveStroke.PaddedBounds`；
- `Overlay.cs:2185` 出图/截图那条路也只补画一条。

多人后要改成遍历"所有正在写的笔"。每一笔的几何缓存是**按 Stroke 自己**的 `Revision` 失效的（`Model.cs:4466`），所以多笔不会互相干扰，只是每帧多做几份几何。

### 2.5 会被绕过的"写字期间"守卫

不止 `_drawing`，这些地方也默认"最多一笔"：

- 板书历史快照：`Engine.cs:215` `if (_drawing || ActiveStroke != null) return;`
- 自动存档：`Engine.cs:288` 同款
- 页面/白板切换：`SetBoardFromUi`、翻页等没有统一"有人正在写"的闸
- `SwitchTool`：只作废多笔图形，不会结束正在写的自由笔迹

多人后统一改成 `AnyWriting`（会话表非空），并在切页/切板/换工具前先结束所有会话。

## 3. Windows 与硬件层

### 3.1 `WM_POINTER` 本来就是多指

- 每个触点在按下时生成一条 `WM_POINTERDOWN`，有独立的 `pointerId`；
- 移动是 `WM_POINTERUPDATE`，抬起是 `WM_POINTERUP`；
- 同一条消息里可能带合并的采样点，现有代码已经用 `PenSampleBuffer` / `PointerSampleBuffer` 的 history 还原（`Engine.cs:9445`）；
- 指针 id 在"这一次接触"期间唯一，抬起后可被复用——按 id 建表、抬起即删，不能长期缓存。

Windows 文档明确：`WM_POINTERDOWN` 时指针**隐式捕获**到窗口，直到接触结束（[WM_POINTERDOWN](https://learn.microsoft.com/en-us/windows/win32/inputmsg/wm-pointerdown)）。这意味着：

- 画布上的第二个触点会自然继续送到我们的窗口，不需要为每一指单独 `SetCapture`；
- 现有代码在按下时 `Native.SetCapture(hWnd)`（`Engine.cs:4582`）是**窗口级鼠标捕获**，不是"按指针捕获"；
- 抬起时 `Native.ReleaseCapture()`（`Engine.cs:5686`）会把整个窗口的捕获放掉——多人时第一个人抬手就可能影响第二个人。

**多人版必须改**：

1. 自由笔迹这条路**不再依赖 `SetCapture`**，靠 `WM_POINTER` 的隐式捕获；
2. 如果保留 `SetCapture`（给界面拖动/旧路径），只允许在**最后一个**活动指针抬起时 `ReleaseCapture`；
3. `WM_POINTERCAPTURECHANGED`（`Engine.cs:4159`）现在无条件 `EndStroke()`——改成用 `wParam` 里的 pointer id 只结束对应会话；如果 `lParam == NULL`（真正丢捕获）才结束全部。

### 3.2 `WM_POINTERCAPTURECHANGED` 的 wParam 是 pointer id

文档：`GET_POINTERID_WPARAM(wParam)`。现在的处理是无条件收笔，多人后会"一个人被系统取消，另一个人也跟着断"。

### 3.3 红外屏的现实

- 这块学校屏是 **SEEWO MT23B-SHA**，Windows 10 19045；常见红外标称 10 点/20 点，但**实际同时上报几个点、扫描率多少，必须现场量**；
- 现有 `--touchhud` 会显示"当前触点数 / 见过的最大触点数 / 接触面积"；`TouchStats` 会记录每次按下时的触点数、面积、判定；
- **按用户口径：一个触点就是一个输入**。学校大屏书写不会出现手掌托屏、手指搭屏的情况，所以不做手掌/手指/面积准入；
- 现场只需要确认两件事：
  - 面板在 2 人（2 点）、4 人（4 点）同时书写时，是否稳定报点、扫描率是否够；
  - 如果面板额外报出触点（鬼点/硬件抖动），记录下来按硬件问题排查，不用软件逻辑去猜。
- 面积/触点数统计保留，但**只用于诊断和性能**，不参与"谁可以写"。

## 4. 参考实现：InkClass / Ink-Canvas-Ultra

`调研-触摸手势-学校大屏.md` 9.3 已经拆过：

- `isInMultiTouchMode` + `VisualCanvas`/`StrokeVisual`：**每个触点/每支笔各建一条笔迹**，抬手时 `Strokes.Add`；
- 双指手势 `ManipulationDelta` 首行：`if (isInMultiTouchMode) return;`——**多人模式和手势互斥**；
- 选择工具 `TouchDown` 首行：`if (EditingMode == Select) return;`——**选择工具下不并行**；
- ULTRA 用 `e.StylusDevice.TabletDevice.Type != Stylus` 区分真笔和手指：**真笔走原生墨迹，手指走多笔合成**；
- 抬笔 `await Task.Delay(5)` + 30ms/100DIP 断线分段；
- 已知缺陷：**同一设备 ID 没做映射，选一个设备会把所有设备的笔迹全选中**（我们没有这个问题：`WM_POINTER` 的 id 是每触点独立的）。

可以直接借的结论：

1. 多人模式 = 显式开关 + 与手势互斥；
2. 每个触点一条独立笔迹对象；
3. 笔和手指分开：笔优先，手指才走多笔；
4. 选择/形状工具下不并行；
5. 抬笔即提交，不要延迟太久（延迟会让"两个人同时抬笔"的撤销顺序变怪）。

## 5. 方案对比

### 方案 A：双槽快改（不推荐，但可应急）

保留 `ActiveStroke` 作为第一笔，再加一个 `ActiveStroke2` / `_secondPointer`，把自由笔迹的起笔/加点/收笔复制一份。

- 优点：不动现有 112 处 `ActiveStroke` 引用，1~2 天能出演示；
- 缺点：两份几乎相同的代码，日志/测量/预测/停顿成型都要复制；第三个人、笔+手指、橡皮并发全部无解；以后必然重写。
- 结论：只适合"明天就要给学校看"的演示，不适合作为产品。

### 方案 B：会话表重构（推荐）

把"正在写的一笔"从全局字段收进 `LiveStroke` 会话，引擎持有一个 `Dictionary<(IntPtr hwnd, uint id), LiveStroke>`。

- 优点：第二人只是多一个会话；第三、第四人只改上限；笔/手指、橡皮、激光可以逐步接；
- 缺点：要动 `ActiveStroke` / `_drawing` / `_activePointer` 这一片，回归面大；必须靠现有自检兜底。

### 方案 C：每个写手一个独立文档/图层

每个人一个 `InkDocument`，最后合并。

- 优点：状态最干净；
- 缺点：撤销、选中、擦除、存档、PPT 页、空间索引全要跨文档合并；对当前代码是伤筋动骨。
- 结论：不做。

## 6. 推荐设计（方案 B）

### 6.1 模式

在现有「设置 → 书写 → 触摸模式」里加第三档：

| 档位 | 行为 |
|---|---|
| 手势（默认） | 现在的行为：单指写、双指手势、三指擦、长按选择、轮盘 |
| 单指 | 只允许一个触点写，无任何手势 |
| **多人** | 最多 2 人同时写；双指手势、三指擦、长按选择、轮盘全部停用 |

落盘：`touch.mode = multi`；手势档不写项，单指档写 `single`（沿用现有逻辑）。

UI 上这一行现在是开关，要改成"值 + 点击循环"（和「历史清理」「界面大小」同一种行样式），显示"手势 / 单指 / 多人"。

### 6.2 数据结构

```csharp
internal sealed class LiveStroke
{
    public uint PointerId;
    public IntPtr Hwnd;              // 多屏时同一 id 可能出现在不同窗口
    public uint PointerType;         // PT_TOUCH / PT_PEN
    public Stroke Ink;               // 正在写的那一笔（不进 Doc）
    public bool HasPressure;
    public double StartMs;

    public List<(float X, float Y, float P)> CleanBuf;   // --clean 用
    public InkPredictorLinear Predictor;                 // 单人且开预测时
    public List<Vector2> Tail;                           // 预测尾（多人模式不用）
    // 诊断：消息数/采样数/合并比/分配/GC（可从全局搬进来，或第一版只记指针 id）
}
```

引擎：

```csharp
private readonly Dictionary<(IntPtr, uint), LiveStroke> _live = new();
private readonly List<LiveStroke> _liveOrder = new();   // 渲染/提交顺序

internal bool AnyWriting => _live.Count > 0;
```

兼容层（减少一次性改动）：

```csharp
// 只给"单笔路径"（形状 / 停顿成型 / 截图）用的兼容属性；
// getter 取唯一会话，setter 仍然允许它们赋值。自由笔迹的多人路径直接读 _live。
internal Stroke ActiveStroke
{
    get => _live.Count == 1 ? _liveOrder[0].Ink : null;
    set { /* 单笔路径的旧语义：清空或建一条无名会话，见 P1 实现 */ }
}
```

> 注意：`ActiveStroke` 现在在 112 处被读/写（`Engine.cs`），不能一步到位改成列表。第一版可以保留这个属性给"单笔路径"（形状、停顿成型、截图），自由笔迹的多人路径直接读 `_live`。等多人稳定后再把形状也收进会话。

### 6.3 指针路由

`OnPointerDown`：

1. 先走现在的界面 / PPT 条 / 计时卡 / 回放 / 穿透判断（不变）；
2. 触摸层：多人模式下 `TouchGestures.Down` 对每个新触点返回 `Write`（只受人数上限），不再返回 `Gesture2/Erase/Ignore`；
3. 若工具是笔/荧光笔、`_live.Count < MaxWriters` → 新建 `LiveStroke`，**不写 `_activePointer`**；
4. 其它工具 / 人数已满 → 走现有单笔路径（`if (_drawing) return;`）。

`OnPointerMove`：

1. 先用 `(hWnd, id)` 查 `_live`；
2. 命中 → 只扩展这一笔（`ExtendFreehand(session, ...)`），**不再看 `_activePointer`**；
3. 未命中 → 走现有悬停/手势路径。

`OnPointerUp`：

1. 先查 `_live`；命中 → 只提交这一笔，移除会话；
2. 未命中 → 走现有界面/手势/单笔收尾；
3. **只有 `_live.Count == 0` 时才 `ReleaseCapture()`**（如果还保留窗口捕获）。

`WM_POINTERCAPTURECHANGED`：

1. 取 `wParam` 的 pointer id；
2. 有对应会话 → 只结束它；
3. `lParam == IntPtr.Zero`（真的丢捕获）→ 结束全部会话。

### 6.4 人数上限（第一版）

按用户口径：**一个触点就是一个输入**，不判手掌、不判面积、不判间距。只判三件事：

1. **工具**：`Tool` 是 `Pen` 或 `Highlighter`；其它工具 → 单人；
2. **人数**：`_live.Count < MaxWriters`；满了 → `Ignore`（记 `rejected=cap`）；
3. **设备**：`PT_PEN` 优先；笔在写时，触摸一律 `Ignore`（沿用现有规则）。

`MaxWriters` 第一版取 2；第三个及以后的触点直接忽略。`TouchStats` 里的触点数/面积只用于诊断和性能，不参与准入。

> 不做"最小间距/大面积不准入"：用户明确学校大屏不会出现手掌托屏、手指搭屏；多加这些规则只会误伤正常书写。

### 6.5 提交与撤销

- 每笔抬手 → `Ink.RawWhileLive = false; Doc.AddStroke(Ink);`，和现在单笔提交同一条路；
- 每笔各自一条 `AddStrokesAction` → **一步撤销一笔**；
- 两个人几乎同时抬手时，按消息到达顺序提交；撤销顺序 = 提交顺序；
- 不做"两人一起算一步撤销"——那会让老师想撤掉其中一个的字时，把另一个也撤掉。

`EndStroke` 现在混着形状/停顿/截图/激光/选择等一大堆分支。多人第一版只给自由笔迹走一个新的 `EndLiveStroke(LiveStroke)`，只做：

1. `RawWhileLive = false`；
2. `Doc.AddStroke`；
3. 每笔日志（带 pointer id / 并发数）；
4. 移除会话；
5. `AnyWriting` 为 false 时再停 GC 低延迟、停 dwell 定时器、更新 `_lastStrokeEndMs`。

形状/停顿/截图/激光仍走原来的 `EndStroke()`，保证不碰它们。

### 6.6 渲染与脏区

- `Overlay.cs:2734`：改成 `foreach (var live in app.LiveStrokes) DrawStroke(live.Ink);`
- `Overlay.cs:2851`：**不能简单 union**（见 1.1）——两个人一左一右就把脏区并成整屏；
- `Overlay.cs:2185`（出图）：同样遍历；
- `SuppressActiveStroke`（`--trailonly`）对全部生效；
- 系统湿墨：只给 `PT_PEN` 的会话，触摸会话不走；
- 预测尾：多人模式下直接关（`PredictTailEnabled && _live.Count == 1` 才画）；否则要给每条会话各配一套预测器，第一版不值得。

**脏区的正确做法（O1/O2 就要做）**：

1. 把 `ComputeTransientBounds` 的"一个并集"改成"一组矩形"：每支活跃笔一个矩形，光标/框选/激光各自一个；`_transientNow` / `_transientHistory` 从单个 `RectF` 改成每帧一个 `List<RectF>`（保留最近两帧，双缓冲需要）。
2. `_frameDirty` 本来就能收多个矩形，`Present1` 也支持多个矩形——这条路是现成的。
3. `RenderFrame` 的 `foreach (var raw in _frameDirty)` 里，**每支活跃笔先判 `PaddedBounds` 是否和当前矩形相交**，不相交就跳过；否则 N 个矩形会把同一笔重画 N 次，反而更慢。
4. 如果矩形数量太多（比如超过 6~8 个），再合并成少量包围盒；合并的阈值用实测帧时间定，不要拍脑袋。
5. 在 2 人阶段就把这条做完并量好，4 人才有基础；不要等 4 人再回头改渲染循环。

性能：每笔的几何缓存按自己的 `Revision` 失效（`Model.cs:4466`），两笔就是两份 `BuildCenterline`。先实测 2 笔 120Hz 的帧时间；如果不够，再把"活笔几何"改成增量画（只画新加的一段），不要一上来就优化。

### 6.7 与其它功能的关系

| 功能 | 多人模式 |
|---|---|
| 双指翻页/缩放 | **停用**（手势总闸在 `TouchGestures.Enabled`，多人模式不喂 Gesture2） |
| 三指擦 | **停用**（第三根手指会被当成第三个人；人数上限 2 时直接 Ignore） |
| 长按选择 / 两指长按轮盘 | **停用**（长按 500ms 会把"停着思考"的学生判成选择） |
| 停顿成型 | **停用**（两笔各有一套 dwell 状态，第一版不接） |
| 墨迹预测 | **停用**（单尾，无法分人） |
| 激光笔 | 第一版单人（`Laser.Writing` 只有一条） |
| 橡皮 / 面积擦 | 第一版单人；显式橡皮照常可用 |
| 形状 / 框选 / 截图 | 第一版单人（第二个人落指忽略） |
| 白板 / PPT 页 | 多人可写；**写字期间禁止切页/切板**（`AnyWriting` 闸） |
| 自动存档 / 板书历史 | `AnyWriting` 期间不写；最后一笔结束后照常 |
| 系统湿墨（真笔） | 只有笔会话；这台学校屏没有真笔，不受影响 |
| 触摸 HUD | 显示当前触点数/写手数；`TouchStats` 增加 `multi` 档 |

### 6.8 设置与文案

「设置 → 书写 → 触摸模式」三档，值显示"手势 / 单指 / 多人"。
提示文案建议：

> 手势 = 双指翻页/缩放 + 三指擦 + 长按选择；单指 = 只允许一个触点写字，完全无手势；多人 = 最多两人同时写，手势和三指擦停用（用工具擦）。

第一次切到多人时，可以在工具条上冒一条一次性提示："多人书写：最多 2 人，双指手势已暂停"。

### 6.9 日志

- `[笔画]` 增加：`writer=1/2`、`concurrent=N`、`pointer=0x...`、`verdict=Write/Ignore(cap/pen)`；
- `TouchStats` 增加：`mode=multi`、`writersMax`、`rejectedCap`；
- session.json / 设备卡带上这些计数（现有 `TouchStats.Json()` 已经进 session.json 和设备卡）；
- 现场验证：让学校用下一版测试版（9.3.2），2/3/4 个人同时按屏，看 `[touch]` 里 `contacts`、`max` 和帧时间——只确认"面板能不能稳定报点、性能够不够"，不做手掌准入。

## 8. 测试计划

### 8.1 自检（`--touchtest` 新增）

1. 两个触点相差 80ms 落下 → **两笔**都进 `Doc`，各自终点正确；
2. 第一个触点先移动 100px，第二个再落下 → 第二个仍然能写（不再判 `Ignore`）；
3. 第三个触点落下 → 超过 2 人上限，被忽略，前两笔不断；
4. 两人同时写时，双指滑动**不产生**翻页/缩放（相机不动、页码不变）；
5. 两人同时写时，长按 600ms **不产生**选中；
6. 两人同时写时，三指落下**不产生**擦除；
7. 先抬一个人 → 另一个人继续写，笔画不中断；
8. 两人各写完 → 撤销两次，分别撤掉两笔；
9. 两个人**靠得很近**同时写（不做间距判定）→ 两笔都正常；
10. `WM_POINTERCAPTURECHANGED` 只结束对应会话（可用测试钩子直接调）。

### 8.2 界面（`--paneltest`）

- 「触摸模式」三档循环：手势 → 单指 → 多人 → 手势；
- 落盘 `touch.mode` 正确；重开界面读回；
- 提示文案/值显示正确。

### 8.3 真机

- 学校 MT23B-SHA：两个人各写一行字、同时画圈、一个人抬手另一个人继续；
- 两个人靠得很近同时写（验证不做间距判定不会误伤）；
- 3 人同时按（第三个人应被人数上限忽略，前两笔不断）；
- `--touchhud` 看最大触点数、扫描稳定性；
- 连续 10 分钟双写，看帧时间/慢帧（`[env]` / HUD）；
- Win11 开发机用合成触点回归（不依赖真屏）。

### 8.4 多人性能基准（实现阶段要加 `--multiwritetest N`）

不靠"感觉流畅"，用同一套合成触点跑可复现的曲线：

| 场景 | 变量 |
|---|---|
| 1 / 2 / 3 / 4 人 | `N` 个触点，各自独立轨迹 |
| 写手距离 | 同一小块 / 屏幕左右两端（专门打脏区并集） |
| 笔画长度 | 短笔画（每 0.5 秒抬一次）/ 长笔画（连续 10 秒不抬） |
| 分辨率 | 1080p / 4K（学校实际） |
| 背景 | 空白 / 已写满一屏 |

每个场景跑 60 秒，输出：

- 帧记录 `avg / p95 / max`、`slow50 / slow150`、上屏脏区面积百分比；
- 每笔几何重建耗时、提交耗时、输入到加点延迟；
- 内存/显存、GC 次数；
- 结束后自动存档/板书历史的停顿。

验收线按 1.1 那张表；**2 人不过线就先优化，不进入 4 人。**

## 9. 风险

1. **红外硬件多报触点**：按用户口径不设计手掌/手指/间距判定；如果面板额外报出触点（鬼点/硬件抖动），它会变成"多出来的一笔"。先记 `TouchStats`，按硬件问题排查。
2. **捕获/释放回归**：窗口级 `SetCapture`/`ReleaseCapture` 改成"最后一个指针释放"后，要重点回归"拖出屏幕外""切窗口""Alt+Tab"。
3. **性能**：
   - **脏区并集**：2 人就会把脏区并成整屏，回到每帧全屏合成；O1/O2 必须先做（见 1.1/6.6）。
   - **活跃笔几何**：每帧每笔重建整条中心线，2 人 2 倍、4 人 4 倍；长笔画更贵。
   - **帧预算共享**：UI 线程是单线程，4 人时任何一笔的几何/渲染变慢都会让所有人一起变慢；先测 2 人 p95，再谈 4 人。
4. **撤销歧义**：两个人同时写时，Ctrl+Z 撤的是最后完成的一笔，不是"我这一笔"；老师需要知道这个口径。4 人时 200 步很快被填满，"自己的上一笔"可能已经不在栈里。
5. **手势没了**：多人模式下不能双指缩放/翻页；需要老师切回手势档，或者用工具栏。这个 trade-off 要跟用户确认。
6. **多屏**：会话 key 用 `(hwnd, id)`；如果两块屏同时写，坐标/相机/提交顺序都要再验。
7. **`_drawing` 语义扩散**：50 处引用里有些是"有人在写"，有些是"这一条指针在写"；P1 要逐个改，不能只改入口。
8. **红外上限**：面板的同时触点数/扫描率不是代码能解决的；4 人前必须现场确认"4 个点同时写"仍能稳定上报。
9. **存档停顿**：4 人写 10 分钟后，板书历史/自动存档的整块序列化是 4 倍笔数；可能出现一次几十毫秒的停手停顿。
