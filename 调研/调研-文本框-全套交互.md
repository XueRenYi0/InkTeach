# 调研：文本框全套交互（对标 Figma / PowerPoint / OneNote）

日期：2026-11-01　　状态：**方案待拍板，尚未改代码**

用户原话（整理）：

> 1. 文本框没钉住时，「更多」里也不要显示；它应该和画笔、荧光笔、激光笔、橡皮擦是同一套互斥逻辑。
> 2. 多行内容怎么快速定位到某一行编辑？现在默认落在最后一行。
> 3. 宽度/高度到底怎么自适应？单行拖很宽没必要；拖了宽度，高度可以随内容；但宽高都固定了，就不该再随内容变。
> 4. 颜色只留一两种（黑/红），像画笔一样能自定义；字号直接选，不要 A−/A+。
> 5. 不要加下划线/加粗，简单文本框 + Markdown 就够。
> 6. 内容没了或只有一个空格，文本框应该消失；现在只有新建空框会消失。
> 7. 找一个成熟产品把全套逻辑抄过来，再对照我们提方案，最后微调。

---

## 〇、一句话结论

**对，抄成熟产品的全套逻辑最省力；但不能只抄一家。**

建议抄这三家的组合：

1. **Figma 的“宽/高是两个独立轴”**：宽可以自动、高也可以自动，互不绑架；
2. **PowerPoint 的默认行为**：文本框默认“高度随内容长”，手动改宽后只固定宽、不固定高；
3. **Figma 的空文本删除**：编辑结束内容为空，整个文本对象删掉。

落到我们产品上，再收紧成一条更适合课堂的总规则：

> **高度永远自动，不允许教师拖高；宽度可以拖，第一次输完后固定。普通文本框没有内部滚动。**
>
> 也就是说：**只让老师控制“多宽”，不控制“多高”。高度永远 = 内容需要的高度。**

理由很直接：老师不喜欢“拖高”带来的两种结果——拖多了留白、拖少了滚动；而滚动在画笔模式下还会和画布滚动打架。干脆把“高度”从可拖项里拿掉，问题就不存在了。

这样用户问的 (a)(b) 两件事同时成立：

- 单行文字默认宽度刚好包住内容，不会天生很宽；
- 拖宽之后高度继续跟着内容长；
- 不存在“固定高 + 又要自适应”的矛盾，因为根本没有“固定高”这个状态；
- 内容多了只往下长，不出现第二个滚动条；真要移动视野，滚的是画布，和画笔模式同一套滚动。

## 一、市场对标

| 产品 | 新建方式 | 宽度 | 高度 | 手动拖过之后 | 空文本 |
|---|---|---|---|---|---|
| **Figma** | 单击 = Auto width；拖框 = Fixed size | 单击后随字宽长；可切固定宽 | 可 Auto height（固定宽、自动高）或固定高 | **手动改尺寸 = Fixed size**（两轴都固定） | **自动删除空文本层** |
| **PowerPoint** | 插入文本框 | 手动拖宽后文字在框内换行 | 默认 **Resize shape to fit text**：高度随内容长 | 要固定高必须显式选 **Do not Autofit**；否则会继续贴合内容 | 不会自动删，会留空框 |
| **OneNote** | 点页面开始输入 | 随内容长；**手动拖宽后锁宽** | 随内容长 | 宽被锁死，且没有“恢复自动宽”的按钮 | 不会自动删 |
| **Excalidraw** | 文本工具 | `autoResize=true` 时随字宽；拖过之后 `false` | 始终按排版内容算高 | 宽固定、高自动 | 空文本不保留 |
| **ClassIn** | 白板“文本输入”工具 | 公开资料只说明有颜色/字号，尺寸细节未公开 | 同上 | 同上 | 未公开 |
| **我们现状** | 点画布新建 | 第一次输入时自动长；**提交时冻结** | 第一次提交时冻结；**读档还被强制改成固定高** | 拖宽只关自动宽；拖上下才固定高 | **只有“新建后没输入”会删** |

### 1.1 为什么不能只抄一家

- **只抄 Figma**：单击创建的文本会一直 Auto width，长段落会一直往右长，直到屏幕边缘才换行；白板上不好用。
- **只抄 PowerPoint**：它默认只“高度随内容”，宽度不会自动贴合单行文字；用户仍然要手动拖宽。
- **只抄 OneNote**：宽一旦手动拖过就永久锁死，没有回头路；我们已经吃过“用户不知道为什么它不自动了”的亏。
- **ClassIn**：它是课堂场景最接近的参考，但公开资料只够确认“文本是工具、带颜色/字号”，尺寸状态机没有公开细节，不能作为主参考。

所以采用 **Figma 的状态机 + PowerPoint 的默认高度行为 + Figma 的空文本删除**，再保留 OneNote 的“拖宽后高度继续长”。

### 1.2 如果只选一个“整套照搬”的产品：Excalidraw

有。最接近、最省心的是 **Excalidraw 的文本对象模型**：

- 它是开源白板，文本就是一个普通对象，不是“富文本编辑器”；
- 点文本工具 → 点画布 → 输入；
- 宽度默认随内容，手动拖过之后固定；
- 高度永远按换行后的内容算，没有固定高、没有内部滚动；
- 字号是独立属性，从面板改；
- 双指/滚轮缩放的是**画布**，不是单个文本对象；
- 编辑结束内容为空，对象直接删掉。

这套东西正好覆盖我们纠结的全部点，而且它就是为白板设计的，不是 Figma 那种设计工具逻辑。

我们只保留三样自己的东西：

1. 原生 RichEdit 编辑窗（中文输入法、选区、复制粘贴）；
2. Markdown 渲染；
3. AI 题卡（它是卡片，不是普通文本框，保留自己的滚动）。

**不抄 Excalidraw 的代码**（它是 TypeScript/React + DOM 文本编辑），只抄它的**对象模型和交互规则**。这样我们不用再一项项设计，也不会把 React 那套复杂度搬进 C#/D2D。

## 三、目标模型：高度自动，宽度可调

### 3.1 两个轴：高度只读，宽度可调

| 宽度 | 高度 | 什么时候出现 | 行为 |
|---|---|---|---|
| 自动 | 自动（永远） | 刚点画布新建 | 单行时宽贴内容；到屏幕边缘换行、高度继续长 |
| 固定 | 自动（永远） | **第一次输完**，或拖了左右边 | 宽不再跳；内容变多/变少只影响高度 |

**没有“固定高度”这一态，也没有内部滚动。** 普通文本框只有“多宽”是老师能定的，“多高”永远由内容决定。

### 3.2 具体规则

1. **新建**
   - 点画布：`AutoWidth=true`、`AutoHeight=true`。
   - 输入时宽随最长行增长；到屏幕右沿后停止变宽，改为换行、高度继续长。

2. **第一次结束编辑**
   - 宽按内容自然宽收一次，然后 `AutoWidth=false`（之后不再跳宽）。
   - `AutoHeight` 永远保持 true。
   - 不再有“内容太高就固定高度、转内部滚动”的收尾。

3. **拖左右边**
   - 选中后，文本框**左右两条边各是一条整高的竖线**，整条线都是拖动区，不是只有中点一个 8×8 的小手柄。
   - 这样哪怕文本框有 2000 像素高，老师在屏幕里看到的任意一段竖线上都能直接拖宽，不用先去找“中间那个点”。
   - 竖线只压在左右内边距上，不盖住文字；鼠标/笔靠近时变成左右箭头。
   - `AutoWidth=false`，宽度听用户的。
   - 高度继续随内容变；老师只决定“多宽换行”，不决定“多高”。

4. **拖上下边 / 四角**
   - **普通文本框不提供上下和四角手柄**，只保留左右两条竖线 + 拖动整框。
   - 这样从交互上就不会出现“拖少了要滚动、拖多了留白”的歧义。

5. **双指缩放**
   - **双指始终缩放画布，不缩放单个文本框。**
   - 选中文本框时双指捏合，还是画布缩放，和没选中时一样；不会出现“这个框被捏小了、字也变小了”。
   - 字号只从字号按钮改；文本框本身没有“对象缩放”这个概念。
   - 这样不会和字号、笔宽、存档产生第二套缩放值，也不会和“改字号”打架。

6. **内容变化**
   - 宽度固定后，文字变多 → 行数变多 → 框向下长；文字删少 → 行数变少 → 框向上收。
   - 不会裁切、不会出现第二个滚动条。

7. **改字号**
   - 字号变大 → 行高变大、可能需要更多行 → 高度自动变高。
   - 宽度保持老师定的值；如果一行放不下就换行。

8. **内容很长怎么办**
   - 框继续向下长；超过屏幕时，滚的是**画布**，不是文本框内部。
   - 这样全局只有一套滚动：画笔模式下怎么滚，输入文字时就怎么滚。不会出现“笔在框里滚、框在画布里滚”的双层滚动。
   - 第二版可以再加“光标接近屏幕底部时自动上移画布”，但第一版不做。

9. **对齐逻辑**
   - 高度永远吸附到**整行**：`高度 = 行数 × 行高 + 上下内边距`，不会出现 37.4 像素这种半行高度。
   - 同一字号的多个文本框，底边天然对齐到行网格；老师再用移动/吸附把它们摆到想要的位置。
   - 如果以后真的需要“固定大小的文字区域”（比如答题框），那是另一种对象——**卡片/容器**，不是普通文本框；固定高、滚动、裁切都留给它。

10. **空框的最小高度**
   - 还没有内容时，保留一行高 + 内边距，保证点得进去。
   - 一旦有内容，高度就按实际行数算，不留多余空白。

> **这一版不采用 Figma 的“永久 Auto width”**：白板上的长段落会一直往右长，课堂场景不好用。我们只在“第一次输入”阶段自动长宽，提交后宽固定、高永远自动。这是 Figma 状态机和 PowerPoint 默认行为的折中。

## 四、输入与编辑体验

### 4.1 进入编辑

| 当前工具 | 操作 | 结果 |
|---|---|---|
| 文本工具 | 单击已有文本 | **直接进入编辑**，光标落在点击位置 |
| 文本工具 | 单击空白 | 新建并编辑 |
| 选择工具 | 单击文本 | 选中（可拖动/改宽） |
| 选择工具 | 双击文本 | 进入编辑，光标落在点击位置 |

现在文本工具下是“第一下选中、第二下才编辑”，多了一次点击，和“文本是工具”的定位不一致。改成单击即编辑，和 Figma/PowerPoint 一致。

### 4.2 多行定位

进入编辑时，不再无条件把光标放末尾，而是：

1. 用点击点的屏幕坐标换算成原生 RichEdit 的客户区坐标；
2. 发 `EM_CHARFROMPOS` 得到字符索引；
3. `EM_SETSEL(index, index)` 把光标放到点击处；
4. `EM_SCROLLCARET` 保证光标可见。

编辑窗打开后，后续点击、方向键、`Home/End`、`Ctrl+Home/End`、`Ctrl+A`、`Shift+方向键`、双击选词都由 Windows 原生 RichEdit 处理，不自己实现。

### 4.3 结束编辑

- `Ctrl+Enter` / `Esc` / 点色带「完成」/ 点画布别处 = 提交。
- `Esc` 仍然是提交，不是丢弃；要反悔用 `Ctrl+Z`（保持现有语义）。
- 编辑中再点文本工具格 = 提交（触摸屏没有 Ctrl+Enter）。

### 4.4 编辑模式

**不加下划线、加粗、斜体这些按钮。** 理由：

- 渲染层已经支持 Markdown：`**粗体**`、`*斜体*`、`` `代码` ``、`#` 标题、`-` 列表、`$...$` 公式、代码块；
- 编辑窗里显示 Markdown 源码，提交后按 Markdown 渲染，符合“简单文本框 + Markdown”的定位；
- 后期主要对接 AI，不需要维护一套富文本 run/选区格式；
- 加富文本会把“文本内容”从纯字符串变成 run 列表，存档、复制、AI 输入全部要跟着改，收益不成正比。

## 五、空文本：任何普通文本框，内容为空就消失

### 5.1 “空”的定义

- `string.IsNullOrWhiteSpace` 为 true；
- 额外把零宽字符（`\u200B`、`\uFEFF`）当空白；
- 全是换行、空格、制表符 = 空；
- Markdown 分隔线 `---` 不算空（它渲染出来是一条线，有内容）；
- AI 题卡不受影响（`Role != Normal` 不参与）。

### 5.2 删除时机

编辑结束（提交）时统一判断：

| 场景 | 行为 |
|---|---|
| 新建后没输入 | 删除，不留撤销记录（和现在一样） |
| 老文本框内容被清空 | **删除整个文本框**，记一步撤销 |
| 老文本框只剩一个空格 | 同上 |
| 撤销“清空导致的删除” | 恢复文本框，并恢复**编辑前的文字**（不是恢复一个空框） |
| 打开旧文件时遇到空文本框 | 建议顺手清掉（无撤销），避免历史空框继续留着 |

### 5.3 撤销语义

现有空框删除只处理“新建”，是因为新建时还没内容可恢复。老框被清空时，不能只把空框删掉了事——用户按 `Ctrl+Z` 应该回到“清空之前那一整段文字”。因此实现上要先把编辑前的文字/尺寸/位置恢复回对象，再走 `RemoveStrokeWithUndo`，这样撤销栈里是一条“删除”，撤销回来就是原文。

## 六、色带与字号

### 6.1 颜色：2 个常用色 + 1 个当前色

不要再摆 8 个色片。文本色带只显示：

1. **黑**
2. **红**
3. **当前色**（如果当前色不是黑/红才出现；深色板上默认是白，所以第三格就是白）

规则和画笔一致：

- 点未选中的色片 = 切到那个颜色；
- 点**已经选中的色片** = 打开取色板，自定义这个颜色；
- 取色板复用画笔那套（HSV + 常用色 + 最近 + 色值），只是把“写回笔的色位”改成“写回文字颜色”；
- 不再给文本单独做一套 40 色常驻色带。

这样既满足“常用只要红/黑”，又保留“像画笔一样自定义”的入口。

### 6.2 字号：直接选，不要 A−/A+

把右端改成一颗按钮：

```
[ 15 ▾ ]
```

点开一个 4×3 的字号网格：

`10 12 14 16`  
`18 20 24 28`  
`32 36 48 64`

- 当前字号高亮；
- 点一个数字立即生效；
- 选中文本框时显示该框字号，没选中时显示“下一次默认字号”；
- 保留 8–72 的合法范围；
- 不再保留 A−/A+，但引擎里的 `AdjustTextFont(delta)` 可以留着给键盘/自检用。

## 七、入口：「更多」里不再放文本框

文本框是**工具**，不是“插入动作”。和画笔、荧光笔、激光笔、橡皮擦一样：

- 主条有格子且钉住 → 从主条进；
- 极简档没这一格 → 就是没有，不去「更多」补；
- 自定义档没钉住 → 就是没有，不去「更多」补。

需要删掉的代码：

- `FullUi.TextBoxInMore`
- `HubCount` 里的 `TextBoxInMore ? 6 : 5`
- `HubTileCode` 里的 `TextBoxTileCode`
- `HubTileInfo` 的 `TextBoxTileCode` 文案
- `ActivateHub` 的 `TextBoxTileCode` 分支
- 自检里“未钉住时更多保留文本入口”那条，改成“更多里不再出现文本入口”

> ⚠ 这和 `AGENTS.md` 第 1 条“功能不得因为图标少而消失，必须在更多/设置里有兜底入口”冲突。
> 建议把规则改成：**工具类（笔/荧光笔/激光/橡皮/文本）不设兜底；动作类和内容类（保存、打开、收藏、AI）必须有兜底。**
> 否则文本框特殊，和“同一套逻辑”矛盾。

## 八、改动清单（按依赖顺序）

1. **引擎：尺寸状态**
   - `TextBoxData.FitToContent`：普通文本框始终保留 `AutoHeight=true`，不再“超过最大高度就固定高 + 滚动”。
   - `EndTextBoxEditFromUi`：提交时只关 `AutoWidth`，不再关 `AutoHeight`。
   - `InkSerializer`：普通文本框读档一律 `AutoHeight=true`（老文件里存的固定高按新规则迁移成自动高）；只有 AI 题卡保留自己的固定高/滚动。

## 九、验收矩阵

| 场景 | 期望 |
|---|---|
| 新建后直接点别处 | 空框消失，不留对象 |
| 老框全选删除后点别处 | 框消失；`Ctrl+Z` 恢复原文字 |
| 老框只留一个空格 | 框消失 |
| 输入一行短文字 | 宽贴内容，高一行 |
| 拖宽后继续输入 | 宽不变，高变高 |
| 文本框被选中 | 只有左右两条整高竖线，没有上下/四角手柄 |
| 超长文本框（比屏幕还高） | 左右竖线任意一段都能拖宽，不用去找中点 |
| 拖上下边 | 没有反应（普通文本框不允许改高） |
| 选中后双指捏合 | 画布缩放；文本框字号不变，位置/宽高不被捏 |
| 固定宽后把内容删短 | 高自动变矮，不留空白 |
| 内容多到超过一屏 | 框继续向下长；没有内部滚动条；滚的是画布 |
| 选择工具双击第 3 行 | 编辑窗打开，光标在第 3 行点击处 |
| 文本工具单击第 3 行 | 直接进入编辑，光标在第 3 行 |
| 改字号 | 行高和高度跟着变；宽度不变 |
| 完整 / 自定义 / 极简档 | 「更多」里都不出现文本框 |
| AI 题卡 | 保留自己的固定高/滚动，以上逻辑不生效 |
| 老文件 | 能打开；普通文本框读进来统一转成自动高 |

## 十、方案状态

1. **高度（本次建议，待确认）**：一律自动，教师不能拖高；普通文本框没有内部滚动，长文本滚画布。
2. **宽度（已同意）**：第一次输入自动、提交后固定；老师可以左右拖宽。
3. **空框删除的撤销（已同意）**：老框清空后删除，`Ctrl+Z` 恢复“清空前的文字”。
4. **颜色（已同意）**：“黑 / 红 / 当前色”最多 3 格 + 取色板。
5. **字号（已同意）**：`[15 ▾]` + 4×3 字号网格，不要 A−/A+。
6. **编辑模式（已同意）**：不加下划线/加粗，保留 Markdown。
7. **入口（已同意）**：「更多」里不再放文本框；文本框按工具类处理。
8. **左右手柄（本次建议）**：普通文本框只保留左右两条整高竖线，整条线都能拖宽；超长文本框也不用找中点。
9. **双指缩放（本次建议）**：双指永远缩放画布，不缩放单个文本框；字号只从字号按钮改，避免和字体大小打架。
10. **整套参照（本次建议）**：以 Excalidraw 的文本对象模型为主，Figma/PowerPoint 只补“拖宽后宽度固定、高度自动”的规则。

高度、整高竖线、双指缩放这三项确认后，按第八节顺序开工：先做尺寸/空文本，再做光标定位，最后做色带和字号。
