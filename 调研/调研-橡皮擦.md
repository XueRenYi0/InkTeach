# 橡皮擦调研与实现

> 2026-09-15。回答四件事：**我们现在有什么橡皮**、**还缺哪一个**、
> **Direct2D 本身支不支持橡皮擦**、以及**我们这次怎么做的**。
> 代码在 `src/InkEngine/Model.cs`（切段 + 撤销）、`Engine.cs`（工具与落点）、
> `Overlay.cs`（落点绘制）；自检 `--pixelerasetest`。

---

## 一、我们现在有什么（盘点）

回退之后（2026-09-14 那次"两种橡皮全部退回"），仓库里**只剩一种**橡皮：

| 有的 | 代码 | 行为 |
|---|---|---|
| **整笔橡皮**（`Ctrl+Alt+4`，工具名"橡皮擦"） | `Model.EraseAt` + `Engine.EraseAlongPath` | 圆环落点，半径 22 逻辑像素；**碰到哪一条就整条删**；沿路径插值，快划不漏；整段拖拽 = 一步撤销 |
| 手写笔**笔尾** | `Engine` 读 `PEN_FLAG_INVERTED` | 反向笔尖自动当上面的整笔橡皮用 |
| 清空 | `Ctrl+Alt+C` | 不是橡皮，但老师真正想"擦掉一大片"时是它的替代品 |

所以现状是：**只有"笔画级"一种擦除**。这在课堂上有两个具体的痛：

1. **改一个字要重写一整行。** 板书是一行连笔写下来的，一个字写错了，整笔删掉就
   得整行重写——老师不会这么干，他会放弃改，让错字留在屏幕上。
2. **圈错了、画歪了的那一笔**也一样：只能整条删，于是只能重画。

## 二、还需要哪一个：像素橡皮

行业里叫法不一，指的是同一件事：**擦掉墨的一部分，一笔被切成两段**。

| 档 | 语义 | 我们的状态 |
|---|---|---|
| (a) 整笔橡皮 | 碰到就整条删 | **已有**（`Ctrl+Alt+4`） |
| (b) **像素橡皮** | 擦到哪块掉哪块，一笔切成两段 | **这次新加**（`Ctrl+Alt+7`） |
| (c) 只擦荧光笔 | 只吃荧光笔，不动笔迹 | **不做**，见第六节 |
| (d) 区域框删 | 拖一个框，框里的整条删掉 | **不做**：框选 + `Delete` 已经能做同一件事 |

**为什么是 (b) 而不是 (d)**：(d) 是"整笔删"的批量化，解决不了"改一个字"；而 (b)
是唯一能改局部的一档。(c) 在 GoodNotes 那种"荧光笔永远垫在墨迹下面"的模型里才必要，
我们的荧光笔就是一条普通笔画（同一个列表、同一个 z 序），整笔橡皮和像素橡皮都能擦它，
所以先不做——**多一个工具就多一个要记的键、多一份要测的分支**。

## 三、同行是怎么做的

同一件事，各家的分档和落点形状都不一样。下面这张表的来源分两类：
**能核对的官方文档**（给了链接）和**产品行为**（打开软件就能看到，写在这里作为对照）。

| 产品 | 有几档 | 部分擦除？ | 落点/形状 | 结论（对我们有用的那一条） |
|---|---|---|---|---|
| **WPF `InkCanvas`**（微软） | 两档：`EraseByPoint` / `EraseByStroke` | **有**：官方定义 `EraseByPoint` = "erases **part of** a stroke when the pen intersects the stroke" | 有 `EraserShape` 属性（例子里给的是 `EllipseStylusShape(5,5)`），橡皮形状**直接决定光标形状** | 微软自己的墨迹控件就是"两档都给你"，而且**落点形状是可配的**——我们做矩形落点是这条思路的正统延续 |
| **UWP `InkToolbar` / `InkPresenter`**（微软） | 一档 | **没有**：官方原文 "An ink stroke touched by the eraser stroke is **deleted in its entirety**, not just the portion under the erase stroke" | 默认 2×2 像素的橡皮笔迹 | 微软**最新**的那套墨迹栈反而只有整笔删。想要部分擦除，**得自己实现**——这就是我们正在做的事 |
| **GoodNotes 5/6** | 三档：完整擦除 / 精细擦除 / 只擦荧光笔 | **有**（精细擦除） | 落点是可调大小的方块 | "精细擦除"就是用户嘴里"擦掉像素"的那个东西；第三档存在的原因见第二节(c) |
| **Notability** | 两档：完整 / 精确 | **有** | 小方块 | 同 GoodNotes，但把"只擦荧光笔"合进精确档 |
| **Xournal++** | 多档（README 原文："Eraser with **multiple configurations**"） | **有**（标准橡皮擦掉一部分 / 还有"整笔擦"模式） | 可配 | 开源实现里最接近我们这套对象模型的一家：它也是"中心线 + 切成段" |
| **OneNote / Microsoft Whiteboard** | 一档（多档粗细） | **没有** | 方块 | 被吐槽最多的地方，也说明"整笔删"对一个要改错字的老师不够用 |
| **Direct2D `ID2D1Ink`** | —— | **没有** | —— | 见下一节：它只管画，不管擦 |

## 四、Direct2D 本身支持橡皮擦吗？

**没有"橡皮擦"这个对象，但它给了三块能做橡皮的积木；而 Windows Ink 那一层有橡皮，
只是只有整笔删。** 逐条说：

### 4.1 Direct2D 没有橡皮擦 API

- `ID2D1Ink`（D2D 自带的墨迹绘制，`d2d1_3.h`）"represents a single continuous stroke of
  variable-width ink"。它的成员只有 `AddSegments` / `GetSegmentCount` / `GetSegments` /
  `RemoveSegmentsAtEnd` / `SetSegmentAtEnd` / `SetSegments` / `SetStartPoint` / `GetBounds` /
  `StreamAsGeometry`——**一个 erase 都没有**。它能做的只有"画"和"取出几何"。
  我们也没用它（我们的几何是 `CreatePathGeometry` + `DrawGeometry`）。

### 4.2 能做橡皮的两块积木

| 积木 | 怎么做橡皮 | 代价 |
|---|---|---|
| **几何布尔**：`ID2D1Geometry::CombineWithGeometry(..., D2D1_COMBINE_MODE_EXCLUDE, ...)` | "笔画轮廓 − 橡皮形状"拿到一个**挖了洞的轮廓** | 结果是**一块轮廓**，不再是中心线：顶点编辑、压感、存档（我们存的是点列）全都对它失效；而且它不便宜，拖动时每帧做会卡 |
| **合成模式**：`D2D1_COMPOSITE_MODE_DESTINATION_OUT`（配合 `DrawImage` / 层） | 在一张**位图**上"擦掉"像素，`Clear` 透明也算这一类 | 只有"整层位图"的模型才吃这一套。我们对每个对象是矢量记录，擦完还是想要"这段笔迹"这条**数据**，不是一堆像素 |

### 4.3 Windows Ink 那一层有橡皮，能调，但不合用

`InkCanvas.EditingMode = EraseByPoint / EraseByStroke`、UWP 的
`InkToolbarEraserButton` + `InkPresenter.StrokesErased` 都是现成的橡皮，**可以直接调**。
但不合用的理由很硬：

1. **它的橡皮只有整笔删**（官方原文见上表）——正是我们要绕开的那件事；
2. **它管的是它自己的墨迹对象**（`InkStroke`）。接进来意味着把笔迹的所有权交出去，
   我们的变换/撤销/分块缓存/存档都得围着它改——这笔账在
   [调研-压感数据与墨迹预测.md](调研-压感数据与墨迹预测.md) 第 617 行已经算过一次；
3. 部分擦除只有 **WPF** 的 `InkCanvas` 有，那是 .NET Framework 那一代的东西。

### 4.4 我们的结论

**用 D2D 的原生描边画（不变），橡皮自己按中心线切段。** 理由：

- 切完还是"一条笔迹"（点列 + 宽度 + 颜色），**其他功能一个都不用改**：命中测试、
  框选、变换、存档、分块缓存全都照旧吃它；
- 这正是 WPF `InkCanvas.EraseByPoint` 干的事，也是 Xournal++ 干的事；
- 几何布尔那条路要新加一种"轮廓对象"，代价和风险都比它换来的收益大。
  （真要做"抠出任意形状的洞"再说，那是一个独立的功能。）

## 五、这次怎么实现的

### 5.1 切在哪：按**墨迹轮廓**切，不是按中心线

橡皮范围 = **矩形 ⊕ 半个笔宽**（Minkowski 和，转角是圆的，用"点到矩形的距离 ≤ 半笔宽"
正好表达）。中心线一离开这个范围就收口。

为什么不能用"中心线出了矩形就收口"：笔迹是圆头端帽的，中心线停在框边上，
**半个圆头还戳在框里**——屏幕上就是"框里剩半个笔尖"。按轮廓切，切点落在
"矩形 ⊕ 半笔宽"的边界上，端帽正好和框边**相切**，框里干干净净。自检里那条
"框里不留墨（切口在边界外）"量的就是这个：左段右端必须 ≤ `cx-halfW-半笔宽`。

> 顺带一个实测抓到的 bug：二分求切点时，**进框**（端点在里）和**出框**（端点在里→外）
> 两个方向的收敛方向是反的。第一版只按"a 在框外"写，出框那一刀收敛到了框内那个
> 采样点上——每条的右半边都多留一截墨。自检的两条判据当场红，改成方向无关的二分。

### 5.2 谁会被切

| 对象 | 像素橡皮怎么处理 | 为什么 |
|---|---|---|
| 笔迹 / 荧光笔 | **切成两段**（可能切成更多段） | 这就是这个工具 |
| 直线 / 箭头 / 矩形 / 椭圆 | 碰到**整条删** | 切成碎线段没有意义，用户也没法再拖它的顶点 |
| 图像（截图 / 粘贴的图） | **不碰** | 那是老师截来的内容；擦掉半张截图不是任何人想要的。要删它用框选 + `Delete` |

"图形碰到"按**轮廓**判（`Stroke.ShapeOutline`），不是按外框：一个画得很大的圆，
外框矩形的正中间是空的——按外框判会出现"橡皮从圆心划过，整个圆没了"。
自检里专门有一条："橡皮从大图形正中间划过 → 不删"。

### 5.3 撤销：一次拖拽 = 一步，而且位置不会错

一次拖拽里会切好几条、每条切成好几段，撤销必须**一步回到拖之前**。麻烦在下标：
前面擦掉几笔，后面几条在列表里的下标就全变了，**撤销那一刻按登记的下标插回去就会错位**
（甚至把同一截墨插两遍）。

解法是**不记下标，记"排在这一笔前面的、没被本批动过的笔画有几条"**
（`SplitStrokesAction.Item.UnaffectedBefore`）：

- 这个数在整个拖拽过程中**恒定**（没被本批动过的笔画永远不动）；
- 撤销时先把本批涉及的全部拿出来，剩下的正好就是这些"没动过的"，按这个数插回去，
  位置和顺序都对；
- 还有一条：本批自己刚切出来的碎片又被擦到，要**并回原来那一条**记录，
  不能另开一条（否则撤销时那截碎片的"上一版"会被放回来，屏幕上多出一截墨）。

### 5.4 落点：竖着的黄金比例矩形 + 半透明

```
宽 93 × 高 150 逻辑像素（高 : 宽 = 1.618），Ctrl+Alt+6 在 46 / 93 / 150 三档之间切
```

| 决定 | 理由 |
|---|---|
| **竖着**（高 > 宽） | 用户实测（2026-09-14 记在快捷键总表里）："这个巨型橡皮擦要换成竖着的"。实际用法是**从上往下抹一段**（一列板书、一个竖排的字），不是横扫一行 |
| **黄金比例** | 用户定的；比随意定 1:2 或 1:1.5 好记——"它该多高"有一个唯一答案，不用每次纠结 |
| **半透明填充 + 双色描边 + 中心十字** | 填充要**看得见"这一块会被擦掉"**，同时**底下的字还得看得见**（太实会挡住要擦的东西）；白外圈 + 深内圈是这笔迹工具里通行的做法，深色 PPT 和白色白板上都看得见；中心十字是因为投影上写字手会抖 |
| **光标画矩形，不画圆环** | 落点是什么形状就画什么形状。画成圆等于告诉用户一个错的形状（WPF 的 `EraserShape` 也是这个道理） |
| **沿路径插值**（步长 = 短边的一半） | 和整笔橡皮同一个理由：只测最新那一点，快划就会在两次采样之间漏掉一整段 |

### 5.5 实测：一步 7.7 ms，比整笔橡皮还快

一万笔的极端画面（`--report`，25 步拖动取平均）：

| | 一步耗时 | 拆开看 | 每步重画几块 |
|---|---|---|---|
| 整笔橡皮（圆环，半径 22 逻辑像素） | 10.60 ms | 删除 + 重画 | —— |
| **像素橡皮（93×150 竖矩形）** | **7.67 ms** | **擦除本身 4.93 ms + 重画 2.74 ms** | **4.0 块** |

橡皮比整笔橡皮大 8 倍多，为什么反而更快？因为**脏区标得准**。这里踩过一个坑，
值得记下来：

> 第一版是 27.4 ms/步，其中重画 22 ms、**每步重画 11.3 块**——而橡皮明明只盖住 2~4 块。
> 原因有两层：
>   ① `RemoveStroke` / `InsertStroke` 默认按**整条笔画的包围盒**标脏；
>   ② 提交动作时 `Commit` 又按 `AffectedUnion`（动过的所有对象的包围盒并集）标了一遍。
>
> 可是切段这件事**框外的墨一点没变**（同一批点、同一个画布坐标、同样的颜色和宽度），
> 缓存里框外那些块完全有效。改成"这个动作自己上报真实重画范围"
> （`SplitStrokesAction.Paint`）之后，重画的块数直接等于橡皮盖住的块数：
> **11.3 块 → 4.0 块，27.4 ms → 7.7 ms**。
>
> 教训不是"要优化"，而是**脏区的粒度不该由对象的形状决定，该由"这次到底改了什么"决定**。
> （撤销/重做仍然按整条标脏——那里保守是对的，慢一点无所谓。）

顺带一提：命中判定也从"每个候选 `IndexOf` 一遍"改成了"扫一遍笔画列表，
一次同时算出下标和处理顺序"，那是 27 ms 里另一块（5 ms 左右）。

## 六、没做的（明确记下来，免得以后当成 bug 报）

| 没做 | 为什么 | 什么时候值得做 |
|---|---|---|
| 只擦荧光笔 | 我们的荧光笔就是普通笔画，没有"垫在墨迹下面"的模型 | 等真的加了"荧光笔永远在下层"再说 |
| 更小的"点擦"档 | 细的像素橡皮 = 笔尖环，和"圈错了想擦一点点"是同一个需求，但多一档就多一个要记的键 | 老师实际用起来觉得 46 还是太大时 |
| 图像局部擦除 | 要引入位图 + 蒙版层，还要解决存档格式 | 明确要"擦掉截图里的一块"时（那更像图像编辑） |
| 压感参与擦除 | 擦除和压感无关 | 不做 |
| 擦除动画/音效 | 不解决任何问题 | 不做 |

## 七、自检（`--pixelerasetest`，15 条判据）

功能用例不靠肉眼，靠"合成输入 + 数屏幕上墨的像素"。像素橡皮这一条：

| 判据 | 量什么 |
|---|---|
| 落点是竖着的黄金比例矩形 | 93×150，高:宽 = 1.618 |
| 落点反馈是矩形 + 系统光标藏起来 | `DrawnCursor == Rect`、`ComputeCursorKind() == Hidden` |
| 一条被切成两段 | 笔画数 1 → 2 |
| 一次擦除只算一步撤销 | 撤销栈 +1 |
| **框里不留墨（切口在边界外）** | 左段右端 ≤ `cx-半宽-半笔宽`，右段左端 ≥ `cx+半宽+半笔宽` |
| 没有一段的中心线伸进框里 | 逐点扫（不只是端点） |
| 撤销回到原来那一条 | 同一个对象引用 + 点数不变 |
| 重做又回到两段 | 笔画数 2，且原对象不在列表里 |
| 框里的整条被擦掉、框外的不动 | 剩下那条**引用相同**（重建过就说明白扔了几何缓存） |
| 撤销把整条放回来（含原顺序） | 顺序 + 引用 |
| 图形的轮廓碰到 → 整条删 | 矩形两条竖边穿过橡皮 |
| **橡皮从大图形正中间划过 → 不删** | 外框相交但轮廓离 370 像素（防的是"按外框判"） |
| 拖拽扫过 5 条 = 一步撤销 | 撤销栈 +1，笔画数 5 → 10 |
| 撤销后逐条回到拖之前 | 条数 + 顺序 + 原对象 |
| **上屏**：框里的墨归零、框外的还在 | 真实像素：画上 26389 → 框里 0、框外 6795 |

（最后一条还带一个**全带对照**：擦完 24232 像素 ≈ 26389 减去被擦掉的那一段——
专门防"脏区标小了，远处的墨被吃掉"。）

```powershell

pwsh -File tools/bench/Run-FuncSuite.ps1 -Only 橡皮

dotnet run --project src/InkTeach -c Release -- --cursorshow 像素橡皮
# 自己抓屏存两张图（擦之前 / 擦之后），不用外部截图工具
dotnet run --project src/InkTeach -c Release -- --pixeleraseshow
#   → reports/像素橡皮-1-落点与擦之前.bmp

```

## 八、更优算法：对象 + 擦除区间表（同日追加，**已实现**）

> **2026-09-15 最终定稿的语义**（用户拍板）："橡皮擦中墨迹或者图形，如果断开了结构，
> 选中分开以后单独算"。所以现在的做法是**两者合起来**：
> **拖拽过程中用区间表**（一趟里同一笔被擦十几刀也不新建对象，便宜、不 churn），
> **松手时一次性把剩下的每一段落成独立对象**（各自能选中、能搬、能单独删），
> 图形被擦到先**熔成笔迹**再走同一条路。
> 代价（用户明确接受）：半透明荧光笔擦断后，两截互相穿过处会各画一次 → 交叠处变深
> （实测差 0 → 56）。
> 实测（一万笔、25 步一次完整拖拽）：**每步 7.2 ms**（擦除本身 2.8 + 重画 4.4），
> **松手结账 20 ms（一次性）**；整笔橡皮同位置 9.7 ms/步。

> 上面这套已经能用、也够快（一步 7.7 ms）。但"拆成新对象"这个做法有**一处会看得见
> 的代价**，是这次专门量出来的。结论：**换成"一条笔迹记住自己被擦掉了哪些参数区间"**
> ——已按 Xournal++ 的 `ErasableStroke` 思路实现，实测数据见 8.9。

### 8.1 先说原理，再说它软在哪

一句话：**笔迹是"中心线点列 + 一个宽度"，我们做的事是"把中心线上落在橡皮范围里的
参数区间减掉，剩下的连续段各自成为新对象"。**

```
判定：点到"橡皮矩形"的距离 ≤ 半笔宽  →  这个采样点在橡皮里（矩形 ⊕ 圆笔头）
切点：在跨越边界的那一段上二分 20 次（距离沿线段是凸的，必收敛）
结果：剩下的每一段 → 一个新建的 Stroke（画布坐标 + 单位变换，样式继承）
```

它软在三处，都能量：

### 8.2 实测一：切一刀会破坏"自交不变深"（新发现，硬数据）

半透明的荧光笔（alpha 0.32）自己穿过自己时，**一次 `DrawGeometry` 只混合一次**，
所以交叠处不会变深——这是 `--selfcross` 一直守着的性质。但把一条笔迹**拆成两个对象**
之后就是两次混合：

| | 交叠处 | 普通处 | 差 |
|---|---|---|---|
| 切之前（1 个对象） | (252,239,182) | (252,239,182) | **0** |
| 在别处切一刀后（2 个对象） | (253,231,135) | (252,239,182) | **56** |

量法：新的 `--eraseselfcross`（**离屏渲染 + 读回像素**，不看屏幕）。

> 为什么不用抓屏量：这次正好踩到——抓屏在锁屏 / 远程会话 / 被别的窗口盖住时，
> 拍到的是桌面壁纸。第一版探针就"量"出了两个几乎一样的颜色差 0，看着像通过，
> 其实两处拍到的都是壁纸。所以这里改成离屏，什么时候跑都一样。

影响面说清楚：**手写体一般不会自己穿过自己，但荧光笔涂抹、圈画、来回划很常见**；
而且它只在"切口把互相重叠的两股墨分到了不同碎片"时才出现。所以不是"橡皮擦错了"，
是"橡皮擦把一个原本不显眼的渲染前提给破坏了"。

### 8.3 实测二：对象会越擦越多

一万笔的压力画面里，25 步拖动一共切到 3123 笔——**每切一刀就多一个对象**，
每个新对象都要建几何、进空间网格、占撤销栈。同一笔被反复擦 N 次就是 N+1 个对象。

### 8.4 实测三：切点是二分出来的，精度过剩

20 次迭代把区间缩到百万分之一，而屏幕上一个像素是 1。12 次就够了（误差 ~0.02 像素），
能省掉"擦除本身 4.93 ms"里的一部分。要更快就上解析解（线段 ∩ 圆角矩形直接求交），
但收益远小于 8.2/8.3 那两条要解决的问题。

### 8.5 同行怎么解：Xournal++ 的 `ErasableStroke`

开源实现里最接近我们这套模型的是 Xournal++，它的做法值得直接沿用：

```cpp
// src/core/model/eraser/ErasableStroke.h
// "A stroke which is temporary used if you erase a part.
//  This class remembers which sections of a stroke have not yet been erased,
//  until the eraser sequence is concluded."
using SubSection = Interval<PathParameter>;
UnionOfIntervals<PathParameter> remainingSections{};   // 还没被擦掉的参数区间
std::vector<std::unique_ptr<Stroke>> getStrokes() const; // 擦完才生成新笔画
```

两个关键点：

1. **擦的过程中用"参数区间"表示，不当场拆对象**；一趟擦完才 `getStrokes()` 生成新笔画；
2. 它专门有一个 `addOverlapsToRange(...)`：**算"剩下的子段之间在哪儿重叠"并把那些区域
   加进重画范围**，注释里明说这是给 **highlighter（荧光笔）** 用的——说明
   "切开之后自相重叠"这件事，他们也撞上过，处理办法是"至少别留残影"。

### 8.6 我们该走的路：对象 + 擦除区间表

把"拆对象"换成"**一条笔迹记住自己被擦掉了哪些参数区间**"：

```
Stroke { 点列, 宽度, 颜色, 变换, 擦除区间表 List<(t0,t1)> }   // 按参数排好、相邻合并
渲染  ：按区间表把剩下的段拼成**一条多子路径的 geometry**，一次 DrawGeometry
擦除  ：往区间表里插一段（二分定位 + 合并）
撤销  ：把这一段从表里删掉
命中  ：跳过落在被擦区间里的那几段
```

它一次解决 8.2 和 8.3：

| 好处 | 为什么 |
|---|---|
| **自交不再变深** | 剩下的段在**同一个 geometry、同一次 DrawGeometry** 里 —— 回到"一次混合" |
| **对象不再爆炸** | 反复擦同一笔，对象数恒为 1；网格、撤销栈、选中框都不受影响 |
| **身份不变** | 对象的 `Id` 不换，选中/变换/复制粘贴的行为完全不变（现在切开后是"换了个对象"） |
| **撤销变轻** | 撤销 = 删一个区间，不是"删掉 N 个碎片、还原 1 个原对象" |
| **变换更正确** | 区间记在**参数**上，与变换无关；现在切开时要把变换烘进画布坐标（非等比缩放下线宽会有偏差） |

代价（要认）：

- 几何缓存的重建频率变高（区间一变就得重拼一条 path），但那条 path 的 figure 数
  和"拆成的对象数"是同一个量级，总代价不增；
- 命中测试要跳过被擦区间（仍是 O(点数)）；
- 存档格式要加一段区间表（升到 v4，旧档照常读）；
- 区间表很长时（被反复擦很多次）单条几何的 figure 数变多，需要"相邻/重叠区间合并"兜住。

**动手前要验的一条**：多子路径单几何是否真的只混合一次。8.2 那张表已经给出间接证据
（同一条自身重叠的折线在**一次** DrawGeometry 下差 0），而验收标准就是
`--eraseselfcross` 改成"用区间法之后差仍为 0"。

### 8.7 也考虑过、但没选的路

| 方案 | 为什么不做 |
|---|---|
| 几何布尔 `CombineWithGeometry(EXCLUDE)` | 结果是**轮廓对象**：顶点编辑、压感、存档、命中测试全得为它另写一套。它换来的是"抠出任意形状的洞"，我们不需要 |
| 每条笔迹一张覆盖掩码（Xournal++ 的 `Mask` 思路，真·像素级擦除 / 软边 / 半透明擦除） | 能同时解决"碎片互相重叠"，但每笔要一张掩码，渲染和内存都贵一个量级。老师要的是"干净地擦掉一块"，不是 PS 式的软橡皮 |
| 把命中判定搬到 GPU | 我们的瓶颈根本不在命中判定（擦除本身 4.9 ms，其中一半是几何构建与网格维护），搬过去只增加复杂度 |

### 8.8 实现成什么样

| 位置 | 改动 |
|---|---|
| `Stroke.Erased` | 新增**擦除区间表**（参数 = 点序号，允许小数），有序、不相邻，插入即合并 |
| `Stroke.BuildCenterline` | 按区间表把剩下的段拼成**一条多子路径的 geometry**（一次 `DrawGeometry`） |
| `Stroke.DistanceTo` | 跳过被擦掉的段——否则拿橡皮点一个已经擦空的缺口会把整条删掉 |
| `InkDocument.EraseRectAt` | 不再新建对象：算出区间 → 并进表 → 整条擦没了才拿走对象 |
| `EraseIntervalsAction` | 一条记录 = 一条原本存在的笔迹，存 Before/After 两张区间表；整条被拿走的用 Anchor 记位置 |
| `InkSerializer` | 格式升到 **v4**：每条笔迹多一段区间表（没有擦除时是 4 个字节）。v1~v3 老文件照常读 |

### 8.9 实测：好处与代价（A/B，同机同状态各跑两遍）

一万笔的极端画面、25 步拖动：

| | 擦除本身 | 重画 | 每步重画 | **合计** | 跑完之后的对象数 |
|---|---|---|---|---|---|
| 拆对象（b0aed4e） | 5.6~6.2 ms | 2.5 ms | 4.0 块 / 764 笔 | 8.2~8.6 ms | 9871 → **12822（+2951）** |
| **区间表（本版）** | **2.9 ms** | 6.0~8.0 ms | 4.0 块 / 886 笔 | 8.8~10.9 ms | 9871 → **9646（−225）** |

**拿到的**：

1. **自交不变深**（这条最硬）：切一刀之后，交叠处与普通处的色差 **0**（拆对象那版是 56）。
   现在它是 `--pixelerasetest` 里的一条判据，`--eraseselfcross` 也是同一件事的独立探针。
2. **对象数不再单向增长**：拆对象时每切一刀 +1 个对象、永不回头（25 步 +2951、+32%）；
   区间表版**反而在回收**（整条被擦掉的拿走，−225）。反复擦同一笔，现在对象数恒为 1。
3. **身份不变**：`Id` 不换 → 选中、变换、复制粘贴的行为完全不受擦除影响；区间记在**参数**
   上，所以"先移动/缩放过、再擦"也不用把变换烘进坐标（拆对象那版得烘）。
4. **撤销栈轻了**：一条记录只存两张区间表（几十字节），不再挂着成百上千个碎片对象。
   仓库按"撤销栈里挂了多少条笔画"限流（`MaxUndoStrokes = 20000`），碎片会把这个额度吃掉。
5. **擦除本身快一倍**：5.9 → 2.9 ms（不新建对象、不动网格）。

**付出的**：

- 每步重画从 2.5 ms 涨到 6~8 ms —— 因为**被擦过的整条笔迹还留在文档里**（身份不变的另一面），
  它跨过的那些块都要重画，每步要画的笔数从 764 涨到 886。这一项是"身份/回收"换来
  "重画范围更保守"的代价，**不是几何构建**（把几何提前建好再计时，重画仍是 5.8 ms）。
- 合计：8.2~8.6 → 8.8~10.9 ms。**极端画面上略慢一点**（同一台机器上整笔橡皮也在 10~12 ms
  波动，所以这个差距在噪声量级），但换来上面五条。

> 想再往前一步的话，出路是"**给渲染用的墨迹包围盒**"：让索引/分块按"剩下的墨"算，
> 而不是按整条的原始范围算（现在为了保守，整条的范围照旧）。那会把重画笔数压回去，
> 代价是每次擦除要重插一次网格。**这次没做**：收益是几毫秒，风险是碰到命中测试与分块
> 缓存这两处最容易出事的地方。

### 8.10 顺带修掉的两件事（这次就改了）

1. `--selfcross` 的探针位置是错的：它探的是相对 `(200, 0)`，而**真正的交点在
   `(161.7, 20.9)`**（两段中心线联立解出来的；推导留在 `EraseSelfCrossProbe` 里）。
   差这 40 像素，探到的地方只有一股墨，两边颜色当然一样——**那条判据一直是空的**。

2. `--selfcross` 增加了"看得见墨吗"的守卫：抓屏拍不到我们这层时明确打 `SKIP`，
