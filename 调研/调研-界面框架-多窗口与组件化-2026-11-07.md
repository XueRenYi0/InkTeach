## 〇、结论先行

1. **不引通用 UI 框架。** Avalonia / WinUI 3 / WPF 都会把 +100～250 MB
   和"第二个渲染器"带回来，和"低端 4 GB 保持现有基线"直接冲突；
   Dear ImGui 的中文 IME、观感和无障碍不适合老师端。
2. **抽一层"应用界面框架"，不是"通用控件库"。**
   范围封死：**3 类界面壳 + 4 种布局 + 12 个控件 + 1 套文字输入 + 1 套设置表单**；
   不做数据绑定、不做可视化设计器、不做跨平台、不做主题市场。
3. **两条渲染轨**：
   - **D2D 自绘**：工具条、色带、收藏/图形面板、画布周边、预览；
   - **原生控件**：设置、表单、简单对话框、文字输入。
     `EDIT / RichEdit / BUTTON / COMBOBOX / TRACKBAR / LISTVIEW` 的
     **中文 IME、选区、撤销、剪贴板、无障碍**是白拿的，不要自己重写。
4. **"屏幕优先，真窗口后置"**：先把"模式 / 页面 / 面板"的壳和组合件做出来；
   真正的多顶层窗口（独立白板窗、独立 PDF 窗）等确认需要再加 `WindowHost`。
   现在的文档模式（PDF/图片）本来就是覆盖层里的一个模式，不是独立窗口。
5. **先做文字输入服务，再做组合件。** 现在有 **9 组**各自手写的原生输入窗，
   统一它们是投入产出比最高、风险最低的第一步（3～5 天）。

## 一、现状盘点（用数字说话）

| 项 | 现状 | 代价 |
|---|---|---|
| 窗口 | 每个显示器一个覆盖层：`WS_EX_TOPMOST｜TOOLWINDOW｜NOACTIVATE｜NOREDIRECTIONBITMAP`，`WS_POPUP`（`Overlay.cs:961`） | 没有"正常窗口"壳：可缩放、最小化、任务栏、标题栏都要另写 |
| 界面主类 | `FullUi.cs` **6996 行 / 420 KB**，工具条 + 色带 + 设置 + 收藏 + 更多 + AI 菜单都在里面 | 每加一个面板都往一个类里塞；改一处容易碰另一处 |
| 控件层 | `Widgets.cs` **112 行**（文字 / 色片 / 分段选择 / 滑条） | 没有布局、没有焦点、没有滚动、没有列表虚拟化 |
| 设计令牌 | `Tokens.cs` 339 行 | 这一块是好的，继续用 |
| 界面契约 | `Ui.cs` 1165 行（`IOverlayUi` / `IUiHost` / `IEngineCommands`） | 只服务"一个覆盖层"，没有"页面 / 窗口"概念 |
| 设置 | `Row[]` 行表 16 行、7 个分类（`FullUi.cs:357`、`:3821`） | 已经是表驱动，**缺的不是 schema，是通用控件与表单壳** |
| 收藏 | 已有分类、回收站、拖放；四态（0/1/多/溢出）是项目硬规则（AGENTS §4） | 列表/滚动容器不可复用；100+ 条目缺虚拟化；每加一个内容面板还要重写一套 |

| 文档模式 | PDF/图片是覆盖层里的一个模式（`计划-文档模式-状态模型.md`） | 不是独立窗口；以后要独立窗才需要 `WindowHost` |

## 二、需求拆解：六类界面各自要什么

| 界面 | 形态 | 必须具备 | 现在缺 |
|---|---|---|---|
| 工具条 / 色带 | 覆盖层浮层 | 自绘、动画、命中、穿透下可点 | 组合件复用（现在手写） |
| 白板 | 覆盖层模式（或未来独立窗） | 页面、缩放/平移、底纹、页码条 | 屏幕壳、页面/缩略图组件 |
| PDF / 文档 | 覆盖层模式 | 页源、翻页、连续滚动、批注层 | 同白板 + 页缩略图 / 虚拟列表 |
| 设置 | 浮层内页面（或独立对话框） | 分类、行表、开关/滑条/下拉/输入、校验、搜索 | 表单壳、通用控件、校验 |
| 收藏 / 图形 | 浮层弹窗 | 0/1/多/溢出、滚动/分页、拖放、多选、回收站 | 虚拟列表、可复用滚动容器 |
| 文字输入 | 横切服务 | 中文 IME、光标、选区、剪贴板、撤销、提交/取消 | **统一服务**（9 组重复） |

### 2.1 哪些能力是共享的

- 窗口 / 屏幕的生命周期、DPI、主题、动画时钟；
- 布局（测量 / 排列 / 滚动 / 裁剪）；
- 输入路由（指针 / 滚轮 / 键盘 / 焦点 / 捕获 / 悬停）；
- 弹层（锚点、层序、Esc / 点外关闭、焦点陷阱）；
- 列表（0 / 1 / 多 / 溢出、虚拟化、拖放、多选）；
- 文字输入（原生宿主 + IME + 校验）；
- 自检（截图 + 脚本输入 + 像素断言）。

**这些共享能力就是"框架"；具体某个面板的画法不是。**

## 三、候选方案对比

| 方案 | 适配我们 | 首版速度 | 空闲内存 | 中文 / IME | 与 D2D 共存 | 主要风险 | 结论 |
|---|---|---|---|---|---|---|---|
| **A. 自研薄框架（D2D + 原生表单）** | 高 | 中 | **+0** | 原生控件最好 | 同一套窗口 / 设备 | 范围蔓延、自维护 | **推荐** |
| B. Avalonia 12（只做设置 / 侧窗） | 中 | 快 | +100～200 MB | 好 | 第二个渲染器（Skia） | 双栈、DPI、层序、包体 | 备选，不做主 UI |
| C. WinUI 3 / XAML Islands | 低 | 中 | +100～250 MB + 运行时 | 好 | 内容岛 / 空域问题 | 部署重、启动慢、复杂度高 | 不推荐 |
| D. WPF + XAML | 低 | 快 | **+148 MB（我们实测）** | 好 | 两个 topmost 窗抢层序 | 每点 +1.4 ms | 不推荐（已有实测） |
| E. Dear ImGui / Hexa.NET.ImGui | 低（老师端） | 快（工具） | 小 | **IME 弱、CJK 字体要自己做** | D3D11 独立后端 | 观感、无障碍、文本编辑差 | 只做内部调试工具 |
| F. WebView2 / Sciter | 低 | 快 | +200～500 MB | 好 | 独立浏览器栈 | 内存、离线、视觉一致性 | 不推荐 |
| G. 纯原生 Win32 控件 + D2D | 高（表单） | 中 | +0 | 最好 | 子窗空域要管 | 观感旧、DPI 要自己处理 | **作为表单轨** |
| H. 维持现状（继续堆 FullUi） | 短期高 | 快 | +0 | 各写各的 | 无 | 7000 行继续长、重复代码 | 不推荐长期 |

> 说明：A 和 G 不是二选一，**推荐架构就是 A + G**：
> 画布周边用 D2D 自绘，设置/表单/文字用原生控件，
> 两者共用 Tokens、输入路由、弹层和自检。

### 3.1 为什么不上 Avalonia（唯一值得认真考虑的备选）

- Avalonia 的 `NativeControlHost` 是"**把 Win32 控件嵌进 Avalonia**"，
  不是"把 Avalonia 嵌进我们的 Win32 覆盖层"——方向反了；
- 一旦用 Avalonia 做设置窗，它就是**第二个渲染器 + 第二套 DPI/输入/主题**，
  和现有 D2D 界面只共享颜色值；
- 社区报告的空闲内存从 100 MB 到 200 MB 不等，长时间运行还会涨；
  我们的目标是 4 GB 教室机，这笔账不划算；
- 唯一值得保留的场景：**设置窗复杂到自研表单扛不住，且能接受 +100 MB**，
  这时可以做一个**独立进程**的 Avalonia 设置器，主进程不加载它。
  这是"用钱换时间"，不是"用架构换时间"。

### 3.2 为什么不上 WinUI 3 / XAML Islands

- XAML Islands 到 2026 年仍在维护，但它是"在 Win32/WPF/WinForms 里嵌 WinUI 控件"，
  需要 Windows App SDK 运行时；self-contained 部署官方明确写"更大、启动更慢、内存更多"；
- 内容岛的空域、焦点、DPI、层序问题，和我们在覆盖层里已经解决的问题**不是同一套**；
- 只为了设置页引入一整套 XAML 运行时，收益不抵成本。

### 3.3 为什么 ImGui 只配做内部工具

- 中文 IME 在 ImGui 里一直是"能用但坑多"：候选窗位置、组合串、输入法切换、
  不同后端行为不一致；老师端不能拿这个冒险；
- 没有原生无障碍、文本编辑弱、观感是"开发者工具"；
- 但它的即时模式、零依赖、自带控件，非常适合**内部调试面板 / 性能 HUD / 自检工具**，
  这部分可以单独评估，不影响产品 UI。

## 四、推荐架构：一层薄框架，两条渲染轨

```
src/InkEngine/                 核心：文档、输入、渲染、工具状态（不动）
      ↕  IOverlayUi / IUiHost / IEngineCommands（现有契约）
src/InkUi/                     产品界面层（现有 FullUi 逐步迁移）
  ├─ Framework/                新：薄框架（不引用 InkEngine）
  │    Shell/                  ScreenHost（模式/页面）、WindowHost（可选真窗口）
  │    Surface/                D2D 覆盖层 / 不透明窗口 / 子区域
  │    Layout/                 Stack / Dock / Grid / Scroll
  │    Input/                  指针、键盘、焦点、捕获、滚轮、IME 路由
  │    Popup/                  锚点、层序、Esc/点外关闭、焦点陷阱
  │    Widgets/                按钮、图标按钮、开关、复选、滑条、下拉、
  │                            色片、标签、卡片、标签页、滚动条、提示
  │    Text/                   TextEditHost（原生 EDIT/RichEdit 桥）
  │    Forms/                  FormBuilder + 字段/校验/行布局
  │    Patterns/               DocumentScreen、PanelScreen、SettingsPage、TextInput
  ├─ FullUi.cs                 现有界面（先保持，按面板逐步迁移）
  └─ Screens/                  新屏幕（白板 / 文档 / 设置 / 收藏）按模板建
```

### 4.1 关键设计

**① 屏幕（Screen）优先，真窗口（Window）后置**

- `ScreenHost` 管"当前是哪个模式/页面"：白板、PPT、文档、设置、收藏；
  进入/退出、输入作用域、动画、返回栈；
- 现有的 `IOverlayUi` 保持不变；`ScreenHost` 是 `IOverlayUi` 内部的一层；
- `WindowHost` 只在"确实需要独立顶层窗"时加：可缩放、最小化、任务栏、
  自己的 D2D swap chain。它和覆盖层共用 `UiSurface` 抽象，页面代码不感知。

**② 元素树：保留模式，允许"整块自绘"**

- `UiElement`：`Measure / Arrange / Render / HitTest`；
- 容器：`Stack`（横/竖）、`Dock`（上下左右）、`Grid`（行列）、`Scroll`；
- 迁移期允许一个 `CustomElement` 包住现有 `FullUi` 的一段绘制代码——
  **不要求一次改成控件树**；
- 布局只在失效时重算；渲染只画脏区；空闲零帧。

**③ 输入路由：一套，不做第二套**

- 指针：按下 → 捕获 → 移动 → 抬起；悬停单独一条；
- 键盘：焦点元素、Tab 顺序、Esc/Enter、快捷键；
- IME：文字输入统一走 `TextEditHost`，不让自绘控件自己处理组合串；
- 穿透：命中测试先问界面矩形，再决定穿不穿（现有 `UiBoundsLogicalContains` 已有）。

**④ 弹层：一个 PopupLayer**

- 锚点、层序、裁剪、Esc / 点外关闭、焦点陷阱、嵌套弹层；
- 收藏、图形、更多、下拉、提示都走同一套；
- 现有"点收藏不切换、不展开色带"的规则继续由业务层决定，弹层只负责显示。

**⑤ 文字输入：`TextEditHost` 是横切服务**

- 一个可激活的 `TOOLWINDOW` 宿主 + 子 `EDIT` / `RICHEDIT50W`；
- 单行 / 多行 / 富文本三种模式；
- 统一：定位、字体、DPI、IME、`WM_CHAR`、回车/Esc、失焦提交、撤销、剪贴板；
- 调用方只给：矩形、初始文本、模式、校验、提交/取消回调；
- 画布文本框继续用 RichEdit，但宿主生命周期由这个服务管。

**⑥ 设置：`FormBuilder` + 字段描述**

现有 `Row[]` 行表已经解决了"同一份名单只写一处"，不要推翻；
在它上面加一层"字段类型 + 校验 + 布局"：

```
字段类型：Toggle / Slider / Select / Text / Number / Color / Path / Button
字段描述：Key、Label、Hint、Default、Range、Validator、RestartRequired、VisibleWhen
页面描述：Category、Title、Rows、SearchKeywords
```

这样新增一个设置项 = 一行描述，而不是"画 + 命中 + 存取 + 自检"四份代码。
复杂的设置页（AI 服务）仍可整块自定义，不强求全部表驱动。

**⑦ 模板：以后开新界面照抄**

| 模板 | 产出 | 必须覆盖 |
|---|---|---|
| `DocumentScreen` | 白板 / PDF 共用的屏幕壳 | 标题栏、页源、翻页、缩放、关闭、自动保存 |
| `PanelScreen` | 收藏 / 图形 / 更多 | 0 / 1 / 多 / 溢出、滚动、拖放、Esc |
| `SettingsPage` | 一个设置分类 | 分类导航、行表、校验、搜索、恢复默认 |
| `TextInput` | 一个输入场景 | 单行/多行、IME、校验、提交/取消 |
| `SelfTest` | 一条 `--xxshow` | 截图、脚本输入、像素断言、失败信息 |

## 五、成熟参考：照搬什么、不照搬什么

按项目规矩（先找成熟参考，再按需改），逐项对应：

| 参考 | 版本 / 来源 | 照搬 | 不照搬 | 我们的差异 |
|---|---|---|---|---|
| **WPF 布局** | .NET / MIT | `Measure / Arrange`、父给约束、子报尺寸 | XAML、依赖属性、数据绑定 | 只做 4 种容器，不做通用布局系统 |
| **Avalonia** | 12.x / MIT | 输入路由、焦点、文本框、`NativeControlHost` 的边界思路 | 整个运行时、Skia、XAML | 不引入第二个渲染器 |
| **Flutter** | BSD | "约束向下、尺寸向上"的布局模型 | Widget/Element/Render 三层全套 | 只借模型，不借引擎 |
| **Qt QWidget** | LGPL / 商业 | 父子树、焦点链、布局器 | 信号槽、QML | 不引入 C++ |
| **Chromium Views** | BSD | View 树、布局管理器、焦点/捕获 | 整套 Views | 只借结构 |
| **WinUI SettingsCard / Expander** | MIT / 微软设计 | 设置行的视觉与信息层级（标题、说明、右侧控件） | WinUI 运行时 | 用 Tokens 复刻观感 |
| **VS Code settings** | MIT | "schema 驱动设置 + 搜索 + 默认值" | JSONC 编辑器、扩展体系 | 只做表单，不做配置编辑器 |
| **Win32 RichEdit / TSF** | 系统 | 文本编辑、IME、撤销、剪贴板 | 自研文本引擎 | 原生宿主 + 统一服务 |
| **UI Automation** | 系统 | 表单/按钮的 Name/Role/Value | 全量自绘控件的 UIA | 原生表单优先，自绘只做最小集 |
| **Dear ImGui** | MIT | 即时模式调试面板 | 产品 UI | 只用于内部工具 |

## 六、分阶段计划（每阶段都能单独验收）

### 方案 2（推荐）：最小框架，3～5 周

| 阶段 | 内容 | 工期 | 验收 |
|---|---|---|---|
| P1 | `TextEditHost` 统一 9 组输入窗，先替换 3 处试点（重命名 / 计时器 / AI 提示词） | 3～5 天 | 微软拼音 + 搜狗输入中文；光标/选区/复制粘贴/撤销；100/150/200% DPI；失焦提交；截图 |
| P2 | `ScreenHost` + `Stack/Dock/Scroll` + 8 个基础控件；先做"设置 → 常规"一页 | 1～2 周 | 0/1/多/溢出；键盘 Tab/Esc/Enter；空闲 0 帧；单帧 ≤2 ms（4 GB 机） |
| P3 | `FormBuilder` + 设置 schema；迁移设置全部分类 | 1 周 | 新增一项只改一行描述；校验/重启提示；搜索；截图 |
| P4 | 模板 + 文档 + 自检脚手架 | 3～5 天 | 新开一个 `SettingsPage` / `PanelScreen` 照模板 1 天内跑通 |

> 这个包**不包含**真窗口、虚拟列表、收藏迁移、白板/PDF 重构。
> 它解决的是"设置 + 文字输入 + 新面板"这三件最常做的事。

### 方案 3（完整）：8～12 周

在方案 2 之上加：

| 阶段 | 内容 | 工期 |
|---|---|---|
| P5 | 虚拟列表 + 拖放 + 多选；收藏 / 图形迁移 | 1～2 周 |
| P6 | `WindowHost`（不透明窗口、DXGI swap chain、resize、DPI、设备丢失） | 1～2 周 |
| P7 | 白板 / PDF 屏幕壳与页缩略图 | 2～3 周 |
| P8 | 无障碍（表单 UIA、键盘、高对比）、组件画廊、文档收尾 | 1 周 |

### 方案 1（最小）：只统一文字输入，1 周

- 只做 `TextEditHost`，不动布局/控件/窗口；
- 适合"现在不想投入框架，但受够了 9 套输入窗"的情况；
- 缺点：设置页和收藏仍然继续长在 FullUi 里。

### 方案 4（备选）：Avalonia 只做设置窗，2～3 周

- 独立进程 / 独立窗口，主进程不加载 Avalonia；
- 优点：表单、校验、键盘、无障碍白拿；
- 代价：+100～200 MB、第二个安装包、设置生效要走 IPC / 文件重载；
- 只在"设置复杂度失控 + 能接受内存"时选。

## 七、风险与可能的问题（全方位）

| # | 风险 | 表现 | 概率 / 影响 | 缓解 |
|---|---|---|---|---|
| 1 | **框架蔓延** | 从"薄框架"长成通用控件库，半年做不完 | 高 / 高 | 范围封死：3 壳、4 布局、12 控件；新需求先问"能不能用现有组合" |
| 2 | **两套 UI 长期并存** | FullUi 和新框架各画一套，观感/行为分叉 | 中 / 高 | 共用 Tokens；新界面必须用新框架；旧面板按季度迁移，不无限期双轨 |
| 3 | **中文 IME** | 组合串丢字、候选窗位置错、失焦不提交 | 高 / 高 | 只用原生 `EDIT/RichEdit`；微软拼音 + 搜狗 + QQ 拼音手测；覆盖层 `NOACTIVATE` 下必须走可激活宿主 |
| 4 | **焦点 / 键盘** | Tab 乱跳、Esc 不关、回车误提交 | 中 / 中 | 焦点作用域、Tab 顺序、Esc/Enter 语义写成表；每条自检 |
| 5 | **多显示器 DPI** | 拖到副屏后字体/控件变小或错位 | 中 / 高 | `WM_DPICHANGED` 重排；每个窗口独立 DPI；100/150/200% 三档截图 |
| 6 | **空域（airspace）** | 原生控件盖住 D2D 内容，滚动时露馅 | 中 / 中 | 原生控件只放表单窗；滚动/裁剪时隐藏；混合窗用分区布局 |
| 7 | **D2D 设备丢失** | 切换显卡/睡眠后新窗口空白 | 中 / 高 | 统一 `UiSurface` 重建；沿用覆盖层现有的设备丢失处理 |
| 8 | **低端机性能** | 布局/绘制每帧重算，4 GB 机掉帧 | 高 / 高 | 只在失效时布局；零分配；单帧 ≤2 ms；每阶段跑低端机 |
| 9 | **内存** | 每个窗口一张大位图 / 多个 D2D 目标 | 中 / 中 | 同进程共享 factory/device；关闭即释放；窗口位图按客户区大小 |
| 10 | **迁移回归** | 设置/收藏搬一半，行为变了 | 高 / 高 | 绞杀者模式：旧代码保留到新实现通过同一套自检；一次只搬一个面板 |
| 11 | **无障碍** | 自绘按钮读屏读不出、键盘不可达 | 中 / 中 | 表单走原生；自绘只做最小 UIA（Name/Role/Value）+ 键盘 |
| 12 | **测试成本** | 每个窗口都要截图/脚本，越写越慢 | 高 / 中 | 模板自带 `SelfTest`；像素断言只测关键区域；共用测试宿主 |
| 13 | **设计一致性** | 新控件和旧界面两种圆角/字重 | 中 / 中 | 组件画廊页；Tokens 单一来源；新控件必须过画廊 |
| 14 | **过度抽象** | 为"以后可能用到"做了一堆没人用的能力 | 中 / 高 | 只按 3 个真实界面（设置/收藏/文档）设计，不为假想需求写 |
| 15 | **人手 / 维护** | 只有一个人，框架和产品抢时间 | 高 / 高 | 分阶段、每阶段可停；先做收益最高的 TextEditHost |

## 八、验收指标（写死，避免"感觉快了"）

| 维度 | 指标 |
|---|---|
| 空闲 | 界面静止时 0 帧；不因为框架常驻出帧 |
| 单帧 | 4 GB 目标机，界面帧 ≤ **2 ms**；输入→上屏不劣化 |
| 布局 | 只在尺寸/内容/DPI 变化时重算；不在 Render 里改布局 |
| 内存 | 新开一个普通设置/文档窗 ≤ **+40 MB**；关闭即还 |
| 文字 | 微软拼音 / 搜狗输入中文不丢字；候选窗跟随光标；复制/粘贴/撤销正常 |
| DPI | 100 / 150 / 200%；跨屏拖动不缩不错位 |
| 列表 | 100+ 条目滚动流畅；0/1/多/溢出四态齐全 |
| 键盘 | Tab / Shift+Tab / Esc / Enter 全可达；焦点可见 |
| 自检 | 每个新界面至少一条截图自检 + 一条脚本输入断言 |
| 依赖 | 不新增 >5 MB 的运行时依赖；不引入第二个渲染器 |

## 九、不做什么（明确写死）

- 不做通用控件库 / 可视化设计器 / 数据绑定 / 跨平台 / 主题市场；
- 不做自研文本编辑器 / TSF / 输入法；
- 不把工具条搬进新框架（先保持，避免动最稳的那块）；
- 不重写 `FullUi`（按面板迁移，旧代码保留到新实现通过自检）；
- 不引 Avalonia / WinUI 3 / WPF / WebView2 / ImGui 作为主 UI；
- 不为"以后可能的多文档"提前做多文档架构（先确认是不是真的需要）。

## 十、需要拍板的点

1. **"窗口"指什么？**
   - A. 现有覆盖层里的"屏幕/页面"（白板、文档、设置、收藏）→ 先做 `ScreenHost`；
   - B. 真正的多顶层窗口（可最小化、进任务栏、可并排）→ 才需要 `WindowHost`。
   建议：**先 A，B 等确认**。
2. **同时只开一个文档，还是多文档？**
   建议先"一个文档、多个视图"；多文档会牵动 `InkEngine` 的 `Doc` 单例模型，
   是另一个量级的改造。
3. **设置用原生控件还是 D2D 自绘？**
   建议：**原生控件 + Tokens 统一观感**；D2D 只做预览区。
4. **无障碍做到哪一档？**
   建议：键盘 + 高对比 + 表单 UIA；自绘工具条只做最小 Name/Role。
5. **投入哪一档？**
   - 方案 1：1 周，只统一文字输入；
   - **方案 2：3～5 周，最小框架（推荐先做）；**
   - 方案 3：8～12 周，完整框架；
   - 方案 4：2～3 周 + 100～200 MB，Avalonia 只做设置。
