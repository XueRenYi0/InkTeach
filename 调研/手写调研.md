# 手写调研

日期：2026-10-08　　性质：可行性评估（底层是否换成 WinUI 3 的 `InkCanvas` / `InkToolbar`）
核对方式：微软官方文档与 Windows App SDK 发布页（2026-10-08 当日核对）；本仓库既有调研文档与代码路径逐处核对。

---

## 一、问题

有人提出：UI 与输入层改用 WinUI 3 的 `InkCanvas` 和 `InkToolbar` 作为基础控件。
理由是 `InkCanvas` 本身就是一块透明覆盖层，非常适合批注场景。
问题：现有手写批注软件的底层换成这个"最新方案"，可行性如何？

## 二、结论

**作为"整体换底层"不可行（三处硬阻断，任一单独成立即足以否决）；
作为"局部借鉴"有三项值得马上做。**
与 [对标-微软墨迹栈与我们的架构.md](对标-微软墨迹栈与我们的架构.md) 第四、五节结论一致；
本文件把外部事实更新到 2026-10-08，并给出落地的借鉴清单。

## 三、外部事实核对（2026-10-08）

| 项 | 当日状态 |
|---|---|
| WinUI 3 墨迹三件套 | 仍在 **Experimental 通道**：`2.5.4-experimental` 含 `InkCanvas` / `InkToolbar` / `InkPresenter`；最新稳定 `2.5.1`（2026-09-16）**不含** |
| 控件形态 | 未变：XAML 控件，只能画在自己的窗口里；没有穿透、没有桌面级透明覆盖形态 |
| 实验版本新增能力 | 笔与触摸输入、笔迹输入、未处理输入、剪贴板、高对比度支持——是"控件内能力"，不是"窗口形态" |
| 社区绕路 | smourier/WinUI3Ink（单文件移植，稳定通道可跑，无 `InkToolbar`，需自维护）；UWP `InkCanvas` 走 XAML Islands（castorix 样例，legacy 路线） |

> 注：上一版 [对标] 文档写的是"稳定通道 2.4.0 还没包含"；截至今天，2.5.1 稳定版同样不包含，
> 结论不变，只是版本号前移。

## 四、三条硬阻断

1. **形态冲突（产品立足点）**：我们的产品是 Win32 无边框置顶透明覆盖层
   （`WS_EX_NOREDIRECTIONBITMAP` + DirectComposition），要盖在 PPT、网页、任意程序之上批注，
   并支持穿透。`InkCanvas` 是 XAML 控件，只能画在自己的窗口里；`InkPresenter` 也没有穿透模式。
   换过去等于放弃"盖住任意程序"这个产品根基。
2. **宿主与合成代价**：换控件 = 换整个 UI / 窗口 / 合成栈（WinUI 3 + Windows App SDK）。
   我们会丢掉：自控的帧配速（`DwmFlush` + `Present(0)`）、画布分块缓存与脏区、
   笔迹+26 种图形+图像共用的统一对象模型（选中框、变换、撤销、存档）。
   内存基线对照：WinUI 3 约 120~250 MB；我们 20 分钟板书实测 96~167 MB（提交/显存区间）。
3. **API 押注风险**：实验通道 API 可能变更、移除或长期不转正；用实验通道等于把产品的
   输入与湿墨管线押在可能变动的接口上（社区已有因此无法上架商店的先例）。

## 五、"系统墨迹到底好多少"——可选实验（不进产品）

如果想亲手量一次差距，可以做一个**独立原型**（单独窗口的 WinUI 3 程序，
`2.5.4-experimental` 或 smourier 移植版均可），不进产品、不引依赖：

- 同一支笔、同一组动作：慢速细线 / 快速画圆 / 网格对位 / 压感斜坡；
- 指标：端到端延迟、快速画圆的折线率、细线抖动、CPU 与显存占用；
- 产出归档到本目录；**明确标注为实验，不作为产品路线**。

## 六、值得立即做的借鉴（不动架构）

1. **形状识别（画完再纠正）**：WinRT `InkAnalyzer` 可被普通桌面进程调用，无需 XAML 宿主；
   本仓库 `tools/InkAnalyzerProbe` 已在验证这条通道。补的是"画完再纠正"，
   与现有"画的当下吸附"互补。
2. **ISF 互通（只做剪贴板一步）**：拷给 Word / OneNote / PPT 的是可编辑墨迹而不是一张图。
   原理与成本见 [调研-ISF互通原理.md](调研-ISF互通原理.md)。
3. **手感与姿态**：手感四项（反折／平滑／分配／预测）与倾角/旋转落地（侧锋、笔尖朝向、
   铅笔排线），以及手掌抑制（P0）。见
   [计划-底层手感-四项（反折-平滑-分配-预测）.md](计划-底层手感-四项（反折-平滑-分配-预测）.md)
   与 [对标-微软墨迹栈与我们的架构.md](对标-微软墨迹栈与我们的架构.md) 第五节、第七节。

## 七、决策

保持"自绘引擎 + 覆盖层"的底层不变；需要系统能力时按需接入（识别、ISF），
不引入 WinUI 3 宿主。等 WinUI 3 墨迹**进入稳定通道**且**支持透明覆盖层形态**这两件事同时成立，
再回来重估整体换栈。

## 八、"独立通道"与阻塞风险（补充 2026-10-08；**10-10 按 10-05 实测定案更正**）

先纠正一个前提：**系统的低延迟墨迹通道不是 InkCanvas 的专属功能。**
它是 DirectComposition 的公共接口 `IDCompositionDelegatedInkTrail`（我们已接入；⚠ 2026-10-05 真笔实测**本机不渲染**，见下），
把湿墨交给 DWM 合成器、在独立于应用主线程的轨道上画——这就是"独立通道"。
现状（10-10 更正）：**真笔实线也并没有走成这条通道**——本机系统不渲染委托轨迹（10-05 实测：喂点全成功、屏幕无墨），**真笔 / 鼠标 / 触摸 / 虚线四条路的湿墨实况都是我们自绘**（合成边界配速，上屏 1.0 帧）。
（见 [延时-实测与优化.md](延时-实测与优化.md) §八 与 [对标-微软墨迹栈与我们的架构.md](对标-微软墨迹栈与我们的架构.md) 3.2 节）

| 场景 | 湿墨谁画 | 主线程卡顿时会不会顿 |
|---|---|---|
| 真笔实线 | ~~DWM 合成器（独立通道）~~ → **我们自绘**（本机轨迹不渲染，10-10 更正） | 会——靠配速把上屏压到 1.0 帧、每帧代价低，实测不构成阻塞 |
| 鼠标 / 触摸 / 虚线 | 我们自己（主线程每帧） | 会（与真笔同一暴露面） |
| 干墨光栅（落笔之后） | 我们自己（单线程） | 实测密集页 1.35 ms、每帧 1.7~1.9 ms；60 Hz 预算 16.7 ms，余量大 |

结论（按 10-05 更正后重估）：**仍然不会"容易阻塞"**——但理由变了：四条路都靠自绘，
风险面比原文更大；好在配速后上屏 1.0 帧、书写期每帧代价 1.7~1.9 ms（60 Hz 预算 16.7 ms）、
GC 低延迟档常开，实测不构成阻塞。要再加固，三条（都不动架构、不依赖 WinUI）：

1. **扩通道适用面**：实验鼠标/触摸实线接 `AddTrailPoints` 的效果与限制
   （整条单色、圆头、无虚线——虚线/荧光笔仍不适用）；
2. **光栅线程化**：干墨分块光栅移出主循环（见 [对标] 第六节"光栅是单线程"）；
3. **重活调度**：截图、导入、整层重铺等大宗操作切片执行，不与书写争主线程。
   换任何 UI 框架都不改变这一点——WinUI 应用的主线程同样会被应用自己的重活卡住，
   InkCanvas 并不是"主线程卡顿"的通用解药。
