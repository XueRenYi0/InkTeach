# 调研：预测尾（B4）的原理与注意点

日期：2026-10-08　　状态：**研究稿（不写码）** —— 两个真机故障的原理已解剖，修法清单见 §五；**等用户拍板再动手**。

> **背景**：v8.11.0（预测尾默认开）暴露两个真机现象——
> ① **"拖端点飘出第二条线段"**（鼠标：停顿变直线 → 手不松继续转圈 → 多出一条线段**慢慢长回"变直线时的原始位置点"**、**松手即消失**）；
> ② **"快写急转偶发跳一下"**（学校大屏 + 手写板）。
>
> 算法与参数证据见既有两份，本文不重复：**`调研-压感与预测-原理.md`**（模型、失效条款、真实数据扫参）、
> **`调研-压感数据与墨迹预测.md`**（微软/安卓/开源方案盘点、设备差异）。
> 本文只补：**这两个故障的原理级解剖 + "以后做预测必须盯住什么"的清单**。

---

## 〇、三句话

1. 两个毛病**都不是"预测算法不够好"**：一个是**状态归属**（换笔没清），一个是**失效边界**（急转门槛 + 回收速率）。
2. 借鉴别人**可以，而且一直在借**（现在这套就是 Chromium 那族）；但"换用别人的算法"**一个坑都躲不掉**——
   他们的实现同样靠一圈**工程规矩**撑着（只在接触时预测、单笔限制、失效重置、真实数据一到就替换预测）。
3. 结论：**先把规矩立全、自检补齐，再谈升级模型**。升级拐点 = "直线/缓弯都已经干净、唯独复杂笔势不满意"（现在还没到）。

---

## 一、原理速览（为什么要有尾、尾是什么）

- 屏幕一帧不可压（60Hz=16.7ms）：只画"已经收到的点"，墨永远落后笔尖 **≥1 帧**。
  预测 = 把"这一帧之后笔尖大概会在哪"也算出来一起画，让**墨的末端回到"现在"**。
- 我们的预测**只做"显示尾"**（B4）：独立几何、每帧重建、**不进文档/不进命中/不进撤销/不进存档**；
  长度按"像素限速"平滑（**伸 ~2.2px/帧、收 ~1.2px/帧**，防"笔头跳跃"）。
- 安卓官方文档把规矩的核心一句话说透了（AndroidX `MotionEventPredictor`）：
  > **预测数据是估计值；真实数据一到，预测就必须被替换掉。**
  （"Predicted data must be replaced with actual MotionEvent data once it is received."）
- 历史数据也说明"模型不是瓶颈"：我们用 48.7 万真实采样点扫过参数——阻尼 0.8 之下，
  二阶线性外推 10ms 地平线能吃掉 **~58%** 的滞后；**速度平滑反而降精度**（0.7 平滑掉到 37%）。
  "再聪明的模型"换来的边际收益，远小于把状态和边界管干净。

## 二、故障①："拖端点飘出第二条线段" = 状态归属错误（已定案）

时间线（鼠标、一按到底）：

| 时刻 | 发生了什么 | 预测器状态 |
|---|---|---|
| 画线中 | 自由笔迹逐点喂预测器（`_predictor.Add`） | 跟着手绘走 ✓ |
| **停顿 → 变直线** | `ActiveStroke` 从手绘**换成图形**；预测器**没有复位** | **留在"旧笔迹"的末点/速度** ✗ |
| 手不松、转圈拖端点 | 每帧 `UpdatePredictTail`：offset = 预测点 − **图形当前末点** = "图形末端 → 旧原点"的整段矢量；长度按 2.2px/帧**慢慢长过去** | 一直用旧状态 ✗ |
| 松手 | 收笔，`ActiveStroke` 清空 → 尾整个消失 | — |

- 用户描述**逐字吻合**："多出来的那条会慢慢回到变直线的原始位置点"（= 尾按限速长回旧原点）、"松手以后就消失了"（= 收笔清尾）。
- 照片里的"Λ" = **真线 + 这条错位尾**；胶囊"α=38.5° 长 524"是**真线**的正常读数。
- **原理级病灶：状态归属**。预测器（记着"上一笔"）与"当前活笔"（已经换人）**脱钩**。
- 为什么以前没露头：预测尾 8.11.0 才默认开；**"尾巴 × 停顿成型拖端点"**这个交叠场景从未被测过
  （DwellProbe 只查角度/长度**数值**，不查"这一帧该不该画尾"）。
- **教训（升级为规矩，注意点①）**：
  > 凡"**每帧读上一笔/活笔状态**"的子系统（预测尾、系统墨迹轨迹、读数锚点……），
  > 在**任何换笔路径**（起笔、收笔、**停顿成型**、图形工具接管、取消/丢捕获）都必须**清或接管**。
  > 换笔路径要**枚举**，一条条挂复位 + 自检断言。

## 三、故障②："急转跳一下" = 失效边界太松（原理拆解）

三个因素叠加，**都在我们自己的实现里，不在别人的模型里**：

1. **门槛太松**：目前只在**完全反向**（转角 >90°，点积 <0）时丢速度；
   60~90° 的急转**不丢**，继续按旧速度+平滑方向外推 → 旧方向多伸一小截。
2. **失效时旧偏移不清**：`Predict` 返回 0 时，`_tailOffsets` 仍是上一帧的（方向 = 旧方向），
   尾巴照旧按旧方向画。
3. **回收太慢**：把尾巴收回只有 1.2px/帧（90Hz≈108px/s）一条速率 → 残留要十几帧才缩完，
   看起来就是"跳/甩一下"。

**这是公认难点，不是一个实现没做好**（旁证）：

| 出处 | 为"急转"做的事 |
|---|---|
| Chromium 线性预测器 | 反向检测丢速度 + 预测硬上限 25ms（"超过会抖/方向错乱"） |
| AOSP `MotionPredictor` | 输出改用**极坐标（r, φ）**——急转时比笛卡尔坐标稳；另带 jerk 跟踪 + 定间隔重采样 |
| （2024~25 专利，三星等） | 训练目标直接以**角度误差**为主（"minimize angular error"）+ 极坐标 + 按"当前状态"选模型 |

**修法（待拍板，注意点②③）**：急转门槛分级（>90° 丢 + 加 ~60° 档、参数化，真机调区间 50°~75°）
+ **失效即快收**（伸出/回收速率分离：伸出保持平滑，回收几帧内完成）+ `--tailjumptest` 补"快写急转"用例。

## 四、"能借鉴别人的吗"——可以；盘点与拐点

| 方案 | 是什么 | 对我们的意义 |
|---|---|---|
| **Chromium 线性预测器** | 一阶/二阶 + 失效条款 | **就是现在这套的出处**，继续用 |
| Chromium 卡尔曼 / 最小二乘变体 | 同 repo 另两个预测器 | 对我们 10ms 级的显示尾，收益不明显、调参变多 |
| 安卓 `MotionEventPredictor`（库） | **卡尔曼滤波**实现（AndroidX；U+ 系统 API **只支持笔**） | 值得读"状态/工具判断"的写法；**架构参考** |
| AOSP `MotionPredictor`（TFLite） | 极坐标 + jerk + 连压力一起预测 | **设计值得抄**（尤其极坐标对付急转）；整包搬运 = 数量级成本 + 新依赖，暂不 |
| 1€ 滤波 | 平滑（不是预测） | 我们已按需用在速度平滑（笔 0.4 / 鼠标 0.6，是抗抖取舍，数据说明它会降"吃到"） |
| perfect-freehand / stabilizer 类 | 平滑/宽度，**不预测** | 不相关 |

**升级判据（写死在这里，免得跟风）**：
1. 先把 §五 的清单做完、三个环境（手写板 ink 开/关、学校大屏）尾巴都干净；
2. 若那时"直线/缓弯已经无感、唯独**复杂笔势**还不满意"→ 才考虑升级；
3. 升级顺序：**先抄设计**（极坐标 r/φ + 定间隔重采样 + jerk，1~2 天、无新依赖）→ 最后才考虑 TFLite（数量级成本）。
4. 别忘了：**任何模型都要配同一圈规矩**（失效、状态、替换）——AOSP 也一样，规矩漏一处就是又一个"Λ"。

## 五、注意点清单（后续实现/验收照这条查）

1. **生命周期（故障①）**：预测状态以"当前活笔"为界——起笔复位 / 收笔清 / **换笔立即复位** / 丢捕获清；
   换笔路径**枚举**（停顿成型、图形工具、取消、工具切换…），逐条挂复位 **+ 自检断言**（如：成型/拖动期间 `PredictTailActive == false`）。
2. **失效快收（故障②）**：预测无效（反向/急转/慢速/断笔/换笔）时，尾巴**几帧内收回**；
   伸出（可平滑）与回收（要快）**分开定速率**，不许"旧方向的尾巴留在屏幕上慢慢缩"。
3. **急转分级**：>90° 丢（已有）→ 增加 ~60° 档；阈值**参数化**，真机验收区间 50°~75°（学校板 + 90Hz 机各看一遍）。
4. **只画显示**（已有）：不进文档/命中/撤销/存档；颜色、宽度与笔身**同源**；短尾（<2px）不画。
5. **脏区含尾**（已有）+ **熄尾也要擦**：复位/收笔/换笔那一帧，把**旧尾所在位置**算进脏区（这次 bug 的另一半：尾"消失"那几帧的旧像素）。
6. **时钟与采样**：统一单调时钟；断笔阈值 40ms（鼠标兼容路突发间隔 ~30ms 的由来）；
   鼠标路速度平滑 0.6 / 笔路 0.4 是"抗抖 vs 精度"的**工程取舍**（有数据支撑，别忘它降吃到）。
7. **速率按时间定义，别按帧**：2.2px/帧在 90Hz=198px/s、60Hz=132px/s——**学校机观感不同**；
   实现时改成 px/ms（或按刷新率换算）。
8. **数据说话**：能扫数据的参数不猜（阻尼 0.8 的来历）；**手感最终只认真机三环境验收**。
9. **借鉴照抄规矩，不照抄公式**：先在本文档更新规矩 → 再动代码；每加一条规矩，配一条自检。
