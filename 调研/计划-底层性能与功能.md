# 底层接下来做什么：性能优化 + 功能完善

日期：2026-09-13　　状态：**待你选择路线**

本文只谈底层（`src/InkEngine/` 与它的可选层）。界面最后做。

---

## 零、这一层要变成什么

现在是"一个笔画列表 + 每笔一段带子"：能画、能整笔擦、能撤销、能上屏。

要变成**对象化的矢量批注文档**。三个概念必须钉死（沿用你已有的
《底层设计-笔迹对象模型》）：

1. **对象有身份**（稳定 Id）——撤销、多选、复制都靠它。
2. **几何与变换分离**——缩放 = 改矩阵，O(1)，几何缓存不重建。
3. **原始墨迹永远保留**——识别成图形后仍可切回，否则用户说"变错了"就没救。

守住这三条，后面加功能就是"填表格"；破掉任何一条，都会返工。

## 一、你列的功能，逐条拆开

### 1. 选中后：复制 / 移动 / 删除

| 操作 | 改什么 | 脏区 | 缓存 |
|---|---|---|---|
| 移动 | `Transform` 乘平移 | 原位置 ∪ 新位置 | 不动 |
| 复制 | 克隆、换新 Id、偏移 `Transform` | 新对象包围盒 | 新建 |
| 删除 | 从图层移除 | 各对象包围盒并集 | 释放 |

要额外定的两件事：

- **多选**：选中集合 + 一个统一包围盒。变换要围绕**选区中心**做，
  不是各自中心，否则一组东西会散开。
- **浮点误差**：每次拖拽都基于"按下时的快照变换"重算，不要在上一帧结果上
  继续乘。否则拖一百次之后会累积可见偏差。

### 2–4. 放大缩小 / 左右拉伸 / 上下拉伸 / 镜像对称

这四个是**同一套东西**，都是 `Matrix3x2`。底层只要把变换矩阵做对，
上面就是"拖动不同的手柄"。

**手柄布局**（八个 + 一个）：四角 = 自由缩放（按住 Shift 等比）；
四边中点 = 单轴拉伸（这就是你说的左右/上下拉伸）；角外侧 = 旋转。

**镜像**要处理三个坑：

1. **填充缠绕方向会翻转。** 我们的轮廓一律用 Winding 填充规则，
   镜像后不会被挖空——这一条现在就是安全的，但要写进测试。
2. **笔宽会被各向异性拉伸。** "左右拉伸"本来要的就是这个效果，
   但圆头端帽会被压成椭圆。这是特性还是缺陷，得你定（见第六节问题 3）。
3. **命中测试必须走逆变换。** 把鼠标点用 `Transform` 的逆矩阵变回局部坐标
   再测，否则镜像之后点击会左右颠倒。

**包围盒**：非等比缩放 + 镜像 + 旋转之后，不能只变换两个角点。
要变换四个角再取并集。

### 5. 图形对象，顶点可拖动（三角形这类）

> **2026-09-15 更新**：这一节的想法已经调研清楚并落成施工单——
> 调研（同行对照 / 倾斜角定义 / 手柄该给哪几个点）见 [调研-图形工具.md](调研/调研-图形工具.md)，
> 施工步骤、自检计划、界面要留的口子见 [计划-图形工具.md](计划-图形工具.md)。
> **顺序改了**：用户决定**界面先行、图形随后**（现在只有热键、没有工具条，
> 课堂上画个三角形要先背 `Ctrl+Alt+T`，不方便）。下面这段早期的设想保留作背景。

需要你设计里那个 `InkGeometry` 抽象：

| 几何类型 | 控制点 |
|---|---|
| 手写笔迹 | 无（或只给"抽稀后的拟合点"） |
| 直线 / 箭头 | 两个端点 |
| 矩形 / 椭圆 | 四角 + 中心（或包围盒） |
| **三角形 / 多边形** | **每个顶点一个** |

拖顶点 → 改图形参数 → 几何重建（**这一步缓存要失效**，和"改变换"完全不同，
两条路径不能混）。

**识别怎么接**：Windows 自带的 `InkAnalyzer` 你已经实测可用，它给
"图形类型 + 包围盒"。但它**不给可拖动的顶点**，所以顶点得自己生成：

- 简单做法：按类型把包围盒映射成正多边形（三角形 = 正三角）。
- 贴近手迹的做法：在包围盒里放好默认顶点，再把**最近的采样点吸附上去**，
  这样"变三角形"之后的样子更像用户刚画的那一笔。
- 建议先用简单做法，觉得不够像再做吸附。

### 6. 橡皮的"面积擦除"

这个词有三种讲法，代价差很多，**必须你来定**：

| 语义 | 行为 | 底层要什么 | 代价 |
|---|---|---|---|
| (a) 整笔擦 | 碰到就整笔删（**你现在就是这个**） | 已有 | 已完成 |
| (b) 区域擦 | 拖一个框/套索，把区域内**完整包含**的对象删掉 | 选区 + 包含判定 | 小 |
| (c) 精确橡皮 | 像 Photoshop 那样，擦掉的地方才算数，**一笔被切成两段** | **几何布尔运算 + 对象分裂** | 大 |

关于 (c)：我查了 Direct2D 的文档，`ID2D1Geometry::CombineWithGeometry` 支持
Union / Intersect / Xor / **Exclude**——"笔画轮廓 减去 橡皮圆"这条操作是原生的，
不用自己写算法。但有两个坑：

1. **布尔运算不便宜**（单次几十微秒到几毫秒），拖动时每帧做会卡。
   要么每移动 N 像素才切一次，要么拖动中只做视觉预览、**松手才真算**。
2. **一笔变多笔**：切开后原来的一个对象变成两个，撤销必须算作**一步**。
   而且样式要继承（颜色、宽度、变换都得复制过去）。

行业里的主流做法是**同时给两种模式**（精确橡皮 + 笔画橡皮），让用户切。

### 7. 常用功能对接系统快捷键

三档方案，安全性差很多：

| 方案 | 怎么做 | 优点 | 致命限制 |
|---|---|---|---|
| A 应用内快捷键 | 覆盖层拿到键盘焦点时处理 | 最安全，和 Word/PPT 习惯一致（Ctrl+C/V/Z/A、Delete、方向键） | 现在覆盖层是 `WS_EX_NOACTIVATE`，**根本不拿焦点**，要改 |
| B 全局热键 | `RegisterHotKey`（你现在用的） | 随时可用 | **别抢 Ctrl+C 这类键**——全局注册会让所有程序的复制都归你。而且被别的程序占了就注册失败（你已经踩过 Ctrl+Alt+W = 微信） |
| C 低级键盘钩子 | `WH_KEYBOARD_LL` | 能按条件拦截任意键（"批注模式下 Ctrl+C 才归我"） | 杀软敏感、有输入延迟、必须保持消息循环 |

**建议分层**：少数几个"切换/呼出"用全局热键；编辑类快捷键走应用内；
只有当"必须给别的程序发按键"时才用钩子。

前提是先有一个明确的**"是否处于批注模式"**状态——否则全局抢 Ctrl+C 是灾难。

## 二、你没提到、但绕不过去的

按"不做会怎样"分级。

### 必须（不做就没法用）

1. **保存与加载。** 现在关掉程序，一切归零。而**序列化会反过来约束对象模型**
   （几何必须是可重建的参数 + 点集，不能只有 GPU 资源），所以这件事越早定越好。
2. **精确的命中测试与包围盒。** 现在用"点到折线的距离"和"笔宽 × 1.45"的经验
   系数，对粗笔、缩放后的对象、镜像后的对象都会不准。Direct2D 有现成的：
   `StrokeContainsPoint`（带线宽和变换的精确命中）、`GetWidenedBounds`
   （含线宽的真实包围盒）。用它们替掉经验值，命中更准、脏区更小。
3. **撤销粒度统一。** 一次拖拽 = 一步。橡皮你已经做到了，变换、顶点拖动、
   多选操作都要这个语义。

### 应该（影响体验）

4. **对齐与吸附**：吸附到其他对象的边/中心、屏幕边缘；Shift 约束水平垂直/等比；
   Alt 从中心缩放。
5. **键盘微调**：方向键 1px，Shift+方向键 10px。
6. **锁定 / 只读对象**：背景底图不希望被误拖走。
7. **图层顺序**：置顶 / 置底 / 上移 / 下移。
8. **导出**：批注层导出 PNG（透明通道）；或者把带批注的整屏截图存下来——
   老师下课要发群里，这个是刚需。
9. **多显示器与 DPI**：对象坐标要**明确统一到虚拟桌面物理像素**，
   否则换显示器或改缩放比例后，批注会漂移。

### 可以（锦上添花）

10. **选中笔迹 → 转文字**：你明确排除过"整页手写识别"，但"选中一段 →
    识别成文字放到剪贴板"是很多老师的刚需，而且只处理一小段、不算实时预算。
    值得单独立项。
11. **录制与回放**：把书写过程录下来回放。课堂工具里这个很受欢迎。
12. **分页 / 多页白板**：一节课的板书不止一屏。
13. **触控双指**：双指缩放/平移画布（如果面向触摸一体机）。
14. **对象列表 / 大纲**：一页里有哪些对象，可以点选。

## 三、底层性能优化清单

你现在的位置（实测）：内容层缓存后每帧 0.64 ms 且**不随对象数量变化**、
结束一笔 0.57 ms、擦除一步 3.9 ms（改前 176 ms）、一万笔整层重建 166 ms。

按"收益 ÷ 代价"排序的候选：

| # | 优化 | 解决什么 | 预估收益 | 代价 |
|---|---|---|---|---|
| 1 | 精确脏区（`GetWidenedBounds`） | 经验系数 1.45 太保守，脏区偏大 | 中 | 低 |
| 2 | 精确命中（`StrokeContainsPoint`） | 粗笔、缩放后点击不准 | 中 | 低 |
| 3 | 拖动期间降精度（LOD） | 拖动/缩放预览时重建贵 | 中 | 低 |
| 4 | 静态对象合批（合并成一个几何） | 整层重建 166 ms | **大** | 中 |
| 5 | 内容层分块（tile） | 每屏一张全屏位图，多屏/4K 内存翻倍 | 大（内存） | 中高 |
| 6 | 几何缓存上限动态化 | 现在固定 4096 个 × 18 KB ≈ 72 MB | 小 | 低 |
| 7 | 书写中只补新增一段几何 | 每帧重建整条带子 | 待实测 | 中高 |
| 8 | 撤销改存反操作 | 长跑内存 | 小 | 低 |

**注意**：从你已有的数据看，**性能目前不是瓶颈**（每帧成本不随对象数增长）。
除非你有新的实测说明不是这样，否则我建议先把功能做起来，
把 1/2/3 这几个"顺手就能做"的做掉，4/5 留到真的需要时。

这个项目最大的资本是那套量化自检工具——**每条优化都应该先测再改**。

# 第二部分：定稿（2026-09-13 决定）

## 七、你拍板的七个问题

| # | 问题 | 决定 | 对底层的直接影响 |
|---|---|---|---|
| 1 | 橡皮默认行为 | **(c) 精确切开** | 需要几何布尔（Exclude）+ 对象分裂 + 样式继承 + 一步撤销 |
| 2 | 是否允许旋转 | **允许** | 命中测试必须走逆变换；包围盒要变换四个角再取并集 |
| 3 | 拉伸时笔宽 | **只变形状，线宽不变** | 拉伸不能只靠矩阵——**轮廓必须用变换后的中心线重新生成**（见下） |
| 4 | 要不要保存 | **要** | 对象模型必须可序列化，阶段 1 就要按这个设计 |
| 5 | 复制 | **系统剪贴板，粘回来还是对象不是图片** | 需要注册私有剪贴板格式；同时附带 PNG 给别的程序用 |
| 6 | 快捷键何时做 | **现在做（见 8.4）** | 命令模型属于底层，必须先有 |
| 7 | 图形识别 | **画完自动吸附** | 识别必须异步，且用"停顿"当触发信号（见 8.3） |

### 7.1 "线宽不变"的两个连带后果

这条决定比看上去影响大：

1. **几何不能只存轮廓，必须同时留着中心线。** 拉伸时要用变换后的中心线
   按**原宽度**重新生成轮廓，直接对已有轮廓做矩阵变换会把线宽也拉扁。
   → 写进阶段 1 的对象模型。
2. **拖动中与松手后要分两套。** 拖动中先用矩阵变换做近似预览（快，略微不准），
   松手时用中心线精确重建一次（准，一次性代价）。这和"预览 / 提交"那套是同一个机制。

### 7.2 "粘贴回来还是原数据"怎么做

用 `RegisterClipboardFormat` 注册一个私有格式（例如 `InkTeach.InkObjects`），
里面放**和保存文件完全一样的序列化数据**。同时再放一份 PNG 和一份 ISF/EMF。

这样同一个复制动作，粘到 Word / PPT 里是一张图，粘回批注里还是可编辑的对象。
主流软件都这么做（Excel 同时给私有格式和位图）。

**顺带的好处**：剪贴板私有格式 == 保存格式，两件事一次做完。

### 7.3 停顿变形（你观察到的那个，是对的）

你见过"一笔画完停顿一下才变形"，这不是偶然，是设计：

- **立即变形是错的**：故意画的不圆的圆、写得快的字都会被改掉。
- **停顿是明确意图信号**：抬笔后光标/笔尖原地停留约 400 ms 才触发。
- **停顿还顺便解决了性能**：识别可以放到后台线程去算，停顿正好给它留出时间预算。
  识别绝不放在抬笔的同步路径上——那会让每一笔都卡几十毫秒。
- **变形必须可还原**：原始墨迹永远保留，变形后给一个短暂的"还原"提示，
  或者直接 Ctrl+Z。误触的代价就只是一次撤销。

### 7.4 多笔变形：先不做

你的判断准确。多笔变形要"跨笔画推断意图"（四条线拼矩形），误触率高，
因为任何几笔都可能偶然构成图形。**先不做**；将来真要做，也必须是
"选中多笔 → 手动点变图形"这种显式操作，不做静默替换。

## 八、性能会不会被功能拖垮？（你最担心的问题）

### 8.1 结论

**不会——前提是守住"什么东西能进每帧路径"这条线。**

你担心的是"功能变多 → 变慢 → 还不如用 WPF"。这个担心成立的条件是
**功能进了每帧路径**。而你列的这些功能，绝大多数是**冷路径**：

| 功能 | 路径 | 对每帧成本的影响 |
|---|---|---|
| 移动 / 缩放 / 旋转 / 镜像 | 冷：改矩阵 | **零**（几何不重建） |
| 复制 / 删除 | 冷：一次性 | 零 |
| 保存 / 加载 / 剪贴板 | 冷：一次性 | 零 |
| 顶点拖动 | 冷 + 拖动预览 | 只跟"这一块"有关，与对象总数无关 |
| 形状识别 | 冷：停顿后异步 | 零（不在输入路径上） |
| 精确橡皮 | 冷 + 拖动预览 | 需要限流，见下 |

WPF 版慢**不是因为它功能多**，是因为它的底座：Visual 树 + 每帧重建
DrawingContext + `InkCanvas` 每次重算 StrokeNode + 更大的托管堆。
你自己那版 InkClass 空闲 255 MB，这套空闲 96 MB——
**差距在底座，不在功能数量**。加功能不会把这个优势吃掉。

### 8.2 真正会拖慢的三处，和对策

| 风险 | 为什么会慢 | 对策 |
|---|---|---|
| 精确橡皮的布尔运算 | 单次几十微秒~几毫秒，拖动中每帧做必卡 | 拖动中只做**视觉预览**（把橡皮圆画出来），**松手才真算**；实在要实时就每移动 N 像素切一次 |
| 自动识别的时机 | 每次抬笔同步识别 = 每笔多几十毫秒 | **停顿触发 + 后台线程**；识别结果回来再替换，输入路径完全不碰 |
| 每个对象一份独立 GPU 几何 | 对象上万时显存和提交次数都涨 | 几何资源设上限（已有 4096 机制）+ 静态对象合批（性能清单第 4 条） |

### 8.3 性能红线（写下来，以后每个功能都对照它）

| 场景 | 上限 |
|---|---|
| 空闲 | CPU ≈ 0%，不重绘 |
| 书写中 | 每帧 ≤ 2 ms，**且不随对象总数增长** |
| 编辑操作（选中/移动/缩放/旋转/镜像） | 每帧 ≤ 2 ms，几何不重建 |
| 单次重活（识别 / 布尔切开 / 保存） | **不阻塞输入**；超过 16 ms 的一律放后台线程 |
| 一万对象整层重建 | ≤ 200 ms，且只在换分辨率 / 清空这类场合发生 |

**审查规则一句话**：这条功能会不会进每帧路径？会，就想办法挪出去；
挪不出去，就明确记下代价并重新评估。

守住它的机制你已经有了：那套量化自检。**每次加完功能跑一遍，数字不许退化。**

### 8.4 快捷键：现在做，但只做一半

**现在做**，理由是：

1. 快捷键只是**编辑命令的入口**，命令模型属于底层，必须先有。
2. 没有快捷键你现在**没法测**编辑功能——总得有个办法触发缩放、镜像、复制。
3. 最重要：全局热键 vs 应用内快捷键会影响**窗口样式**（`WS_EX_NOACTIVATE`
   要不要改、要不要拿键盘焦点、输入法怎么办）。这是架构决策，早定早好。

**界面阶段做的部分**：键位提示、可视化、可配置键位表、按钮。

现在要做的部分：命令模型 + 一套开发用键位（能测就行）+ 决定全局/应用内的边界。

建议的边界（对应第一部分第 7 节）：

- **全局热键**只放"切换类"：开关批注、切换工具、穿透、清空、退出。
- **编辑类**（复制/粘贴/撤销/删除/方向键微调/Shift 约束）走应用内——
  绝不能全局注册 Ctrl+C，那会把所有程序的复制都抢走。
- 前提：先有一个明确的**"当前是否处于批注模式"**状态。

### 8.5 功能是不是有点多？——是，但可切

多，但**大部分是同一个地基上的一行**。真正需要一次性想清楚、晚了要返工的
只有三件：

1. 对象模型（Id / 变换 / 原始墨迹 / **中心线**）
2. 序列化（决定几何怎么存）
3. 坐标系归属（见第九节第 1 条——这条你可能还没定，但它影响最大）

**建议的"课堂最小可用"**（做完就能拿去上课）：

> 画 · 精确擦 · 撤销 · 选中 · 移动 · 缩放 · 旋转 · 镜像 · 复制 · 删除 ·
> 保存 · 快捷键

**可以晚一档的**：图形识别、顶点编辑、图层、吸附、锁定、导出、多页。

### 8.6 如果目标是"性能最好"，走哪条路线？

**就是路线 B**，而且这不是巧合——B 里那几条（变换独立于几何、命令 + 脏区、
预览与提交分离）**本身就是性能设计**，不是功能设计。

反过来，先做功能再补性能，才会真的返工。

唯一的取舍在橡皮和识别（8.2 那两行），而它们的对策已经定好了。
所以：**走 B，就是把性能和功能一起做对的那条路。**

## 九、你可能还漏掉的（补充清单）

### 最要紧的一条：批注"跟不跟着内容走"

现在批注画在**屏幕坐标**上。老师翻 PPT 下一页、或者滚动网页时，
批注**不会跟着动**，会留在原地——这是透明批注软件最本质的体验问题。

三种做法，必须选一个（它决定坐标系的含义）：

| 方案 | 行为 | 代价 |
|---|---|---|
| (a) 屏幕坐标（现在） | 翻页就作废，老师自己清 | 无，但体验差 |
| (b) 冻结截图模式 | 先截一屏冻结成底图，再在**图片坐标**上批注。翻页 = 换一张图 | 小，且**最稳**。你早期调研里就提过 |
| (c) 跟随下层窗口 | 真的跟 PPT 内容走 | 极大，需要知道下层是什么，基本放弃 |

**建议 (b)**。而且它和"图形对象 + 顶点编辑"是同一套坐标体系（都是图片局部坐标），
做起来互相加分。**这条要现在定**，因为它影响阶段 1 的坐标系设计。

### 其余容易漏的

2. **手掌误触**：触摸一体机上，手腕压在屏幕上会画出一堆乱线。
   靠 `WM_POINTER` 的设备类型区分笔/触摸，笔在画时忽略触摸。
3. **崩溃恢复 / 自动保存**：一节课的板书丢了，比任何性能问题都严重。
4. **文件格式版本号**：保存的文件必须带版本，否则以后改格式读不了旧文件。
5. **对象上限与降级策略**：画了五万笔之后怎么办？要有明确行为
   （提示 / 降采样 / 拒绝），不能是"越来越卡直到崩"。
6. **多显示器与投影切换**：拔插显示器、切投影分辨率时，对象怎么重新定位。
   这条和第 1 条绑定（图片坐标天然免疫）。
7. **连接型对象**（箭头连两个图形，图形动了箭头跟着动）。
   教学示意图里很常用，但它把对象模型从"独立对象"变成"有关系的对象"，
   是对象模型的一次升级。**如果以后想要，现在就要在设计里留位置**。
8. **角度捕捉**：Shift 画线锁 15° 增量；这是画示意图的刚需。
9. **导出带批注的整屏截图**：老师下课要发群里。比"导出 PNG"更常用。
10. **临时隐藏批注**：讲课时想看一眼原屏幕，按一下就隐藏、再按回来。
11. **性能档位开关**：给用户一个"流畅优先 / 画质优先"，低配机器上能自救。
12. **选中高亮的层级**：选中框/手柄要画在每帧浮动层上，**不进内容层**，
    否则每次选中都要重画内容层（第一阶段就要守住）。

## 十、阶段 1 的清单（已按你的决定更新）

阶段 1 只改数据，不改渲染，但**它是唯一一个"越晚做越贵"的阶段**：

- [x] `Id` + `Transform`（对象身份与变换）——**1-1 已完成**

- [x] 精确命中（`StrokeContainsPoint` / `FillContainsPoint`）——**1-2 已完成**，
      新增 `--shapetest` 自检，9 项全过
- [ ] `OriginalInk` + `Style`（样式分组与识别回退）——分组是排版性改动，价值中等，缓做
- [ ] 保留**中心线 + 宽度**（因为选了"线宽不变"）——跟形状编辑一起做
- [ ] 坐标系：**图片局部坐标 + 相机**（对应第九节方案 b）——相机随滚动功能一起落
- [x] 编辑命令模型：影响区域 + `TransformObjectsAction`——**1-3 已完成**
- [x] 序列化格式（带版本号）——**1-3 已完成**，同时也是剪贴板私有格式
- [x] 选中高亮不进内容层，且区域已纳入每帧脏区——1-3 顺带修掉一个残留 bug

### 10.1 一项刻意没做：精确脏区

计划里原写"用 `GetWidenedBounds` 替掉 1.45 那个经验系数"。实际算了一下，
**收益接近零**：那个系数让脏区多外扩 `(1.45-1.4) × 笔宽 / 2`，
24 像素的粗笔也只有 **0.6 像素**；而 3 像素的笔完全看不出来。
而脏区现在只占整屏的 0.1~1%，本来就不是瓶颈。

所以决定**不做**：保留解析式外扩（零成本、保守但足够），
把精确 API 用在真正需要它的地方——命中测试（1-2 已做）。

（`Bounds` → `WorldBounds` 那套变换是精确的，因为它只是把矩形按矩阵变换，
不涉及"笔宽到底画到哪儿"。）

### 10.2 一个测量纪律

1-2 之后复测"每帧记录"，单次跑出 1.27 ms（历史 0.96），看着像退化。
连跑三次得到 **1.42 / 1.16 / 0.76**——同一份代码波动 ±40%。

**结论：这个指标不能看单次值。** 以后判断有没有退化，至少要跑三次取中位数；
`reports/` 里那些单次数字只能当量级参考，不能当精确基准。

### 10.3 1-3 的两个实现选择

**命令模型保留了 `Undo/Redo` 的命名，没有改成 `Apply/Revert`。**
两种约定只差"谁先动手"：现在是"先改模型、再把动作记进栈"，而 Apply/Revert 是
"动作负责动手"。改成后者要把所有调用点翻一遍，而它换来的只是命名统一。
但**影响区域（`AffectedBefore` / `AffectedAfter`）是真的落地了**——
那是拖动预览（计划文档 4.3 那套"擦上一帧、画这一帧"）需要的东西，
不是命名问题。同时把"标脏"收口到 `Commit`：命令报告区域，脏区统一合并，
功能代码不必各自记得标脏（漏标是留残影的头号原因）。

**序列化只存原始采样点，不存任何"渲染结果"。** 笔迹长什么样完全由
采样点 + 笔宽决定（引擎只有一条画法），所以文件里不需要、也不该存几何。
（2026-09-14 补：原来这里写的是"不存优化器产出的轮廓，加载时由优化器重算"——
优化层已经整层删除，这条纪律反而更干净了。）

### 10.4 新增的三个自检模式

| 模式 | 验什么 | 结果 |
|---|---|---|
| `--transformtest` | 改变换不碰几何：几何版本号不变、包围盒与空间索引跟着走、撤销精确回原位 | 6 项全过 |
| `--savetest` | 保存/加载往返逐字段一致（含变换、颜色、压感、时间）；乱数据与截断数据要明确失败且不动文档 | 9 项全过 |
| `--shapetest` | 图形精确命中（1-2 加的） | 9 项全过 |

`--transformtest` 里那条"几何版本号未变"是整条路线的要害：它一旦不成立，
就说明变换被烘焙进几何了，缩放旋转会退化成 O(点数) 并累积误差。

**顺带修掉一个真 bug**：选中高亮的区域原先没有算进每帧脏区，
所以"取消选中 / 改选一批"之后旧的高亮框会留在屏幕上擦不掉（见 `ComputeTransientBounds`）。

### 10.5 阶段 1 还剩什么

- `OriginalInk` + `Style`：等形状识别一起做（那时才真正需要回退）
- 中心线 + 宽度：等"线宽不变"的变换落地时一起做
- 相机：随滚动功能落地（现在对象已经不认识屏幕，只差视图变换那一层）
- 剪贴板的**实际读写**：格式已经就绪（`InkSerializer` + `ClipboardFormatName`），
  还差 `RegisterClipboardFormat` 与 OLE 剪贴板那几十行胶水

# 第三部分：滚动 · 白板 · 翻页（调研 InkClass 之后）

调研对象：`D:\文件集中\code\画布测试\Ink-Canvas-Dev`（InkClass 的前身，WPF）。

`Hotkeys.md`、`DEVELOPMENT.md`。

## 十一、滚动方向：纵向，双向，默认向下

**结论：纵向滚动，可以往上回看，新空间往下延伸。** 这也正是 ClassIn 的做法，
而且你自己的 InkClass 已经这么做了（`MW_Scroll.cs` 标题就叫"笔记上下滚动（虚拟无限画布）"）。

理由是课堂实际需求，不是偏好：

| 理由 | 说明 |
|---|---|
| 手势天然 | 鼠标滚轮、触摸板双指、一体机双指滑动**全是纵向**。横向要 Shift+滚轮；一体机上双指横扫还容易和"画横线"冲突 |
| 和 PPT 一致 | PPT 是横版、一页一张。**纵向堆叠 = 一页接一页**，像翻书，心智模型和翻 PPT 一样 |
| 和板书一致 | 中文板书从左写到右，写满往下挪。横向扩展不符合书写方向 |
| 能回看 | "只往下不能往上"会很难用——老师要回头指某个地方 |

**不要把方向写死**：相机是通用的（平移 + 缩放），纵向只是默认手势绑定。
将来要做左右分栏、双页并排，只是换一种布局，不用改底层。

## 十二、白板和翻页要不要现在做

**现在不实现，但现在必须把坐标系设计成"能容纳它们"。**

关键认识：**冻结截图、白板、翻页，本质是同一个东西**——
一条纵向排列的"画布块"序列：

| 概念 | 在模型里是什么 |
|---|---|
| 一个截图块 | 一块画布，内容是截图 |
| 一页白板 | 一块画布，内容是空白（或底纹） |
| 一页黑板 | 一块画布，内容是深色 |
| 滚动 | 相机在纵向上移动 |
| 翻页 | 相机跳到下一块 |

所以阶段 1 只要把坐标系定成 **"画布局部坐标 + 一个相机（滚动位置）"**，
相机先固定不动（= 当前的单屏），以后加滚动、加翻页、加白板都是**加功能**，
不是改架构。

**序列化格式要从一开始就留出"多块"的结构**（哪怕现在只写一块进去），
否则以后加页要改格式，旧文件全读不了。

## 十三、InkClass 里能借什么、不能借什么

### 13.1 不能借：它的"坐标物化"做法

他们的滚动机制是——**滚动时把平移矩阵直接写进所有笔画的点数据**
（`inkCanvas.Strokes.Transform(matrix, true)`），而不是用渲染变换。
注释里写了理由：这样橡皮命中检测、墨迹保存、撤销/重做的坐标天然一致。

优点：实现简单，不用引入相机概念。

**但对我们是错的**：每次滚轮 = **O(对象数)** 的重写。一万笔的板书上滚一格，
要重写十万个点。而我们这套的核心优势恰恰是"每帧成本不随对象数增长"，
这个做法会直接把它破坏掉。

**我们的做法**：滚动属于**相机**，不进对象数据。
滚一格 = 改一个浮点数，O(1)；内容层按块缓存，滚动时只有**新露出来的那条**
需要重画。这和"变换独立于几何"是同一条原则。

### 13.2 要借：他们花钱买的那些坑

这些都在 `MW_Scroll.cs` 的注释和 `DEVELOPMENT.md` 里，直接沿用：

1. **滚轮要有归属**：画布收起时，滚轮**穿透给底层应用**（PPT 翻页），
   不被画布吃掉。这条最重要——否则老师在 PPT 里滚不了页。
2. **滚动位置按页记忆**（他们的原话），不能翻回来又回到顶部。
3. **选区要跟随滚动**：滚了之后选中框还在对象上，不能错位。
4. **光标在选区内时滚轮要转发**（他们原话"选区内滚轮转发"），
   否则拖到一半滚不动。
5. **滚动条按需浮现**：静止 3 秒淡出（他们试过 1.5 秒，"消失得太快"）。
   常驻的滚动条在小屏幕上碍眼。
6. **步长**：滚轮一格 = 工作区高度的 10%（细粒度顺滑）；
   按钮一次 = 35%（小半屏）。

### 13.3 跟随 PPT：能借思路，别押上产品

他们的做法是 **PowerPoint COM**：`Marshal.GetActiveObject("PowerPoint.Application")`
取到对象，然后挂 `SlideShowNextSlide` 事件，换页时切画布。

问题（他们自己的 `DEVELOPMENT.md` 待优化项里就记着）：

- 依赖装了**桌面版 PowerPoint**；WPS / 网页版不认。
- 依赖 COM 能被访问；他们有"COM 桥在 64 位进程静默失败"的记录。
- 位数、Office 版本敏感。

**建议**：你已经选了**冻结截图模式**，那条路不依赖任何外部程序，最稳。
把 PPT COM 监听做成**可选增强**——能连上就自动翻页，连不上就手动。
不要把产品的可用性押在 COM 上。

## 十四、快捷键：他们替我验证了那条判断

`Hotkeys.md` 开头就是一次修复记录，结论和我们的分析完全一致：

> 画板的典型用法是盖在 PPT 放映之上——**放映时键盘焦点在 PowerPoint 上**，
> 画板根本没有焦点，于是所有窗口层快捷键必然失效。

他们的处理：

- **窗口层**（需要焦点）：`Ctrl+P` 画笔 / `Ctrl+E` 橡皮 / `Ctrl+M` 选择 /
  `Ctrl+A` 全选 / `Ctrl+Z` 撤销 / `Ctrl+Y` 重做 / `Ctrl+Del` 清空 /
  `F6` 图形 / `Ctrl+=` `Ctrl+-` 缩放批注 / `Shift+Esc` 退出。
- **全局层**（`RegisterHotKey`）：只挑六个最需要跨应用调用的，
  统一用 `Ctrl+Alt+Shift+数字` 前缀。
- 明确写下：「窗口层的快捷键仍然是'有焦点才生效'，这是**有意保留**的：
  否则 `Ctrl+P`、`Ctrl+Z` 这类常用键会把整个系统的按键都吃掉」。

**对我们的启示**：我们的覆盖层是 `WS_EX_NOACTIVATE`，处境和他们一模一样。
所以编辑类快捷键也必须有"全局可达"的通道，否则老师在 PPT 全屏放映时
按 `Ctrl+Z` 会毫无反应。

但全局注册 `Ctrl+Z` / `Ctrl+C` 绝对不能做。可行的是：

- 全局热键只放**模式切换类**（切工具、穿透、清空、退出）——和他们一样。
- 编辑类走"**批注模式激活时**才归我"的条件拦截（低级键盘钩子），
  或者让覆盖层在批注模式下临时取得焦点。

**值得直接沿用的一个好设计**：他们把 `WM_HOTKEY` 的消息 id 固定成 101–107
并写进文档，作为**外部程序驱动画板的契约**——
PPT 插件、启动器只要 `PostMessage(hwnd, WM_HOTKEY, 101, 0)` 就能切画笔。
id 一旦发布就不再改动。我们也应该有这么一套（自己的 id 段）。

## 十五、从他们的"待优化项"里再学两条

`DEVELOPMENT.md` 的"已知待优化项"是花钱买的教训，我们要一开始就避开：

1. **图片操作不进撤销栈** —— 他们拖动/缩放/翻转图片后不能 Ctrl+Z，
   只能靠一个"统一还原"按钮。**我们要让图片和笔迹走同一套撤销**。
2. **旋转手柄对图片无效** —— 他们墨迹用矩阵变换、图片用 `RenderTransform`，
   两套机制导致旋转对图片失效、选框不贴合。
   **我们要让图片和笔迹用同一种变换表示**（这正好也是第 3 节问题 3
   "线宽不变"那条要求的同一件事）。

一句话：**图片层从一开始就要是"一等公民"**，不能是后加的补丁。

# 第四部分：能不能把 InkClass 的底层换成我们这个？

## 十六、先看数据：换了到底能好多少

数据来自你自己的 `reports/底层性能对比-三家.md`（同机同屏，合成手势，
每笔 40 个采样点，外部计数器采集）。

| 指标 | InkClass (WPF) | 本原型 | 差多少 |
|---|---|---|---|
| 空载工作集 | 255 MB | **96 MB** | **省 159 MB** |
| 每笔内存增量 | 0.50 MB | **0.10 MB** | **省 5 倍** |
| 空载 CPU | 1.0 % | **0.0 %** | 好 |
| 书写 20 笔 CPU | 14.5 % | **13.1 %** | **只差 1.4 个点** |
| 书写 60 笔 CPU | 15.9 % | **14.2 %** | 只差 1.7 个点 |
| 书写 GPU | **2.3 ~ 2.6 %** | 2.9 % | **WPF 反而更省** |
| 输入被消费速率 | 43 ~ 46 点/秒 | **55 点/秒** | 好约 25 % |

**结论：不是全面碾压，要看指标。**

- **内存：压倒性胜利。** 省一半以上，而且每写一笔的增长只有 1/5。
- **CPU：只小幅领先。** 书写时差 1~2 个百分点。
- **GPU：不会更好，甚至略差。** WPF 的动态渲染器（跑在独立线程）在
  "书写中"这一小段其实很省。
- **手感：会好一些。** 输入吞吐 55 vs 43，同样手势下我们收下的点更多。
  真实手写笔采样率更高时，这个差距会被放大。

### 16.1 一个必须说清楚的边界

上面这个对比只画了 **20 笔和 60 笔**——那正好是 WPF 最舒服的区间。

我们真正的优势是"**每帧成本与画面里已有多少笔画无关**"：一万笔时每帧
仍然 0.6 ms；而 WPF 的 `InkCanvas` 会随笔画数退化。

所以**"写满一屏、几百上千笔"的场景下差距会明显拉开**，而这个区间
现有报告没有覆盖。如果你要给这个决定找依据，应该先补一次
"1000 笔在屏再继续写"的对比测试。

### 16.2 换底层不会改善的那部分开销

InkClass 书写时的 CPU 里有很大一块是**它自己的业务逻辑**，跟底座无关：

| 模块 | 行数 | 干什么 |
|---|---|---|
| `MW_ShapeDrawing.cs` | 2002 | 图形绘制 |
| `MW_SelectionGestures.cs` | 1728 | 选择手势 |
| `MW_SimulatePressure.cs` | 1242 | 压感模拟 + 墨迹转图形 |
| `MW_PreserveCornerSmoothing.cs` | 162 | 保角平滑 |

这些是每个采样点/每帧都在跑的。换底座**不会**减少它们——
它们会原样搬到新底座上继续跑。所以"换了 CPU 就降下来"这个预期是不成立的。

## 十七、再算一遍工作量：耦合到底有多深

实测统计（`Ink Canvas` 目录下的 `MW_*.cs`）：

```
MW_* 合计           16767 行，30 个文件
其中直接操作 WPF 笔迹模型的行（Strokes / StrokeCollection / inkCanvas /
StylusPoint / DrawingAttributes / StylusPlugIn）：
                     1762 行，分布在 30 个文件里
```

两个结论：

1. **耦合只有约 10%**（1762 / 16767）——所以"全盘重写"不是唯一选择，
   理论上可以只搬这 1762 行。
2. **但它散在全部 30 个文件里**——没有"一个模块可以整体替换"的边界。
   每个功能模块都要改，一个都跑不掉。

## 十八、一个反直觉的坑：只换笔迹层，内存可能不降反升

这条最重要：

InkClass 那 255 MB 里，**绝大部分是 .NET Framework + WPF 的底座**，
不是 `InkCanvas` 本身。而我们的引擎会创建自己的 D3D 设备、DirectComposition
合成器和离屏内容层（约 40~60 MB）。

| 做法 | 内存结果 |
|---|---|
| 保留 WPF 壳，只把笔迹层换成我们的覆盖层 | WPF 底座还在（~200 MB）+ 我们的设备（~50 MB）= **可能比现在更差** |
| 整个应用脱离 WPF（连界面一起换） | 才拿得到 255 → ~100 MB 的收益 |

**所以"换底层"这个词有误导性。** 想拿内存收益，实际要动的是整个栈，
包括设置页、悬浮条、面板、图形库——那些是 WPF 最省事的部分。

## 十九、那到底该不该换

分三种目的，答案完全不同：

| 你的目的是 | 该不该换 | 说明 |
|---|---|---|
| **降内存**（低配教室机、8 GB） | 值得，但**必须整机换栈** | 只换笔迹层拿不到 |
| **降 CPU / 提帧率** | **不值得** | 只差 1~2 个百分点，GPU 还略差 |
| **要那些 WPF 架子上做不出来的功能** | **最值得** | 见下 |

### 19.1 真正的理由不是性能，是能力

InkClass 自己的"已知待优化项"就写了三个在 WPF 架子上做不出来的东西：

1. **图片操作不进撤销栈**——拖动/缩放/翻转图片后不能 Ctrl+Z。
2. **旋转手柄对图片无效**——墨迹用矩阵变换、图片用 `RenderTransform`，
   两套机制打架，旋转会导致选框不贴合。
3. **COM 框选识别失败**（WPF 笔迹 → IInkDisp → LoadInk 的转换桥在 64 位下
   静默失败）。

这三条都不是"性能问题"，是**数据模型问题**。而我们已经决定要做的
对象模型（统一变换、图片一等公民、几何与变换分离）刚好就是为了解决它们。

**所以：换底层的正当理由 = 拿到 WPF 版本做不到的能力，顺带省内存。
如果只为了 CPU 数字，这件事不值得做。**

## 二十、务实的路径（如果要做）

不要设想"某天把底层整个换掉"。实际可行的是一条渐进路线：

1. **新底层继续做成独立的覆盖层**（它本来就是这个形态），能和 InkClass 并存。
2. **先把四个最高频的动作做到明显更好**：写、擦（精确）、撤销、滚动。
   再加"批注在 PPT 上"这条主场景。
3. **做成一个可选的新模式**放给老师试用，功能补齐一个就迁一个。
4. 等到"新模式的日常使用已经不需要退回老版本"时，再决定是否整体替换。

这样任何一步走不通都可以停，不会把现有产品押进去。

### 二十、一 先补一次测试再决定

如果你要给这个决定找依据，建议先做这一件事：

> **把对比测试补到"屏幕上已有 1000 笔"再继续书写**，同时量 CPU、GPU、
> 输入吞吐和内存。这才是课堂真实场景（一节课板书几百笔往上）。

现在的报告只覆盖 20/60 笔，是 WPF 的舒适区，不足以支撑"换或不换"的判断。

# 第五部分：换成 C / Rust 能不能再上几个台阶？

## 二十一、这个实验你已经做过了

仓库里有 `src/InkTeachNative/main.cpp`（C++20），是同一个覆盖层的原生孪生实现。
它的注释写着唯一目的：「回答'同样的透明 GPU 合成覆盖层，在没有 .NET 运行时
垫底时到底花多少内存'」。

同一台机器、同一条管线（D3D11 + Direct2D + DirectComposition + 全屏离屏内容层）：

| 阶段 | C# (.NET 8) | C++ | 差 |
|---|---|---|---|
| 进程刚启动 | 私有 11.3 MB | 提交 1.4 / 工作集 7.5 MB | 就是运行时那点底 |
| 建完 D3D11 设备 | 私有 44.7 MB | 提交 34.5 / 工作集 32.6 MB | |
| 建完离屏内容层 | 私有 79.5 MB | 提交 68.5 / 工作集 48.0 MB | |
| **空闲稳态（提交大小）** | **85.7 MB** | **73.7 MB** | **省 12 MB（14%）** |
| 一万笔时 | 187.4 MB | 164.8 MB | 省 22 MB |
| 一万笔整层重建 | 179.1 ms | 165.5 ms | 快 8% |

**换语言的实际收益：空闲省 12 MB，一万笔时省 22 MB，重建快 8%。**

不是几个台阶，是十几个百分点。而且两边的大头完全一样——D3D / D2D /
DirectWrite / 交换链 / 离屏层加起来约 42 MB，跟语言无关。

你自己的内存报告里已经把这件事写死了：

> 笔画数量带来的增长主要在 GPU 侧，而且清空之后并不会还回操作系统
> （Direct2D 内部留着复用），所以峰值是「棘轮式」保持的。
> **这是 Direct2D 的行为，不是 .NET 的行为；换成 C++ 也一样。**

## 二十二、为什么换语言救不了

因为瓶颈不在语言上。看你自己的实测：

| 指标 | 数值 | 说明 |
|---|---|---|
| 空闲 CPU | 0.0 % | 没有可省的东西 |
| 书写时每帧"记录"（CPU 提交绘制命令） | 0.7 ~ 1.0 ms | 60 fps 下约 6% 单核 |
| 书写时 GPU | 2.9 % | 余量充足 |
| 上屏（Present）8~9 ms | 基本都是**垂直同步等待** | 不是计算，换语言也省不掉 |

真正在跑的是图形 API 调用、几何算法、输入处理——三样都跟语言无关。
用 Rust 重写，调用次数一样多、算法一样复杂，省下的只有托管运行时垫底的那十几兆。

反方向的账也要算：**C# 的 GC 和 JIT 在这个引擎里几乎不构成问题**，
因为热路径是刻意零分配的（空间索引查询不分配、画刷有缓存、几何有上限）。
换语言换来的是"没有 GC"，可你本来就没有 GC 问题。

## 二十三、真正的"台阶"在哪

要"再上一个台阶"，方向是这三条，**没有一条跟语言有关**：

| 方向 | 现状 | 能拿到什么 |
|---|---|---|
| 内容层分块（tile） | 每屏一张全屏位图（+20.7 MB/层；4K 每层 32 MB；双缓冲翻倍；多屏再翻倍） | 多屏 / 4K 下内存大幅下降 |
| 静态对象合批 | 一万笔整层重建 179 ms | 重建降到十几 ms |
| 湿墨通道（DWM 委托墨迹轨迹） | 已探测可用、默认关闭（合成输入看不到效果，缺真笔验证） | **延迟从"一帧"降到"几乎无"** |

第三条最值得注意：它是唯一能让**手感**上一个台阶的东西，同样跟语言无关，
纯是接口选择。你已经把这个接口探明白了（`IDCompositionInkTrailDevice`），
只差一支真笔去验证。

## 二十四、真要在 .NET 里再榨一点

按投入产出比排序：

1. **先试 NativeAOT**（.NET 8 支持）。编译成原生、去掉 JIT、裁掉用不到的运行时，
   内存和启动都会改善，改动量远小于换语言。风险是 Vortice 的 COM 互操作在 AOT
   下不一定支持——但一次 `PublishAot=true` 的试验就能知道，成本极低。
2. **减少离屏层**：那 26 MB 是屏幕尺寸决定的，分块后能显著下降。
3. **显存上限调优**：几何实现缓存现在固定 4096 个，可以按对象数动态定。

## 二十五、结论

**不换。** 投入产出比不成立：

- 能拿到的：12~22 MB，8% 的重建速度，没有可测量的 CPU 台阶。
- 要付出的：把约 5000 行引擎（加那 16767 行的产品逻辑）重写一遍，
  并且放弃 .NET 的开发效率、调试体验和现成生态。

**什么时候才值得考虑原生**：当你把产品定位改成"极致内存"（目标 30 MB 以内），
并且愿意放弃 Direct2D 的离屏内容层（那 26 MB）和脏区增量能力——
那时换语言也不是主要手段，改架构才是。

## 二十六、NativeAOT 试验结果（2026-09-13 实做）

**结论：代码层面没发现障碍，但这台机器缺 C++ 工具链，走不到最后一步。**

### 做了什么

| 步骤 | 命令 | 结果 |
|---|---|---|
| 1. 真实 AOT 发布 | `dotnet publish -r win-x64 -p:PublishAot=true` | 托管程序集编译通过，卡在 `SetupOSSpecificProps`：**Platform linker not found** |
| 2. 换用 AOT 分析器 | 加 `IsAotCompatible=true` 重编译三个工程 | **0 警告 0 错误** |
| 3. 验证分析器有效 | 故意加一个 `AssemblyBuilder.DefineDynamicAssembly` 探针 | 报出 **IL3050**，证明分析器确实在跑（探针已删） |
| 4. 扫第三方库 | 在 DLL 元数据里找 `GetDelegateForFunctionPointer` / 反射发射 / `GetActiveObject` | **都没有** |

### 关键细节

第 1 步失败的位置很关键：错误在 `SetupOSSpecificProps` 目标里，而它是 `IlcCompile`
的**前置**目标——也就是说 **ILC 根本没跑**，这一步没拿到任何兼容性信息，
只证明了"缺链接器"。

好在第 2、3 步补上了：AOT 分析器用的就是 ILC 那套 IL 分析，而探针证明了它真的在跑。
所以"我们的三个工程 0 警告"是可信的——代码里没有反射发射、没有未标注的反射、
没有 `RequiresDynamicCode` 调用。

第 4 步扫出来的命中只有两类，都不构成障碍：

- `GetFunctionPointerForDelegate`——我们挂 `WndProc` 用，以及 SharpGen 做 COM
  vtable 转发用。AOT 支持（只要委托类型静态可知，我们的就是）。
- `System.Text.Json` 里的 `DynamicMethod` / `Reflection.Emit`——那是它的
  **反射序列化**路径，我们没有用（引擎里没有任何 JSON 序列化调用）。

### 还缺什么才能定论

只有真实链接能给出最终答案。需要装 **"Visual Studio Build Tools + 使用 C++ 的桌面开发"**
（约 2~4 GB）。这台机器上目前：

- 没有 Visual Studio（连 vswhere 都没有）
- 没有 Windows SDK（`Windows Kits` 下只有 `NETFXSDK`）
- 没有 clang / lld

装好之后的验证方式：

```
dotnet publish src\InkTeach\InkTeach.csproj -c Release -r win-x64 -p:PublishAot=true
```

然后量四件事：空闲提交大小、启动时间、书写 CPU、以及**能否正常起窗口并画上墨**
（COM 互操作在 AOT 下能不能跑起来，是这次试验真正要回答的问题）。

### 期望值（先说清楚，免得到时候失望）

能拿到的**上限就是 C++ 那一档：空闲 73.7 MB**。因为 42 MB 的图形栈两边完全一样，
不是运行时那部分。所以 AOT 的结果会落在 **85.7 → 73.7 MB 之间**，
大概率是 80 MB 上下。

**不会有的**：CPU 和延迟的台阶。空闲 CPU 已经是 0%，书写每帧 1 ms，
Present 的 8~9 ms 是垂直同步等待——AOT 一样等。

## 二十七、一次失败的尝试：几何按需重建（2026-09-13）

**想法**：几何重建只要 3µs（reports/inkprobe-report.txt 实测），而常驻一份要
几 KB，所以不值得常驻——让几何只服务于"正在被重画的那一批"，其余在帧末丢掉。

**做法**：加 `LiveGeometries` 计数与 `MaxGeometries = 1024`，每 30 帧扫一遍，
把两帧内没被画到的几何 `Release()` 掉。

**结果：内存不降反升。**（`--memory` 提交大小对比，同一台机器、同一场景）

| 场景 | 改动前 | 改动后 |
|---|---|---|
| 空闲 | 84.8 MB | 91.5 MB |
| 500 笔 | 91.2 MB | 104.9 MB |
| 2000 笔 | 111.5 MB | 129.9 MB |
| 10000 笔 | 187.4 MB | **215.9 MB** |

**原因：建立和销毁不是对称的。** Direct2D 的资源分配器会留着释放过的块以备复用
——这一点**在我们自己的内存报告里早就写着**：

> 清空之后并不会还回操作系统（Direct2D 内部留着复用），所以峰值是「棘轮式」保持的。

频繁地"丢—建—丢—建"会让那些块越攒越多，反而把常驻内存推高。

**结论：几何要常驻，不要频繁建销。** 那 3µs 是 CPU 成本，而丢掉它换来的是内存
分配器的棘轮。改动已回退，结论记在这里，免得以后又想当然地"优化"一遍。

**教训**：缓存类改动**必须实测**，而且要用**同一个可比的固定场景**（`--memory`
那条曲线）。否则很容易被"3µs 很便宜"这种局部数字骗到——便宜的是 CPU，
贵的是分配器行为。

**那内存还能怎么降？** 剩下真正有效的方向是**减少对象本身的常驻开销**，而不是
折腾缓存的生命周期：
- 点数据量化（x/y 用 int16 相对坐标、压力用 byte）→ 每点 20 字节降到 5 字节，
  且几乎无损（误差 ≤0.1 像素）。
- 存储层只留拟合后的贝塞尔控制点、丢掉原始采样点 → 典型 30 点降到 8 个控制点。
  代价是顶点编辑与"精确橡皮"要改成直接在曲线上做（Direct2D 支持）。

## 二十八、测量方法的硬伤：跨会话的数字不可比（2026-09-13）

今天复测 `--memory`：**空闲 91.9 MB**。而仓库里那份报告（同日 09:36）是
**84.8 MB**。空闲时几乎什么都没发生，差 7MB 只能是**环境漂移**
（其它进程、GPU 驱动状态、系统缓存……）。

**后果很严重，必须承认：**

- 我判断"几何按需重建让内存变差"（10000 笔 187.4 → 215.9 MB）**可能是错的**。
  两次测量不在同一个环境状态里，那 28MB 可能全部来自漂移。**那个改动也许本来
  是对的，被我误杀回退了。**
- 同理，"细分缓存 4096 → 1024 省了内存"这个结论也不可靠——显存那一列反而
  从 154 涨到 168，同样在漂移范围内。

**结论：跨会话比数字是无效的。** 判断一个改动的好坏，必须在**同一个进程里
背靠背地测两种配置**，中间不重启、不让别的程序插进来。

**所以下一步的第一件事不是优化，是把 A/B 测量工具补上**：
`--memab` 在同一个进程里交替跑两种配置若干轮，输出中位数与波动范围。
在那之前，任何"省了多少 MB"的说法都只能当参考，不能当结论。

这条和前面那几条（截屏类测试要串行、看最长帧而不是平均）是同一类问题：
**这个项目最强的资产是那套量化工具，而工具的可靠性决定了结论的可靠性。**

## 二十九、上下滚动：方案、陷阱与边界（方案定稿，未实现）

**现状：没做。** 对象坐标就是虚拟桌面像素，没有相机那一层。阶段 1 留了口子
（几何存局部坐标、变换独立），但滚动本身没接。

### 一屏多少字

板书楷书一字约 100~150 逻辑像素（含间距），1440×900 逻辑屏：
**6~9 行 × 9~14 列 = 50~120 个汉字/屏**，一字约 8~9 个对象
-> **一屏 400~1000 个对象**。

实测：1000 对象每帧 1ms 级，10000 对象仍 1.36ms。
**"保证一屏流畅"这个目标我们超出十倍。真正的问题从来不是一屏，是累积。**

### 同行怎么做

- **Xournal++**：`XournalView` 里维护一个页范围 `pagesLower..pagesUpper`，
  **只保留视口附近那几页**，其余连同渲染好的 PDF 位图一起释放。粒度＝页。
- **Rnote**：视口驱动（`update_background_rendering_current_viewport`）；
  每个对象缓存光栅小图，状态里明确区分 `ForViewport`。

### 方案（两步，顺序不能反）

**第一步：相机。** canvas → screen 的平移。滚动只改这个平移，
**O(1)，绝不动对象数据。**

> InkClass 的 `MW_Scroll` 是"把平移矩阵烘焙进所有笔画的点坐标"，
> 一次滚轮 = O(对象数) 的重写。一万笔滚一格重写十万个点——这是它慢的根源，
> **不能沿用**。

- 输入侧：指针位置在进入引擎时立刻从屏幕坐标换算到画布坐标（按下/移动/抬起三处）
- 渲染侧：窗口变换里带上相机平移
- 命中测试、橡皮、框选、激光：全都自动跟着，因为它们都吃画布坐标

**第二步：内容层改成"滚动缓冲"或"分块"。** 现在内容层恰好一屏，
滚出去的内容没地方放，只能重画整屏。要么让它比屏幕大（滚动缓冲），
要么分块（tile + 冷块淘汰）。**后者同时实现"出界面就不占"**——
Xournal++ 的页级释放就是这个意思。

### 性能边界（可推算，实现后按此验收）

| 阶段 | 滚动一格代价 | 一屏量级(~1000 对象) | 累积一万笔 |
|---|---|---|---|
| 只做第一步 | 整屏重画 = O(屏内对象数) | 约 20ms -> **约 50fps，可用** | 154ms -> **滚一格卡一下** |
| 做完第二步 | 只重画新露出的那条带子 | 与文档总量无关 | 与文档总量无关 |

### 关于"出界面就不占内存"

**性能上对**——我们已经在做（脏区机制本来就不碰屏外）。
**内存上省不动**——实测能释放的缓存很便宜：

| 能释放的 | 一万笔时的成本 |
|---|---|
| 几何缓存 | 10 MB |
| 细分缓存 | 显存差 0 |
| **不能释放的：笔画数据本身** | **约 15KB/笔 = 150MB** |

笔画数据不能丢：老师要往回滚看、要保存、要撤销。
**真要在屏外省内存，方向是压缩（屏外只留拟合后的贝塞尔控制点），不是丢弃。**

### 两个只做纵向的理由

1. 板书是纵向累积的，横向没有用武之地
2. 省掉一堆边界问题：双指横扫和"画横线"的手势冲突、选区左右边界、平移方向歧义

### 开工前必看的坑（InkClass 踩过的）

滚轮要有归属（画布收起时穿透给 PPT）｜滚动位置按页记忆｜选区跟随滚动｜
光标在选区内时滚轮要转发｜滚动条按需浮现（静止 3 秒淡出）

## 三十、滚动第二步的备选方案：滚动缓冲（**最终没用它**，见第三十一节）

**问题**：内容层现在恰好一屏。相机一动，整屏内容位置全变，只能整层重画——
实测 5000 笔 41ms、10000 笔 82ms。滚轮一格（72px）就重建一次，一屏 1800px
要重建 25 次，所以累积量下"滚一屏就是一路卡"。

**做法：量化带 + 子矩形合成**（比全量分块简单得多，先拿八成收益）

1. 内容纹理高度从 `H` 改成 **`H + 2M`**（`M` 取 600 物理像素，约三分之一屏）。
   代价：内容层显存从 20.7MB 涨到约 27MB（+33%）。
2. 引入 `_contentOriginY` = 内容纹理第 0 行对应的**画布 Y**，取值**按 M 对齐**：
   `_contentOriginY = round((视口顶部 - M) / M) * M`
3. `EnsureContent` 的变换从 `translate(-OriginX, -OriginY)` 改成
   `translate(-OriginX, -_contentOriginY)`。其余不动——它照旧把**所有**笔画画进
   内容纹理，落在纹理外的被裁剪自然不画（要显式 `PushAxisAlignedClip`）。
4. 帧合成从"1:1 贴整张"改成**贴子矩形**：
   `srcRect = (0, 视口顶部 - _contentOriginY, W, H)` -> `destRect = 整个窗口`。
5. 滚动时：
   - `_contentOriginY` **变了**（跨过一个带）-> 重建（就是现在的整层重画）
   - **没变** -> 只把**整个视口**标脏，走第 4 步的子矩形合成，**不重建**

**收益（按实测的整层重建时间推算）**

| | 现在 | 改后 |
|---|---|---|
| 重建频率 | 每滚一格（72px） | 每滚一个带（600px） |
| 1 万笔时每格平均 | 82 ms | **约 3 ms** |
| 一屏 1800px 的重建次数 | 25 | **3** |

**必须守住的不变量（这几条错了就出残影，而残影最难查）**

- 双缓冲回溯的语义不能变：`_transientHistory`、`_contentDirtyPrev` 照旧
- `Present1` 的脏矩形必须是**窗口坐标**；滚动引起的整屏变化就整屏标脏
- 擦屏用 `BoardBrush`（Copy 混合），**别用 `Clear()`**——它无视裁剪
- 内容纹理的边界必须显式裁剪，否则画出界的点会跑到别的行上去

**验收标准**

- `--cameratest` 的曲线：一屏 1000 对象应保持 <3ms；10000 对象应从 82ms
  降到约 3ms/格
- 滚动时**无残影**：拖动的笔迹、性能面板、激光、选中框都要跟着滚
- 白板模式（`BoardBrush` 不透明）下滚动同样正确
- 滚回原处、来回滚多次，画面与不滚时逐像素一致

**为什么不用全量分块（tile）**
分块能进一步解绑"多屏/4K 的显存"，但要让每一块各自维护脏区、各自重建、
各自淘汰，改动面比上面大一个量级。上表这套先把"滚动卡"解决掉；
真要上 4K 多屏，再在它之上换成 tile——两者的接口形状是一样的
（都是"内容纹理 -> 视口子矩形"），不会白做。

## 三十一、滚动第二步：**分块缓存**（已实现并实测，2026-09-13）

结论先说：**内容层不再跟屏幕走，改成画布空间的分块光栅缓存**。
滚动是"换个位置把已经画好的块贴上去"，一个像素都不重画。

这不是当初写的滚动带方案。写滚动带时又推了一遍，发现分块把滚动带的好处
全覆盖了，而且顺带解决了另外两件事，所以直接上了分块。

### 31.1 为什么是分块，不是滚动带

| | 滚动带（第三十节） | 分块（实际采用） |
|---|---|---|
| 滚动代价 | 带内免重画，跨带时**整带重画**（1.67 屏） | 只画**新露出来的那一小块** |
| 一万笔跨带一下 | 约 34~137ms（还是卡） | 约 0.5ms/块，一帧几毫秒 |
| 滚回去 | 带已经挪走了，**要重画** | 块还在，**直接命中，0ms** |
| 显存 | 固定 1.33 屏 | 可见一屏 + 8MB 回滚余量（有上界） |
| 4K/多屏 | 得重做 | 天然支持（改的只是可见块集合） |

一句话：**滚动带是用内存换重建次数，分块是让重建次数归零**。

### 31.2 实现（`src/InkEngine/CanvasTiles.cs`）

1. 画布切成 256×256 的块（和空间索引的格子同宽，查询不多扫格子）。
2. **块在画布空间**，原点恒为 256 的整数倍。滚轮只改相机，块一动不动。
3. 块按需光栅化：可见且脏才画。文档脏区是画布坐标，直接映射到块，
   **这一步完全不看相机**——这是老做法踩四次坑的那一步。
4. 合成时**相机只出现一次**：窗口矩形 → 画布矩形 → 取每块相交的子矩形 →
   贴回窗口。整数对齐 + NearestNeighbor ⇒ 相邻块之间不会有接缝。
5. 淘汰：常驻块超预算就按最近使用丢，**绝不丢这一帧可见的块**；
   预算 = 可见块 + 8MB 回滚余量（教室机 4GB，不能无限涨）。
6. 擦除块用 `Copy` 混合的填充，矩形写**画布坐标**（见 31.4 的坑）。

### 31.3 实测（2880×1800@192DPI，Intel 核显）

滚动代价（走真实 `HandleWheel`，内容铺开 8 屏，一格 144 物理像素）：

| 文档笔数 | 每格平均 | 最慢一格 | 判断 |
|---|---|---|---|
| 1000 | 3.3 ms | 7.4 ms | 不掉帧 |
| 5000 | 3.8 ms | 8.2 ms | 不掉帧 |
| 10000 | 3.6~4.1 ms | 9.3 ms | 不掉帧 |

对照：**老做法（整层重画）一屏量级 20ms、5000 笔 41ms、10000 笔 82ms。**
现在每格代价与文档总量基本无关——新露出来的永远只有那一条。

内存（长跑 25 秒 / 481 轮，同机同机位对照）：

| | 老做法 | 分块 |
|---|---|---|
| 工作集 | 135.2 MB | 167.5 MB |
| 提交 | 110.3 MB | 145.2 MB |
| 最慢单帧 | 7.23 ms | 5.87 ms |

多的这 30 多 MB 就是分块缓存本身（可见约 96 块 × 256KB ≈ 24MB，
再多几行回滚余量）。**它是有上界的**；老做法那张整屏位图是 20.7MB，
量级相同。用 30MB 换"滚动不再随内容变卡"，在 4GB 教室机上划算。

### 31.4 这轮踩掉的坑（写下来，别重犯）

1. **块内变换写反**：擦块的矩形一开始写成 `(0,0,256,256)`，但当时变换已经
   是"画布 → 块内"，于是整块擦到画面外——数据擦掉了，屏幕上三条线还在。
   矩形必须写**画布坐标**。（`--erasertest` 抓到的。）
2. **空间索引只索引中心线**：笔迹画在中心线两侧，只按中心线索引会让
   "中心线在块外、笔身伸进块里"的粗笔画查不到，块边界上缺一条边。
   索引改成按**带笔宽外扩**的框，查询也用同一个范围。
3. **浮动层还在混用两套坐标**：选中框 / 框选 / 激光 / 正在写的笔的脏区，
   一半是画布坐标一半是窗口坐标（相机为 0 时恰好相等）。已统一走
   `CanvasRectToWindow`。
4. **界面层也被相机带跑了**：`DrawUi` 的变换里含相机偏移，一滚动工具条
   就会跟着内容往上跑。界面是贴在屏幕上的，不能带相机。

### 31.5 新增自检：`--tiletest`

分块有一类特别难查的 bug——**接缝**（笔画跨块时缺一条边），平时看不见，
只有粗笔画压在块边界上才露出来。所以专门量：

```
横线压在块边界上不缺墨     边界 67200 vs 块中间 67200（差 0）
竖线压在块边界上不缺墨     边界 67200 vs 块中间 67200（差 0）
跨十几个块的长笔画不断线   6 段采样里有 0 段是空的
滚下去再滚回来画面一致     14807 -> 14807
回程复用了块缓存（没有重画） 去程光栅 24 块，回程 0 块
常驻分块不超预算          120 块 / 预算 128（每块 256KB）
```

### 31.6 已知边界与可调项

- **整层重画的场景变慢了一点**：一万笔全塞在一屏时，清空/换底色/换分辨率
  从 162ms 变成 246ms（画得更碎，且跨块会重复画）。这些是极少发生的动作，
  换来的滚动收益大得多。真嫌慢可以让"整层作废"走一条不查索引的直通路径。
- **块大小可调**（`--tilesize 256|512`）。实测 256 与 512 的取舍：
  写完一笔要重画"它压到的那几块"，块越大这一笔越贵（长跑平均 1.25ms vs
  3.34ms），而大范围重画时块越大贴图次数越少。**写字是最高频的路径，
  所以定 256。**
- **显存预算**：可见块 + 8MB。要更省可以调小 `ScrollBackBytes`。
- 还没做：左右滚动（无需求）、白板翻页、滚动条拖拽（现在只有比例的显示）。

### 31.7 关于"全用矢量、不要位图"

试过也想过，结论不变：**矢量是数据，位图是缓存**，两者都要。
一万笔纯矢量每帧重画 154ms（`--nocache`），核显上不可能 60fps。
同行的做法也一样：Xournal++ 按页缓存位图 + 只保留视口附近的页
（`XournalView::cleanupBufferCache`、`deleteViewBuffer`），
Rnote 用相机（`Camera::viewport()`、`transform_for_gtk_snapshot()`）+ 视口裁剪
（`if !page_bounds.intersects(&viewport) { continue; }`）。
Win32 时代就是 `ScrollWindowEx`：搬已经画好的位，只重画露出来的那一条。

**绝不能做的**：把平移烘焙进点坐标（InkClass 的做法），那是 O(对象数)/次，
一万笔滚一格重写十万个点——正是我们要躲开的那个坑。
