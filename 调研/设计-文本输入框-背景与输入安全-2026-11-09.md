# 设计调研：文本输入框——背景、流式输入 / Markdown、编辑框与自研路线

日期：2026-11-09
状态：**只做调研与规则，暂不改代码**

> 用户原话（整理）：
> “我打算优化文本输入框，主要是背景，流失输入，自己图型功能，或者其他大品牌都有的功能，你去调研一下，看看。”

**先对齐**（按用户 2026-11-09 补充）：

- **“流式输入”= 大模型逐 token 返回时，内容边到边渲染**（不是用户逐字打字）。
  文内单列“流式输入 / Markdown 增量渲染”一节。
- “输入不丢失”仍作为独立 P0（焦点丢失 / 切页 / 崩溃 / 草稿恢复），和“流式”分开。
- “自己图型功能”按 **文本框自己的背景/形状样式**（不只是白纸，还能便签、重点框、气泡等）理解；

- “编辑框背景处理不了”按 **RichEdit 编辑窗无法做透明/圆角/图案背景** 理解；文内有原因和三条路线。

## 〇、结论

按“课堂使用频率 / 风险 / 实现成本”排，最值得做的 6 件：

1. **文本框样式（背景 + 边框 + 圆角 + 内边距 + 阴影 + 形状）**，带 4–6 个预设，可保存默认样式。
2. **自动对比度**：文字颜色永远按“实际背景”（纸面或白板/PPT 底色）算，杜绝白纸白字、黑底黑字。
3. **输入草稿日志**：编辑中的文字每秒落一份本地草稿，崩溃/重启能恢复；不是只靠 15 秒自动存档。
4. **切页/切工具不丢字**：提交到原页；提交失败就留在草稿里，不能静默丢。
5. **大纲级文字功能**：对齐（横/纵）、行距、列表、高亮、链接、加粗/斜体/下划线；不做到 Word 级。
6. **形状底 + 文字**：便签/气泡/重点框/圆角矩形，文字放在形状里；解决“标注贴到图形上”的课堂场景。

不建议第一版做：渐变/纹理/3D/艺术字、完整富文本、每个文本框单独 AI 改写、无限画布式正文排版。

**本次补充（流式输入 / MD / 编辑框背景 / 图片）**：

- **流式输入不要直接灌进可编辑的 RichEdit**：另开“只读块渲染”，按帧合并 token、只重排最后一个未闭合块；生成完再允许“转为文本框/插入”。
- **Markdown 走块模型**：标题/列表/粗斜体/代码/公式先做；表格/图片后置；不整篇重排。
- **编辑框背景受普通 RichEdit 窗口限制**：`WM_CTLCOLOREDIT` 不支持，`EM_SETBKGNDCOLOR` 只能纯色；
  但 **无窗口 RichEdit（ITextServices/ITextHost）官方支持透明/非矩形**——优先验证“自宿主”，
  跑不通再用“纯色 + 圆角”近似，最后才是完整自绘/WebView2。
- **图片不内联进文本框**：图片是独立对象/块，最多“绑定/成组”；文本框保持“文字容器”。

## 一、InkTeach 现状

### 1.1 已有的

- 普通文本框：透明背景，文字颜色默认按**白板底色**自动选深/浅（`DefaultTextColor`）。
- 识别到文本框：`Paper = true`，画白色 0.98 圆角纸面 + 1px 边框（`DrawTextBox`）。
- 字体（雅黑/楷体/宋体/黑体）、字号、行距、逐行红蓝、逐字颜色、LaTeX 行内公式。
- 自动宽高（首次按内容长宽；之后可拖）；20000 字上限；内部滚动；编辑撤销。
- 原生 RichEdit 编辑：输入中实时写回 `TextBox.Text`；点画布外提交；焦点丢失**不结束**编辑；Esc / Ctrl+Enter 提交。
- 白板/PPT 自动存档：默认每 15 秒；崩溃恢复有自动存档（板书级）。

### 1.2 缺口

| 缺口 | 现状 | 影响 |
|---|---|---|
| 背景只有 `Paper` 布尔 | 要么透明，要么固定白纸（0.98 + 灰边） | 不能便签黄/蓝/绿、重点框、半透明、深色纸 |
| 无边框/圆角/内边距/阴影设置 | 白纸固定 12 圆角、18 内边距、固定边 | 不能做“重点框/标签/气泡” |
| **对比度按白板算，不按纸面算** | `DefaultTextColor` 看 `BoardColor`；`Paper` 白纸仍用原墨色 | 黑板上写白字 → 识别成白纸文本框 → **白纸白字**，可能看不见 |
| 样式不能保存为默认 | 每次新建都回到同一套 | 老师每次都要重调 |
| 编辑草稿只在内存 | 输入实时写模型 + 15 秒自动存档 | 崩溃最多丢 15 秒；新建框未提交时更危险 |
| 无保存状态提示 | 只有“墨迹状态”文字 | 老师不确定“刚才那段存了没有” |
| 无版本历史 | 自动存档轮转，但不是可浏览版本 | 误删/改错只能靠撤销栈 |
| 切页/切工具的行为不透明 | 工具切换会提交；页面切换路径未统一检查 | 极端情况下可能把字提交到错误页/丢焦点 |
| 无形状底 | 文本框永远矩形 | 便签、气泡、重点框要另画图形 + 文字，麻烦 |

### 2.2 输入不丢失

| 产品 | 做法 | 对我们的意义 |
|---|---|---|
| **OneNote** | **没有保存按钮**，输入/编辑/格式/组织全部持续自动保存；退出即存；页面版本历史 | “无感保存”是目标；老师不该想着按保存 |
| **Google Docs** | 持续自动保存 + **版本历史**（可查看/恢复/命名版本） | 版本历史是误删/改错的兜底 |
| **Notability / GoodNotes** | 笔记自动保存；文本框点外面提交；无手动保存 | 提交语义要稳定：点外面=提交，不是丢弃 |
| **Figma** | 自动保存 + 版本历史 + 多人实时 | 单人版至少做到自动保存 + 本地历史 |
| **PowerPoint** | AutoSave / AutoRecover；崩溃后可恢复未保存演示 | 我们已有板书自动存档，文本框要纳入同一套恢复 |

### 2.3 其他值得看的功能

- **自动调整**（PowerPoint）：`不自动 / 缩小文字 / 形状随文字长`；我们目前是“宽度固定、高度随文字长 + 内部滚动”，可以补“缩字”档。
- **文字高亮**（GoodNotes）：高亮跟随文字，编辑/缩放/移动不丢；我们目前只有逐行/逐字颜色，没有“文字底色高亮”。
- **列表 / 对齐 / 行距**（GoodNotes/Notability）：课堂板书做步骤、要点很常用。
- **链接**（GoodNotes/Notability）：文本框里可放可点链接；课堂引用资料有用，优先级中。
- **Scribble / 手写转文字**（Notability/Apple）：我们已有 AI 识别到文本，方向一致。
- **样式复制/粘贴**（Freeform/Miro）：把一套背景/字体快速套到另一个框；实现成本低，收益高。
- **文字上限/大粘贴**（Miro 6000 字符会转 Doc；GoodNotes 提示分小段粘贴）：我们 20000 字上限要**明确提示**，不能静默截断。

## 二·补、流式输入 / Markdown / 编辑框背景 / 图片

### 2.4 流式输入（LLM 逐 token 返回）

**现状**：InkTeach 现在没有“聊天式 LLM 流式返回”；OCR 是一次性结果，AI 题卡是静态排版。文本框是 RichEdit 编辑窗 + DirectWrite 最终排版两套。

**规则**：

1. **流式内容进“只读块渲染”，不进可编辑 RichEdit。**
   - 理由：RichEdit 的 caret/选区/IME/撤销/滚动会和“每 token 变一次文本”打架；每 token `SetWindowText` 还会丢光标、触发重排、闪烁。
   - 做法：AI 卡片内部用 `StreamingTextView`（块模型 + DirectWrite）逐块长；生成结束才提供“转为文本框 / 复制 / 插入到当前页”。
   - 如果一定要在文本框里流式：进入**只读流式态**（不显示 caret、不可编辑），结束后切回可编辑；不要一边流一边让用户改。
2. **按帧合并 token，不按 token 重绘。**
   - 100 token/s 全部重排会拖垮 UI；把 token 放进 buffer，每帧（≈16ms）取一次，最多 60 次/秒。
   - 内容比屏幕快时，丢弃中间帧只画最新；保留“停止生成”按钮。
3. **只重排最后一个未闭合块。**
   - 已完成块缓存 AST/布局/高度；新 token 只影响尾部块。
   - 尾部块可能“段落 → 列表/表格/代码块”变类型：先按当前类型画，闭合后再换；表格/公式等**闭合后再正式排版**，避免半截跳动。
   - 代码围栏未闭合时临时补一个闭合符再解析，避免显示原始 ```。
4. **滚动锚定**：用户没手动上滚时，新内容到达后让底部保持可见；用户上滚后不要抢滚动，显示“回到底部”。
5. **状态**：生成中显示“生成中… / 停止”；失败保留已生成部分 + 重试；不要整段清空。
6. **安全/限额**：流式文本长度上限（例如 20k 字）和超时；链接不自动打开；不执行 HTML；图片不自动联网拉取。

### 2.5 Markdown 渲染优化

**现状**：`AiCard` 已有行级 Markdown：分隔线、代码围栏（latex/tex 走公式）、`\[...\]` / `$$...$$`、`#` 标题、`-` / `*` 列表、`**粗体**` / `*斜体*`；没有表格、链接、图片；每次内容变化走整块排版，没有流式增量。

**建议**：

- 引入**块模型**：`Heading / Paragraph / List / Code / Math / Table / Image / Divider`；每个块独立测量、独立缓存。
- Markdown 解析用成熟库（C#：**Markdig**；不要在业务里手写解析器），流式时：
  - 已完成块不重新解析；
  - 只解析“最后一个未闭合块”的尾部；
  - 表格、图片、公式在闭合后再渲染；
  - 链接做安全校验（只允许 http/https，不自动打开）。
- 排版只重算变化块；`TextBoxData.EnsureLayout` 现在是整框重排，需要加**按块布局缓存**（或至少“尾部块”重排）。
- 代码高亮后置；公式沿用现有 CSharpMath/LaTeX 渲染；表格第一版可以只做简单管道表格。
- 不做完整 CommonMark（引用链接、脚注、HTML 内嵌等）第一版不做；AI 回答常用子集足够。

### 2.6 编辑框背景为什么处理不了

**根因**（Win32 文档）：

- RichEdit **不支持 `WM_CTLCOLOREDIT`**；普通 EDIT 才支持。
- RichEdit 设置背景只能用 **`EM_SETBKGNDCOLOR`**，参数是 `COLORREF`：**只能纯色，没有 alpha、没有圆角、没有图案**。
- 现在的编辑宿主窗口用 `WM_ERASEBKGND` 填一个纯色刷子，所以编辑时只能看到矩形纯色，不能和“白纸 98% / 便当黄 / 半透明 / 圆角 / 气泡”完全一致。

**三条路线**：

| 路线 | 做法 | 代价 | 建议 |
|---|---|---|---|
| A. 纯色近似 + 圆角区域 | `EM_SETBKGNDCOLOR` 设填充色；`SetWindowRgn` 裁圆角；编辑时用“实心编辑纸” | 1–2 天；透明/图案背景只能近似（下面内容被盖住） | 保底方案 |
| **B0. 无窗口 RichEdit（自实现 ITextHost）** | `CreateTextServices` + `ITextServices`/`ITextHost`；宿主自绘背景/D2D，RichEdit 只画文字/caret/选区 | 1–3 周；要实现 `ITextHost` 的 COM 接口（C# 手工 vtable 或 C++/CLI）、DC/IME/DPI 互操作 | **首选，先做 1–2 天技术验证** |
| B. 完全自绘编辑器 | 隐藏 RichEdit/TSF 收 IME，DirectWrite 画文字/caret/选区 | 3–6 周；IME/选区/撤销/无障碍/剪贴板都要自己写，风险高 | 只有 B0 走不通才考虑 |
| C. WebView2 + ProseMirror/Lexical | 网页编辑器做富文本/Markdown/图片/CSS 背景 | 2–4 周；多一个 WebView2 表面，IME/DPI/层级/性能要调 | 要做完整 Markdown 编辑时再评估 |

**B0 为什么值得先试**：

- Win32 官方文档明确：**windowless RichEdit 可以非矩形、透明**；宿主通过 `ITextHost::TxGetBackStyle` 返回 `TXTBACK_TRANSPARENT`，RichEdit 只画文字/caret/选区，背景由我们自己画。
- 它保留 RichEdit 的 **IME、选区、撤销、剪贴板、无障碍、文本模型**——这些正是“完全自研”最难的部分；我们只写“宿主”，不写“文字引擎”。
- Office 的 XAML `TextBox`/`RichTextBox`、Word/Outlook 的一部分是 windowless RichEdit 跑 D2D/DirectWrite 路径；但那是 **Office 自带 `riched20.dll` 的 RichEditD2D**，系统 `msftedit.dll` 没有移植（spike 实测 `TxDrawD2D` 空画）。
- 系统版的可行路径：`ITextServices::TxDraw` 画到**宿主先画好背景的内存 DIB/兼容 DC**，RichEdit 只画文字/caret/选区；视觉上就是透明，最终稿仍走现有 DirectWrite 排版。

**验证顺序（1–2 天）**：

1. 用 C# 手工 COM vtable 实现最小 `ITextHost`（`TxGetDC/TxReleaseDC/TxGetClientRect/TxGetBackStyle/TxGetSysColor/TxCreateCaret/TxSetCaretPos/TxNotify` 等），`CreateTextServices` 创建、`TxSendMessage` 输入。
2. 把 `TxDraw` 画到一张 32 位 DIB/兼容 DC（背景由宿主先画），验证：白板/深色板/图片上编辑时背景无缝、圆角裁剪正常、IME 候选窗位置正确。
3. 如果 1–2 天能跑通中文输入/光标/选区，就走 B0；跑不通再退回 A（纯色近似）。
4. B0 成功后再接：样式背景（我们画）、富文本 run（RichEdit 自带）、Markdown/流式（仍走只读块渲染）。

**不建议从零写完整编辑器**：Figma/Google Docs 这类“画布 + 隐藏输入”架构是成熟做法，但工作量在 IME、选区、撤销、无障碍、剪贴板，不在画字本身。B0 让我们**保留系统文字引擎、只换宿主**，是“自己写输入框”里风险最低的一条。

### 2.7 图片能不能放进文本框

**各家做法**：

- **Word / PowerPoint**：支持内联图片/对象，但这是文字处理器逻辑；图片作为字符/对象参与排版。
- **Notion / Lexical / ProseMirror**：图片是 **block 或 inline atom node**，选中/删除按一个整体；很多编辑器把大图强制单独一行，避免行内重排问题（Aztec 的教训）。
- **GoodNotes / Notability / Miro / Figma 的文本框**：基本是纯文字；图片是独立对象，不内联。
- **我们的现状**：图片是独立 `StrokeKind.Image`，文本框是纯文字；没有内联图片模型。

**建议**：

- **第一版不做内联图片**：图片保持独立对象，允许“绑定/成组到文本框”（移动/缩放一起走），但不参与文字排版。
- **AI 图像建议**用“块”而不是“文本框内联”：AI 卡片里可以有 `ImageBlock` + 说明文字；生成完可“插入为独立图片对象”。
- 如果以后一定要“图文混排”，做 **block 容器**（Notion 式：段落块 + 图片块 + 表格块），不要把它塞进现在的 `TextBoxData`；否则命中、选择、导出、撤销都会变复杂。
- 小图标/表情：用 emoji/Unicode，不引入内联图片。

### 2.8 自己研制一个文本框？

| 方案 | 能力 | 工期/风险 | 适合 |
|---|---|---|---|
| **RichEdit 窗口 + DirectWrite 最终稿（现状）** | 输入/IME/撤销/无障碍成熟；编辑时只能纯色矩形 | 低 | 基础文本框 |
| **无窗口 RichEdit 自宿主 + DirectWrite 最终稿** | 编辑时透明/非矩形背景；保留 IME/选区/撤销/无障碍；MD/流式仍走只读块 | 1–3 周，中（COM 宿主/DC/IME/DPI） | **首选，先做技术验证** |
| **完全自绘原生编辑器**（隐藏 RichEdit/TSF + DirectWrite caret/选区） | 完全透明、任意排版、内联图片 | 3–6 周，高（IME/选区/撤销/无障碍） | B0 走不通才考虑 |
| **WebView2 + ProseMirror/Lexical** | 完整富文本/Markdown/图片/CSS 背景 | 2–4 周，中高（多表面/IME/DPI/性能） | 要做“Notion 式块编辑”时 |

**建议**：**先验证 B0（无窗口 RichEdit 自宿主）**，不要直接从零写文字引擎：
- 用户键入：无窗口 RichEdit（IME/撤销/选区/无障碍白拿），宿主自绘背景；
- 最终显示：DirectWrite 自绘（样式/背景/圆角/公式）；
- AI 流式/Markdown：独立的只读块渲染；
- 编辑时背景：透明/圆角由宿主画，RichEdit 只画文字；
- B0 跑不通再退回 A（纯色近似）；完整自绘/WebView2 作为兜底。

**设置页 API 输入框**：现在走 `TextInputService` 的原生 EDIT/RichEdit，背景是系统白底；如果 B0 成功，可以把“单行/多行输入”也收编到同一个自绘宿主，设置页输入框背景就能和页面主题一致。第一版不必改；先把文本框 B0 验证通过。

### 2.9 自研 vs 无窗口 RichEdit：AI / 体验 / 性能对比

先澄清：

- “系统的无边框”如果指**去掉窗口边框的普通 RichEdit**，背景仍然只能纯色（`EM_SETBKGNDCOLOR`），没有 alpha/圆角。
- 真正能透明的是 **无窗口 RichEdit（ITextHost）**；下面说的 B0 都是它。

| 维度 | B0：无窗口 RichEdit 自宿主 | A/C：完全自研 / 块编辑器 |
|---|---|---|
| **AI 流式输出** | 不适合把 token 直接灌进编辑区；流式要走**外部只读块渲染** | 天然适合块级增量、逐 token 追加、只重排尾块 |
| **AI 改写/翻译/润色** | 用 TOM/`EM_*` 取选区、替换 range，能做；格式受 RichEdit 的 run 模型限制 | 直接改文档模型，diff/建议/接受/拒绝更自然 |
| **AI 选中上下文** | TOM 取文本/选区/格式，成熟 | 自建模型，可按块/span 精确取 |
| **Markdown** | 不原生；只能存纯文本/富文本 run，Markdown 需另做只读渲染 | 块模型 + Markdown AST，天然支持 |
| **内联图片/表格** | OLE 对象/表格能做但复杂；建议图片独立 | block/inline node 自然，图片/表格/引用都行 |
| **背景/形状** | **透明/非矩形（宿主自绘背景）** | 完全控制（任意 CSS/几何） |
| **IME / 光标 / 选区 / 撤销 / 无障碍** | **系统级，成熟** | 全部自写，风险最高、最耗时间 |
| **性能（小文本）** | RichEdit C++ 布局，很快；`TxDraw` 走 DC/D2D，小文本框足够 | DirectWrite + 块缓存可以更快，但实现不好更慢 |
| **性能（大文本/流式）** | 逐 token 全量 `SetText` 会整框重排；不适合流式 | 只重排尾块 + 脏区，流式/长文更优 |
| **交互/动画/ghost text** | 受 RichEdit 限制；自绘 caret/选区叠加复杂 | 完全可控：ghost suggestion、动画、inline diff 都好做 |
| **工期/风险** | **1–2 天验证 + 1–3 周落地，中风险** | **3–6+ 周，高风险**（WebView2 + ProseMirror 约 2–4 周） |
| **适合** | 稳定输入、透明背景、设置页输入统一、纯文本+公式 | Notion 式块编辑、内联图片/表格、AI 原生建议/协作 |

**一句话**：

- B0 是“**把系统文字引擎装进我们的画布**”：解决背景/透明/输入体验，风险低，但不解决 Markdown 块/内联图片/流式。
- 完全自研是“**连文字引擎一起重写**”：AI 原生内容最顺，但 IME/光标/选区/撤销/无障碍全部重做，工期和 bug 尾巴大一个数量级。
- 两者不是二选一：**B0 做可编辑文本，独立块渲染做 AI 流式/Markdown**，是当前最稳的组合；等“块编辑”成为核心再上 WebView2 + ProseMirror/Lexical。

### 2.11 场景方案：设置输入 / AI 流式 / 出题图片 / 语音按钮 / 公式所见即所得

先把“一个输入框打天下”拆开：不同场景对“编辑”的要求不一样。

| 场景 | 需要什么 | 推荐 |
|---|---|---|
| **设置页 API Key / 地址 / 模型** | 单行/密码、系统 IME、简单校验 | **继续用原生 EDIT**（或 B0 单行宿主）；不值得为它上富文本/WebView2 |
| **AI 识别（OCR）** | 识别中状态、结果逐行出现 | OCR 多数是一次性返回，**不能真 token 流**；用“识别中 → 逐行揭示/淡入”，不要假装逐字 |
| **AI 回答（LLM）** | 真 token 流、Markdown、代码、公式、图片、可停止 | **只读块渲染 + SSE 流**；按帧合并、只重排尾块 |
| **AI 出题（含图片）** | 题干/选项/答案/解析 + 图片块 | 结构化 JSON + **ImageBlock**；图片独立缓存/对象，不内联进文本框 |
| **触摸屏语音输入** | 大按钮、按住说话/点按、实时转写、可取消 | 原生浮动麦克风按钮 + 流式 STT；插入光标处 |
| **Markdown 公式编辑（所见即所得）** | 点公式就改、虚拟键盘、即时预览 | **WebView2 + MathLive/KaTeX**（AI 面板）；普通文本框先用 LaTeX 弹层+预览 |

#### 2.11.1 设置页 API 输入

- 现在是 `TextInputService` 的原生 `EDIT`，背景是系统白底；这是**可接受**的，设置页不是画布，用户对“系统输入框”不敏感。
- 如果以后 B0 无窗口 RichEdit 验证通过，可以把单行/多行输入也换成同一个宿主，主题、圆角、背景一致；但**不要为了 API Key 输入先上 WebView2**。
- 密码/Key 输入要保留掩码、粘贴、全选、IME；这些原生控件已经成熟。

#### 2.11.2 AI 识别能不能“流式出现”

- **OCR 本质上不是 token 流**：多数视觉 OCR API 是整页识别后一次性返回；少数支持逐行/流式，但不通用。
- 可以做“**感知上的流式**”：
  - 先显示“识别中…”和进度/骨架；
  - 结果返回后按行/按块**逐行淡入**（每行 20–30ms），而不是整块突然出现；
  - 每行出现时可带轻微高亮，让老师知道“这一行刚出来”。
- **不要伪造逐字流**：如果后端没有逐字结果，前端逐字动画会和真实结果不一致，反而显得慢/假。
- **LLM 回答才是真流式**：SSE/HTTP chunk，按 token 到达；按帧合并渲染（见 2.4）。

#### 2.11.3 AI 出题里有图片怎么办

- **题目卡片用结构化模型**，不要塞进一个 `TextBoxData`：

```text
QuestionCard {
  Stem:      RichText/Markdown
  Options:   [{ Text, Correct }]
  Answer:    string
  Explain:   RichText/Markdown
  Images:    [ImageBlock]   // 题干图/选项图/解析图
  Source:    "AI" | "教材截图" | ...
}
```

- 图片是 **ImageBlock**：
  - `ImageData` + `Caption` + `Role`（题干/选项/解析）；
  - 本地缓存（`%APPDATA%\InkTeach\ai-images\`），不每次重新下载；
  - 导出/打印时一起排；
  - 生成图先显示占位骨架，生成完替换；失败保留占位+重试。
- **不要让 AI 返回 base64 大图**直接塞进文本：请求体/内存/存档都会爆炸；返回 `image_id`/URL/本地缓存路径，或由我们单独调用图像生成 API。
- 图片排版：题干图居中、选项图跟随选项、解析图在解析下方；宽度不超过卡片 90%；点击可放大。
- 来源图（教材/PPT 截图）走 `crop → ImageBlock`，不内联进文字。

#### 2.11.4 屏幕中间的大语音按钮

- **只在“文本编辑 / AI 提问”态出现**：一个 72–96px 的圆形麦克风，屏幕下方居中（或键盘上方），触摸好按。
- 交互照豆包/微信：
  - **按住说话**：按下开始、松手结束；上滑取消；实时显示波形 + 部分转写；
  - 或**点按开始/点按结束**（长文本更适合）；设置里可切换；
  - 取消/失败不清空输入框，已转写部分保留在草稿里。
- 转写：
  - **用户 2026-11-09 定：默认云端流式 STT**（Whisper/讯飞/阿里/火山等），需要 Key/网络；
  - 系统语音（Windows Speech）离线但中文一般，作为**离线兜底/可选**；
  - 和 OCR API 一样走“设置 → AI 识别 API”的服务商配置；云端失败时提示并保留草稿，可切离线。
- 插入位置：**当前光标处**；没有编辑框时，新建文本框并插入。
- 不抢笔：按钮只在自己范围命中，画布其他区域照常写；不显示时完全不占命中。

#### 2.11.5 Markdown 公式“所见即所得”与豆包式显示

两条路：

1. **WebView2 + ProseMirror/Lexical + KaTeX/MathLive**（推荐做 AI 面板）
   - Markdown/富文本块、代码、表格、图片、链接、公式都能统一；
   - 公式点一下 → MathLive 就地编辑（虚拟键盘、LaTeX、即时预览）；
   - 流式 Markdown、AI 建议、复制/插入/导出都容易；
   - 豆包/ChatGPT 式聊天卡片本质就是这种“块编辑器/渲染器”。
2. **原生块渲染 + DirectWrite + CSharpMath**
   - 性能最好、和画布无缝；但 Markdown 解析/排版/公式编辑/图片/表格/链接/选区全部自己写；
   - 公式“点开编辑”只能做 LaTeX 弹层 + 预览，不是真正所见即所得；
   - 工期高，适合“只读 AI 卡片”，不适合复杂编辑。

**建议分工**：

- **画布文本框**：B0 无窗口 RichEdit，负责普通文字/简单富文本；公式用“LaTeX 弹层 + 预览”（不是全 WYSIWYG）。
- **AI 面板 / AI 题卡**：WebView2 + ProseMirror/Lexical + MathLive/KaTeX，负责 Markdown、流式、图片、表格、公式所见即所得、语音按钮。
- **共享**：文档模型/图片缓存/语音服务；AI 面板生成完可“插入为画布对象”（文字→文本框，图片→ImageBlock，题目→QuestionCard）。
- 这样不会为了“AI 面板”把整个画布输入换成 WebView2，也不会为了“公式 WYSIWYG”重写整个文字引擎。

**WebView2 的代价**：多一个运行时依赖（Win10/11 一般有 Edge WebView2，学校机器要确认）；多一个窗口表面/IME/DPI/层级；内存比原生高。只放在 AI 面板里，影响面可控。

#### 2.11.6 推荐组合（一句话）

- **普通文本**：B0 无窗口 RichEdit（透明背景 + 系统 IME）。
- **AI 回答/出题/公式/图片/语音**：WebView2 的 AI 面板（块编辑器 + Markdown + MathLive + 图片块 + 语音按钮）。
- **设置页**：原生输入够用；B0 成功后再统一。
- **AI 识别**：OCR 不做假流式，逐行揭示；LLM 才做真 token 流。
- **图片**：独立 ImageBlock/对象，不进文本框。

### 2.12 对优先级的影响

- 如果近期要接 LLM 流式回答：先做 **只读流式卡片**（块渲染 + 按帧合并 + 尾部块重排），不要先改文本框。
- Markdown 只做 AI 卡片/只读块；文本框继续纯文本 + LaTeX。
- 图片先做独立对象/绑定，不做内联。
- 背景样式按 P0 做；编辑时先用纯色近似，B0 验证通过后换成“透明/圆角自宿主”。
- **B0（无窗口 RichEdit）先做 1–2 天技术验证**：能跑通中文 IME/光标/选区/透明背景，就把文本框切过去；跑不通再退回纯色近似。
- 完整自绘编辑器/WebView2 只有在“富文本/Markdown 块编辑”成为明确需求后再立项。

### 2.13 当前代码的优化路径（先不动架构）

#### 2.13.1 设置页 API 输入：不是“颜色不支持”，是“几何不匹配”

- 代码：`TextInputService` 用**普通 EDIT**（不是 RichEdit），所以 `WM_CTLCOLOREDIT` 是支持的；`HostWndProc` 已经设 `SetBkColor/SetTextColor`，并返回 `_brush`。
- `FullUi.ApiSettings.BeginApiField` 已经把 `ApiFieldBg / InkCol / FontSize=13 / Padding=8` 传进来，颜色本身是对的。
- 看起来“不和谐”的原因是：
  - `editRect = field ± 2`，几乎盖满整个字段，把字段的**圆角/边框**盖成方角；
  - EDIT 没有圆角，四角露出白/暗矩形；
  - 字段的内边距/字体/基线是 D2D 画的，EDIT 是 GDI 画的，边缘会差 1–2px。
- **1–2 天可改**：
  1. `editRect` 改成字段的**内缩矩形**（让字段 1px 边框和圆角露出来）；
  2. 给 `_hostHwnd` 加 `SetWindowRgn(CreateRoundRectRgn(...))`，圆角半径跟字段一致（如 10 逻辑像素）；
  3. `TextInputVisual` 增加 `CornerRadius`/`Border`，由页面传；EDIT 仍用 `WM_CTLCOLOREDIT` 填色；
  4. 字体、Padding、垂直居中沿用现有 `EM_SETRECT`，只调 1–2px。

> 结论：**设置 API 输入不需要自研/无窗口 RichEdit，先把 EDIT 的内缩和圆角区域修好即可。**

#### 2.13.2 文本框编辑：RichEdit 只能纯色，且现在颜色选错了

- 代码：`TextBoxEditing` 用 `RICHEDIT50W`；RichEdit **不支持 `WM_CTLCOLOREDIT`**，只能用 `EM_SETBKGNDCOLOR` 设**纯色**。
- `UpdateTextBoxEditColors` 现在：
  - 白板页：用 `BoardColor`；只有字/板太接近才用灰/白高对比底；
  - **PPT/PDF/文档页：一律用 `0.44 灰` 或 `0.95 白灰` 兜底**，不看 `TextBox.Paper`、不看页面实际底色。
- 所以“文本编辑突然有背景”是**必然**：编辑宿主必须有一块不透明底，而当前兜底色和页面/纸面不一致；`Paper=true` 的白纸框反而可能对得上，透明框/PPT 上最明显。
- **1–2 天可改**：
  1. 编辑底色按优先级取：`TextBox.Paper`/未来 `Style.Fill` → 白板 `BoardColor` → 文档页 `DocPaperColor`（大多数 PDF/PPT 是白底）；
  2. 只有“字和底色太接近”时才换高对比兜底；
  3. `SetWindowRgn` 圆角（跟纸面/字段圆角一致），`SetWindowPos` 内缩 1–2px，让最终纸面的边框/阴影露在编辑窗外面；
  4. 编辑窗加 1px 细边/淡强调色，明确告诉用户“这是编辑态”，不再是“莫名其妙多了一块灰”；
  5. 透明背景 + 深色图片/PPT：原生 RichEdit 做不到真透明，只能显示一块**接近页面色的编辑纸**；要真透明再上 B0。

#### 2.13.3 建议顺序

1. **先做 2.13.1 + 2.13.2**（1–2 天）：不改架构，立刻改善设置页和文本框编辑的“突然一块背景/方角”。
2. **B0 已跑通**（见 2.13.4）：透明背景、选区、光标、WM_CHAR、IME 上下文、`ITextServices2` 都过；
   下一步是把它接进现有 `TextBoxEditing`（C# `ITextHost` 或 C++ helper），再让设置页输入统一。
3. **AI 流式/Markdown/公式/图片/语音**仍走独立 AI 面板；不要为了这些先改文本框。
4. WebView2 只放在 AI 面板；设置页/文本框不背这个运行时。

> 用户反馈的“WebView 效率低”是对的：WebView2 启动/内存/窗口表面都更重，**只在 AI 富内容面板用**；普通输入框先用原生/B0。

#### 2.13.4 B0 spike 实测结果（2026-11-09，已跑通）

源码：`tools/B0Spike/B0Spike.cpp`；截图：`tools/B0Spike/b0-transparent.png`、`b0-caret.png`。

| 项目 | 结果 |
|---|---|
| 透明背景（`TXTBACK_TRANSPARENT`） | **通过**：文字压在棋盘格 + 红色竖条上，没有白/灰矩形 |
| 选区（`EM_SETSEL`） | **通过**：前 6 个字半透明蓝色高亮，背景仍透出 |
| 光标（`TxCreateCaret` / `TxSetCaretPos`） | **通过**：点击能把 caret 放到字符间，caret 正常闪烁 |
| 输入（`WM_CHAR` 转发） | **通过**：字符进入文本，`WM_GETTEXTLENGTH`/`EM_EXGETSEL` 正确 |
| IME 宿主（`TxImmGetContext`） | **已接上**：`ImmGetContext` 非空，`WM_IME_*` 已转发；候选窗跟随 caret 需真人中文输入确认 |
| `ITextServices2` / `TxDrawD2D` | QI 返回 `S_OK`，但 **`TxDrawD2D` 在系统 `Msftedit.dll` 上是空画**（返回 `S_OK`、目标无字）；D2D/DirectWrite 版只在 Office 的 `riched20.dll`，系统版没移植 → **接入用 GDI `TxDraw`** |
| 性能（GDI `TxDraw`，1200×800） | 16k 字符 **约 1.9–2.0 ms/帧**；500 次 `WM_CHAR` 约 **320 ms**（0.64 ms/字符） |

坑：`TxNotify` 里对 `EN_CHANGE/EN_UPDATE` 再 `InvalidateRect` 会造成重绘循环、把定时器饿死；
宿主应只依赖 RichEdit 的 `TxInvalidateRect` / `TxViewChange`。

**接入方式（下一步）**

1. **C# 实现 `ITextHost`**（`UnmanagedCallersOnly` + 函数指针表）：不加原生 DLL，JIT/AOT 都能用；
   40 个左右方法，机械但量大，vtable 顺序错会崩。
2. **C++ 小 helper DLL**：COM 实现更稳，但发布/构建多一个原生依赖（需要 MSVC）。
3. **绘制**：用 **GDI `TxDraw`** 画到内存 DC/DIB（`TxDrawD2D` 在系统 `Msftedit.dll` 上是空画，不能用）。
4. **背景**：宿主先画背景，再 `TxDraw` 文字。第一版画“纸面/板色/页色”；透明框在编辑前
   **截取画布该区域快照**当背景，视觉上就是无缝的（画布在编辑时是静态的）。
   真·逐像素透明（背景是视频/动态内容）要 alpha 提取或换编辑器，第一版不做。
5. **窗口**：保留独立编辑窗收焦点/IME，宿主自绘背景 + `SetWindowRgn` 圆角；
   最终形态可把文字并入主画布渲染，去掉独立窗口。

> 结论：**B0 可用，透明背景/选区/光标/输入都过；只差真实中文 IME 候选窗和现有编辑状态机的接入验证。**

#### 2.13.5 已落地：设置页 API 输入（2026-11-09）

- `TextInputVisual` 新增 `CornerRadius`；API 字段的宿主窗 + EDIT 子窗用 `SetWindowRgn` 裁 6 逻辑像素圆角，
  EDIT 内缩 2 逻辑像素，露出 D2D 字段的 8 圆角/边框；字号 12.5 和字段文字对齐。
- 打开服务商/模型下拉前先 `Commit()` 输入：原生 EDIT 是置顶窗口，不收起会盖在 D2D 下拉上面。
- 下拉选择/模型选择也会先提交当前输入，避免切换服务商时用旧输入覆盖新字段。
- 回归入口：`--apiinputshot reports/api-input.bmp 401|402|403`（截编辑态字段）、
  `--apimenushot`（编辑 Key 后开服务商下拉，断言输入已收起、菜单已打开）。
- 相关自检：`--textinputaudit` 10/10、`--settingsaudit` 36/36。

#### 2.13.6 文本框 B0 接入结果（2026-11-09，已跑通）

- 新增 `src/InkEngine/WindowlessTextControl.cs`：C# 实现 `ITextHost` + `ITextServices`，
  仍是一个普通子窗 HWND；`TextBoxEditing` 的 Begin/Commit/边打边长/选区/颜色 span 几乎原样保留。
- 绘制：宿主先画背景，再 `TxDraw`（GDI）。系统 `Msftedit.dll` 的 `TxDrawD2D` 是空画，不能用。
- 背景：
  - 纸面框：铺白纸（`Paper=true`）；
  - 透明框：编辑前让主画布跳过当前文本框，等一帧后 `ScreenCapture.Grab` 截取它下面的画布，
    作为宿主背景；绿粗线从文字后面透出，说明不是纯色近似。
  - 快照抓取约 **17–19ms**（868×239），只在进入编辑时一次。
- 文字内缩用 `TxGetViewInset`（windowless 路径下 `EM_SETRECT` 不参与排版）；
  字号 twips 在 windowless 路径按物理像素换算，否则 2x 屏只有一半大。
- 选区文字色强制白色（`COLOR_HIGHLIGHTTEXT`），深色板不会一选中变黑。
- `TxGetText` 末尾的段落结束符要裁掉，否则自动宽会把光标放到“下一行”，表现为再输入不变宽。

### 2.14 其他软件的文本输入怎么做（2026-11-09 调研）

先给结论：**“文本输入”不是一种技术，而是“编辑面”和“最终渲染”分开的两层。**
成熟产品只在“编辑面”上做选择，没有一个是自己从 IME 开始写的。

#### 2.14.1 五种主流做法

| 类型 | 代表 | 编辑面 | 最终显示 | 背景透明 | 代价 |
|---|---|---|---|---|---|
| **A. 原生输入控件** | WordPad、WinForms TextBox、经典 Notepad、设置页 API 框 | 原生 `EDIT`/`RichEdit` 窗口 | 同一个控件 | 不能（矩形纯色） | 最低 |
| **B. 原生文字引擎 + 宿主自绘** | Office/XAML `TextBox`/`RichEditBox`（内部 RichEdit/WinUIEdit）、Windows 11 Notepad（`RichEditD2DPT`）、我们的 B0 | 无窗口/原生 RichEdit，宿主画背景 | DirectWrite/GDI 最终稿 | 视觉透明（宿主背景），无逐像素 alpha | 中（`ITextHost`/TSF） |
| **C. Canvas + DOM 覆盖层** | Excalidraw（`textarea`）、tldraw 纯文本（`textarea`）/富文本（TipTap）、Konva 推荐、Miro 代码块（Ace/Monaco 覆盖层）、InvokeAI（contenteditable 覆盖层） | DOM `textarea`/`contenteditable` 定位在画布上 | Canvas/Konva 最终渲染 | CSS 透明 | 中低；要对齐字体/缩放/旋转，bug 多 |
| **D. Canvas + 隐藏输入代理 + 自绘** | Google Docs（隐藏 contenteditable iframe + canvas tiles）、Figma（自研文本引擎）、Fabric.js（hiddenTextarea + 画布 caret/选区）、WeaveJS（hidden textarea + 自绘 caret/选区） | 隐藏 `input`/`textarea` 收 IME | Canvas 自绘 | 完全可控 | 高（文本引擎/选区/无障碍） |
| **E. DOM 富文本** | Notion、ProseMirror/Lexical/TipTap 系、豆包/ChatGPT 这类聊天输入 | `contenteditable` DOM 就是文档 | DOM | CSS 透明 | 中（富文本/Markdown 免费；性能/画布集成差） |

#### 2.14.2 具体怎么做的

**Excalidraw（C，最值得抄状态机）**

- 源码 `textWysiwyg.tsx`：编辑时动态创建一个 `<textarea>`，按文字元素的 x/y/宽高/旋转/缩放定位，字体、字号、颜色、对齐都设成和画布文字一致；
- `editable.focus({ preventScroll: true })`，避免焦点把画布滚走；
- 输入时把 `textarea.value` 同步回元素并重绘画布；失焦/点画布提交；
- 打开属性面板/弹层时不提交、不抢焦点；关闭后把焦点还给 textarea；
- 光标跑出视口时滚动/平移画布让 caret 可见；
- Alt+拖拽 = 先提交再复制，保持和画布一致；
- 提交后 textarea 销毁，只剩画布文字。

**tldraw（C）**

- 纯文本用 `textarea` 覆盖层；富文本用 TipTap（ProseMirror）的 `RichTextArea`，最终仍由画布渲染；
- 富文本导出用 SVG `foreignObject`，官方也承认这不是理想方案；
- 教训：富文本一旦进来，编辑面、测量、导出会分成三套，容易不一致。

**Konva（C，官方明确推荐覆盖层）**

- 官方文档直接说：Canvas API 不适合做文本编辑，建议用 `input`/`textarea` 覆盖层；
- 同时列出覆盖层的坑：缩放/换行时编辑视图和最终视图不一致、Web 字体加载后行高变化、单段多样式要自己拆、撤销栈要和画布合并、导出保真度；
- 原话大意：做到这一步，你已经在写文本引擎，而不是加一个编辑功能。

**Fabric.js（D）**

- `IText` 用 `hiddenTextarea` 收键盘/IME，画布自己画文字、caret、选区；
- textarea 虽然是隐藏的，但要跟着 caret 移动，否则中文/日文候选窗位置不对；
- 选区要同步 `selectionStart/selectionEnd`，否则 macOS 长按替换、输入法联想等会错；
- 教训：隐藏代理 + 自绘 caret 可行，但边界情况很多。

**Miro（C）**

- 代码块：查看态由画布渲染；编辑态把 Ace/Monaco 的 HTML 编辑器覆盖上去，用 CSS transform 按“画布缩放 × 控件缩放”手动缩放；
- 提交后回到画布静态高亮；
- 教训：连成熟产品也要手动处理 HTML 编辑器的缩放/旋转/对齐。

**Google Docs（D）**

- 正文用 canvas tiles 渲染；输入走隐藏的 `.docs-texteventtarget-iframe` 里的 contenteditable；
- caret/选区由 Docs 自己画；另有 DOM mirror 给屏幕阅读器；
- 教训：顶级 WYSIWYG 是“canvas 渲染 + 隐藏输入”，投入是年级别的。

**Figma（D）**

- 主文本是自研文本布局/编辑引擎（Evan Wallace 的总结：文本选择/编辑没有现成库，必须自己写）；
- 代码层反而用 CodeMirror 的 DOM 覆盖层；
- 教训：只有“文本是核心产品”才值得自研引擎；普通画布文本框不值得。

**XAML / Office / Notepad（B）**

- XAML 的 `TextBox`/`PasswordBox`/`RichEditBox` 内部就是用 Win32 RichEdit（WinUI3 是 `WinUIEdit.dll`），IME 走 TSF；
- Windows 11 Notepad 用 `RichEditD2DPT` 窗口类，文字走 DirectWrite；
- Office 的 RichEditD2D 在 Office 自带 `riched20.dll`，系统 `msftedit.dll` 没有移植（我们 spike 已实测 `TxDrawD2D` 空画）；
- 教训：微软自己的控件也是“原生文字引擎 + 框架外观”，不是从零写文字引擎。

#### 2.14.3 共同规律（可直接抄）

1. **编辑面 ≠ 最终渲染。** Excalidraw/Konva/tldraw/Fabric 都是编辑时用一个输入面，提交后由画布画最终稿。我们的 B0 是原生版：RichEdit 收输入，D2D 画最终稿。
2. **透明背景靠编辑面自己。** DOM 用 CSS `background: transparent`；B0 用宿主先画背景再 `TxDraw`。普通窗口 RichEdit 做不到。
3. **不自己写 IME/选区。** A/B 用系统引擎；D 也要一个隐藏的系统输入元素收 IME。没人从 TSF 开始写。
4. **覆盖层最大的坑是“对不齐”。** 字体度量、缩放/旋转、换行、padding、caret 滚动、失焦/工具栏交互、导出；Konva/tldraw/Excalidraw 的 issue 大量是这些。
5. **富文本/块编辑会把你推向 DOM 或自研引擎。** tldraw 用 TipTap；Figma/Google Docs 自研。普通画布文本框不值得。

#### 2.14.4 对 InkTeach 的映射

| 场景 | 抄谁 | 我们怎么做 |
|---|---|---|
| 设置页 API 输入 | Windows/macOS 表单、Web `<input>` | 原生 `EDIT` + 内缩/圆角/主题色；不换编辑器 |
| 画布文本框 | Excalidraw 的编辑状态机 + XAML 的原生引擎 | B0 无窗口 RichEdit；宿主画纸面/板色/页色/快照；提交后 D2D 最终稿 |
| AI 面板/聊天 | Notion/ProseMirror/Lexical/TipTap | 先只读块渲染；要 Markdown/公式编辑再上 WebView2 + ProseMirror/MathLive |
| 复杂富文本画布 | Figma/Google Docs | 不做；除非“块编辑”成为核心 |

**画布文本框要抄 Excalidraw 的状态机，不是抄它的 DOM：**

- 双击进入；点画布空白提交；点工具栏/色带/属性面板不提交（只丢焦点）；
- Esc 提交；Ctrl+Enter 提交；空的新框丢弃；
- 打开属性面板时保留选区，关闭后焦点回到编辑框；
- 编辑时缩放/平移：要么提交，要么让编辑框跟随并同步字号/位置；
- 编辑框字体/行高/内边距必须和最终 D2D 渲染一致；
- 编辑时临时隐藏最终稿，提交后只留最终稿，避免“双份文字”。

**不要抄的：**

- 不要抄 Google Docs/Figma 的自绘 caret/选区（除非要做完整块编辑器）；
- 不要抄 Excalidraw 的 textarea 样式细节（我们是原生 RichEdit，不是 DOM）；
- 不要把 AI 聊天输入做成画布文本框（它是 DOM 富文本场景）。

#### 2.14.5 一句话

**其他软件的“文本输入” = 选一个成熟输入面（原生控件/隐藏输入/DOM 覆盖层）+ 自己画最终稿。**
B0 就是原生版的 Excalidraw 覆盖层：系统负责 IME/光标/选区/撤销，我们负责背景和最终样式；
设置页继续用原生 `EDIT`；AI 富文本以后再用 DOM/WebView2。

## 三、规则一：背景与样式

### 3.1 一条样式模型

```text
TextBoxStyle {
  Shape:        Rect | Rounded | Sticky | Callout | Pill
  Fill:         Color4 + Alpha (0–100%)
  Border:       Color4 + Width (0–3) + Dash (Solid/Dash/Dot)
  CornerRadius: 0–24
  Padding:      4–32
  Shadow:       None | Soft
  AutoFit:      GrowHeight（默认）| ShrinkText | Fixed
}
```

- `Paper=true/false` 迁移成 `Style.Fill`：白纸 = 白 98% + 1px 灰边 + 圆角 12；
  透明 = Fill Alpha 0 + 无边框。
- 旧存档 `Paper` 字节保留，读回时生成等价 Style；写新档用 v29 样式字段。
- 样式只影响外观，不改变文本、排版、撤销、导出语义。

### 3.2 预设（第一版 6 个）

| 预设 | 适用 | 规则 |
|---|---|---|
| **透明**（默认） | 白板/PPT/PDF 上直接写字 | 无填充、无边框；文字色按底色自动深浅 |
| **白纸** | 深色板、图片上、需要遮住底纹 | 白 98% + 1px 灰边 + 圆角 12 + 阴影轻 |
| **便签黄** | 重点/待办 | 暖黄 96% + 同色深边 + 圆角 8；文字深色 |
| **便签蓝/绿** | 分类/分组 | 同上，换色 |
| **重点框** | 强调一句 | 透明底 + 2px 红/橙边 + 圆角 8 |
| **气泡/标注** | 指向图形/板书 | 白纸 + 小三角/圆角气泡；文字深色 |

- 预设不是“主题”，是**文本框样式**；点一下套用，可再微调。
- “保存为默认”：新建文本框默认用这一套（GoodNotes 的 Save as Default）。
- “应用到选中”：多选文本框时统一样式（Freeform 的 Copy/Paste Style 思路）。

### 3.3 自动对比度（最重要的背景规则）

**按“实际可见背景”算，不按白板算。**

```text
effectiveBg = Style.Fill.Alpha >= 0.85 ? Style.Fill.Color : BoardColor/PageColor
effectiveText = Style.TextColor
if contrast(effectiveBg, effectiveText) < 3.0:
    effectiveText = luminance(effectiveBg) > 0.55 ? 深色 : 白色
```

- 白纸 + 白墨 → 自动改深色（或把纸改成深色），**绝不白纸白字**。
- 黑/绿板 + 深墨 → 自动改白字，或建议加白纸。
- OCR 识别到文本框：`Paper` + 原墨色可能撞色；识别完成时按上面的规则校正一次。
- 用户手动选的颜色**不强制覆盖**，但对比度低于 2.0 时给一行提示：
  “文字和背景太接近，可能看不清 · 一键提高对比度”。
- 半透明背景（Alpha < 0.85）按“背景色 + 板色”混色后再算。

### 3.4 背景边框的取舍

- **默认无边框**（Miro 把边框砍掉后大量用户抱怨，说明“需要时能有”比“默认一直有”重要）。
- 边框是可选样式，不做强制；重点框/便签才有。
- 阴影只给“纸面/便签”一档轻阴影，不做多层重阴影（避免虚影和“脏”）。
- 圆角 0–24；默认 12（白纸）/8（便签/重点框）。
- 内边距默认 18 逻辑像素；最小 8，最大 32；背景越大，文字不贴边。

## 四、规则二：输入不丢失

### 4.1 提交语义（保持简单、可预期）

- **点画布空白 / 点其他对象** = 提交。
- **点工具栏 / 色带 / 面板** = 不结束编辑（只丢焦点，`WM_KILLFOCUS` 不提交）。
- **Esc** = 提交（不是丢弃；用户已经打了一大段，Esc 丢弃是最坏体验）。
- **Ctrl+Enter** = 提交。
- **空的新框** = 丢弃，不留空框。
- **老框被清空** = 恢复原文 + 一步删除撤销（现有逻辑，保留）。
- **删除文本框时正在编辑** = 先收起编辑窗再删（现有逻辑，保留）。

### 4.2 草稿日志（新增，P0）

- 每个正在编辑的文本框，**每 1 秒**（或每次文本变化后 300ms 防抖）把：
  `strokeId`、`text`、`caret`、`selection`、样式、原文本、时间戳 写入
  `%APPDATA%\InkTeach\drafts\textbox.json`。
- 正常提交 / 取消后删除草稿。
- 启动时如果草稿比文档新：
  - 弹出轻提示“上次有一段文字没保存，已恢复”；
  - 把草稿写回对应文本框（找不到框就新建一个，位置用最后位置）。
- 不做“每敲一个字写一次盘”：防抖 + 1 秒上限，SSD 压力可忽略。
- 草稿只存**正在编辑的那一段**，不复制整份板书；体积小。

### 4.3 自动存档与状态

- 文本框提交后立即进入文档撤销栈；白板/PPT 自动存档继续每 15 秒。
- 编辑中实时写模型（已有），自动存档会带上；草稿日志是“崩溃兜底”。
- 页脚/状态行给一个**很轻的保存状态**：
  “已保存 · 14:32” / “保存中…” / “保存失败，已留草稿”。
  不弹窗、不阻塞；失败才提示。
- 可选：每 5 分钟留一个只读版本（最近 12 个），在“更多 → 墨迹 → 历史板书”里恢复；P1。

### 4.4 切页 / 切工具 / 切文档

- 切工具：提交到**当前页**（现有 `SetTool` 已提交）。
- 切页 / 翻页 / 进 PPT 下一页：先提交当前文本框，再切页；提交失败就保留草稿并提示。
- 切文档 / 打开历史板书：先提交当前编辑；未提交的草稿不跨文档串页（草稿带 pageKey）。
- 撤销 / 重做：编辑中先走 RichEdit 内部撤销；提交后走文档撤销；不要两层撤销混着用（现有设计要保持）。

### 4.5 IME / 手写 / 大粘贴

- 中文输入法组合中（composition）不提交、不截断；Enter 在组合中只上屏，不换行/不提交。
- 手写输入（Scribble/我们 AI 识别）：识别中不自动替换正在编辑的文本，先给候选/确认。
- 粘贴超过 20000 字：**明确提示并保留前 20000 字 + 剪贴板原内容**，不静默丢；参考 Miro 的“超限转 Doc”思路，我们可以提示“分两段粘”。
- 粘贴含公式/图片：公式按现有 `$...$` 处理；图片不塞进文本框（单独图片对象），避免文本框变成富文本编辑器。

## 五、规则三：“自己的图型”——文本框形状

### 5.1 第一版只做“背景形状”，不做“框内画图”

- `Rounded`（默认）、`Rect`、`Sticky`（便签，轻微折角/阴影）、`Callout`（气泡 + 小三角）、`Pill`（胶囊标签）。
- 形状只是背景，文字排版仍在内部矩形里；不改命中、选择、旋转、缩放。
- 形状的圆角/内边距/边框走同一套 Style；不为每种形状写一套绘制。
- 不做：任意多边形/手绘轮廓作为文本框背景（复杂、命中难、导出难）。

### 5.2 文字放在图形上（P1）

课堂常见“在图形里写标签/在箭头上写说明”：
- 选中图形 → “添加文字” → 生成一个绑定到图形的文本框（文字随图形移动/缩放）；
- 或选中文本框 + 图形 → “绑定到图形”；
- 导出/存档保持绑定关系；解绑后变普通文本框。
- 参考 PowerPoint“形状内文字”、Miro“形状里打字”、Freeform“形状双击输入文字”。
- 这比“文本框自己变成任意形状”更实用，也更稳。

### 5.3 样式复制/粘贴（P1，低成本）

- `Ctrl+Alt+C / Ctrl+Alt+V`（Miro 口径）或操作条“复制样式 / 粘贴样式”；
- 只复制 TextBoxStyle + 字体/字号/行距/对齐，不复制文字；
- 多选时可“应用到选中”。

## 六、建议优先级

| 优先级 | 内容 | 预估 | 风险 |
|---|---|---|---|
| **P0** | TextBoxStyle（背景/边框/圆角/内边距/阴影/形状）+ 6 预设 + 保存默认 | 3–5 天 | 低 |
| **P0** | 自动对比度（按实际背景；OCR 纸面校正） | 1–2 天 | 低（规则清晰） |
| **P0** | 草稿日志（1s 防抖）+ 启动恢复 + 保存状态 | 2–3 天 | 中（磁盘/恢复路径） |
| **P1** | 对齐/行距/列表/高亮/链接/加粗斜体下划线 | 3–5 天 | 中（RichEdit 与自绘排版两套） |
| **P1** | 形状底（便签/气泡/重点框）+ 文字绑定图形 | 3–5 天 | 中 |
| **P1** | 自动调整三档（长高/缩字/固定） | 2 天 | 低 |
| **P1** | 样式复制/粘贴 | 1 天 | 低 |
| **P2** | 版本历史（最近 12 版） | 2–3 天 | 中 |
| **P2** | AI 改写/摘要/翻译、文字转语音 | 3–5 天 | 中高（依赖 AI/费用） |

**建议先做 P0 三项**：样式 + 对比度 + 草稿日志。它们直接解决“背景不好看/看不清/怕丢字”，且不碰 AI。

## 七、数据与框架影响

- `TextBoxData.Paper`（bool）→ `TextBoxStyle Style`；`Paper` 保留为兼容读入。
- 序列化：v29 增加样式字段；旧档 v28 读入时 `Paper=true` → 白纸预设，`false` → 透明预设。
- `TextBoxData` 已有 `Face/Font Size/LineSpacing/LineColors/ColorSpans`；样式只加“外观”，不动这些。
- 草稿日志独立 `TextDraftJournal`（类似 `BoardHistory`），不写进 `.inkb`；
  恢复时只写回文档，走正常撤销栈。
- 对比度工具 `Contrast` 放 `InkEngine`，绘制、OCR、设置预览共用一份。
- 设置页：`设置 → 文本` 加“默认文本框样式 / 自动对比度 / 草稿恢复”三项；
  不要每项都开一个页面，沿用现有单列滚动。
- 自检：
  - `--textstyleaudit`：6 预设 × 0.8/1.0/1.3，背景/边框/圆角/内边距像素；
  - `--contrastaudit`：白纸白字、黑板白字、半透明混色、OCR 纸面；
  - `--drafttest`：编辑中杀进程/重启恢复、提交后草稿清除、切页不串页；
  - `--textboxsim` 扩展：样式/对比度/草稿各 3–5 条。

## 八、明确不做 / 后置

- 渐变、纹理、3D、艺术字、文字描边（WordArt）：课堂收益低，渲染/导出复杂。
- 完整 Word 级富文本（分栏、页眉页脚、目录）：我们不是文档编辑器。
- 任意手绘轮廓当文本框：命中/缩放/导出都难，先不做。
- 每个文本框自动 AI 改写：打断书写、费用不可控；只做“选中后手动”。
- 边框默认常显：Miro 的教训——需要时能有，默认不要。
- 把图片/表格塞进文本框：保持“文本框 = 文字”，图片/表格是独立对象。
