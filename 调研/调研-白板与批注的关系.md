# 白板和桌面批注是什么关系：一层遮罩，还是两套手写？

日期：2026-09-16　　状态：调研 + 建议（模型层，动引擎之前要定）

---

## 〇、先给事实：**现在就是"遮了一层"，手写是同一套、互相可见**

代码里白板的全部内容就三处：

```csharp
// Engine.cs
internal bool BoardOn;                                    // 一个 bool
internal Color4 BoardColor = new(0.99f, 0.99f, 0.98f, 1f); // 一个颜色
internal void SetBoardFromUi(bool on)
{
    if (BoardOn == on) return;
    BoardOn = on;
    Doc.InvalidateAll();      // 只是重画，不动笔迹
    _dirty = true;
}

// Overlay.cs
var want = app.BoardOn ? app.BoardColor : Transparent;   // 底色：板色 or 全透明
```

**关键三点**：

1. **只有一份文档**（`Doc.Strokes`），白板不新建笔画层、也不清笔画 ——
   `SetBoardFromUi` 里唯一做的事就是"让所有分块重画"；
2. **底色是"画进分块缓存"的**（注释原话：透明批注 = 擦成全透明，白板 = 铺底色），
   **不进文档**。所以换底色 = 所有块过期重画（`MarkAllDirty` + `forceFullFrame`）；
3. 因此：**在白板上写的字、切回 PPT 之后还在**（它本来就是同一批笔画，
   只是底色从"板色"换回了"透明"）。

顺带澄清一个常见的担心：**白板上用橡皮擦过的地方，切回 PPT 不会留白块**。
因为像素橡皮是"把一笔切成两段"（矢量层面），
"白"只是缓存里的底色，不是文档里的内容。

---

## 一、机制：这层"遮罩"在系统上**是怎么落下去的**

要真正看懂"为什么它必然是同一套手写"，得往下走四层。每层各回答一个问题。

### 第 1 层　窗口：桌面和 PPT **根本不知道我们存在**

覆盖层是一个 Win32 窗口：`WS_POPUP | WS_EX_TOPMOST | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE
| WS_EX_NOREDIRECTIONBITMAP`，交换链走 `CreateSwapChainForComposition` ＋ `AlphaMode.Premultiplied`
（`Overlay.cs` 的 `Create` / `CreateDeviceResources`）。

于是有三件事是天生成立的：

- **我们不是桌面的一部分，是浮在桌面之上的一块玻璃。**
  玻璃上 alpha = 0 的地方，桌面原样透过来；不透明的地方就把桌面盖住。
  **所谓"白板"，就是把这整块玻璃从"全透明"刷成"不透明板色"** —— 就这么一件事。
- **底下的程序照常跑**：PPT 动画、视频、鼠标、计时都不受我们影响。白板**不是暂停键**，
  它只是一块盖在上面的板。（反过来，透明批注时学生看得见底下鼠标在动 —— 讲演示时这是优点，别丢。）
- **不抢焦点**（`WS_EX_NOACTIVATE`）：我们写字的时候 PPT 仍然收得到键盘。
  这是所有交互的前提；"批注键盘模式"是唯一的例外，它临时去掉这个样式。

### 第 2 层　文档：**只有一份**，白板不新建、不清空、不复制

`Doc.Strokes` 是唯一的笔画列表，`ViewOffsetY` 是它的相机（所以画布可以比屏幕更高，能往下滚着写）。
白板**不是第二份文档** —— `SetBoardFromUi` 里除了 `BoardOn = on` 和一个"全部重画"以外什么都不做。

**"A 模型"的定义就落在这一层**：白板是"底"，不是"层"。

### 第 3 层　像素：底色是**画进分块缓存里**的，不是窗口属性

渲染是分块的（256×256 的纹理缓存，`CanvasTiles.cs`）。每块光栅化时第一件事是
用 `BoardBrush` 把这块刷成"板色 **或** 全透明"，然后才往上画笔画。

所以底色一变，**所有已经缓存好的块立刻过期**：`MarkAllDirty()` ＋ `forceFullFrame`，
整屏重画一次。（`Overlay.cs` 自己会发现板态变了；引擎的 `SetBoardFromUi` 里还多调了一次
`Doc.InvalidateAll()` —— 两条路殊途同归，那一句其实可以省。）

| 这个设计带来什么 | 说明 |
|---|---|
| 切板有**一次性**代价 | 一次全屏重画，成本与"当前可见笔迹量"成正比。万笔量级的全量重建实测 **274 ms**（`reports/stress-0914`）；课堂上一页通常低一个量级，体感是一次轻微的"重铺" |
| 像素橡皮**不会**在白板上留白块 | 橡皮在矢量层面把一笔切成两段，"白"只是缓存里的底、不是文档里的内容 —— 所以切回 PPT 不留疤 |
| 板色可以随便换 | 因为它不进文档，换色＝重画，没有历史包袱（界面上已有白 / 绿 / 黑三色） |

### 第 4 层　截图：走的是"把我们的窗口藏起来再抓桌屏"，与板态是两条路

`ScreenCapture.HiddenOverlay`：把覆盖层 `SW_HIDE` → `DwmFlush` → `BitBlt` 桌面 → 再
`SW_SHOWNOACTIVATE` 显示回来（`SW_SHOWNOACTIVATE` 是为了截完图别抢走焦点，
否则正在放的 PPT 就收不到键盘了）。

- 界面上的"**隐藏批注截取**"就是这条路：抓到的是干净的桌面 / PPT，这正是它存在的意义；
- 界面上的"**直接截取**"那一档，引擎里目前**还没有**对应的路（`EndCapture` 一律走 HiddenOverlay）；
  要实现就是"不藏、直接抓"，落点很小。**这两档都和板态无关。**
- `--board` 那个命令行开关**不是产品功能**，是自检截图的技巧：把板打开让覆盖层变成不透明，
  自检抓屏时就"只有我们自己的内容，不含桌面"（`App.cs`、`README.md` 都注明了产品里的截图不能这么做）。

### 一页总结：白板**是**什么、**不是**什么

| 是 | 不是 |
|---|---|
| 一块更不透明的"底"（画布底色） | 一个独立文档 / 独立图层 |
| 同一套笔迹换了个背景 | 两套互不可见的手写 |
| 盖在桌面之上的一层玻璃 | 对桌面内容的"接管"或"暂停" |
| 一个随时开合的开关 | 一种"模式"（工具、撤销栈、清空范围都不分板内板外） |
| 盖住**整个虚拟桌面**（所有显示器） | 只盖一块选定区域 |

> **一句话**：白板和桌面批注是**同一张纸的两面** —— 同一份笔迹，只是纸背面的底色
> 从"透明"换成了"板色"。所以"手写互不可见"既不是现在的行为，
> 也**不是靠加个开关就能调出来的行为**：要它就得动第 2 层（给每一笔加标记），见下面的 B 模型。

## 二、那"互不可见"是另一种模型，得先说清三种可能

| | A. 一层遮罩（**现状**） | B. 一份文档 ＋ 每笔一个标记 | C. 两套文档（两个层） |
|---|---|---|---|
| 白板是什么 | 画布底色 | 底色 ＋ "这一笔属于哪种底" | 独立的第二份文档 |
| 手写关系 | **同一套，互相可见** | **互不可见**（按标记过滤） | 互不可见，且各自独立 |
| 切回 PPT 后白板上的字 | **还在** | 看不见（被过滤） | 看不见 |
| 清空清掉什么 | 全部（白板＋批注） | **当前这种底的** | 当前层的 |
| 撤销栈 | 一条 | 一条（跨两种底） | 一条或两条（要定） |
| 引擎改动 | **0（已经这样）** | 改 5～6 处（都有现成钩子） | 动文档模型，几天量级 |
| 风险 | 低 | 中（要保证"过滤规则处处一致"） | 高 |

### 教室里的四个真实场景，三种模型谁满足

| 场景 | A 遮罩 | B 标记 | C 两层 |
|---|---|---|---|
| ① 讲题时在白板上打草稿，讲完切回 PPT，**草稿要消失** | ✗ 还在 | ✓ | ✓ |
| ② 在 PPT 上圈了重点，切白板继续写，**切回来圈还在** | ✓ | ✓ | ✓ |
| ③ **只想擦掉白板上的字**，PPT 上的标注留着 | 只能框选着擦 | ✓ | ✓ |
| ④ 白板的板书要留、PPT 上的标注不要 | 只能框选着删 | ✓ | ✓ |

看这张表就知道：**A 能满足的是场景 ②（也是最常见的那个：标注跨页保留）；
B 四个都能满足；C 和 B 一样全满足，但贵得多。**

## 三、建议：**先留在 A，但要补三条交互；真要"互不可见"就走 B，不要走 C**

### 为什么先留在 A

1. **引擎已经这么做，改动为 0**；
2. 场景 ②（标注跨页保留）是教室里最常见、也最符合"批注"这个词的行为；
3. 场景 ①（草稿要消失）用**清空**一步就能达到，而且清空可撤销 —— 代价是"多按一下"。

### A 需要补的三条（都是为了消除"A 的三个困惑"）

| 困惑 | 补什么 |
|---|---|
| "我切回 PPT，怎么上面还有刚才白板写的字？" | **切回批注时给一次轻提示**：`白板上的 5 笔已保留在画布上（清空或框选可去掉）`。只在"白板期间真的画过"时才提示 |
| "清空把 PPT 上的标注也清掉了" | 清空按钮的文字/提示写明**作用范围是整个画布**；真要分开，用框选删除。这条要写进《快捷键总表》 |
| "我怎么知道现在是在白板上？" | 白板按钮的**激活态**（已经有了）＋ 底色的对比（白/绿/黑板）足够 |

### 如果后来场景 ①③④ 变成刚需：**做 B，不做 C**

B 的具体做法（这是我最想记下来的部分）：

1. `Stroke` 加 **一位** `OnBoard`（存档 v4 加一位，老档默认"批注"，老文件照样能开）；
2. 给 `Doc` 加**唯一一处"可见性"判断**（`VisibleTo(bool board)`），
   **所有遍历都走它**：内容层重建、命中测试、框选/套索、橡皮、清空、存档/剪贴板。
   —— 关键是**只写一处**，五六个调用点各自写一遍必然会出现"框选能选到看不见的东西"这类 bug；
3. 切板时的重画**已经现成**（`MarkAllDirty` + `forceFullFrame`）；
4. 清空改成"清当前可见的"，一步撤销；
5. 撤销栈**保持一条**（简单、可预期），但撤销掉"当前看不见的那一笔"时**给一次提示**
   （`刚撤销的一笔画在白板上`），否则用户会觉得"按了没反应"。

**成本估计**：B 是一天量级（有现成钩子），C 是几天量级且要动核心数据结构 ——
所以将来要升级，也是 B。

> 还有一个变体值得记一笔：**"白板 = 一次性草稿纸"**（关板自动清掉白板上的笔画，可撤销）。
> 它就是 B 加一条"关板即弃"。有人会喜欢，但**不能做默认**（关了板板书就没了，教室里太危险），
> 可以作为设置项。

---

## 四、这件事要现在定吗

**不用现在做，但要现在定"往哪边走"。** 因为：

- 界面这边做的事与模型无关（白板按钮、板色、开板关穿透都已经做完且自检通过）；
- 而**存档格式**与它有关：如果确定将来要走 B，`InkSerializer` 的下一版就**留一位**给 `OnBoard`；
  如果确定永远走 A，那一版就不用留。**这个决定越早越省事**（改存档格式要兼容老文件）。

**我的建议**：**A + 三条交互**，并在下一版存档格式里**留一位**（先都写 0），
这样将来想升级到 B 时不用再动格式。

## 五、这条也该有自检（接引擎时）

| 检查 | 判据 |
|---|---|
| 切板不改笔迹数量 | 开板/关板前后 `Doc.Strokes.Count` 不变（**A 的核心不变量**） |
| 切板不改笔迹内容 | 每笔的采样点与颜色逐字段一致 |
| 切板后像素橡皮擦过的段仍然擦着 | 擦断形成的两段仍是两段 |
| （若做 B）切板只改可见性 | 关板后"属于白板"的笔画进不了命中测试与框选 |
| （若做 B）清空只清当前底 | 清空前统计两种底的笔数，清空后另一种底的数量不变 |
