## 〇、结论先行

1. **成熟系统没有把“页面、浮层、文字输入”做成同一个 Page。**
   它们至少分成四层：**窗口（宿主）→ 页面（路由）→ 浮层（层）→ 服务（输入/焦点/滚动）**。
   这正好对应我们计划的 `WindowManager → PageHost → OverlayLayerManager → TextInputService`。
2. **页面管理的核心不是“画一个面板”，而是“栈 + 路由身份 + 生命周期 + 返回结果”。**
   Flutter `Navigator`、WPF `NavigationService + Journal`、Qt `StackView`、Android `FragmentManager`
   都是同一套：push / pop / replace / popToRoot，返回时恢复上一页，页面有进入/离开/暂停/恢复。
3. **浮层管理的核心不是“z-index 数字”，而是“一张唯一的优先级表 + 命中测试 + 输入捕获 + 轻关闭”。**
   Web 的 top layer / `popover`、Slate 的 `FWidgetPath`、Chromium 的 event phase、Avalonia 的
   `OverlayLayer` 都在解决同一件事：谁在最上面、谁先吃输入、点到外面算不算关闭。
4. **模态不是“画一层黑色遮罩”，而是四件事同时成立：**
   阻断下层输入（inert）、焦点陷阱（focus trap）、Esc/点外关闭策略、关闭后恢复焦点。
   Web `<dialog>.showModal()` 是最完整的现成范本。
5. **输入路由的先进做法是“从最上层往下命中 + 捕获 + 隧道/冒泡 + 手势竞技场”。**
   不是在每个 `OnPointerDown` 里手写“图库 → 回放 → 界面 → 计时 → 点名 → PPT → 画布”。
6. **焦点必须按“作用域”管理：一个窗口一个 FocusManager，一个模态一个 FocusScope。**
   Avalonia、Flutter、Chromium、Unity、Qt 都有明确的 focus scope / focus ring / restore 概念。
7. **滚动是一个容器能力，不是每个页面自己写一套。**
   viewport + content + offset + max + 滚轮/触摸/键盘/滚动条，全部走同一条 `ScrollBy`；
   惯性参数全应用共用一套（我们已抽成 `UiTouchFling`）。
8. **文字输入是服务，不是页面，也不是“第三类原生窗”。**
   一个窗口一个可激活的原生输入宿主；页面只提供“矩形 + 初值 + 校验 + 提交/取消”；
   IME、光标、选区、复制粘贴、撤销交给 `EDIT/RichEdit`。真透明要另走 windowless RichEdit 或 TSF，不能靠色键硬做。
9. **设置页的成熟规范是“单列、限宽、分组、卡片、即时生效”。**
   WinUI 明确建议：全屏、可滚动、最大宽度约 1000–1100、`SettingsCard`/`SettingsExpander`、
   整页尽量 4–5 项、单列从上到下。我们功能多，做不到“整页 4–5 项”，
   用**分组 + 折叠**控制首屏；**2 列只能是短行的例外，3 列不做。**
10. **真窗口是独立一层，不能塞进覆盖层。**
    白板 / PDF / 视频展台 / 类 OneNote 笔记需要 `WindowManager`：每屏 DPI、owner、任务栏、位置记忆、关闭生命周期。
11. **我们该抄的是“状态机和契约”，不是框架。**
    不抄 XAML/绑定/设计器，不抄 Flutter 的 rebuild，不抄 Slate 的整棵树，不抄 Chromium 的图层合成，
    不抄 Unity 的 USS/UXML，不自己写 IME/TSF。
12. **Phase 1 仍然是 `PageHost + SettingsPage` 试点，但设计要按本文修正：**
    页面栈只做“更多 → 设置 → AI 子页”这一层；页面高度 470–480、行高 44、组头 24；
    左栏独立滚动/可折叠；墨迹区默认单列，宽屏且短行才 2 列。

## 三、逐系统深读

### 3.1 Web：`dialog` / `popover` / top layer / `inert`

#### 它解决什么问题

Web 过去用 `div + z-index + 手写遮罩 + 手写焦点陷阱` 做弹层，问题集中在：

- z-index 战争：任何祖先的 `transform`/`filter` 都能改变层叠上下文；
- 点外关闭、Esc、焦点陷阱、背景可交互，各写一套；
- 弹层被祖先 `overflow:hidden` 裁掉；
- 关闭后焦点丢到 `<body>`，键盘用户迷路。

#### 核心机制

1. **top layer**：`<dialog>` 调用 `showModal()`、或元素带 `popover` 属性时，浏览器把它放进
   “顶层”（top layer），位于所有普通层叠上下文之上，不受祖先 `overflow`/`transform` 裁剪。
2. **模态 `<dialog>.showModal()`**：
   - 有 `::backdrop` 遮罩；
   - 背景自动变成 **inert**：不能被点击、不能 Tab 进去、辅助技术也读不到；
   - 焦点被限制在对话框内；
   - Esc 触发 `cancel` 事件，可取消关闭；
   - `close()` 后焦点**恢复到打开前的元素**；
   - `returnValue` 可以带回结果。
3. **`popover`**：
   - `popover="auto"`：**light dismiss**（点外面/Esc 关闭），同时只显示一个；
   - `popover="manual"`：只能显式关闭；
   - `popover="hint"`：不关闭其他 popover，适合提示；
   - 可用 `popovertarget` / `popovertargetaction` 声明式开关；
   - 仍在 top layer，可用 CSS anchor positioning 定位到触发元素。
4. **`inert`**：把一棵子树从命中测试、Tab 顺序、辅助技术树里移除；不是 `pointer-events:none` 的替代。
5. **焦点规则**：打开时把焦点放到第一个可聚焦元素或 `autofocus`；关闭时恢复到触发元素；
   如果触发元素已不存在，则恢复到逻辑上的父区域。

#### 可照搬的逻辑

- **模态四件事**：阻断下层输入 + 焦点陷阱 + 关闭策略 + 恢复焦点。
- **light dismiss**：点遮罩/点外面关闭，且这一下不再落到下层。
- **inert**：页面打开时，下层浮层“继续画、但不接输入”。
- **top layer 优先于 z-index**：我们的层序用一张优先级表，不靠各层自己写数字。
- **返回结果**：页面关闭时带一个结果（保存/取消/选择项），调用方据此更新。

#### 不照搬

- DOM/CSS 的层叠上下文、`anchor positioning` 的完整 CSS 语法；
- 浏览器的自动焦点陷阱实现（我们自己做，但语义照搬）；
- 浏览器对 `popover` 的自动关闭栈（我们只需要一层“当前可轻关闭层”）。

#### 我们的差异

- 我们是 D2D 立即绘制，没有 DOM；用 `OverlayLayer` 的 `Priority + BlocksInputBelow + DismissPolicy` 表达同样语义。
- 我们的“页面”是覆盖层里的模态面板，不是浏览器全屏路由；`PageHost` 只借“模态四件事”。
- 我们的文字输入是原生 HWND，天然在 D2D 之上；打开下拉/菜单时要先处理 airspace（见 §6.4）。

### 3.2 Flutter：Navigator / Overlay / OverlayPortal / Focus / GestureArena

#### 它解决什么问题

Flutter 要把“页面导航、对话框、菜单、提示、下拉”统一到一棵可组合的树上，同时保证
返回键、焦点、手势冲突、动画都有确定行为。

#### 核心机制

1. **Navigator = Route 栈**
   - `Navigator.push` 压入一个 `Route`，`pop` 弹出，`push` 返回 `Future`，`pop(result)` 把结果带回；
   - `Navigator.pages`（声明式 API）把页面列表映射成 Route 栈，配合 `onDidRemovePage` 清理；
   - `PageRoute` 负责转场动画；`PopupRoute` 是“非全屏、带 barrier”的路由；
   - `ModalRoute` 提供 `barrierColor`、`barrierDismissible`、`barrierLabel`；
   - `Route` 有 `didPush`/`didPop`/`didPopNext`/`didPushNext` 等生命周期。
2. **Overlay = 独立的 entry 栈**
   - `Overlay` 管理一组 `OverlayEntry`，每个 entry 可独立插入/移除；
   - `OverlayEntry` 有 `opaque`（是否完全遮住下面）、`maintainState`（不可见时是否保留状态）；
   - `Overlay` 是“视觉浮动”的通用机制，不绑定导航；`Navigator` 只是用它来放 Route。
3. **OverlayPortal = 跟随源组件的浮层**
   - 浮层内容由 `OverlayPortal` 自己 build，但渲染在最近的 `Overlay` 上；
   - 可以超出源组件边界、不被裁剪，但仍受 Overlay 边界限制；
   - 浮层可以依赖源组件同一套 `InheritedWidget`（主题、方向等）；
   - 绘制顺序：在关联的 `OverlayEntry` 之后、下一个 entry 之前；多个 portal 按 `show()` 顺序叠。
4. **Focus**
   - `FocusNode` 组成焦点树；`FocusScope` 把焦点限制在一个子树；
   - `requestFocus`、`autofocus`、`traversalEdgeBehavior`；
   - 新 Route 默认请求焦点（`requestFocus: true`），关闭后焦点回到上一个 Route；
   - 键盘事件沿焦点树传播，`Shortcuts`/`Actions` 负责快捷键。
5. **GestureArena（手势竞技场）**
   - 命中测试从叶子到根，多个 `GestureRecognizer` 同时进入 arena；
   - 每个 recognizer 可以 `accept`（赢）、`reject`（输），或等 sweep；
   - 同类型手势通常**子级先加入、先赢**（例如父子都有 `onTap`，点 child 只触发 child）；
   - `onTapDown` 可能在胜负未定时先触发；`onTapCancel` 即使输了也可能触发；
   - `HitTestBehavior.opaque/translucent` 控制“是否让后面的目标也参与命中”，但不改变父子竞技场的胜负。
6. **HitTestBehavior**
   - `opaque`：自己命中，阻止后面；
   - `translucent`：自己命中，同时允许后面也命中；
   - `deferToChild`：只有子级命中才算自己命中。

#### 可照搬的逻辑

- **Route 栈 + 返回结果**：我们的 `PageHost.Push/Pop` 返回 `PageResult`，调用方 await/回调。
- **barrier 语义**：`BlocksInputBelow` + `DismissOnBackdrop` + `DismissOnEsc` 三件事分开配置。
- **`maintainState`**：页面被覆盖时是否保留滚动位置/表单草稿；默认保留设置页滚动位置。
- **`OverlayPortal` 的锚点思想**：下拉/菜单挂在触发控件上，但画在浮层里，不被父容器裁剪。
- **手势竞技场**：我们的“双指滚动 vs 画布漫游 vs 页面滚动”需要一个明确的赢家规则，而不是各自判断。
- **焦点作用域**：一个页面/浮层一个 FocusScope，关闭后回到触发控件。

#### 不照搬

- Widget rebuild / `InheritedWidget` / 每帧重建；
- 完整 `Route` 转场系统（我们只需要 150–200ms 高度/透明度）；
- 完整 `GestureArena`（鼠标/笔不需要；触屏只需要“页面滚动 vs 画布漫游”二选一）。

#### 我们的差异

- 我们的画布是持续渲染的墨迹层，不是 Widget；页面和浮层只占 UI 位图。
- 我们的“返回”只有一层：More → Settings → ApiSettings；不需要任意深路由。
- 我们的触摸手势已经在 `TouchGestures` 里有一套；PageHost 只接管“页面内的双指纵滑”，
  不重写画布的双指漫游。

### 3.3 WPF：Page / Frame / NavigationService / Journal / AdornerLayer

#### 它解决什么问题

桌面应用需要“浏览器式前进/后退”，同时页面可能很重（视频、图形），不能无限保留实例；
还需要在不改变布局的情况下，在元素上方画装饰（选择框、错误提示、拖拽预览）。

#### 核心机制

1. **导航宿主**：`NavigationWindow`、`Frame` 实现 `INavigationService`；`Page` 是常用内容单元。
2. **Journal（日志）**：
   - 两个栈：back stack / forward stack；
   - 每次导航把当前页加入 back stack；后退时当前页进 forward stack；
   - 默认 JournalEntry 只存**页面元数据**，返回时重新创建 Page（省内存）；
   - `Page.KeepAlive = true` 才保留实例；保留实例时，初始化逻辑要放 `Loaded`，不能放构造函数。
3. **导航生命周期**：
   - `Navigating` 可取消；
   - `Navigated`、`NavigationProgress`、`NavigationStopped`、`NavigationFailed`、`LoadCompleted`；
   - Page 的 `Loaded`/`Unloaded` 每次进入/离开都会触发（即使 KeepAlive）。
4. **AdornerLayer**：
   - `AdornerDecorator` 在视觉树里提供一个 `AdornerLayer`；
   - Adorner 永远画在被装饰元素之上，**不影响布局**；
   - `IsHitTestVisible = false` 可以让点击穿透到下面；
   - 适合选择框、焦点框、错误提示、拖拽预览。
5. **路由事件**：隧道（Preview）从根到目标，冒泡（Bubble）从目标到根；可 `Handled` 停止。

#### 可照搬的逻辑

- **回退栈语义**：`Push/Pop/GoBack/CanGoBack`；我们的 More → Settings → Api 只需要 back，不需要 forward。
- **KeepAlive 默认关闭**：设置页可以保留滚动位置（轻量状态），但不保留整页对象；
  API 草稿单独存，不靠“页面实例还活着”。
- **可取消导航**：离开有未保存内容的页面时，先问“保存/放弃/取消”，再决定是否 Pop。
- **Adorner 的“画在上面但不吃输入”**：提示、HUD、取景框、选择框的浮层可以用同一语义；
  但**选择框手柄/光标/激光仍留在画布层**，不搬进 UI。
- **`Loaded/Unloaded` 与 `OnEnter/OnLeave` 对应**：页面每次显示都重新计算布局/焦点，而不是只构造一次。

#### 不照搬

- XAML/Frame/URI 导航；
- 每个页面都进 Journal（我们只有少数页面，且不希望“后退”穿越到设置外部）；
- WPF 的布局/依赖属性系统。

#### 我们的差异

- 我们的页面是覆盖层里的面板，不是窗口内容；返回只回到“更多”启动器。
- 我们的画布文档不随页面切换而销毁；页面只影响 UI 状态。
- 我们的 Adorner 对应“浮层”，但浮层有自己的优先级表，不依附某个 UIElement。

- Adorners Overview：https://learn.microsoft.com/en-us/dotnet/desktop/wpf/controls/adorners
- AdornerLayer：https://learn.microsoft.com/en-us/dotnet/api/system.windows.documents.adornerlayer

### 3.4 WinUI 3：NavigationView / SettingsCard / SettingsExpander / 设置规范

#### 它解决什么问题

Windows 应用的设置页最容易做成“一长串复选框”，在宽屏上阅读困难、在窄屏上溢出；
NavigationView 还要处理左导航、紧凑模式、设置项固定在底部。

#### 核心机制

1. **NavigationView**
   - 左侧导航，`IsSettingsVisible=true` 时“设置”自动固定在底部；
   - 支持展开/紧凑/最小模式；窄窗时自动切换；
   - 导航项有图标、文本、选中指示条。
2. **设置页规范（官方）**
   - 设置页**全屏**、填满窗口；
   - 使用**可滚动布局**，内容最大宽度约 **1000–1100px**，保证宽屏可读；
   - 用 **BodyStrong** 作为分组标题；
   - 用 `SettingsCard` / `SettingsExpander` 构建；
   - 每张卡：Header、可选 Description、可选 HeaderIcon、右侧动作控件；
   - `IsClickEnabled=true` 让整张卡可点，适合“进入子页/外链”；
   - `SettingsExpander` 用于“有子选项”的设置，避免页面过长；**不要嵌套超过一层**；
   - 相关设置放同一分组；**官方建议整页尽量 4–5 项**（我们按分组/折叠控制首屏，不删功能）；
   - 设置项**从上到下单列**，需要时滚动；
   - 改变设置**立即生效**，不要“保存”按钮；
   - 禁用项要在 Description 里解释原因；
   - “关于”放页面底部，用 Expander 收起应用名/版本/链接/法律信息。
3. **控件选择**
   - 二元：ToggleSwitch；
   - 2–5 个互斥：RadioButtons；
   - 多选一但选项多：ComboBox；
   - 文本：TextBox（按 email/password 等类型）；
   - 跳转：Hyperlink / 可点卡片；
   - 立即动作：Button。

#### 可照搬的逻辑

- **单列 + 限宽 + 分组 + 卡片**：这是设置页的成熟骨架。
- **官方建议整页 4–5 项**：我们 16 行分成 7 组，靠**分组/折叠**控制首屏，而不是删功能。
- **即时生效**：我们的开关/档位已经是即时生效，继续保持；不要加“保存设置”。
- **禁用原因**：例如“墨迹预测”在触摸模式下不可用，要在行副标题说明。
- **关于放底部**：我们的“关于”分类已经存在，保持在最后。
- **Expander 用于高级项**：备份/恢复、日志等低频项可以折叠，减少首屏长度。

#### 不照搬

- 全屏设置页：我们是覆盖层面板，不是独立窗口；
- XAML 控件 / `SettingsCard` 的实现；
- 1000–1100px 最大宽度：我们的面板宽 560–980，内容区更窄；
- “整页最多 4–5 项”作为硬上限：我们功能多，按语义分组/折叠即可，不为了凑数删设置；

#### 我们的差异

- 设置页在 55% 工作宽、最大 980 的覆盖层里；
- 左栏独立滚动/可折叠，右侧连续滚动（已实现）；
- 正文高度目标 470–480，总高约 570；
- 行高 44、组头 24；
- 墨迹区默认单列；只有“宽屏 + 短行”才 2 列；3 列不做。

### 3.5 Avalonia：TopLevel / OverlayLayer / Popup / FocusManager / InputElement

#### 它解决什么问题

Avalonia 要在 Windows/macOS/Linux 上提供统一的视觉根、布局、渲染、焦点、弹出层；
同时要处理“覆盖层在内容之上、但在 Popup 之下”的层序。

#### 核心机制

1. **TopLevel**
   - 视觉根，负责调度布局、样式、渲染；
   - `Window` 是 TopLevel 的一种；
   - 每个 TopLevel 有自己的 `FocusManager`、渲染表面、DPI。
2. **FocusManager**
   - 跟踪当前焦点元素和当前 focus scope；
   - 通过 `TopLevel.FocusManager` 访问；
   - `GetFocusedElement()` 是某一刻的快照；要监听变化用 `InputElement.GotFocusEvent` 路由事件；
   - Tab 导航、焦点恢复、焦点作用域由它统一处理。
3. **InputElement 路由事件**
   - 隧道/冒泡两阶段；`Handled` 可停止；
   - `IsHitTestVisible` 控制是否参与命中；
   - `Focusable`、`TabIndex`、`IsTabStop` 控制焦点环。
4. **OverlayLayer**
   - 覆盖层：显示在其他元素之上，但在 **Popup 之下**；
   - 适合遮罩、浮动面板、拖拽预览；
   - `IsHitTestVisible` 控制是否吃输入。
5. **Popup**
   - 可以是窗口内 overlay，也可以是独立顶层窗口（平台相关）；
   - 有 `PlacementTarget`、`Placement`、`IsOpen`、`StaysOpen`；
   - 焦点作用域要跟所属 TopLevel 对齐；跨窗口/overlay 的焦点是常见坑。
6. **测试**
   - Headless 测试：不显示窗口，直接跑控件逻辑/布局/输入；
   - Appium：跑真实窗口的端到端 UI 测试；
   - Avalonia 自己就用 Appium 测跨平台。

#### 可照搬的逻辑

- **每个窗口一个 FocusManager**：我们以后有真窗口时，焦点不能全局单例。
- **层序三段**：内容 → OverlayLayer（页面/浮层）→ Popup（菜单/下拉/提示）。
  我们的对应：画布 → 页面/浮层 → 文字宿主/菜单。
- **`IsHitTestVisible` 分离“画”和“吃输入”**：提示/HUD 画在最上面但不吃输入。
- **Headless 测试优先**：几何、命中、焦点、滚动都能无窗口断言；真窗口只测 IME/DPI/airspace。
- **Popup 的 `PlacementTarget`/`Placement`/`StaysOpen`**：我们的下拉/菜单需要锚点、翻转、点外关闭。

#### 不照搬

- 完整控件树、XAML、样式系统；
- Popup 的平台分支（overlay vs 独立窗口）；
- `NativeControlHost` 的 airspace 方案（我们已经有自己的原生宿主）。

#### 我们的差异

- 我们只有一个主覆盖层 HWND，页面/浮层都在同一张 D2D 位图里；
- 文字宿主是唯一的独立 HWND，天然在 Popup 之上，需要专门处理遮挡；
- 我们不引入 Avalonia，只借 `TopLevel`/`OverlayLayer`/`FocusManager` 的概念。

#### 来源

- FocusManager：https://docs.avaloniaui.net/docs/services/focus-manager
- OverlayLayer：https://docs.avaloniaui.net/api/avalonia/controls/primitives/overlaylayer
- TopLevel：https://docs.avaloniaui.net/docs/fundamentals/top-level
- UI Testing with Appium：https://docs.avaloniaui.net/docs/testing/ui-testing-with-appium

### 3.6 Chromium Views：View / Widget / LayoutManager / FocusManager / EventHandler

#### 它解决什么问题

Chromium 桌面 UI 要在 Windows/macOS/Linux/ChromeOS 上有一致的 View 树、布局、焦点、事件路由；
同时要支持原生窗口、层合成、无障碍。

#### 核心机制

1. **View**
   - UI 元素，类似 DOM 节点；
   - 每个 View 占据一个矩形（bounds），坐标是**父 View 坐标系**；
   - 可以有子 View，由 `LayoutManager` 布局，也可以重写 `View::Layout`；
   - 可以有 border/background；可绘制到 layer。
2. **Widget**
   - View 树的宿主，桥接原生窗口；
   - 每个 Widget 有 RootView → ContentsView → 其它 View；
   - Widget 负责：键盘焦点（FocusManager）、窗口缩放/最小化/最大化、窗口形状、输入事件路由。
3. **布局**
   - `InvalidateLayout()` 会向上标记祖先需要布局；
   - `Widget::LayoutRootViewIfNecessary()` 在合适时机从 RootView 向下 `Layout()`；
   - `LayoutManager` 负责计算 preferred size 和子 View bounds；
   - 布局是“失效向上、布局向下”，避免每帧全树重排。
4. **焦点**
   - 每个 Widget 一个 `FocusManager`；
   - 跟踪当前 focused view、focus traversal（Tab/Shift+Tab）、快捷键；
   - `RequestFocus()`、`HasFocus()`、focus behavior（ALWAYS/NEVER/…）。
5. **事件**
   - 原生窗口消息 → View 树；
   - `EventHandler::OnEvent()` 分 **PreTarget → Target → PostTarget** 三段；
   - 事件可被标记 handled，停止后续；
   - FocusManager 负责键盘事件和 accelerator 的路由；
   - 命中测试从最上层/最具体 View 开始。
6. **Layer**
   - View 可以有自己的 `ui::Layer`，也可以把 layer 加到 View 的上方/下方区域；
   - 用于动画、变换、裁剪、合成；不是每个 View 都必须有 layer。

#### 可照搬的逻辑

- **布局失效向上、布局向下**：页面内容变化只标记 dirty，下一帧统一布局；不要在每个 draw 里改位置。
- **事件三段**：页面可以先在 PreTarget 处理 Esc/快捷键，再让子控件处理，最后 PostTarget 兜底。
- **每个窗口一个 FocusManager**：真窗口/覆盖层各自有焦点作用域。
- **命中测试从最上层开始**：与 OverlayLayerManager 的优先级表一致。
- **`IsHitTestVisible` 式的“画/吃输入”分离**：提示/HUD 不参与命中。
- **Widget/ContentsView 的分层**：窗口壳与内容分离；对应我们的 `WindowHost` / `PageHost`。

#### 不照搬

- 完整 View 树、LayoutManager 家族、layer 合成；
- 每个 View 都可独立成层（我们只有页面/浮层两级）；
- Chromium 的跨平台原生窗口抽象（我们只做 Windows）。

#### 我们的差异

- 我们的 UI 是立即绘制，View 数量少；用显式矩形布局即可，不需要通用 LayoutManager。
- 我们的页面内容多为“行/列表/滚动”，用 `PageFrame` + `ScrollView` 足够。
- 我们的“layer”是逻辑层，不是 GPU 合成层；不需要 `ui::Layer`。

#### 来源

- Views Overview：https://chromium.googlesource.com/chromium/src/+/refs/heads/main/docs/ui/views/overview.md
- Views intro：https://www.chromium.org/chromium-os/developer-library/guides/views/intro/
- Focus and Activation：https://www.chromium.org/developers/design-documents/focus-and-activation-in-views-and-aura/
- Life of an input event：https://chromium.googlesource.com/chromium/src/+/HEAD/docs/ui/input_event/index.md
- Views glossary：https://chromium.googlesource.com/chromium/src/+/main/docs/ui/learn/glossary.md

### 3.7 Unreal Slate：SWidget / SPanel / SOverlay / FWidgetPath / FSlateApplication

#### 它解决什么问题

游戏 UI 需要高性能、可组合的控件树，支持鼠标/键盘/手柄、弹出菜单、模态窗口、拖拽、工具提示；
还要能在运行时检查控件树（Widget Reflector）。

#### 核心机制

1. **SWidget 三种类型**
   - 叶子控件（`SLeafWidget`）：无子槽，自己画，如 `STextBlock`；
   - 面板（`SPanel`）：动态数量子槽，负责布局，如 `SVerticalBox`、`SOverlay`；
   - 合成控件（`SCompoundWidget`）：固定命名槽，如 `SButton` 的 Content。
2. **Slot**
   - 父控件持有 Slot，Slot 持有子控件和相对父控件的布局信息；
   - `SOverlay` 的每个 Slot 是一层，按声明顺序从下到上绘制。
3. **FWidgetPath**
   - “控件树的一个垂直切片”，**leafmost last**（最叶子在最后）；
   - index 0 是顶层窗口；
   - 路径包含每层的 `FArrangedWidget`（几何）；
   - 可用于命中测试、焦点、事件路由。
4. **输入路由**
   - 平台输入 → `GenericApplication` → `FSlateApplication` → `FWidgetPath` → `SWidget` → `UWidget`；
   - **隧道（tunneling）**：从根到叶子；
   - **冒泡（bubbling）**：从叶子到根；
   - 事件在隧道阶段可以被处理，冒泡阶段兜底；
   - 焦点路径（focus path）从根到最深可聚焦控件；
   - `FSlateApplication` 负责指针按下/移动/抬起/滚轮/双击的路由；
   - 支持指针捕获（mouse capture）、模态窗口栈、Popup 菜单栈。
5. **Widget Reflector**
   - 运行时检查控件树、层级、几何、焦点、命中；
   - 对调试“为什么点不到/被谁挡住”非常有效。

#### 可照搬的逻辑

- **`FWidgetPath` 思路**：命中时生成“从顶到底”的路径，便于调试和事件路由。
- **隧道/冒泡**：页面级快捷键先隧道，控件处理，页面冒泡兜底。
- **模态窗口栈**：`PushMenu` / `CanAddModalWindow` 的思路；我们的 PageHost 只需要页面栈 + 浮层栈。
- **指针捕获**：拖动滑块/滚动条/窗口时，按下后捕获，移动/抬起不再依赖命中。
- **Widget Reflector**：做一个 `--uigraph` 或调试浮层，显示层序、bounds、命中结果、焦点。
- **SOverlay**：浮层按声明顺序叠；我们的优先级表就是“声明顺序”的显式化。

#### 不照搬

- 完整 Slate 控件树、Slot 系统、UMG；
- 每帧 Tick 的控件逻辑；
- 手柄导航/复杂焦点路径（我们只需要鼠标/笔/触屏/键盘）。

#### 我们的差异

- 我们的浮层是扁平的优先级列表，不需要任意深的 WidgetPath；
- 我们的页面内容是手绘行，不是 Slate 控件；
- 我们的输入来自 Win32 pointer 消息，不是 Slate 的 GenericApplication。

- FWidgetPath：https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/SlateCore/FWidgetPath
- SOverlay：https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/SlateCore/SOverlay
- FSlateApplication：https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Slate/Framework/Application/FSlateApplication
- UE4 UI input routing：https://notesbywei.com/en/articles/ue4-ui-input-routing

### 3.8 Unity UI Toolkit：VisualElement / Panel / EventDispatcher / FocusController

#### 它解决什么问题

Unity 编辑器/运行时需要一套类似 HTML 的 UI 树，支持样式（USS）、布局（Flex）、事件传播、焦点、
面板事件；同时要和游戏循环、渲染分离。

#### 核心机制

1. **VisualElement**
   - UI 树节点；有 `parent`、`Children`、`contentContainer`；
   - `pickingMode`：`Position` 可被命中，`Ignore` 不参与命中；
   - `focusable`、`tabIndex` 控制焦点环；
   - `enabledInHierarchy` 控制是否响应。
2. **Panel**
   - VisualElement 必须挂到 Panel 才能渲染/接收事件；
   - `AttachToPanelEvent` / `DetachFromPanelEvent`；
   - Panel 有自己的焦点环（`IFocusRing`）。
3. **事件传播**
   - `EventDispatcher` 选择目标（指针事件 = 最上层可命中元素；键盘事件 = 焦点元素）；
   - 传播路径：根 → 目标（**TrickleDown**），目标 → 根（**BubbleUp**）；
   - 每个元素（包括目标）可收到两次；`Event.target` 不变，`Event.currentTarget` 随当前元素变；
   - `StopPropagation()`：当前元素回调跑完后停止；`StopImmediatePropagation()`：立即停止；
   - 隐藏/禁用元素不接收事件，但事件仍会经过其祖先/后代。
4. **焦点**
   - `FocusController` 处理输入导致的焦点变化；
   - 通过 `IFocusRing` 决定下一个可聚焦元素；
   - 默认焦点顺序是视觉树的**深度优先**；`tabIndex` 可改；
   - `FocusOutEvent`/`FocusInEvent` 在变化前沿路径传播；
   - `FocusEvent`/`BlurEvent` 在变化后只发给目标；
   - `delegatesFocus=true` 时，焦点自动给可聚焦子元素。
5. **焦点事件的两类**
   - 变化前：FocusOut/FocusIn，可沿路径传播；
   - 变化后：Blur/Focus，只给目标。

#### 可照搬的逻辑

- **Trickle/Bubble**：页面级 Esc/Enter 先隧道，行控件处理，页面冒泡兜底。
- **焦点环 DFS + tabIndex**：设置页的行/开关/下拉需要确定的 Tab 顺序；默认按视觉顺序，必要时显式 tabIndex。
- **FocusIn/FocusOut 与 Focus/Blur 分开**：页面可以在焦点变化前拦截（例如“未保存，先别走”）。
- **`pickingMode=Ignore`**：提示/HUD 不参与命中。
- **Panel 事件**：页面 attach/detach 时注册/注销，避免泄漏。

#### 不照搬

- USS/UXML、Flex 布局、完整 VisualElement 树；
- Unity 的 PanelSettings/渲染管线；
- 每个行都做成 VisualElement（我们的行是绘制的，不是控件对象）。

#### 我们的差异

- 我们的设置行是“数据 + 绘制 + 命中矩形”，不是可组合控件；
- 我们只需要一个轻量 `FocusRing`（行/开关/按钮的 Tab 顺序），不需要完整事件树；
- 我们的页面只有一层内容，不需要 Panel 嵌套。

### 3.9 Qt Quick：StackView / Popup / Overlay / FocusScope

#### 它解决什么问题

QML 需要页面栈、弹出层、模态遮罩、焦点作用域；同时要适配桌面/移动/嵌入式。

#### 核心机制

1. **StackView**
   - 页面栈：`push(item, properties)`、`pop()`、`replace()`、`clear()`；
   - 支持转场动画；
   - 页面有 `StackView.status`（Active/Inactive/Deactivating/Activating）；
   - 返回时恢复上一页；页面可被销毁或保留（`StackView.DontDestroy` 等）。
2. **Popup**
   - `modal`：模态，背景可 dim；
   - `focus`：打开时是否请求焦点；
   - `closePolicy`：`NoAutoClose` / `CloseOnPressOutside` / `CloseOnEscape` / `CloseOnReleaseOutside`；
   - `Overlay.modal` / `Overlay.modeless` 控制背景遮罩；
   - 可设置 `parent`/`anchors.centerIn: Overlay.overlay`。
3. **Overlay**
   - 为 Popup 提供一层“在所有内容之上”的层；
   - 模态时背景变暗；
   - Popup 只能在其直接父级或窗口 Overlay 中居中。
4. **FocusScope**
   - 把焦点限制在一个子树；
   - 页面切换时保存/恢复焦点；
   - StackView 的页面通常需要 `FocusScope` 来正确恢复焦点。

#### 可照搬的逻辑

- **push/pop/replace/clear**：PageHost 只需要 push/pop/replace/popToRoot。
- **closePolicy**：把“点外关闭/Esc 关闭/不自动关闭”做成枚举，而不是每层自己判断。
- **Overlay 遮罩**：模态页面统一画遮罩，不每页重复。
- **FocusScope**：页面/浮层各自保存“上次焦点”，关闭后恢复。
- **页面状态**：Active/Inactive 对应 `OnEnter/OnLeave`；需要时加 `OnPause/OnResume`。

#### 不照搬

- QML/Quick 场景图、转场系统；
- 每个 Popup 独立窗口；
- Qt 的模型/视图体系。

#### 我们的差异

- 我们的页面是 D2D 绘制，不是 QML Item；
- 我们只需要少量页面，不需要任意 StackView 嵌套；
- 我们的浮层是同一 HWND 内的层，不是 Popup 窗口。

#### 来源

- Popup：https://doc.qt.io/qt-6/qml-qtquick-controls-popup.html
- Overlay：https://doc.qt.io/qt-6/qml-qtquick-controls-overlay.html
- StackView：https://doc.qt.io/qt-6/qml-qtquick-controls-stackview.html

### 3.10 Android：FragmentManager 回退栈 / DialogFragment

#### 它解决什么问题

Android 的返回键是系统级行为；页面、对话框、配置变化（旋转/深色模式）都需要一致的状态恢复。

#### 核心机制

1. **FragmentManager**
   - 管理 Fragment 的添加/替换/移除；
   - `addToBackStack` 把事务加入回退栈；返回键弹出；
   - `popBackStack`、`popBackStackImmediate`；
   - 状态保存/恢复由系统驱动。
2. **DialogFragment**
   - 是一个 Fragment，但显示为浮动对话框窗口；
   - 由 `FragmentManager` 管理，返回键默认关闭；
   - 适合“对话框也是导航的一部分”；
   - 使用 child `FragmentManager` 避免状态恢复问题；
   - 不要持有 Activity 的强引用。
3. **返回键**
   - 系统把 Back 分发给当前 Activity/FragmentManager；
   - 有 DialogFragment 时先关闭对话框；
   - 没有可回退项时才退出应用。

#### 可照搬的逻辑

- **回退栈**：PageHost 的 `Back` 先弹当前页，再回到启动器，最后关闭 More。
- **对话框也是栈的一部分**：API 子页/确认框应该入栈，而不是“另一个独立窗口”。
- **状态恢复**：设置页滚动位置、API 草稿在页面被覆盖/恢复时保留。
- **返回键优先级**：文字输入 > 弹层 > 页面 > 启动器 > 关闭 More > 画布。

#### 不照搬

- Activity/Fragment 生命周期、配置变化重建；
- 每个对话框一个 Window；
- Android 的 Intent/导航组件。

#### 我们的差异

- 我们只有一个主窗口，没有配置变化重建；
- 页面状态由页面自己保存（滚动/草稿），不靠系统恢复；
- 返回键由 `PageHost` + `OverlayLayerManager` 统一路由。

#### 来源

- DialogFragment：https://developer.android.com/guide/fragments/dialogs
- FragmentManager：https://developer.android.com/guide/fragments/fragmentmanager

### 3.11 iOS UIKit：模态呈现 / presentation controller / 自适应

#### 它解决什么问题

iPhone/iPad 的模态呈现要适配不同尺寸：全屏、页 sheet、form sheet、popover；
还要处理交互式关闭、安全区、焦点/键盘。

#### 核心机制

1. **modalPresentationStyle**
   - `fullScreen`：全屏覆盖；
   - `pageSheet`：卡片式，顶部露出下层，可下拉关闭（iPhone 默认自 iOS 13）；
   - `formSheet`：居中固定尺寸（iPad）；
   - `popover`：锚定到 `sourceView`/`sourceRect`/`barButtonItem`，点外关闭；
   - `overCurrentContext` / `overFullScreen`：保留下层可见。
2. **UIPresentationController**
   - 控制呈现容器、尺寸、布局、转场；
   - 可自定义 dimming view、圆角、阴影；
   - 自适应：紧凑宽度下 popover 自动变成 sheet。
3. **交互式关闭**
   - `isModalInPresentation` 阻止下拉关闭；
   - `presentationControllerDidAttemptToDismiss` 可拦截“未保存”；
   - 关闭后焦点/键盘回到触发控件。
4. **preferredContentSize**
   - 页面给出期望尺寸，系统根据可用空间夹取/适配。

#### 可照搬的逻辑

- **preferredSize + 系统夹取**：页面给 `PreferredHeight`，PageHost 夹进工作区（`min(preferred, workArea - 24)`）。
- **pageSheet 的“露出下层”**：我们的 More 面板不是全屏，保留一点背景可见，降低“进了一个新世界”的感觉。
- **popover 锚点 + 自适应**：下拉/菜单锚定触发控件；空间不够时翻转/夹取。
- **交互式关闭 + 未保存拦截**：API 页有未保存内容时，返回先问“保存/放弃/取消”。
- **关闭恢复焦点**：回到触发按钮/行。

#### 不照搬

- UIViewController 生命周期、Auto Layout；
- 全屏 modal 导航；
- 手势驱动的 sheet 转场（我们只需要 150–200ms 高度/透明度）。

#### 我们的差异

- 我们的页面是覆盖层面板，不是全屏 ViewController；
- 尺寸由 PageHost 统一夹取，不交给系统；
- 不需要安全区/键盘避让（桌面）。

#### 来源

- View Controller Programming Guide（Presenting）：https://developer.apple.com/library/archive/featuredarticles/ViewControllerPGforiPhoneOS/PresentingaViewController.html
- UIPresentationController：https://developer.apple.com/documentation/uikit/uipresentationcontroller

### 3.12 Win32 / TSF / RichEdit：原生输入宿主

#### 它解决什么问题

中文输入不是“收键盘字符”这么简单：IME 需要组合串（composition）、候选窗、光标位置、
选区、输入上下文、TSF 文档/范围/属性。自己画文本光标和输入法，成本极高。

#### 核心机制

1. **`EDIT` / `RichEdit`**
   - 系统原生文本控件，支持 Unicode、IME、选区、复制粘贴、撤销、无障碍；
   - `RichEdit`（`MSFTEDIT_CLASS`）支持多行、富文本、TOM 接口、URL 识别、透明（windowless 模式）；
   - 普通 **windowed** RichEdit 的背景是不透明的；它不向父窗口发 `WM_CTLCOLOREDIT`，
     所以“把背景刷成透明”的旧 EDIT 技巧对它无效；
   - 官方特性表写有 “Transparency support — Also in windowless mode”，即 **windowless RichEdit**
     （`ITextHost` / `ITextServices`）可以把内容画到宿主 DC，理论上可透明；
   - 但 windowless 模式要自己实现 `ITextHost`（设备上下文、字体、滚动、光标、IME 定位），
     工作量和风险远高于 windowed 模式。
2. **TSF（Text Services Framework）**
   - `ITfThreadMgr`：线程管理器，激活/停用文本服务、创建文档管理器、维护焦点；
   - `ITfDocumentMgr`：文档管理器，管理编辑上下文栈；
   - `ITfContext`：编辑上下文；
   - `ITfComposition`：组合串；文本服务用 `ITfContextComposition::StartComposition` 开始，
     `ITfComposition::EndComposition` 结束；
   - 应用要实现 `ITextStoreACP`（或 `ITextStoreAnchor`）让 TSF 读写文本；
   - 文本服务通过 `ITfContextView::GetTextExt` 获取光标/候选窗位置；
   - RichEdit 本身是 TSF-aware 的，所以用 RichEdit 就自动获得大部分 IME 能力。
3. **Layered window**
   - `WS_EX_LAYERED`：`SetLayeredWindowAttributes` 支持 `LWA_ALPHA`（整体透明度）或
     `LWA_COLORKEY`（颜色键透明）；`UpdateLayeredWindow` 支持逐像素 alpha（顶层窗口）；
   - Windows 8 起 `WS_EX_LAYERED` 也支持子窗口；
   - **颜色键透明的区域可能不接收鼠标命中**（社区实测：透明背景的 EDIT 点不进去；
     把 alpha 设为 1 而不是 0 可以保留命中）；
   - 因此**不要用 layered + color key 做可编辑文本框的“真透明”**。
4. **DPI**
   - Per-Monitor V2：进程声明 PMv2；窗口收到 `WM_DPICHANGED`；
   - 必须用 `lParam` 给的建议矩形 `SetWindowPos`，否则会出现递归 DPI 变化/尺寸跳变；
   - `WM_GETMINMAXINFO` 处理最小/最大尺寸；
   - 用 `GetSystemMetricsForDpi` / `GetDpiForWindow` 等 DPI-aware API。

#### 可照搬的逻辑

- **原生控件 + 系统 IME**：不自己写输入法；文字输入宿主用 `EDIT`/`RichEdit`。
- **一个窗口一个宿主**：IME/焦点是窗口级的；覆盖层一个宿主，真窗口各一个。
- **宿主是独立可激活 TOOLWINDOW**：覆盖层是 `WS_EX_NOACTIVATE`，输入宿主必须能拿焦点；
  编辑时短暂激活，提交后把焦点还回去。
- **定位跟随 + 裁剪隐藏**：页面滚动/切换时更新宿主矩形；滚出视口就隐藏/提交。
- **提交/取消语义**：Enter 提交（单行）、Esc 取消、失焦提交、页面关闭提交/取消按配置。
- **DPI 变化重建字体/尺寸**：宿主窗口收到 `WM_DPICHANGED` 时重设字体、位置、行高。

#### 不照搬

- 现在自己实现 TSF 文本服务/ITextStoreACP（除非以后真要做“只有光标”的自绘文本）；
- windowless RichEdit（第一版不做；作为后续评估项）；
- layered + color key 的“透明编辑框”（命中/渲染都不可靠）；
- 自绘 IME 候选窗。

#### 我们的差异

- 我们的画布文本框是 RichEdit 宿主 + 板色/近白底；不是真透明；
- 我们已经有 9 组原生输入，计划收成一个 `TextInputService`；
- 我们的覆盖层是 NOACTIVATE，所以宿主必须是独立顶层 TOOLWINDOW；
- 第一版只做“无边框 + 柔和浅底 + 内边距”，真透明以后单独评估 windowless RichEdit/TSF。

#### 来源

- TSF Edit Contexts：https://learn.microsoft.com/en-us/windows/win32/tsf/edit-contexts
- TSF Compositions：https://learn.microsoft.com/en-us/windows/win32/tsf/compositions
- TSF Interfaces：https://learn.microsoft.com/en-us/windows/win32/tsf/text-services-framework-interfaces
- About Rich Edit：https://learn.microsoft.com/en-us/windows/win32/controls/about-rich-edit-controls
- Create Rich Edit：https://learn.microsoft.com/en-us/windows/win32/controls/create-rich-edit-controls

## 四、横向对比：七个维度

### 4.1 页面模型

| 系统 | 页面栈 | 返回结果 | 页面生命周期 | 保留实例 | 适合我们借什么 |
|---|---|---|---|---|---|
| Web | 无（站点自己） | `dialog.returnValue` | open/close | DOM 保留 | 模态结果 |
| Flutter | `Navigator` Route 栈 | `pop(result)` → Future | didPush/didPop/... | `maintainState` | 栈 + 结果 + 生命周期 |
| WPF | Journal back/forward | `Navigate` 返回值/事件 | Loaded/Unloaded | `KeepAlive` | 回退栈 + KeepAlive |
| WinUI | NavigationView 导航 | 参数 | OnNavigatedTo/From | 页面缓存 | 左导航 + 设置项 |
| Avalonia | 自建 | 自建 | 自建 | 自建 | FocusScope/层序 |
| Qt | `StackView` | `pop(result)` | Active/Inactive | `DontDestroy` | push/pop/replace |
| Android | FragmentManager 回退栈 | Fragment result | onResume/onPause | 状态保存 | 回退键优先级 |
| iOS | 导航控制器/模态 | completion | viewWillAppear/... | 由系统 | preferredSize/锚点 |

**结论**：`PageHost` 只需要 **push / pop / replace / popToRoot + PageResult + OnEnter/OnLeave**。
不要做 URI 路由、深链、任意嵌套。

### 4.2 浮层模型

| 系统 | 层序 | 模态 | 轻关闭 | 焦点 | 适合我们借什么 |
|---|---|---|---|---|---|
| Web | top layer | `showModal` + inert | `popover=auto` | trap + restore | 模态四件事 |
| Flutter | Overlay entries | `ModalRoute` barrier | `barrierDismissible` | Route focus | barrier 三配置 |
| WPF | AdornerLayer | 手写 | 手写 | 手写 | 画在上面不吃输入 |
| Avalonia | OverlayLayer < Popup | 手写 | `StaysOpen` | FocusScope | 层序 + Popup |
| Chromium | View 层 | 手写 | 手写 | FocusManager | 事件三段 |
| Slate | SOverlay slots | modal window stack | menu stack | focus path | 路径 + 捕获 |
| Qt | Overlay | `modal` | `closePolicy` | `focus`/FocusScope | closePolicy 枚举 |
| Android | DialogFragment | 是 | 返回键 | 窗口焦点 | 对话框也是栈 |
| iOS | presentation | 是 | 下拉/点外 | 恢复 | 自适应/锚点 |

**结论**：`OverlayLayer` 必须有 `Priority / BlocksInputBelow / DismissPolicy / RestoresFocus / Anchor`。
不要每层自己写“点外面关不关”。

### 4.3 输入路由

| 系统 | 命中顺序 | 捕获 | 传播 | 手势竞争 | 适合我们借什么 |
|---|---|---|---|---|---|
| Web | 最上层 | pointer capture | capture/bubble | 浏览器 | 捕获 + 轻关闭 |
| Flutter | 叶子→根 | `GestureDetector` | arena | **GestureArena** | 手势竞技场 |
| WPF | 最上层 | `CaptureMouse` | Preview/Bubble | 手写 | 路由事件 |
| Chromium | 最具体 View | `SetCapture` | Pre/Target/Post | 手写 | 事件三段 |
| Slate | WidgetPath | mouse capture | tunnel/bubble | 手写 | 路径 + 捕获 |
| Unity | 最上层 pickable | `CapturePointer` | trickle/bubble | 手写 | 传播阶段 |
| Qt | 最上层 | `grabMouse` | 过滤 | 手写 | closePolicy |
| Android | 窗口焦点 | 手写 | 手写 | 手写 | 返回键优先级 |

**结论**：输入管线固定为：

```text
原生文字宿主（编辑中）
  → 页面模态（PageHost）
  → 截图/取景模态
  → 浮层按 Priority 从高到低
  → 工具条/色带（FullUi 自身）
  → 穿透放行
  → 画布/墨迹
```

每层只回答：`HitTest` 是否命中、`PointerDown` 是否消费、是否 `Capture`、`DismissPolicy` 是什么。

### 4.4 焦点

| 系统 | 焦点管理器 | 作用域 | Tab 顺序 | 关闭恢复 | 适合我们借什么 |
|---|---|---|---|---|---|
| Web | 浏览器 | dialog/popover | 自动 | **是** | 恢复焦点 |
| Flutter | FocusManager | FocusScope | 焦点树 | 是 | FocusScope |
| WPF | FocusManager | 窗口/控件 | TabIndex | 手写 | 每窗口一个 |
| Avalonia | FocusManager | TopLevel/FocusScope | TabIndex | 是 | TopLevel 级 |
| Chromium | FocusManager | 每 Widget | focus list | 是 | Widget 级 |
| Slate | SlateApplication | 用户/窗口 | focus path | 是 | 路径 |
| Unity | FocusController | Panel/FocusRing | DFS + tabIndex | 是 | DFS + tabIndex |
| Qt | 焦点链 | FocusScope | 焦点链 | 是 | FocusScope |

**结论**：`PageHost` 持有一个 `FocusRing`（页面内行/控件），打开页面时设初始焦点，
关闭时恢复到触发控件；`OverlayLayerManager` 在弹层关闭时做同样的事。

### 4.5 滚动

| 系统 | 滚动容器 | 惯性 | 滚轮 | 触摸 | 键盘 | 适合我们借什么 |
|---|---|---|---|---|---|---|
| Web | `overflow:auto` | 浏览器 | 是 | 是 | 是 | 统一 viewport |
| Flutter | `Scrollable`/`ScrollView` | `ScrollPhysics` | 是 | 是 | 是 | 一套 physics |
| WPF | `ScrollViewer` | 是 | 是 | 是 | 是 | viewport/content |
| WinUI | `ScrollViewer` | 是 | 是 | 是 | 是 | 设置页滚动 |
| Avalonia | `ScrollViewer` | 是 | 是 | 是 | 是 | 统一 |
| Qt | `Flickable` | 是 | 是 | 是 | 是 | 惯性 |
| Android | `ScrollView`/`RecyclerView` | 是 | 是 | 是 | 是 | fling |
| iOS | `UIScrollView` | 是 | 是 | 是 | 是 | rubber band |

**结论**：`ScrollView` 只做一件事：`ScrollBy(delta)`。
滚轮、双指、键盘、滚动条、惯性全部调它；不要每个页面自己算 offset。
我们已经有 `UiTouchFling`，继续共用。

### 4.6 文字输入

| 系统 | 输入宿主 | IME | 透明 | 适合我们借什么 |
|---|---|---|---|---|
| Web | `<input>`/`contenteditable` | 浏览器 | CSS 背景透明 | 语义：value/selection/commit |
| Flutter | `EditableText` | 平台 | 可透明 | 输入框契约 |
| WPF | `TextBox`/`RichTextBox` | 系统 | 可透明 | 原生控件 |
| WinUI | `TextBox`/`RichEditBox` | 系统 | 可透明 | 表单控件 |
| Avalonia | `TextBox` | 系统 | 可透明 | 原生宿主 |
| Qt | `QLineEdit`/`QTextEdit` | 系统 | 可透明 | 表单 |
| **Win32** | **EDIT/RichEdit** | **TSF** | **windowed 不行；windowless 可以** | **原生宿主 + 一个服务** |

**结论**：不要自己写 IME。第一版 windowed RichEdit + 柔和浅底；真透明以后评估 windowless RichEdit/TSF。

### 4.7 窗口与测试

| 系统 | 窗口模型 | DPI | 测试 | 适合我们借什么 |
|---|---|---|---|---|
| WPF | Window/Frame | 系统/PMv2 | UI Automation | 窗口生命周期 |
| WinUI | AppWindow/Window | 自动 | WinAppDriver | AppWindow/设置 |
| Avalonia | TopLevel/Window | PMv2 | Headless + Appium | Headless 测试 |
| Chromium | Widget/native window | PMv2 | 浏览器测试 | Widget/内容分离 |
| Slate | SWindow | 平台 | Widget Reflector | 运行时检查器 |
| Qt | QWindow/QWidget | 平台 | Qt Test | 窗口状态 |
| Win32 | HWND | **PMv2 + WM_DPICHANGED** | WinAppDriver/UIA | 必做清单 |

**结论**：`WindowManager` 另做；`PageHost` 可以装进窗口，但不负责窗口 chrome/DPI/任务栏。

## 五、提炼：先进管理方式的 14 条原则

### 原则 1：分层，不做万能 Page

```text
Window（真窗口：白板/PDF/展台/笔记）
  └─ PageHost（页面：更多/设置/收藏/图形/帮助/日志/AI 子页）
       ├─ TextInputService（原生输入宿主）
       └─ OverlayLayerManager（浮层：PPT 条/回放/计时/点名/操作条/提示）
```

- 页面负责“整块内容 + 标题/返回/关闭”；
- 浮层负责“浮动、可拖动、可锚定、可轻关闭”；
- 文字输入是服务，不是页面；
- 窗口是宿主，不是页面。
- **来源**：Flutter Navigator/Overlay 分离、Avalonia TopLevel/OverlayLayer/Popup 分层、WinUI NavigationView + ContentDialog。

### 原则 2：层序用一张唯一的优先级表

- 不要在 `OnPointerDown/Move/Up` 里各写一遍顺序；
- 不要在每层里写 `z-index` 数字；
- 只在一张表里改。
- **来源**：Web top layer、Slate SOverlay 声明顺序、Avalonia OverlayLayer < Popup。

### 原则 3：模态 = 输入阻断 + 焦点陷阱 + 关闭策略 + 恢复焦点

四件事缺一不可。只画遮罩不叫模态。
- **来源**：Web `<dialog>.showModal()` + `inert`；Qt `Popup.modal` + `closePolicy`；iOS `isModalInPresentation`。

### 原则 4：轻关闭是一等公民

- 点遮罩/点外面/Esc 是三种不同策略；
- `DismissPolicy` 枚举：`None` / `Outside` / `Escape` / `OutsideOrEscape`；
- 关闭这一下不再落到下层。
- **来源**：Web `popover=auto`、Qt `closePolicy`、Flutter `barrierDismissible`。

### 原则 5：页面栈 + 路由身份 + 返回结果 + 生命周期

- `Push(page)` / `Pop(result)` / `Replace(page)` / `PopToRoot()`；
- `Page.Id` 稳定，状态按 Id 保存；
- `OnEnter` / `OnLeave` / `OnPause` / `OnResume`；
- 返回可取消（未保存拦截）。
- **来源**：Flutter Navigator、WPF NavigationService/Journal、Qt StackView、Android FragmentManager。

### 原则 6：KeepAlive 默认关闭，状态单独保存

- 不保留整页对象，避免内存增长；
- 滚动位置、草稿、焦点用 `PageState` 保存；
- 需要保留实例时才显式 `KeepAlive`。
- **来源**：WPF `Page.KeepAlive` 默认 false；Flutter `maintainState`。

### 原则 7：布局“失效向上、布局向下”

- 内容变化只标记 dirty；
- 下一帧统一 `Layout`；
- 不要在 `Render` 里改位置/尺寸。
- **来源**：Chromium Views `InvalidateLayout` / `Layout`；WPF Measure/Arrange。

### 原则 8：输入“从最上层命中 + 捕获 + 隧道/冒泡”

- 命中测试从最上层开始；
- 按下后捕获，移动/抬起不依赖命中；
- 页面级快捷键先隧道，控件处理，页面冒泡兜底；
- 一次只允许一个拖动/手势会话。
- **来源**：Slate `FWidgetPath`、Chromium Pre/Target/Post、Unity trickle/bubble、WPF Preview/Bubble。

### 原则 9：手势竞争用“竞技场”，不用各自判断

- 双指纵滑：页面滚动 vs 画布漫游，只能一个赢；
- 明确“谁先接受、谁输、何时 sweep”；
- 输家收到 cancel，不产生副作用。
- **来源**：Flutter GestureArena；Android `onInterceptTouchEvent` 的类似思想。

### 原则 10：焦点按作用域管理

- 一个窗口一个 FocusManager；
- 一个模态页面/弹层一个 FocusScope；
- 打开设初始焦点，关闭恢复触发控件；
- Tab 顺序 = 视觉顺序，必要时显式 `tabIndex`。
- **来源**：Avalonia FocusManager、Flutter FocusScope、Unity FocusRing、Qt FocusScope、Chromium FocusManager。

### 原则 11：滚动是容器能力，一条 `ScrollBy`

- viewport + content + offset + max；
- 滚轮/触摸/键盘/滚动条/惯性全走同一条；
- 惯性参数全应用共用；
- 当前项自动滚入视野。
- **来源**：Flutter ScrollPhysics、WPF ScrollViewer、iOS UIScrollView、Android RecyclerView。

### 原则 12：文字输入是服务，原生宿主 + 系统 IME

- 页面只给矩形/初值/校验/提交/取消；
- 一个窗口一个宿主；
- IME/光标/选区/剪贴板/撤销交给 `EDIT/RichEdit`；
- 真透明另评估 windowless RichEdit/TSF。
- **来源**：Win32 RichEdit/TSF、WPF TextBox、WinUI TextBox、Qt QLineEdit。

### 原则 13：窗口管理独立

- 系统 chrome 优先；
- PMv2 + `WM_DPICHANGED` 建议矩形；
- owner/taskbar/topmost/位置记忆/关闭生命周期；
- 内容层可以装 PageHost。
- **来源**：Windows App SDK AppWindow、Win32 PMv2、WPF Window。

### 原则 14：可测试性是一等需求

- 几何/命中/滚动/焦点用 headless/隐藏窗口断言；
- 页面截图做 golden；
- 输入宿主检查“无残留 HWND”；
- 运行时层检查器（Widget Reflector 思路）。
- **来源**：Avalonia Headless/Appium、WinAppDriver、Slate Widget Reflector。

### 6.2 PageHost

#### 6.2.1 契约（建议）

```csharp
interface IPage
{
    string Id { get; }
    string Title { get; }

    // 页面想要的尺寸；宿主夹进工作区
    PageSize PreferredSize { get; }

    bool CanBack { get; }              // 是否显示返回
    bool Modal { get; }                // 是否阻断下层输入

    void OnEnter(PageContext ctx);
    void OnLeave(PageLeaveReason reason);
    void OnPause();                    // 被另一个页面覆盖
    void OnResume();                   // 回到栈顶

    void Layout(in PageFrame frame);
    void Render(ID2D1DeviceContext ctx, in PageFrame frame);

    PageHit HitTest(float x, float y);
    bool PointerDown(in UiPointerEvent e);
    bool PointerMove(in UiPointerEvent e);
    bool PointerUp(in UiPointerEvent e);
    bool Wheel(float x, float y, int delta);
    bool Key(int vk, bool ctrl, bool shift);

    bool IsAnimating { get; }
}
```

`PageFrame` 提供：

```text
HeaderRect      标题栏
ContentRect     内容区
FooterRect      底栏（可选）
ScrollViewport  内容裁剪/滚动
BackRect        返回
CloseRect       关闭
PopupLayer      页面内下拉/菜单
FocusRing       页面内焦点顺序
DpiScale / NowMs / Theme
```

`PageHost` 负责：

- 页面栈：`Push` / `Pop` / `Replace` / `PopToRoot`；
- 标题栏：返回 / 标题 / 关闭；
- 遮罩：整屏半透明，点外关闭（可配置）；
- 高度：`PreferredSize` 夹进工作区（`min(preferred, workArea - 24)`）；
- 滚动：`ScrollViewport` 统一滚轮/双指/惯性（复用 `UiTouchFling`）；
- 焦点：Esc/Enter/Tab、点击外部、弹层焦点陷阱；
- 转场：高度/透明度 150–200ms；系统关动画时跳终态；
- 自检：页面截图、命中、滚动、关闭/返回。

#### 6.2.2 页面栈语义

```text
MoreHome (root)
  └─ Settings (push)
       └─ ApiSettings (push)
```

- 打开 More：`Push(MoreHome)`；
- 点设置：`Push(Settings)`；
- 点 AI 服务：`Push(ApiSettings)`；
- 返回：`Pop()`；Api → Settings → MoreHome → 关闭 More；
- 关闭按钮：`PopToRoot()` + 关闭 Modal；
- 设置页被 Api 覆盖时：`OnPause`，保留滚动位置；
- Api 关闭：`OnResume` 设置页，恢复滚动位置/焦点。

**不要做**：

- 任意深路由；
- URL/深链；
- 每个页面一个独立 HWND；
- 页面之间直接互相引用（用 `PageResult`/回调）。

#### 6.2.3 页面尺寸

| 项 | 目标 |
|---|---|
| 宽 | `min(55% 工作宽, 980)`（沿用当前） |
| 高 | `min(PreferredHeight, 工作高 - 24)` |
| 设置正文 | **470–480**（当前 560） |
| 设置总高 | 约 **570** |
| 行高 | **44**（当前 48） |
| 组头 | **24**（当前 26） |
| 页面内边距 | 20 |
| 左栏宽 | 160–180；可折叠成 44 图标栏 |
| 滚动条 | 右缘留白内 |
| 触摸目标 | ≥44 |

#### 6.2.4 迁移方式

- 用 `LegacyPage` 适配器包现有 `DrawMoreXxx` / `MoreHitAt`；
- 不改绘制逻辑，只把“壳”交给 PageHost；
- 设置页先原样搬，再改高度/行高/左栏；
- 迁移期保留旧路径，自检通过后删旧分支。

#### 6.2.5 验收

- 7 分类 / 16 行 / 连续滚动 / 双指惯性 / 滚轮 / 滚动条全部不回归；
- 页面打开/关闭/返回/点外/Esc/焦点恢复；
- `--settingsaudit` 从 18 项扩到页面级；
- `FullUi` 明显变短（设置页绘制/命中/高度/滚动迁出）；
- 不新增前台自检；用离屏渲染 + 隐藏窗口。

### 6.3 OverlayLayerManager

#### 6.3.1 契约（建议）

```csharp
interface IOverlayLayer
{
    string Id { get; }
    int Priority { get; }              // 越大越先吃输入
    bool Visible { get; }
    bool ConsumesInput { get; }
    bool BlocksInputBelow { get; }
    RectF Bounds { get; }
    DismissPolicy Dismiss { get; }     // None/Outside/Escape/OutsideOrEscape
    bool RestoresFocus { get; }
    bool IsAnimating { get; }

    bool HitTest(float x, float y);
    bool PointerDown(in UiPointerEvent e);
    bool PointerMove(in UiPointerEvent e);
    bool PointerUp(in UiPointerEvent e);
    bool Wheel(float x, float y, int delta);
    void Draw(ID2D1DeviceContext ctx);
}
```

#### 6.3.2 优先级表（初稿）

| 层 | 优先级 | 说明 |
|---|---:|---|
| 原生文字输入宿主 | 1000 | 编辑中最高；独立 HWND |
| 页面模态（PageHost） | 900 | 打开页面时盖住浮层 |
| 取景/截图特殊层 | 850 | 模态 |
| 收藏/图形浮层 | 800 | 当前最上常驻浮层 |
| 回放条 | 700 | 回放控制 |
| 计时卡 / 点名卡 | 600 | 运行型卡片 |
| PPT 条 / 页号面板 / 菜单 | 500 | 放映工具 |
| 选择操作条 / 面板 | 400 | 选中对象 |
| 提示 / 悬停卡 | 300 | **不吃输入** |
| HUD / 调试层 | 100 | **不吃输入** |

> 数值可调，但**只在这张表里调**；新增浮层不改 `OnPointerDown/Move/Up`。

#### 6.3.3 输入管线（伪代码）

```text
OnPointerDown(e):
  textInput.HitTest? -> if editing and inside host, host handles (native)
  if pageHost.Modal and pageHost.HitTest -> pageHost.PointerDown
  if captureLayer != null -> captureLayer.PointerDown
  for layer in layers.OrderByDescending(Priority):
      if !layer.Visible or !layer.ConsumesInput: continue
      if layer.HitTest(e):
          if layer.PointerDown(e):
              if layer.WantsCapture: captureLayer = layer
              return consumed
  if uiChrome.HitTest -> uiChrome.PointerDown
  if passThrough -> canvas pass-through
  else -> canvas
```

**关键**：

- 命中不等于消费：`HitTest` 只回答“在不在范围内”，`PointerDown` 才决定吃不吃；
- 捕获后，后续 Move/Up 直接给捕获层，不再重新命中；
- `BlocksInputBelow` 的层即使 `HitTest=false`，也要阻断下层（模态遮罩）；
- `DismissPolicy` 只在“这一下没被任何层消费”时触发；
- 提示/HUD 可以画在最上面，但 `ConsumesInput=false`。

#### 6.3.4 轻关闭与 inert

- 页面打开：下层浮层 `Visible` 可以保留（继续画），但 `ConsumesInput=false`；
- 点遮罩：先问 `PageHost` 是否允许关闭；允许则 `Pop()`，这一下不落画布；
- Esc：按“文字输入 → 弹层 → 页面 → More → 画布”顺序；
- 关闭后：`RestoresFocus` 的层把焦点还给触发控件/行。

#### 6.3.5 拖动与位置记忆

- 拖动会话：`PointerDown` 记录起点，超过阈值才算拖动；`PointerMove` 更新；`PointerUp` 落盘；
- 夹取到工作区，允许贴边；
- `PlacementStore` 统一保存：`Id → (x, y, w, h, orientation)`；
- 多显示器：按工作区/DPI 恢复，找不到原显示器就夹到主屏。

#### 6.3.6 迁移顺序

1. PPT 条 / 页号面板 / 菜单（几何现成）；
2. 回放条；
3. 计时卡 / 点名卡；
4. 收藏/图形浮层（引擎侧适配器，不搬绘制）；
5. 选择操作条 / 面板；
6. 提示 / 取景 / HUD（特殊层）。

#### 6.3.7 调试图层（Widget Reflector 思路）

做一个 `--uigraph` 或调试开关，显示：

- 层 Id / Priority / Bounds / Visible / ConsumesInput；
- 当前命中层；
- 当前捕获层；
- 当前焦点；
- 页面栈深度。

这对“为什么点不到/被谁挡住”比日志有效得多。

### 6.4 TextInputService

#### 6.4.1 契约（建议）

```csharp
interface ITextInputService
{
    bool IsEditing { get; }
    string? EditingId { get; }

    void Begin(TextInputRequest request);
    void UpdateRect(RectF rect);
    void Commit();
    void Cancel();
    void SetOwner(IntPtr ownerHwnd);
}

sealed class TextInputRequest
{
    public string Id;
    public RectF Rect;                 // 界面逻辑坐标
    public string InitialText;
    public TextInputMode Mode;         // SingleLine / MultiLine / RichText
    public int MaxLength;
    public bool Password;
    public Func<string, string?> Validate;
    public Action<string> OnCommit;
    public Action OnCancel;
    public TextInputVisual Visual;     // 背景、文字色、字号、内边距
}
```

#### 6.4.2 宿主策略

- **一个顶层窗口一个宿主**；覆盖层一个，真窗口各一个；
- 宿主是 `WS_POPUP | WS_EX_TOOLWINDOW` 的**可激活**顶层窗，owner = 覆盖层/主窗；
- 不显示在任务栏；不抢 Alt+Tab；
- 位置 = 页面输入框矩形换算到屏幕；
- 编辑时显示并 `SetFocus`；提交/取消后隐藏，焦点还给之前的窗口/画布；
- 页面滚动/切换：`UpdateRect`；滚出视口：隐藏或提交（按配置）；
- 页面关闭：提交或取消（按配置），不能留下孤儿 HWND；
- 字体/颜色/内边距/行高随 `TextInputVisual`；DPI 变化重建字体。

#### 6.4.3 视觉：第一版

- 无边框、无标题；
- 背景：白板 = 板色；PPT/PDF = **柔和近白**（例如 `#F7F7F5`，不要纯白）；
- 1px 淡边 + 页面自己画的圆角底（宿主内缩 1–2px，避免方角露馅）；
- 内边距 8–10px；
- 文字色用当前文本色；对比度不足时自动换深/浅底（现有逻辑保留）；
- 光标/选区用系统颜色；不做自绘。

#### 6.4.4 透明：后续评估

- **windowed RichEdit 不能真透明**；不要用 `WS_EX_LAYERED + LWA_COLORKEY`（命中不可靠）；
- 官方特性表说 **windowless RichEdit** 支持透明；但需要实现 `ITextHost`/`ITextServices`，
  处理 DC、字体、滚动、光标、IME 定位；工作量大；
- 另一条路是自绘文本 + TSF（实现 `ITextStoreACP`），更重；
- 第一版只做“柔和浅底”，真透明单独立项，不混进 P1/P2。

#### 6.4.5 迁移顺序

1. **AI API 页**（3 个字段 + 模型下拉）——第一个页面内表单；
2. **日志备注**（多行）；
3. **重命名 / 计时 / 点名 / PPT 页码**（单行）；
4. **画布文本框**（富文本，最后接，保留现有 `TextBoxEditing` 逻辑）。

#### 6.4.6 Airspace 注意

- 文字宿主是独立顶层窗，天然盖在 D2D 页面之上；
- 打开页面内下拉/菜单前：先提交或隐藏宿主，否则菜单可能被宿主挡住；
- 或者把菜单也做成独立顶层窗（成本高）；第一版用“先提交再开菜单”；
- 页面滚动时宿主跟随；滚出视口立即隐藏；
- 关闭页面时先 `Cancel/Commit`，再销毁/隐藏宿主。

#### 6.4.7 验收

- 同一时间只有一个输入宿主；
- 中文 IME（微软拼音/搜狗）、光标、选区、复制粘贴、撤销正常；
- 100/150/200% DPI、页面滚动、页面关闭、点击外部；
- 后台自检：宿主矩形跟随、提交/取消、无残留窗口。

### 6.5 ScrollView（页面共用）

#### 6.5.1 模型

```text
ScrollView
  ViewportRect    可视区
  ContentHeight   内容总高
  Offset          当前偏移（0..Max）
  Max = max(0, ContentHeight - ViewportHeight)
  ScrollBy(delta) 统一入口
```

#### 6.5.2 输入映射

| 输入 | 行为 |
|---|---|
| 滚轮 | `delta / 120 * 72` 逻辑像素 |
| 双指纵滑 | 1:1 逻辑像素（`UiTouchFling` 惯性） |
| 滚动条拖动 | 按滑块中心映射到 offset |
| PageUp/PageDown | 视口高 × 0.9 |
| Home/End | 0 / Max |
| 焦点进入 | 自动滚入视野 |

#### 6.5.3 规则

- 只有一个 `ScrollBy`；不允许页面自己改 `_settingsScroll`；
- 滚动到顶/底夹取，不越界；
- 惯性期间来新输入 → 先停惯性；
- 页面切换保存 offset（`PageState`）；
- 左栏独立 `ScrollView`，右栏滚动不影响左栏；
- 当前分类自动滚入左栏视野；
- 组头吸顶（当前分类标题固定在上沿）。

### 6.6 设置页的具体设计

#### 6.6.1 尺寸

| 项 | 现在 | 目标 |
|---|---:|---:|
| 正文高 | 560 | **470–480** |
| 总高 | 约 656 | 约 **570** |
| 行高 | 48 | **44** |
| 组头 | 26 | **24** |
| 面板宽 | 55% 工作宽，560–980 | 不变 |
| 内边距 | 20 | 20 |

#### 6.6.2 左栏

- 宽 160–180；
- **独立滚动**：分类多时只滚左栏；
- **可折叠成 44px 图标栏**：当前项始终可见；
- **当前项自动滚入视野**：右栏滚动时高亮跟着走；
- 选中：**左侧 2–3px 强调竖条 + 8% 强调色底**，不要整块高饱和蓝；
- 悬停：4% 底色；
- 行高 44，触摸目标 ≥44；
- 分组之间 1px 淡分隔；
- 键盘焦点：1.5px 外框；
- 不建议“整个目录随便拖动”——设置是模态页，拖动会挡内容且多一套位置状态。

#### 6.6.3 右栏

- **默认单列**（WinUI 规范：从上到下单列）；
- 组头 24，吸顶；
- 行高 44；行内：标签左、说明次行、控件右对齐距右 12；
- 行悬停 4% 底；行选中左侧 2px 强调条；
- 开关 44×26；下拉/按钮右对齐；
- 组之间 14–16 间距；
- 滚动条在右缘留白内，滑块最小高度 32；
- 内容底部留 12–16 空白；
- 搜索：16 行暂时不需要；PageHost 预留搜索入口，超过约 20 行再启用（Windows 11 设置/VS Code 的成熟做法）。

#### 6.6.4 2 列 / 3 列

- **默认 1 列**；
- **2 列仅当**：内容宽 ≥760，且该组所有行都是“短行”（标签 ≤6 个汉字 + 开关/短值），
  且顺序阅读不被打断；例如“墨迹”组的 3 个开关可以 2 列；
- **3 列不做**：每列约 170，中文标签 + 控件会挤，Tab 顺序也会乱；
- 2 列是“宽屏优化”，不是默认布局；窄屏/中屏保持单列；
- 如果用 2 列，Tab 顺序按“行优先”而不是“列优先”，避免键盘跳来跳去。

#### 6.6.5 选中与排版

- 左栏选中：竖条 + 8% 底；
- 右栏行选中：左侧 2px 强调条（仅当前操作行）；
- 行悬停：4% 底；
- 开关/值统一右对齐，距右 12；
- 行之间 1px 淡分隔；
- 组头吸顶；
- 键盘焦点 1.5px 外框；
- 禁用行：文字 50% 透明 + 说明原因；
- 危险操作（清空/恢复）：红色文字 + 二次确认，不放在首屏主位置。

#### 6.6.6 API 内嵌页

- 入口：设置 → AI 服务 → “管理…”（不再弹独立窗）；
- 页面内容：
  - 服务商列表（预置 + 自定义）；
  - 添加/删除；
  - 服务地址（Base URL）；
  - API Key（密码框，掩码显示）；
  - 模型（下拉/可编辑）；
  - “获取模型”按钮 + 状态；
  - “测试连接” + 状态；
  - 保存/取消；
- 文字字段走 `TextInputService`；
- 模型下拉走 `OverlayLayer`（锚定按钮，空间不够翻转）；
- 打开下拉前先提交/隐藏文字宿主（airspace）；
- 未保存离开：保存/放弃/取消；
- 不再创建 `AiApiSettings` 独立窗。

#### 6.6.7 验收

- 7 分类 / 16 行全部可点、可执行；
- 滚轮/双指/惯性/滚动条/键盘；
- 左栏独立滚动/折叠/当前项自动滚入；
- 高度 470–480、行高 44、组头 24；
- 2 列只在宽屏短行出现；3 列不存在；
- API 页完整可用，无独立窗；
- 离屏截图顶部/底部/中间各一张。

### 6.7 WindowManager（另立项目）

#### 6.7.1 窗口类型

| 窗口 | 内容 | 说明 |
|---|---|---|
| 白板 | 画布 + 工具条 | 现有主窗 |
| PDF | 文档视图 + 批注 | 多文档/多视图前置 |
| 视频展台 | 视频表面 + 控制 | 原生视频表面 |
| 笔记 | 页面列表 + 文本/墨迹 | 类 OneNote，独立文档模型 |

#### 6.7.2 必做

- 系统 chrome 优先（标题栏/最小化/最大化/关闭）；
- Per-Monitor V2；`WM_DPICHANGED` 用建议矩形；
- `WM_GETMINMAXINFO` 最小/最大尺寸；
- owner/任务栏/Alt+Tab 行为；
- 位置/尺寸/最大化状态记忆（多显示器夹取）；
- 关闭生命周期：未保存拦截、后台/退出；
- 内容层可装 `PageHost`；
- 暗色标题栏/高对比度/减少动画。

#### 6.7.3 不做

- 不把真窗口塞进覆盖层；
- 不在 PageHost 里做窗口 chrome/DPI；
- 不在本计划里做多文档/多视图（WindowManager 的前置）。

## 八、反面模式（不要学）

1. **万能 Page**：一个 Page 既管窗口、又管浮层、又管文字输入，最后变成第二个 FullUi。
2. **页面自己写输入优先级**：每加一个页面就在 `OnPointerDown/Move/Up` 插一段。
3. **每个功能自己建原生窗**：IME/焦点/DPI/关闭各写一套，永远修不完。
4. **z-index 数字到处飞**：没有唯一优先级表，层序靠猜。
5. **模态只画遮罩**：不阻断输入、不 trap 焦点、不恢复焦点。
6. **页面高度写死**：小屏顶天立地，大屏空一大块。
7. **3 列设置**：中文标签 + 控件挤，Tab 顺序乱。
8. **现在自己写 IME/TSF**：成本极高，收益低；先用原生 RichEdit。
9. **用 layered + color key 做透明编辑框**：命中/渲染不可靠。
10. **把 Overlay 的墨迹/选择框/光标搬进 UI 框架**：破坏现有渲染，风险巨大。
11. **把真窗口塞进覆盖层**：DPI/任务栏/最小化/关闭全部错。
12. **只测几何不测焦点/输入/残留窗口**：几何全绿，真机点不进去。
13. **每帧重排/重绘**：页面动画/滚动时全树 rebuild，电池和帧率都受不了。
14. **过度动画**：页面切换 500ms、弹层弹簧，操作变慢；150–200ms 足够。

## 九、落地建议：参考 → 阶段

### Phase 0：设计冻结（1–2 天）

- 确认本文的分层、契约、优先级表；
- 确认设置页尺寸/行高/左栏/2 列规则；
- 确认 TextInputService 边界（原生宿主，不写 IME）；
- 确认 P1 只做 PageHost + Settings，不动 Overlay/引擎输入主循环；
- 不动代码。

**参考**：WinUI 设置规范、Web 模态四件事、Flutter Navigator 栈语义。

### Phase 1：PageHost + Settings 试点（2–3 周）

- `PageHost` / `IPage` / `PageFrame` / `LegacyPage`；
- `SettingsPage` 包当前设置页（连续滚动/双指/滚轮/滚动条原样）；
- 页面高度 470–480、行高 44、组头 24；
- 左栏独立滚动/折叠/当前项自动滚入；
- 关闭/返回/点外/Esc、焦点、页面转场；
- 自检：`--settingsaudit` 扩展 + 离屏截图 + 隐藏窗口；
- **停止点**：行为一致、代码变短、无前台自检。

**参考**：WPF Journal（back 语义）、Qt StackView（push/pop/replace）、
WinUI SettingsCard（单列/卡片）、Avalonia FocusManager（焦点恢复）。

### Phase 2：TextInputService + AI 子页（2–3 周）

- 一个原生输入宿主（单行/多行/富文本接口）；
- 先接 3 组：AI API 字段、日志备注、重命名；
- `ApiSettingsPage` 替代独立 API 窗；
- 页面内输入框定位/滚动跟随/提交/取消；
- 自检：IME 手测 + 宿主跟踪 + 无残留；
- **停止点**：AI 配置完全在设置页内完成，不再弹独立窗。

**参考**：Win32 RichEdit/TSF、WPF TextBox、Qt QLineEdit、WinUI TextBox。
透明暂不做；第一版柔和浅底。

### Phase 3：迁更多/帮助/日志（1–2 周）

- `MoreHomePage`、`HelpPage`、`LogPage`；
- 删除/收窄 `FullUi` 里的 MorePage 壳代码；
- 自检：四页打开/返回/关闭/滚动/命中；
- **停止点**：`FullUi` 只保留装配 + 工具条。

**参考**：Flutter Navigator（栈）、WPF Page（生命周期）、Qt StackView（转场）。

### Phase 4：OverlayLayerManager（3–4 周）

- 层注册/优先级/输入路由/拖动/记忆；
- 先接 PPT 条/页号面板/菜单；
- 再接回放条、计时/点名卡；
- 收藏/图形用引擎侧适配器；
- 自检：每层命中/拖动/记忆/穿透/页面打开；
- **停止点**：新增浮层只注册，不改输入主循环。

**参考**：Slate FWidgetPath/模态栈、Chromium Pre/Target/Post、Avalonia OverlayLayer < Popup、
Web top layer/light dismiss。

### Phase 5：选择条/提示/取景（2–3 周，可选）

- 选择操作条/颜色/层级/字体/导出面板；
- 提示/HUD/取景特殊层；
- 画布手柄/光标/激光**不动**；
- 自检全量相关项。

**参考**：WPF AdornerLayer（画在上面不吃输入）、Unity pickingMode=Ignore、Slate Widget Reflector。

### Phase 6：WindowManager（另立项目）

- 白板/PDF/展台/笔记真窗口；
- PageHost 可装进窗口；
- 文档/视图拆分是多窗口的前置，不混在本计划。

**参考**：Windows App SDK AppWindow、Win32 PMv2、WPF Window、iOS presentation controller（preferredSize/锚点）。

## 十二、需要拍板的点

1. **PageHost 范围**：只包“更多 / 设置 / 帮助 / 日志 / AI 子页”，还是也包收藏/图形？
   建议先只包前五类；收藏/图形仍走引擎侧适配器，P4 再注册为 Layer。
2. **返回栈**：只做 Back，还是也做 Forward？
   建议只做 Back；设置页没有“前进”语义。
3. **KeepAlive**：设置页保留滚动位置；API 草稿单独存；页面对象默认不保留。
4. **TextInputService 宿主**：一个窗口一个；覆盖层一个；真窗口各一个。确认。
5. **真透明**：P1/P2 不做；P2 之后单独评估 windowless RichEdit/TSF。确认。
6. **2 列墨迹**：先做单列，截图后再决定是否开 2 列；3 列不做。确认。
7. **设置正文高度**：470 还是 480？建议 476（中间值），按 800 高屏实测再微调。
8. **API 页字段**：服务商预置哪些？是否支持自定义 Base URL/模型？是否需要“测试连接”？
9. **OverlayLayerManager 迁移顺序**：PPT 条 → 回放 → 计时/点名 → 收藏/图形 → 选择条 → 提示/取景。确认。
10. **WindowManager 时间**：P1–P4 之后另立项目；不混进本计划。确认。

## 十三、一句话总结

**我们不需要一个 UI 框架，只需要把成熟系统已经验证过的四件事搬过来：**

1. **页面栈**（Navigator/Journal/StackView 的 push/pop/result/lifecycle）；
2. **浮层优先级表**（top layer/OverlayLayer/FWidgetPath 的命中与轻关闭）；
3. **焦点作用域**（FocusManager/FocusScope/FocusRing 的初始焦点/陷阱/恢复）；
4. **原生输入服务**（RichEdit/TSF 的一个宿主 + 页面只给矩形/校验/提交）。

这四件事做好，新增界面就只需要“加一个 Page”或“注册一个 OverlayLayer”，
不用再改输入优先级、页面高度、遮罩、返回/关闭、焦点、滚动和文字宿主。
