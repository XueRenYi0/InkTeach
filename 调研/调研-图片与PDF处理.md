## 0. 结论速览

1. **方向可行，但要拆开看**：
   - **容易**：旋转、裁切、手动四点透视纠正、文档美化预设、数字 PDF 的文字层提取、手动框选题目。
   - **中等**：本地 OCR 接入、自动文档边缘检测、扫描件按题切分。
   - **难**：数学公式 OCR、完全自动的题目切分、弯曲书页去畸变。
2. **不需要"先接大模型"**。美化、透视、OCR、PDF 文字提取、按题切分都可以本地做；大模型只在"题目理解 / 公式转写 / 讲解 / 自动整理"时才是可选项，而且建议沿用现有 AI 调研的 **BYOK（用户自备 Key）**。
3. **最大的技术依赖是 OCR，不是图像美化**。美化可以用现成的 Direct2D 效果；OCR 要么带本地模型（包体变大、要 AOT 验证），要么走云（网络、隐私、费用）。
4. **Windows 自带的 `Windows.Media.Ocr` 不能直接用**：微软文档明确要求桌面应用具有 **package identity（MSIX 安装）**；我们是绿色版 / 单 exe，不符合。见 §4.1。
5. **数字 PDF 是最高性价比的入口**：PDFium 本身带文字层 API，数字版 PDF 可以直接抽文字 + 字符框，不需要 OCR；只有扫描版 PDF / 图片才需要 OCR。
6. **建议第一版（MVP）先不做 OCR/LLM**：
   - 图片/PDF 页：旋转、裁切、**手动四点透视**、美化预设、预览/重置；
   - 数字 PDF：抽文字层 + 按题号/大间距切题，手动调整；
   - 题目输出：裁成图片插入白板/画布，或导出 PNG；先不做自动识别和公式。
   - 这个 MVP 约 **3~5 周**（一人、熟悉仓库、含自检）。
7. **完整版（本地 OCR + 自动切题 + 公式）约 8~12 周**；如果还要 LLM 讲解/整理，再加 2~4 周，并涉及 API Key、网络和隐私同意。

### 1.1 两个必须分清的对象

- **文档页**（打开图片/PDF 后的"一叠纸"）：不在 `Doc.Strokes` 里，不参与撤销/存档/回放；位图是惰性生成、可回收的。适合做"整页美化 / 整页 OCR / 按题裁切"。
- **画布图片对象**（截图/粘贴图，`StrokeKind.Image`）：是真正的对象，参与选中/移动/旋转/翻转/复制/撤销/存档/导出。适合做"这张图裁一下 / 美化一下 / OCR 一下"。

> 同一个功能在这两条路上实现方式不同：文档页要存"处理配方"（否则重开就回到原图），画布图片可以直接把处理后的 BGRA 存进 `.inkb`（但文件会变大）。

## 2. 功能拆解：到底要做什么

### 2.1 图片美化（文档向，不是社交滤镜）

老师最需要的不是"滤镜"，而是"把手机拍的/扫描的试卷变得清楚"：

- 自动白平衡 / 去偏色；
- 对比度、亮度、gamma；
- 去阴影（页面光照不均）；
- 锐化 / 去轻微模糊；
- 黑白 / 灰度 / 护眼（暖白）预设；
- 去噪（轻量，不能把字磨没）。

**技术路线**：

- **预览**：Direct2D 内置效果直接上 GPU，不改原图，实时看；
  - 可用：Brightness / Contrast / Exposure / GammaTransfer / HighlightsShadows / Sharpen / Grayscale / TemperatureTint 等（微软 Built-in Effects 列表）。
- **导出/OCR 前**：把同一套参数在 CPU 上跑一遍（或 D2D 渲染到离屏位图再读回），生成新的 BGRA。
- **去阴影**：背景估计（大核模糊/形态学闭运算）后做除法/归一化；比简单阈值更稳，但需要自己写像素循环。
- **黑白**：自适应阈值（Sauvola / 局部均值）比全局 Otsu 更适合光照不均的试卷。

**工作量**：预设 + 滑杆 + 预览 + 导出，约 **4~6 个工作日**；去阴影/自适应黑白再加 **3~5 天**。

**风险**：过度锐化会把压缩噪点放大；黑白模式会丢失彩色标注/图形信息。必须给"原图/重置"和前后对比。

### 2.2 变形纠正（透视 / 旋转 / 裁切）

分三档：

| 档位 | 做法 | 难度 | 建议 |
|---|---|---|---|
| **旋转 90° / 微调角度** | 现有 `Stroke.Transform` 就能做；微调可用滑杆/双指旋转 | 低 | 直接做 |
| **手动四点透视** | 用户拖四个角 → 单应变换（homography）→ 双线性重采样成矩形 | 中 | **MVP 做这个** |
| **自动找纸张四角** | Canny/Hough/轮廓 + 四边形筛选；或 OpenCV / 小模型 | 中高 | 第二版再做，先手动 |
| **弯曲书页去畸变** | 需要页面曲面建模/曲线检测 | 高 | 第一版不做 |

**关键点**：

- 当前 `Stroke.Transform` 是 `Matrix3x2`（仿射），**表达不了透视**。透视纠正必须把像素重采样成一张新的 `ImageData`，不能只改对象矩阵。
- 手动四点透视不需要 OpenCV：自己写 3×3 单应矩阵 + 双线性采样即可；一张 2000×3000 的图在 CPU 上约几十毫秒到一两百毫秒，放后台线程可接受。
- 自动检测如果引 OpenCvSharp，Windows 原生包约 **38MB**（NuGet 包体积），会明显增大安装包；第一版不建议为"自动找角"付这个代价。

**工作量**：手动四点 + 预览 + 重采样 + 撤销，约 **8~12 个工作日**；自动检测再加 **5~8 天**（含调参/误检处理）。

### 2.3 OCR（文字识别）

先问清楚目标，不同目标难度差很多：

| 目标 | 需要什么 | 难度 |
|---|---|---|
| 把题目文字**复制/搜索** | 文字 OCR + 行/段合并 | 中 |
| 把题目给 **AI 讲解** | 其实可以直接把**裁剪后的题目图片**交给视觉大模型，不必先 OCR | 中（但走云） |
| 识别**数学公式** | 公式 OCR / 视觉模型；普通 OCR 会把公式打散 | 高 |
| 识别**手写学生答案** | 手写 OCR；准确率远低于印刷体 | 很高，不建议第一版承诺 |

#### 2.3.1 Windows 自带 OCR：不能用（重要）

微软 `Windows.Media.Ocr` 文档明确：

> APIs in the Windows.Media.Ocr namespace are only supported for desktop apps with **package identity**. This means that the app is installed and run from an MSIX package.

我们的绿色版/单 exe 没有 package identity，**不能直接调用**。为了 OCR 单独做 MSIX/sparse package 不值得。

#### 2.3.2 本地 OCR 方案

| 方案 | 优点 | 缺点 | 适合 |
|---|---|---|---|
| **RapidOcrNet**（PaddleOCR ONNX，.NET） | 官方 README 标 **AOT-compatible**、net10、去掉 OpenCV 依赖（SkiaSharp + PContourNet）；中文印刷体好 | 要带 ONNX Runtime / SkiaSharp 原生库 + 模型；包体增加；需要实测 4GB 机器 | **首选本地方案** |
| **Tesseract 5** | 轻；Apache-2.0；chi_sim fast 仅 2.35MB | 中文版面/公式准确率一般；需要自己处理行/段 | 低成本备选 |
| **PaddleOCR 原生/其他 .NET 封装** | 中文强 | 依赖重、部署复杂 | 不优先 |
| **云 OCR**（百度/腾讯/阿里/讯飞等） | 准确、无需本地模型 | 网络、费用、隐私；学校可能断网 | 可选"在线识别" |
| **视觉大模型**（Qwen-VL / 豆包视觉 / GPT-4o 等） | 公式/版面理解可能更好 | 费用、隐私、幻觉；结果不稳定 | 公式/难题的可选增强 |

> RapidOcrNet 的 AOT 兼容是它 README 的声明，**必须在我们自己的 NativeAOT 发布里实测**；包体/内存/模型加载时间都要量。

#### 2.3.3 数学公式：普通 OCR 不够

- 普通 OCR（Tesseract/RapidOCR）输出的是"文字行"，分式、根号、上下标、矩阵会被打散或识别成乱码。
- 专用公式 OCR：Mathpix、SimpleTex、Pix2Text 等；Mathpix 准确但收费/云；SimpleTex 国内可用；本地模型重。
- 视觉大模型可以直接"看图转 LaTeX"，但可能幻觉，必须给用户预览/校对。
- **建议**：第一版明确"只做印刷体文字 OCR，不做公式"；公式作为单独的可选云服务，或在 AI 讲解场景直接传题目图片，不承诺转写。

**工作量（本地 OCR 接入）**：模型/依赖接入、AOT 验证、后台任务、进度/取消、置信度、错误处理、真机性能，约 **10~20 个工作日**；云 OCR 约 **5~8 天**（不含账号/合规）。

### 2.4 题目切分

#### 2.4.1 数字 PDF：先抽文字层，不要 OCR

PDFium 提供文字层 API：

- `FPDFText_LoadPage` / `FPDFText_ClosePage`
- `FPDFText_CountChars` / `FPDFText_GetText`
- `FPDFText_GetCharBox`（字符框）/ `FPDFText_GetFontSize`

数字版 PDF 可以直接得到**文字 + 字符坐标**，不需要 OCR。按题号正则 + 行/段聚类 + 大间距切分即可：

- 题号：`1.`、`1、`、`（1）`、`一、`、`例1`、`练习1` 等；
- 用字体大小/加粗/缩进区分"大题"和"小问"；
- 用纵向空白、分栏位置辅助；
- 结果给用户预览，允许合并/拆分/拖动边界。

**工作量**：PDFium 文字层 P/Invoke + 行/段重组 + 题号规则 + 预览/调整，约 **8~12 个工作日**。这是性价比最高的一块。

#### 2.4.2 扫描 PDF / 图片：OCR 框 + 规则

- 先 OCR 得到文字行框；
- 行合并成段（按纵向间距、缩进、字体大小）；
- 题号正则 + 大间距/分栏；
- 自动结果只能"建议"，必须允许手动框选/调整。
- 两栏试卷、跨页题、图表题、公式题：自动切分容易错，**手动框选作为兜底**。

**工作量**：自动切题 + 手动调整 UI + 题目卡片/裁切/插入，约 **10~15 个工作日**（不含 OCR 本身）。

#### 2.4.3 要不要大模型做切分？

- **不是必需**。数字 PDF 用文字层 + 规则最稳；扫描件先用 OCR 框 + 规则。
- 大模型适合：版面很乱、题号不规律、需要理解"这一题到哪结束"；但返回的坐标不可靠，仍需人工确认。
- 如果做，建议只把 **OCR 文字 + 行框**发给文本模型（不上传整页图片），成本低、隐私风险小；视觉模型只在用户明确同意时用。

### 2.5 PDF 的额外问题

- **PDFium 只读**：能渲染、能抽文字，但不能写 PDF、不能删页/合并页。
- 如果"题目切分"只是**在软件里一题一题显示/批注/导出图片**：不需要 PDF 写入，工作量小。
- 如果要**导出新的 PDF（只含选中的题）**：需要 PDFsharp（MIT）之类的写库，或先把题裁成图片再合成 PDF；约 **5~10 天**。
- PDF 页面可能是：
  - 文字层完整（数字版）→ 直接抽；
  - 扫描图（无文字层）→ OCR；
  - 文字被转成曲线/公式（数学排版常见）→ 文字层可能缺失，只能 OCR/视觉模型。
- PDF 的旋转/裁剪/页面框（CropBox）要和 PDFium 坐标换算；工作量中等，但必须做对，否则题框会偏。

## 4. 架构落点（接进现有代码的方式）

### 4.1 图片编辑：两条路

**A. 画布图片对象（截图/粘贴图）**

- 直接改 `ImageData.Bgra`，重建 D2D 位图；对象仍然是 `StrokeKind.Image`。
- 优点：选中/移动/旋转/复制/撤销/存档/导出全部复用；`.inkb` 已经存 BGRA。
- 缺点：处理后像素写进存档，文件变大；撤销要保存旧/新像素（或重新从源图生成）。
- 需要给 `ImageData` 加"替换像素 + 使位图缓存失效"的入口（现在只有 `Adopt` / `Release`）。

**B. 文档页（图片/PDF 页）**

- 页图不在 `Doc.Strokes` 里，不能直接当图片对象改。
- 建议加一个**非破坏性编辑配方**（`PageEdit`）：
  - 旋转角度 / 裁切矩形 / 四点透视 / 美化预设 / 输出尺寸；
  - 存进文档会话（按源文件 + 页号 + 配方 hash）；
  - 重新打开时按配方重新生成，源文件不动。
- 如果直接把处理后的位图写盘：要额外的 cache 文件，内存/磁盘/清理都变复杂；不建议第一版。
- **注意**：如果页面已经写了批注，再改页面几何（裁切/透视），批注坐标会错位。第一版建议"有批注的页不允许改几何"，或改几何时明确提示/另存为新页。

### 4.2 题目卡片/题目切分

三种输出形态，工作量不同：

1. **临时裁切显示**：不改文档，只在屏幕上把某一页的某个矩形放大/全屏显示；最简单。
2. **插入画布图片**：把题裁成 `ImageData`，`Doc.AddImage` 放到白板/当前页；可移动/缩放/导出，复用现有对象体系。**推荐 MVP**。
3. **新文档页/题目卡片**：把题变成独立页或带 OCR/标签的卡片；需要新的页面/元数据模型，工作量最大。

### 4.3 后台任务与性能

- 复用文档页 worker 的思路：图像处理/OCR 全部在后台线程，主线程只收进度和结果。
- 任务要可取消；切换页面/关文档要能丢弃结果。
- 一次只处理一页；OCR 前把图缩到约 2000px 长边，别把 6000px 原图直接喂模型。
- 4GB 机器：OCR 运行时 + 模型 + 一张 2000px 图可能占几百 MB；必须实测，必要时做"低内存档"或云识别。
- UI：进度条 + 取消 + 失败原因；不要在 UI 线程解析 PDF/跑模型。

### 4.4 存档/撤销

- 画布图片：BGRA 直接存档；编辑动作要一步撤销（替换前/后像素或重做配方）。
- 文档页：存配方最干净；如果配方包含 OCR 文本/题目框，也要版本化，避免源文件变了配方失效。
- 题目卡片：若作为图片对象，走现有存档；若作为新页，需要扩展 `DocPages.Spec` / 文档存档。
- 不要把 OCR 文本/题目图片写进日志。

## 5. 大模型 API：需不需要？

**结论：不是这条功能的前置条件。**

| 场景 | 要不要 LLM | 说明 |
|---|---|---|
| 美化、透视、裁切 | 不要 | 纯图像处理 |
| 印刷体 OCR | 不要 | 本地/云 OCR 即可 |
| 数字 PDF 抽文字/切题 | 不要 | PDFium 文字层 + 规则 |
| 扫描件自动切题 | 可不用 | OCR 行框 + 规则 + 手动调整 |
| 数学公式转写 | 可选 | 专用公式 OCR 或视觉模型；普通 OCR 不够 |
| 题目讲解/分类/生成变式 | 要 | 这是 AI 助手功能，不是图片处理 |
| 很乱的版面自动理解 | 可选 | 视觉模型；坐标仍需人工确认 |

如果要做 LLM：

- 沿用 `调研-AI助手与大模型语音接入.md` 的 **BYOK**：用户自己填 Key，软件不做官方托管/备案；
- 图片/题目可能含学生姓名、答案，**不能沿用设备统计的同意**；必须单独、逐次或明确开关同意；
- 优先只发 OCR 文字/题目裁图，不发整页；能本地就不上云；
- 结果要给用户预览/确认，不能直接改板书。

## 6. 工作量与分期（建议）

> 估算口径：一名熟悉本仓库的开发者，含自检/真机，不含长期调参和模型训练。

### MVP（3~5 周）——"先让图片/PDF 好用"

1. 画布图片对象：旋转/裁切/手动四点透视 + 美化预设（原图/清晰/黑白/护眼）+ 预览/重置。
2. 文档页：同样的旋转/裁切/透视/美化，存"编辑配方"；有批注的页先禁止改几何。
3. 数字 PDF：PDFium 文字层抽取 + 题号/间距切题（只对文字层完整的 PDF）。
4. 题目输出：手动框选 → 裁成图片插入画布/导出 PNG；不做自动 OCR、不做公式。
5. 后台任务 + 进度/取消 + 自检。

**这个 MVP 已经能解决"把试卷拍清楚、裁出来、一题一题讲"的大部分需求。**

### V2（+3~5 周）——本地 OCR

1. RapidOcrNet / PP-OCR 模型接入，AOT/4GB 机器实测。
2. 图片/扫描 PDF 的文字识别（印刷体），置信度 + 手动修正。
3. OCR 行框 + 规则做题目切分建议；手动框选兜底。
4. OCR 结果可复制/搜索/给 AI（文本，不上传整页）。

### V3（+3~6 周）——自动切题 / 公式 / LLM（可选）

1. 自动纸张四角检测（OpenCV 或小模型；包体换体验）。
2. 复杂版面自动切题 + 题目卡片/标签。
3. 公式 OCR（Mathpix/SimpleTex/视觉模型，按次计费）。
4. 题目讲解/分类/变式（BYOK LLM）。

**总计**：
- 只做 MVP：**3~5 周**；
- MVP + 本地 OCR + 基本自动切题：**8~12 周**；
- 再加公式/LLM/复杂版面：**12~18 周**（且需要持续调优）。

## 7. 依赖与包体/性能账

| 依赖 | 用途 | 大约增量 | 备注 |
|---|---|---|---|
| Direct2D 内置效果 | 美化预览 | 0（已有） | 无新依赖 |
| 自写单应/重采样 | 手动透视 | 0 | 推荐 MVP |
| PDFium 文字 API | 数字 PDF 抽字 | 0（已有 pdfium.dll） | 只需加 P/Invoke |
| RapidOcrNet + ONNX Runtime + 模型 | 本地 OCR | 约 30~80MB（含中文模型） | 需 AOT/4GB 实测 |
| Tesseract + chi_sim fast | 轻量 OCR | 约 10~20MB | 准确率较低 |
| OpenCvSharp 原生 | 自动找角/轮廓 | 约 38MB 包 | 第一版不建议 |
| PDFsharp | 导出新 PDF | 小（纯托管） | 只有要写 PDF 才引 |
| 云 OCR / 公式 OCR / LLM | 云能力 | 0 包体 | 网络/费用/隐私 |

当前绿色包约 9.3MB；加本地 OCR 后可能到 **40~90MB**。学校 U 盘/局域网更新可以接受，但"下载更新"会变慢；可以考虑"基础包 + OCR 模型包按需下载"，但离线学校要能一次装全。

性能预期（需实测，不是承诺）：

- 美化/透视：一张 2000×3000 图，CPU 几十到几百毫秒；GPU 预览 <16ms。
- 数字 PDF 抽字 + 切题：一页几十毫秒到几百毫秒。
- 本地 OCR：一页 A4 印刷体约 0.5~3 秒（i5 级 CPU），首次模型加载 1~3 秒；4GB 机器要实测内存峰值。
- 云 OCR/LLM：取决于网络，1~5 秒/页；必须有超时/重试/取消。

## 8. 隐私与合规

- 图片/PDF 可能包含**学生姓名、班级、答案、批改痕迹**，属于个人信息/未成年人信息。
- 设备与性能统计的同意**不能覆盖**图片/OCR/LLM 上传；需要单独的、明确的同意（逐次或设置开关）。
- 本地 OCR/本地处理优先；云识别必须显示"将上传什么、给谁、做什么"，并允许取消。
- 不把 OCR 文本、题目图片、文件名写进日志；日志上传仍是手动。
- 如果接 LLM，沿用 BYOK，不做官方托管；公式/题目图片尽量裁剪后再发，不发整页。
- 学校网络可能禁止外网；离线可用是底线。

---

## 9. 风险

1. **OCR 准确率**：印刷体尚可，手写/公式/表格/分栏明显下降；不能承诺"全自动"。
2. **包体/内存**：本地 OCR + 模型会让安装包从 9MB 涨到几十 MB；4GB 机器可能吃紧。
3. **AOT 兼容**：RapidOcrNet 声称 AOT-compatible，但必须在我们自己的 NativeAOT 发布里验证 SkiaSharp/ONNX Runtime。
4. **PDF 文字层缺失**：数学 PDF 常把公式转曲线；数字 PDF 也可能抽不出公式，仍需 OCR/视觉模型。
5. **批注错位**：页面裁切/透视后，已写的批注坐标会变；第一版要限制或提示。
6. **题目切分误判**：题号不规律、跨页题、两栏、图表题；自动结果必须可手动修正。
7. **持久化**：文档页处理配方/题目卡片是新模型，存档/撤销/重开都要设计；不要只做"当前屏幕好看"。
8. **隐私**：云 OCR/LLM 涉及学生信息；同意、脱敏、日志都要单独处理。

---

## 10. 建议与需要拍板

### 建议

- **先做 MVP，不接 OCR/LLM**：手动透视 + 美化 + 数字 PDF 文字层切题 + 手动框题插入。
- **数字 PDF 优先**：PDFium 文字层是现成的，性价比最高；扫描件后置。
- **本地 OCR 选 RapidOcrNet 做验证**，Tesseract 作为轻量备选；先做技术验证（AOT/4GB/包体），再决定是否进产品。
- **自动找角/自动切题放第二版**；第一版手动四点/手动框选就够用。
- **公式/LLM 单独立项**：不要和"图片美化"绑在一起；公式 OCR 的准确率和隐私成本都高。
- **页面编辑做非破坏性配方**；有批注的页先不允许改几何，避免坐标错位。

### 需要拍板

1. 第一版是否只做 **MVP（无 OCR/LLM）**？
2. "题目切分"的输出是：**插入画布图片** / **独立题目卡片** / **导出新 PDF**，选哪个？
3. 是否接受本地 OCR 让安装包涨到 **40~90MB**？还是只做"云 OCR 可选"？
4. 数学公式 OCR 是否在范围内？如果只做印刷体文字，第一版可以简单很多。
5. 页面编辑是否允许在**已有批注**的页上做？建议第一版禁止，或另存为新页。
6. 云 OCR/LLM 是否走 BYOK、默认关闭、逐次同意？
