## 〇、一句话

**三条路都不划算。** 换引擎省的是「安装包 1.5~2.5 MB + 文档对象几 MB」，
省不掉真正的 100~250 MB（页位图在 CPU 与显存各一份，跟引擎无关）；
「转磁盘图再释放引擎」是拿**首开 30~90 秒**去换**文件句柄**。
所以：**引擎不换、不加转图，现状保留。**

---

## 一、被否掉的三条路（连同各自的真实代价）

### A. 换 `Windows.Data.Pdf`（WinRT，系统自带）

功能上确实能替：全仓没有 `FPDFText_*`，只用了「加载 + 渲成 BGRA」。

| 项 | 数字/判断 |
|---|---|
| 安装目录 | 34.8 → 约 27.6 MB（−7.15 MB） |
| 分发 zip（9.9.2 实测 15.91 MB） | 约 −3.54 MB；再扣 CsWinRT 投影（预计 +2~4 MB）→ **净 1.5~2.5 MB** |
| 内存 | 只省文档对象（交叉引用表 / 页面树 / 字体对象）——几 MB 到十几 MB |
| 新增开销 | 输出必走**编码流再解码**（比直接写 BGRA 多一份峰值） |
| 缩放 | 有 `SourceRect` 能区域渲，但大尺寸行为需实测；PDFium 现在的负原点裁块方案更直接 |
| 批注/表单 | PDFium 显式 `FPDF_ANNOT`；`PdfPageRenderOptions` **没有「渲批注」开关** |
| 文件访问 | 路径直给原生库 → 改为 `StorageFile.GetFileFromPathAsync`（**网络盘 / U 盘 / 受限目录 / 长路径失败率更高**） |
| 容错 | 细错误码 → 异常 + HRESULT（畸形文件更易失败） |
| **AOT（决定性风险）** | 默认 AOT 发布；CsWinRT 的 `IAsyncOperation<T>` helper 在 AOT 下抛 `NotSupportedException`（CsWinRT issue #1871，2024-11 提出、2026-03 仍在跟）。`LoadFromFileAsync` 返回的正好是这个类型 —— **API 形状直接落在已知坑里**，必须先 spike |

**判定：不换。** 拿「整节课能不能打开课件」换「装包小 2 MB」，方向错了。

### B. 打开即全转图片，转完释放引擎

技术上成立（顺序硬约束：**先停补丁 worker，再关文档句柄**；`DocImport.cs:577` 就是 2026-11-16 P0-1 的教训）。

| | 现在 | 全转图 |
|---|---|---|
| 打开 100 页扫描版 | ~1.5 s | **30~90 s**（实测 270~900 ms/页，未计编码） |
| 内存 | 静止 1 页 13.8 MB | 全渲 N×14 MB（100 页 ≈ 1.4 GB），必须落盘 |
| 磁盘 | 0 | 1600 宽 PNG 约 1~2 MB/页 → 100 页 **100~200 MB**；转 JPEG 压到 30~60 MB 但文字边糊 |
| 放大 200~300% | 可见区按**设备分辨率**重画，清晰 | 清晰度**钉死在转换倍率**，之后是位图拉伸 |
| 书写 | 只在翻页那一下 | 后台批量转图**与笔抢 CPU**，低配掉笔 |
| 文件句柄 | 打开期间可能占着 | 转完可立刻还（**唯一明确成立的收益**） |

**判定：不做默认路径。** 若将来真需要「不碰原文件」，只能做成**显式动作**「转成图片文档 / 归档」，不能挂在打开流程里。

### C. 「渲完就释放 PDFium」（只关文档、不转图）

能省几 MB 文档对象，但代价是**下次翻回去要重新 `LoadDocument`**，
且必须补一套「路径+大小+时间 校验 + 重开 + 加载中占位 + 空白兜底」，否则就是产品事故。

**判定：单独做不值。** 只有在做「页图磁盘缓存」时才顺带做（见第四节触发条件）。

## 二、为什么「PDF 内存涨很多」换引擎救不了（实测账）

`reports/docmem-20261116-150232.md`，16G / 2520×1680 / 省内存档 / 3 页合成 PDF：

| 项 | 100% 静止 | 200% 放大 | 产生者 |
|---|---:|---:|---|
| 页位图 `ImageData` | 13.8 MB | 13.8 MB | 渲染结果（**换引擎一样**） |
| 高清补丁 | 0 | **25.4 MB** | 渲染结果（**换引擎一样**） |
| D2D 分块 | 17.5 MB | 24.0 MB | 显示管线（**与引擎无关**） |
| GPU 专用 | 84.5 MB | **118~162 MB** | 页位图在显存**再存一份** |
| 私有字节 | 133.4 MB | 176~269 MB | 合计 |
| 无文档时整机私有 | 约 58 MB | — | 基线 |

**读法**：大头是「页位图 CPU 一份 + 显存一份」，再叠补丁和分块缓存。
PDFium 自己只占几 MB 到十几 MB。**换任何一个引擎，这四个数都不会变小。**

## 三、当初真正该做的（如果还要碰这块，按这个顺序）

1. **先测量，再决策**：同一页面分别存 PNG 与单页 PDF，各跑一遍 `--docmem`，
   比 `私有 / GPU L / LOH` 的差值 = PDFium 的真实开销。**差值 <20 MB 就不要再谈换引擎。**
   （本轮未做：用户判断不值得继续投入。）
2. **省安装包 → PDF 组件按需下载**：`csproj:70` 早就是「vendor 里有就拷、没有也能编译」，
   `Pdfium.EnsureLoaded` 已备「缺 pdfium.dll」提示。首次开 PDF 下 3.5 MB →
   **zip 直接 −3.54 MB，零画质 / 零可靠性 / 零内存风险**。这是唯一「白拿」的收益。
3. **省内存 → 扫描页不建高清补丁**：能识别「整页是一个图像对象」时不建补丁，
   一次拿回约 **25 MB CPU + 对应显存**，比换引擎大一个数量级。
4. **想还文件句柄 → 页图磁盘缓存 + 空闲关文档 + 按需重开**：
   稳态内存不变，但文件不被长期占用、翻回不重渲。

以上 2/3/4 都**不碰渲染引擎、不改画质**，任一条都优于换引擎。

## 五、这次的教训（防重蹈覆辙）

1. **「内存涨很多」不等于「引擎占很多」**——本仓的 PDF 内存 90% 以上是**我们自己**的页位图与显示管线，
   换供应商改不了自己的账。先按项归因（`--docmem` 已经能打出来），再谈替换。
2. **「省安装包」和「省内存」是两个正交目标**，不能用一个「换引擎」同时宣称解决。
   本次混在一起谈，导致多绕了两轮。
3. **体积账必须用真实产物算**：`dist/*.zip` 实测（15.91 MB）而不是估算原生库大小；
   新增的投影 / 运行时依赖必须从收益里扣。
4. **AOT 是硬门槛，不是加分项**：引入 WinRT 投影前先做 20 行 spike，
   否则可能写完才发现 `IAsyncOperation<T>` 在 AOT 下直接抛异常。
5. **别把「转图」挂进打开流程**：任何让老师等 30 秒的方案，功能再干净也不可接受；
   它只能做成显式动作。
6. 用户 2026-11-17 的收口态度值得记住：**收益 ≤2 MB 的架构改造，不值得投入**，
   宁可留着现状、把精力放在手感与课堂流程上。
