# 调研-系统墨迹两条路线：委托墨迹轨迹 vs Windows Ink 桌面宿主

> 日期：2026-10-11。缘起：外部对"DelegatedInkTrailVisual 接入方案"的一份点评提出两条路线
> （DelegatedInkTrailVisual ／ InkDesktopHost + IInkPresenterDesktop）。
> 本文把两条路线的**官方文档逐条核实**，并与本仓库的实测数据
> （2026-09-14 的 `coreink-probe`、2026-10-11 的委托轨迹实测与 9.0.6 上线）逐项比对。
>
> **一句话**：委托轨迹＝"只借系统画最新一小段"（已在本项目上线，Win11 24H2+ 有效）；
> 桌面宿主＝"把整套系统墨迹（输入＋湿墨＋干墨）搬进你的视觉树"（Win10 1511+ 可用，但**输入主权要让给系统**）。

---

## 〇、结论先行（给本项目的处置）

| 问题 | 结论 |
|---|---|
| 我们现在用的是哪条？ | **路线 A 的 Win32 变体**：`IDCompositionInkTrailDevice` → `IDCompositionDelegatedInkTrail`（`dcomp.h`）。2026-10-11 已在产品里跑通并随 **9.0.6** 发布。 |
| 我们的输入路径是哪一种？ | **A：WM_POINTER 直收**——`WM_POINTERDOWN/UPDATE/UP` ＋ `GetPointerPenInfoHistory`（合并点恢复）＋ raw 输入补点；笔/鼠标/触摸分流（对应点评里的选项 A，外加 raw 补点）。**不是**鼠标消息、**也不是** InkPresenter。 |
| 路线 B（InkDesktopHost）要不要上？ | **不要**。它相对 A 的独有能力是"Win10 也有系统湿墨"，代价是把**输入主权**交给系统——我们 2026-09-14 探针实证：接入后**我们窗口收到的指针消息归零**（DOWN 0/UPDATE 0/UP 0）。这与"全屏透明批注层＋自研输入/笔迹模型"正面冲突。 |
| "先做最小验证程序"要不要做？ | **路线 A 的验证已经在产品里完成**（无需新项目）；路线 B 的关键未知不是"能不能画"（探针已证能画），而是"输入被吞后我们的功能还剩多少"——那是产品级取舍，不是技术未知。 |
| 遗留（待拍板） | ① Win11 21H2~23H2 的"顶三分之一屏闪烁"：要不要照 Chromium 加"低于 24H2 不开轨迹"的版本门槛（本机 25H2 不受影响）；② Win10 教室机没有系统湿墨，现状＝自绘＋合成边界配速 1.0 帧；③ 触摸快速书写受面板 120Hz 上限（预测点方案已证甩尾，维持现状）。 |

## 一、两条路线是什么（官方口径）

### 1.1 路线 A：委托墨迹轨迹（Delegated Ink Trail）

**作用（官方原文）**：`DelegatedInkTrailVisual`——
"Represents a 'wet' ink stroke rendered by the system while the application processes the 'dry' ink rendering pass."
即：应用把"正在写的最新一截"交给系统合成器，**系统替你画湿墨**，应用自身的渲染延迟不再影响这一截的跟手程度。

**两个化身（同一机制，两副门面）**：

- **WinRT 侧**：`Windows.UI.Composition.DelegatedInkTrailVisual`
  - 工厂：`Create(Compositor)` / `CreateForSwapChain(Compositor, ICompositionSurface)`
  - 方法：`AddTrailPoints(InkTrailPoint[])`、`AddTrailPointsWithPrediction(real[], predicted[])`、
    `RemoveTrailPoints(uint generation)`、`StartNewTrail(Color)`
  - **官方 Requirements：introduced in 10.0.20348.0**（Windows 11 21H2 一代 / Server 2022），
    UniversalApiContract **v12**。
  - 官方 Remarks：预测点"像真实点一样，追加在真实点之后"；**下一次 Add 调用会自动清掉上一批预测点**。
- **Win32/COM 侧**：`IDCompositionInkTrailDevice`（从 `IDCompositionDevice` QI）
  → `CreateDelegatedInkTrail()` / `CreateDelegatedInkTrailForSwapChain(IUnknown* swapChain)`
  → `IDCompositionDelegatedInkTrail`（方法同上，多一个 `out generationId`）。
  - 文档是**prerelease 空壳**（无要求说明、无 Remarks）——"能不能用"**只能运行时探测（QI）**。

**我们实测（2026-10-11，本机 Win11 24H2 / 26100.7462〔版本号 2026-10-12 更正：原写 26200 系笔误〕；详见《实测-委托墨迹轨迹-2026-10-11.md》）**：
官方文档**没写**、但与 Chromium 源码对齐后补齐的三个关键点——

1. 轨迹对象必须**作为视觉内容挂进 DComp 视觉树**、叠在交换链之上。
   只创建不挂树＝COM 调用全成功、`generation` 正常递增，屏幕上永远没有墨（我们此前"系统不渲染"的旧结论就是这个根因）；
2. 每帧要把"已经由我们画上屏"的点用 `RemoveTrailPoints` **结账删掉**。
   系统单条轨迹上限 128 点（Chromium 常量 `kMaximumNumberOfDelegatedInkPoints = 128`），
   只喂不删超限后会回滚（真机症状"先出墨、中途变透明、抬笔才补全"）；
3. 它画的永远是"**还没上屏的那一小段**"：喂点 → 系统立刻画 → 我们下一帧自己画上去 → 这一截被"消化"。
   所以"只让系统画"的诊断模式下屏幕上只剩"闪一下"——**结构性表现，不是故障**。

**版本边界**：Win10 没有此通道（接口在 Win11 一代才存在；Chromium 门槛是 24H2——
其注释写明"顶三分之一屏的闪烁问题 24H2 才修好"）。

### 1.2 路线 B：Windows Ink 桌面宿主（InkDesktopHost / IInkPresenterDesktop）

**作用（官方原文）**：`IInkDesktopHost`——
"enables ink input, processing, and rendering through the creation of an app thread to host an
**IInkPresenterDesktop** object and insert it into the app's **DirectComposition** visual tree."
即：给传统 Win32 桌面应用一条**完整接入 Windows Ink 平台**的路——系统在**自己的低延迟后台线程**上
收笔输入、把**整条湿墨**画进你提供的 DComp 视觉树；干墨可交给系统，也可由你自绘（自定义干燥）。

**API 面（本机 SDK 头文件核实）**：

- `IInkDesktopHost`（`inkpresenterdesktop.h`，IDL `InkPresenterDesktop.idl`）
  - `CreateInkPresenter` / `CreateAndInitializeInkPresenter` / `QueueWorkItem`
  - 最低要求：**Windows 10（桌面应用）**；`InkPresenter` 文档注明 "**InkDesktopHost（Windows 10 version 1511 及更新）**"
- `IInkPresenterDesktop`
  - `SetRootVisual(IUnknown*)`（接入你的 DComp 视觉树） / `SetSize` / `GetSize`
  - `SetCommitRequestHandler`（**允许应用**而不是 presenter 提交 DComp 命令；回调接口 `IInkCommitRequestHandler::OnCommitRequested`）
  - `OnHighContrastChanged`
- 同一实现对象的 **WinRT `InkPresenter` 面**：`InputDeviceTypes`（Pen/Mouse/Touch）、
  `StrokesCollected`、**`ActivateCustomDrying()`**、`InkSynchronizer`、`PredictionTime`……
- **`IInkD2DRenderer`**（`inkrenderer.h`；另有 `IInkD2DRenderer2` 带 `INK_HIGH_CONTRAST_ADJUSTMENT`）
  - `Draw(IUnknown* pD2D1DeviceContext, IUnknown* pInkStrokeIterable, BOOL fHighContrast)`
  - 作用：把墨迹（含系统同款外观）画进**你自己的 D2D 设备上下文**——自定义干燥时保证"湿/干外观一致"。
- **新一代变体**：`CoreInkPresenterHost`（Windows 10 Fall Creators Update / 1709 起；
  "Host an InkPresenter in your own Windows.UI.Composition tree without an associated InkCanvas control"）
  ——我们 2026-09-14 探针用的就是它。

**湿/干墨的分工（官方与 MSDN 杂志口径）**：
- "By default, ink input is processed on a **low-latency background thread** and rendered 'wet' as it is drawn."
- **自定义干燥**（custom drying）：`ActivateCustomDrying()` 后，系统只负责湿墨层，
  干墨由应用渲染到自己的 DirectX 表面；`InkSynchronizer` 的 **BeginDry/EndDry** 用来把
  "从湿墨层撤下"与"自己画上干墨"同步在**同一帧**。
  - 官方明说：SIS/VSIS 有同步保证；**SwapChainPanel 不保证**（可能有"两层同现或短暂空墨"的闪）。
  - 官方列的典型用途：墨与非墨内容交错保 z 序；大画布平移缩放；把墨"干燥"成直线/图形等。

**我们已有的探针数据（`reports/coreink-probe.txt`，2026-09-14）**：

| 运行 | 配置 | 我们窗口收到的指针消息 | InkPresenter 产出 | 屏幕墨色像素 |
|---|---|---|---|---|
| A | 覆盖层窗口 ＋ `CoreInkPresenterHost` ＋ 合成笔 | **DOWN 0 / UPDATE 0 / UP 0** | 1 笔 | **2615**（系统真的画了） |
| B | `--nohost` 对照 ＋ 合成笔 | DOWN 1 / UPDATE 22 / UP 1 | 0 笔 | 0 |
| C | `InputDeviceTypes=Pen\|Mouse` ＋ 合成鼠标 | **DOWN 0 / UPDATE 0 / UP 0** | 1 笔 | **0**（有笔画数据、无湿墨渲染） |
| D | `InputDeviceTypes=Pen`（只给笔）＋ 合成鼠标 | DOWN 1 / UPDATE 0 / UP 1 | 0 笔 | 0（鼠标不被受理，消息也没被吞） |

→ 三条硬结论：**① 它能画**（连我们这种 TOPMOST+NOACTIVATE+NOREDIRECTIONBITMAP 的窗口也能画）；
**② 它吞输入**（A/C 两轮里我们窗口的指针消息全为 0）；③ 非笔输入能产出"笔画数据"
（C 轮 1 笔）但**系统湿墨的渲染走的是笔通道**（C 轮墨色 0）。

## 二、正面对比（各方面）

| 维度 | A. 委托墨迹轨迹（DelegatedInkTrail） | B. InkDesktopHost / InkPresenter（桌面宿主） |
|---|---|---|
| 定位 | 合成器上的**一个低延迟湿墨原语**（只画"最新一小段"） | **整套系统墨迹平台**（输入采集＋湿墨渲染＋干墨事件/自定义干燥） |
| 输入归属 | **完全归应用**（我们的 WM_POINTER 管线原封不动） | **归系统墨迹线程**（探针实证：我们窗口指针消息归零） |
| 湿墨画什么 | 只有"还没上屏的那一小段" | **整条正在写的笔画**（系统持续画） |
| 干墨 | 始终应用自绘（不进系统模型） | 默认系统管；可 `ActivateCustomDrying` 自绘（`InkSynchronizer`＋`IInkD2DRenderer`） |
| 数据模型 | 点＋半径＋颜色（瞬时数据，`generationId` 管理回收；**非文档对象**） | 产出 **InkStroke**（含压感/倾角/变换/颜色），需自行转成我们的 Stroke 模型 |
| 预测 | `AddTrailPointsWithPrediction` 的 predicted 数组（**我们实测：顶采样间隙会甩尾，已撤**） | 湿墨预测由系统内部管理（`InkPresenter.PredictionTime` 等） |
| 版本门槛 | **Win11 21H2+ 才有 API**；Chromium/Edge 只认 **24H2+**；**Win10 完全没有** | **Windows 10（1511+）就有**；CoreInkPresenterHost 需 1709+ |
| 与自研 D2D 渲染 | 无缝：同一棵 DComp 树，加一个视觉把"最新一截"交给系统 | 需在你的 DComp 树里给它一块根视觉；干墨自绘还要接 D2D 渲染回调与同步 |
| 与自研输入管线 | 零冲突（点是我们喂的） | **正面冲突**：raw 补点、合并点恢复、压感回填、触摸手势、停顿成型、橡皮、选中……全部建立在"我们自己收到指针消息"之上 |
| 我们现在的状态 | **已接入并随 9.0.6 发布**；笔/鼠标/触摸都喂；实测尾巴峰值 163/163/407 | 探针验证过"能画"与"吞输入"；**未接入** |
| 适配成本/风险 | 已完成 | 高：输入管线大改＋笔迹数据模型迁移＋湿/干墨同步（含 SwapChainPanel 的不同步已知问题） |
| 收益 | 最新一小段提前 ≤1 帧上屏（60Hz≈16ms、120Hz≈8ms） | 理论上"整条湿墨"都不受应用渲染延迟影响（比 A 大）；**但只在 Win10 上才有增量价值**——Win11 24H2+ 上 A 已能覆盖 |

## 三、第三方点评的逐条核实

| 原话 | 判断 | 补正/证据 |
|---|---|---|
| "DelegatedInkTrailVisual 可以实现低延迟湿墨迹" | **对** | 补：Win32 侧等价物是 `IDCompositionInkTrailDevice`；我们**已在产品里落地**（9.0.6，笔/鼠标/触摸实测都在画）。 |
| "ActivateCustomDrying() 可以接管干墨迹" | **基本正确，需限定** | 它是 `InkPresenter`（宿主/UWP 路线）的机制，且**要在控件加载前**调用；桌面自绘场景的对应件是 `InkSynchronizer`（BeginDry/EndDry）＋`IInkD2DRenderer`；SIS/VSIS 有同步保证、**SwapChainPanel 没有**。 |
| "支持 Windows 10 21H2 及以上" | **不准确** | Win10 没有这个 API：WinRT 侧要求 **10.0.20348.0＋contract v12**（那是 Win11 一代/Server 2022）；Chromium 门槛 **24H2**。我们有本机实测＋社区实测双重证据（详见《实测-委托墨迹轨迹-2026-10-11.md》§四）。 |
| "必须使用 WinUI 3 或 UWP" | **错** | Win32 桌面可直接用 Win32 侧接口——本项目就是 .NET/Win32＋D2D＋DComp 全自绘，未用 WinUI/UWP，已跑通。 |
| "调用 CreateForSwapChain 就能完成接入" | **不完整** | 还差**视觉树挂载**、**逐帧结账回收**、坐标空间与生命周期——这三处我们都有实测教训（旧的"系统不渲染"结论正是缺前两步）。 |
| "在 PointerMoved 中传入预测点即可" | **不完整** | 预测点的更新/回滚/与真实点的衔接要自己管；我们实测"用 predicted 顶采样间隙＝甩尾"（真机拍板撤除）。 |
| "需要支持触摸屏的硬件" | **不完全正确** | API 可用性与设备无关；设备决定"有没有笔/压感"，系统决定"给不给画"。我们实测：笔/鼠标/触摸**都会画**（逐帧采样各自量到尾巴）。 |
| "Win32 桌面能通过 InkDesktopHost 接入 Windows Ink" | **属实** | `IInkDesktopHost`/`IInkPresenterDesktop`（Win10 1511+；CoreInkPresenterHost 1709+）。但要强调：**它与委托轨迹不是同一个 API，不可互换**——一个是"借一段合成器湿墨"，一个是"把整套墨迹平台搬进来"。 |

## 五、遗留问题（需要拍板/继续）

1. **Win11 21H2~23H2 的版本门槛**：是否照 Chromium 加"低于 24H2 不开轨迹"的判断（现无门槛，
   接口在 21H2+ 就能 QI 到）——本机 25H2 不受影响，等拿到那类机器验证"闪烁"是否真的存在再定。
2. **Win10 教室机**：没有系统湿墨，现状（自绘＋合成边界配速 1.0 帧）即最终答案；
   若将来真要上 InkDesktopHost，第一步不是写代码，而是先做**"输入让渡"的产品评估**
   （哪些功能会被吞掉、能接受吗）。
3. **触摸快速书写**：面板 120Hz 采样上限；预测点方案已证甩尾；维持现状（记录在案）。
4. **荧光笔/激光笔的喂点状态**（2026-10-12 核）：这两者的线型都是"实线"，所以**一直在喂轨迹**
   （连旧的"只对真笔"条件也拦不住——它们本来就是笔设备画的）；`--syswet` 全交名单不含它们
   （观感对不上）。**待真机核对观感**：荧光笔颜色带 alpha 0.32，系统轨迹是否按半透明画未验证——
   若湿墨段比干墨"更实/更亮"，就把它们从喂点名单摘掉。**虚线/点线笔故意不喂**（系统只画实线，
   会发生"写时实线、收笔变虚线"的闪变），维持自绘＋预测。

## 六、复盘：为什么几轮调研都没接上，最后靠"别处文献"接上（2026-10-12 补记）

**结论：角度确实有偏差，能定位到三个具体偏差。**

1. **信源类型偏差：文档导向，而不是"生产实现导向"。**
   让它真正跑起来的三把钥匙——①轨迹视觉**挂进 DComp 视觉树**、②**每帧 `RemoveTrailPoints`
   结账**、③"只画还没上屏的一小段"——**没有一条写在官方文档里**（Win32 侧文档还是 prerelease
   空壳）。它们出自 **Chromium 的生产实现**（`dc_layer_tree.cc` /
   `delegated_ink_point_renderer_gpu.cc`）。旧模式＝官方文档＋自家探针；缺的是
   "**谁在生产环境里用它**"（Edge/Chromium 源码、GitHub 代码搜索 `AddTrailPoints`、
   绑定库的测试样例）。→ **以后凡"系统能力能不能用"：先找在用它的生产代码，再读文档。**
2. **现象误判：把"结构性表现"当成"不支持"。**
   轨迹的设计就是"只画还没上屏的一段"，肉眼看常是"闪一下"；旧探针把这个判成
   "系统不渲染"。→ **现象与预期不符时，先假设"是我误解了它的工作方式"，再下"不支持"的结论。**
3. **结论管理：探针结论被当终审，且没标"何时需复核"。**
   "系统不渲染"的错结论曾写进约 20 份文档。→ 探针结论必须带**验证条件与假设清单**
