## 〇、一句话

**Avalonia 做"壳和控件"，原生 D2D 做"墨迹和覆盖层"；同一个进程、同一个 UI 线程优先。**
这样能拿到 Avalonia 的窗口/表单/列表/文字/无障碍，又不把笔迹延迟押上去。
先用 2 周试点验证"单线程 + 原生画布"是否稳；不稳再退到双线程，不先上双线程。

## 〇.1 为什么主推荐 Avalonia（控件层对比）

> 不是"Avalonia 控件天下第一"，而是"在我们这个混合架构里，它的综合分最高"。
> 对比对象：WPF（.NET 10）、WinForms（.NET 10）、Win32 系统控件、WinUI 3。

| 维度 | **Avalonia 12** | WPF（.NET 10） | WinForms（.NET 10） | Win32 系统控件 | WinUI 3 |
|---|---|---|---|---|---|
| 渲染 | Skia + ANGLE/D3D11，GPU，可软件回退 | DirectX 9 时代 retained mode | GDI+ / 原生控件 | GDI / DWM | DirectX 合成 / Fluent |
| 控件 | 70+ 免费，现代 | **最成熟**；RichTextBox/DataGrid 免费；三方多 | 原生 common controls；成熟但旧 | 系统 common controls | Fluent 齐全；原生感最好 |
| 主题/自定义 | 强（selector/template/animation） | 强（XAML/style） | 弱（owner-draw） | 弱/手工 | 强（Fluent） |
| 高 DPI | Per-monitor，好 | 有支持，历史坑多 | .NET 8+ 改善，仍有限 | 手工 | 好 |
| 触摸/笔 | 指针/手势现代；画布仍原生 | 旧 stylus/RTS，触摸弱 | 弱 | 原生但无现代手势 | 好 |
| 中文 IME/文字 | TextBox 好；触屏键盘不自动弹（#10136） | 好；RichTextBox 免费 | **最好**（原生 EDIT/RichEdit） | **最好** | 好（原生集成） |
| 无障碍 | UIA 完整 | UIA 完整 | 原生完整 | 原生完整 | 完整 |
| 窗口/贴靠/多窗 | 多窗、DPI、客户区装饰；12 贴靠模拟 | 多窗；自定义 chrome 贴靠坑 | 原生窗口 | 原生 | **最好**（Mica/贴靠/标题栏） |
| 嵌原生 D2D 画布 | `NativeControlHost`（子窗，有空域） | `HwndHost`（空域/DPI 坑） | 容易（原生子窗） | 最容易 | `SwapChainPanel`（无空域，但绑 WinUI） |
| 内存/部署 | +100～200 MB；Skia 包 +20～40 MB | **我们实测 +148 MB**；Windows-only | +约 10～20 MB | +0 | +100～250 MB + WinAppSDK 运行时；self-contained 更大更慢 |
| 生态/工具 | 成长中；部分工具/组件付费 | **最大**；设计器成熟 | 大；设计器成熟 | 无设计器 | 成长中；Fluent |
| 许可 | MIT 核心；部分组件付费 | MIT | MIT | 系统 | MIT + 运行时 |
| 开发速度 | 快（XAML/绑定/预览器） | 快（XAML/设计器） | 最快（简单表单） | 最慢 | 中（部署/互操作） |
| 主要风险 | 触屏键盘、客户区装饰、组件缺口 | 内存/每点延迟、DPI、旧渲染 | 观感/触摸/主题 | 观感/手工/暗色 | 运行时/部署/互操作 |

### 逐家说为什么

**vs WPF（.NET 10）**

- WPF 的控件生态最成熟，RichTextBox/DataGrid 免费，设计器好用；
  但它是 **DirectX 9 时代的渲染管线**，我们实测同一个应用 WPF 版
  提交 **227 MB / 工作集 255 MB**（我们 79 / 96 MB），每个采样点贵 **1.4 ms**；
- WPF 的触摸/stylus 是旧栈（RTS/WISP），高 DPI 和自定义 chrome 的贴靠/动画历史坑多；
- WPF 仍会维护，但不是微软投入现代 UI 的方向；Avalonia 12 在性能/DPI/触摸上更现代。
- **WPF 唯一明显赢的地方**：免费 RichTextBox、三方控件多、设计器成熟。
  我们的富文本已经用原生 RichEdit，不需要它。

**vs WinForms（.NET 10）**

- WinForms 是 Win32 控件的薄包装：做简单表单最快、原生 IME/无障碍最好、内存最低；
- 但观感旧、暗色主题要 owner-draw、布局手工、触摸/动画/自定义视觉弱；
- 它适合"几个设置框"，不适合"一整套有品牌感的批注软件"。
- **我们只保留它的强项**：原生 EDIT/RichEdit + 系统文件/颜色对话框。

**vs Win32 系统控件**

- 原生 `BUTTON/EDIT/COMBOBOX/LISTVIEW`：IME、无障碍、系统行为最好，零运行时；
- 但暗色主题支持不完整、布局/命中/滚动全手工、没有现代控件（Toggle/Flyout/虚拟化）、
  观感和我们的自绘工具条割裂；
- 只适合文字输入和系统对话框，不适合做全部界面。

**vs WinUI 3（Windows App SDK）**

- WinUI 3 的"原生 Windows 11 感"最好：Mica、贴靠、标题栏、Fluent 控件、系统主题；
- 但需要 **Windows App SDK 运行时**；self-contained 官方明确"更大、启动更慢、内存更多"；
- 和我们的 Win32 覆盖层/原生 D2D 画布混用，要走 XAML Islands 或 `SwapChainPanel`，
  应用模型和互操作复杂度都上一个台阶；
- **如果这个产品是纯 Windows、没有原生覆盖层/画布，WinUI 3 会是第一选择**；
  我们不是这个形态。

**vs ".NET 10 的 WPF/WinForms"**

- .NET 10 是运行时版本，不是 UI 现代化；WPF/WinForms 还是那两套 2006/2002 年的设计；
- Avalonia 12 是这一代 actively developed 的 .NET UI 框架，目标就是 .NET 8/10。

### Avalonia 控件的具体优势

1. **样式/模板强**：selector、`ControlTheme`、伪类（`:pointerover/:pressed/:disabled`）、
   动画/过渡；可以把现有 Tokens 1:1 映射过去，不用 owner-draw；
2. **布局/虚拟化**：Grid/Stack/Dock/Wrap、`ItemsControl` 虚拟化、DataTemplate；
   100+ 收藏条目不用自己写滚动/回收；
3. **绑定/校验**：编译绑定、MVVM、`INotifyDataErrorInfo`；设置页加一项是改 ViewModel，不是改绘制；
4. **文字**：TextBox/ComboBox 的选区/剪贴板/撤销/IME/UIA 现成；TextBlock 用 HarfBuzz 排版；
5. **窗口**：多窗口、模态/非模态、Per-monitor DPI、客户区装饰、Popup、TrayIcon；
6. **渲染**：Skia GPU、分辨率无关；需要特殊绘制时还能用 `DrawingContext` 自绘；
7. **许可/部署**：MIT 核心，无运行时授权费；自包含 .NET 应用，不依赖系统 WebView/运行时；
8. **开发速度**：XAML + 绑定 + 预览器，少写大量手绘/命中代码；新窗口从几天降到几小时。

### Avalonia 的短板（不回避）

- **免费组件有缺口**：RichTextBox、PDF Viewer、TreeDataGrid、Virtual Keyboard、Media Player
  是付费 Pro 组件；我们用原生 RichEdit/PDFium/自绘列表/系统键盘替代；
- **触屏键盘**：Avalonia TextBox 在 Windows 上不会自动弹系统触摸键盘（#10136 open），
  要手动调 `TabTip`/`ITipInvocation`；
- **客户区装饰**：Avalonia 12 强制客户区装饰，贴靠/动画由框架模拟；要试点对比 11.3 原生标题栏；
- **生态**：三方控件/设计器不如 WPF/WinForms 多；DevTools/热重载等生产力工具在订阅里；
- **两套视觉语言**：Avalonia 控件和现有 D2D 工具条要统一 Tokens/模板，否则像两个软件。

### 结论

- **只做 Windows、没有原生画布/覆盖层、追求原生感** → WinUI 3；
- **团队 WPF 熟、内存不在乎、要最成熟控件/设计器** → WPF；
- **只做几个设置框、要最快最稳** → WinForms/原生控件；
- **我们的形态**（自定义视觉 + 触摸 + 多窗口 + 原生 D2D 画布 + 覆盖层 + .NET 10 + MIT）
  → **Avalonia 综合分最高**，但不是"每个控件都最强"。

## 〇.2 付费组件怎么付 & "只做白色界面"能不能用 WinForms/原生控件

### Avalonia 的付费结构（2026-11 官网）

| 档 | 价格（组织价，未含 VAT） | 包含什么 | 我们要不要 |
|---|---|---|---|
| **Free** | **€0** | MIT 框架、70+ 内置控件、VS Code 扩展、社区支持 | **够用**（框架 + 免费控件） |
| **Plus** | **€299 / 年 / 座位** | Free + Visual Studio 扩展、DevTools、Parcel、Hot Reload | 可选（想要调试/热重载再买） |
| **Pro** | **€899 / 年 / 座位** | Plus + Media Player、TreeDataGrid、Markdown、RichTextEditor、OnScreenKeyboard、PDF Viewer、Charts | **不需要**（我们用原生 RichEdit/PDFium/自绘列表/系统键盘） |
| **Enterprise** | **€21,000 / 年起，含 3 个座位** | Pro + 组件源码、SLA、LTS、IP 赔偿、离线激活 | 不需要（小团队） |

关键点：

- **按"开发者座位"收费，不是按终端用户/安装量收费**；座位是给做 UI 的开发者用的；
- 年付比月付便宜 30%+；价格未含 VAT；符合条件可反向征收；
- **框架本身 MIT，可商用**；"Community 免费档"是**非商业**工具档，商业产品不要用它；
- Pro 组件是"开发授权"，不是运行时版税；但我们要避免这些组件，成本就是 **€0（Free）**
  或 **€299/座位/年（Plus 工具）**；
- VS Code 扩展免费；Visual Studio 扩展/DevTools/Hot Reload 在 Plus；
- 个人授权有折扣（官网 Individual 页），以官网为准。

**结论：我们只用 Free 档 + 免费控件，付费组件一个都不需要。**
如果开发时想要 DevTools/Hot Reload，买 Plus（€299/座位/年）即可；
Pro 的 RichTextEditor/PDF/VirtualKeyboard 用原生替代，不花这笔钱。

### 如果界面只做"Windows 那种白色"，WinForms/原生控件够不够？

**够，而且可能是更划算的选择。** 关键看"白色"是哪一种：

| 你想要的 | WinForms + 原生控件 | Avalonia | WinUI 3 |
|---|---|---|---|
| 纯白底 + 标准按钮/输入框/列表 | **够，最快、最省内存、原生 IME/无障碍** | 够，但要多带一套 Skia/主题 | 够，但要 Windows App SDK 运行时 |
| Windows 11 设置那种"白卡片 + 圆角 + 强调色" | 要 owner-draw/第三方控件，费劲 | 可以，用 ControlTheme 做 | **最原生**（Fluent 自带） |
| 触摸优先、大按钮、动画/过渡 | 弱（要自己补） | **好** | 好 |
| 自定义品牌视觉（颜色/圆角/图标/间距） | 弱（owner-draw） | **强** | 中（Fluent 限制多） |
| 多窗口/最小化/最大化/贴靠/任务栏 | **原生窗口全给** | 可以（12 客户区装饰） | 最好（Mica/贴靠） |
| 中文 IME/触屏键盘 | **最好**（原生 EDIT/RichEdit） | 好，但触屏键盘要手动调 | 好（原生集成） |
| 内存 | **最低**（+10～20MB） | +100～200MB | +100～250MB + 运行时 |
| 开发速度（简单表单） | **最快**（设计器/拖控件） | 快（XAML） | 中（部署/互操作） |
| 开发速度（自定义列表/复杂面板） | 慢（手绘/owner-draw） | **快** | 中 |
| 长期维护 | 维护模式 | **活跃** | 活跃 |

**判断规则：**

- 如果最终界面就是**标准白底、标准控件、少量设置/对话框**，而且你能接受
  "Windows 原生观感"（不是 Win11 设置那种精致卡片）：
  **WinForms + 原生控件足够，风险最低、内存最低、IME/触屏键盘最好。**
  画布/覆盖层继续原生 D2D，不需要 Avalonia。
- 如果你要的是**"白色但现代"**（圆角卡片、统一间距、触摸大按钮、动画、品牌色）：
  WinForms 要大量 owner-draw，反而慢；这时 Avalonia（或 WinUI 3，如果纯 Windows）
  更合适。
- 如果你要的是**Windows 11 原生 Fluent 白**（Mica/卡片/贴靠/系统主题）：
  **WinUI 3 最像**；Avalonia 可以仿，但不是原生；WinForms 做不到。
- 如果界面数量多、表单多、列表多、还要跨窗口统一：
  Avalonia 的开发速度优势才会真正体现。

**建议：做 1 天 A/B 原型再定。**
同一个"设置 → 通用"页，分别用 WinForms 和 Avalonia 各做一遍，放同一台触摸屏上比：
观感、触摸、DPI、中文 IME、开发耗时。眼睛和手会告诉你答案，不用争理论。

> 我前面的推荐是"如果要做现代/自定义/多窗口 UI，Avalonia 综合分最高"；
> **如果只是标准白色 Windows 界面，WinForms/原生控件完全够，而且更省。**
> 这两句话不矛盾——取决于你要的是"标准白"还是"现代白"。

## 〇.3 能不能"简单界面 WinForms + 复杂窗口 Avalonia"？

**技术上可以，但不建议。** 这不是"两个框架各干各的"，而是同一个进程里
同时维护 **WinForms + Avalonia + 原生 D2D** 三套 UI 栈。

### 为什么不适合

| 问题 | 具体表现 |
|---|---|
| **消息循环** | WinForms 要 `Application.Run`；Avalonia 要自己的 lifetime。两者互相嵌入要走 `SetupWithoutStarting` + `WinFormsAvaloniaMessageFilter`；Avalonia 12.1.2 在"外部消息泵"场景还有 open bug（#22234） |
| **两套焦点/输入** | WinForms 控件焦点、Avalonia 焦点、原生画布焦点三套；Tab/Esc/快捷键/IME 要各写一遍 |
| **两套 DPI/主题** | WinForms 的高 DPI 缩放 + Avalonia 的 Per-monitor + 原生画布 DPI，三种缩放规则 |
| **两套视觉语言** | WinForms 标准灰白 vs Avalonia Fluent 主题 vs 自绘工具条；字体/圆角/间距/悬停态不一致，像三个软件 |
| **两套窗口管理** | WinForms 窗体、Avalonia Window、原生覆盖层，三种 owner/置顶/任务栏规则 |
| **两套依赖** | WinForms（System.Windows.Forms）+ Avalonia（Skia/ANGLE）+ 原生 D2D；安装包/内存都涨 |
| **维护** | 每加一个窗口要决定"放哪边"；改主题/改交互要改两处；新人要学两套 |

### 两个干净选项

| 选项 | 适合 | 代价 |
|---|---|---|
| **A. 全部非画布界面用 WinForms** | 最终就是标准白底/标准控件；团队熟 WinForms；想最低风险/最低内存 | 复杂窗口（PDF 缩略图/白板工具栏/展台）观感旧、触摸/动画弱；自定义要 owner-draw |
| **B. 全部非画布界面用 Avalonia** | 想要现代白/触摸/自定义/多窗口；后期白板/PDF/展台界面多 | +100～200MB；触屏键盘要手动调；客户区装饰要试点 |

**推荐：二选一，不要混。**
- 如果最终是"标准 Windows 白 + 少量设置/对话框" → **A（WinForms 全家桶）**；
- 如果后期白板/PDF/展台要现代、触摸、统一视觉 → **B（Avalonia 全家桶）**，
  设置/收藏也用 Avalonia——多出来的工作量远小于维护两套框架。

### 如果一定要混

只接受两种"干净混法"，不接受"按窗口类型混"：

1. **按进程分**：WinForms 设置器一个独立 exe，Avalonia 主程序一个 exe，文件/IPC 同步；
   代价是双进程、双任务栏、状态同步、拖放复杂；
2. **按线程分**：一个 UI 线程跑 WinForms，一个 UI 线程跑 Avalonia；
   代价是跨线程焦点/拖放/状态，Avalonia 多 UI 线程目前不支持，风险高。

> 所以"简单设置用 WinForms、复杂窗口用 Avalonia"听起来省事，实际是把
> 消息循环、焦点、DPI、主题、窗口管理五件事都变成两份。**不建议。**

## 〇.4 4 GB 老机器上，打开收藏会不会"突然卡一下"？

**有可能，第一次最明显；但不是必然，也不是"内存数字"本身造成的。**
卡顿来自这几件事叠加：

| 来源 | 第一次打开时发生什么 | 老机器上的代价 |
|---|---|---|
| Avalonia 运行时初始化 | 加载程序集、建 Dispatcher、主题资源、字体缓存 | 冷启动 + 机械硬盘/杀软扫描 → 几百 ms 到 1～2 s |
| JIT | 第一次走 XAML/控件/绑定代码，编译成机器码 | 几十～几百 ms |
| Skia / ANGLE / D3D11 | 建 GPU 设备、编译着色器、建交换链 | 老核显/驱动 → 100～500 ms，甚至回退软件渲染 |
| 视觉树 + 布局 | 创建收藏列表、分类、缩略图容器 | 100+ 条目若不做虚拟化 → 明显卡 |
| GC / 换页 | 一次性分配较多对象；4 GB 剩余内存少时触发换页 | 机械硬盘页面文件 → 几百 ms～数秒 |
| 首帧动画 | 展开/淡入和初始化抢 UI 线程 | 看起来"卡住不动" |

### 关键澄清

- **100～200 MB 是"进程级一次性"开销，不是每个窗口都加 100～200 MB。**
  第一个 Avalonia 窗口付运行时/GPU/主题的成本；之后打开收藏/设置/展台，
  通常只增加视觉树/图片/缓存的十几～几十 MB。
- 如果启动时已经初始化过 Avalonia（比如先开过设置），再开收藏通常不会"突然卡一下"；
  真正贵的是**第一个** Avalonia 窗口。
- 4 GB 机器上，问题往往不是"多 100 MB"本身，而是**当时还剩多少空闲内存**：
  如果 PPT + 浏览器 + 杀软已经吃掉 3.5 GB，再多 100 MB 就可能触发换页；
  如果还剩 800 MB，100 MB 通常只是短暂的工作集增长。
- 卡不卡还取决于**硬盘**：机械盘 + 页面文件 → 第一次加载/换页会非常明显；
  SSD 上好很多。

### 怎么避免"点收藏卡一下"

1. **预热（最有效）**：覆盖层上屏后、老师还没点收藏时，在空闲时初始化 Avalonia，
   建一个 1×1 隐藏窗口，强制加载主题/字体/控件模板；之后点收藏只建列表，不再付运行时成本。
   - 代价：内存提前占用；4 GB 机器要观察是否影响 PPT。
   - 可以做成"检测到空闲 2～3 秒再预热"，避免和启动抢资源。
2. **运行时只初始化一次**：不要每次开窗口都 `AppBuilder`/建新 Dispatcher；
   Avalonia 的 `Application`/`Dispatcher` 进程内只建一次，窗口复用。
3. **列表虚拟化**：收藏 100+ 条目只创建可见项；缩略图懒加载/分批解码；
   不要一次 `Bitmap` 全读。
4. **首开不做动画**：先出窗口骨架/列表，内容就绪后再淡入；不要在初始化时跑 200ms 展开动画。
5. **降低 GPU 开销**：`MaxGpuResourceSizeBytes` 先给 64～128 MB；
   老核显可回退 `Software` 渲染；不要在首开时建大阴影/毛玻璃。
6. **减少 GC/LOH**：预分配集合、复用缓冲、避免大字符串/大数组；
   缩略图用流式解码，不要一次性 LOH 分配。
7. **测量再决定**：4 GB 真机 + PPT + 浏览器同时开，量：
   - 点击→窗口出现的时间；
   - 点击→列表可交互的时间；
   - 最大单帧间隔；
   - 打开前后私有工作集/可用内存/页面文件；
   - GC 次数/暂停。
   目标：首开 ≤300 ms、无单帧 >50 ms、工作集 +≤150 MB；达不到就预热或改用 WinForms。

### 如果 4 GB 是硬指标

- 收藏/设置这种**简单白界面**，WinForms 的首开成本远低于 Avalonia：
  没有 Skia/ANGLE/主题运行时，原生控件直接建，通常几十 ms；
- 如果最终选择 **WinForms 全家桶**，这个问题基本不存在；
- 如果选择 **Avalonia 全家桶**，就把"预热 + 虚拟化 + 首开无动画"作为硬要求，
  并在 4 GB 真机上过一遍，不靠猜。

> 一句话：**第一次打开可能卡一下，但可以通过预热把"卡一下"移到用户不注意的时候；
> 100～200 MB 是一次性的，不是每个窗口都涨。**

## 〇.5 开发速度：WinForms vs Avalonia（按我们的窗口拆）

> 粗估，1 个开发，含基本自检，不含全量回归；实际取决于熟练度。
> 最大的工期风险不是 UI 框架，而是**原生画布/窗口集成 + 多文档模型**，这两项两边都要做。

| 任务 | WinForms | Avalonia | 说明 |
|---|---|---|---|
| 框架/主题/窗口壳 bootstrap | **0.5～1 天** | **1～2 周** | Avalonia 要建 App/主题/ControlTheme/窗口壳/预热；WinForms 拖个窗体就能开工 |
| 设置（全部分类） | **1～2 周** | 1～2 周 | 标准白：WinForms 略快；现代卡片/搜索/校验：Avalonia 更顺 |
| 收藏/图形（100+、拖放） | 1～2 周 | **1～1.5 周** | WinForms 虚拟列表 + 拖放能做；卡片/圆角/悬停要 owner-draw |
| 视频展台 | 1 周 | 1 周 | 摄像头/视频表面两边都要原生；UI 控件量不大 |
| 白板/PDF 窗口壳 | **1～2 周** | 2～3 周 | WinForms 原生窗口 + 原生画布子窗更直接；Avalonia 要 NativeControlHost/DPI/输入 |
| 触摸/现代观感打磨 | 1～3 周（owner-draw） | **3～5 天** | 这是 Avalonia 真正省时间的地方 |
| 首开/内存/预热 | 1～2 天 | 3～5 天 | Avalonia 要预热、GPU 缓存、首开无动画 |
| **合计（5 类窗口，标准白）** | **约 4～7 周** | 约 6～9 周 | 标准白 + 简单控件，WinForms 更快 |
| **合计（5 类窗口，现代/触摸）** | 约 8～12 周（大量 owner-draw） | **约 6～9 周** | 现代/触摸，Avalonia 反超 |

### 结论

- **标准 Windows 白 + 简单控件 + 少量窗口** → **WinForms 开发更快**；
  没有主题/预热/空域/触屏键盘这些额外工作，原生 IME/触屏键盘也最好。
- **现代白 + 触摸 + 自定义卡片/圆角/动画 + 多窗口** → **Avalonia 开发更快**；
  前 1～2 周的 bootstrap 会在后面每个窗口赚回来，WinForms 的 owner-draw 会越写越慢。
- **两边都要做的**：原生画布子窗、引擎命令/状态、窗口位置记忆、自检；
  这部分不要算进"框架开发速度"的对比里。
- **不要混**：WinForms + Avalonia + 原生 D2D 三套栈，开发速度会被集成/焦点/DPI/主题吃掉。

> 想用数据而不是感觉：做 1 天 A/B——同一个"设置 → 通用"页 + 一个 PDF 窗口壳，
> 两边各做一遍，记录实际耗时、观感、触摸、DPI、IME。结论会很清楚。

## 〇.6 如果坚持自绘（D2D）呢？

**自绘不是"更快"或"更慢"的单一答案：它快在"已有的、独特的、画布周边的"，慢在"通用表单/列表/窗口/文字/无障碍"。**

| 任务 | 自绘 D2D | WinForms | Avalonia | 说明 |
|---|---|---|---|---|
| 工具条/色带/呼出盘/画布预览 | **最快**（已有代码/肌肉记忆） | 慢（owner-draw） | 中（要主题/模板） | 自绘的主场 |
| 窗口壳（最小化/最大化/贴靠/DPI/位置记忆） | **1～2 周**（要自己写 WindowHost） | **0～3 天**（原生） | 0～3 天（框架给） | 自绘并不省窗口层 |
| 设置（全部分类） | 2～4 周 | **1～2 周** | 1～2 周 | 行表已有，但控件/校验/搜索/滚动要补 |
| 收藏/图形（100+、拖放、四态） | 2～3 周 | 1～2 周 | **1～1.5 周** | 虚拟列表/拖放/多选最费工 |
| 视频展台 | 1～2 周 | 1 周 | 1 周 | 摄像头/视频表面两边都原生 |
| 白板/PDF 窗口 | 2～4 周 | **1～2 周** | 2～3 周 | 自绘要 WindowHost + 画布 + 页条 |
| 文字输入/IME | 3～5 天（统一 TextEditHost） | 原生免费 | 原生 TextBox（触屏键盘要调） | 9 套宿主必须合并，跑不掉 |
| 无障碍/键盘 | 1～2 周（UIA 手工） | 原生免费 | 内置 | 表单多时差距明显 |
| **合计（5 类窗口，标准白）** | **约 8～14 周** | **约 4～7 周** | 约 6～9 周 | 自绘在表单/列表上最吃亏 |
| **合计（现代/触摸）** | 约 8～14 周 | 8～12 周 | **6～9 周** | 自绘可控但工时长 |

### 结论

- **自绘适合**：工具条、色带、呼出盘、画布预览、选区框、笔尖/墨迹这些"独特且已有"的部分；
- **自绘不适合**：设置表单、收藏列表、通用对话框、文字输入、无障碍；
  这些是框架的主场，自绘会把"画 + 命中 + 状态 + 键盘 + 滚动 + UIA"全部自己写一遍；
- **自绘不会省掉窗口层**：最小化/最大化/贴靠/DPI/任务栏/位置记忆仍要写 `WindowHost`；
- **自绘不会省掉文字层**：9 套原生输入宿主仍要合并成 `TextEditHost`；
- **最现实的分工**：**覆盖层/工具条/画布继续自绘；窗口/表单/列表用 WinForms 或 Avalonia。**
  这不是"混三套"——覆盖层是特殊形态，必须自绘；窗口层只选一个框架。

> 如果你只想做"现有工具条 + 几个设置行 + 一个收藏面板"，自绘短期最快；
> 一旦窗口/表单/列表多起来，自绘的边际成本会超过框架。

## 〇.7 自己写一个"可复用框架"，是不是最匹配？

**是的，理论上最匹配；但"最匹配"不等于"最划算"。**
自己写框架 = 把框架当一个小产品做，先付 6～10 周，再在每个界面上赚回来。

### 先分清三个东西

| 做法 | 是什么 | 复用性 | 成本 |
|---|---|---|---|
| **自绘（现状）** | 每个面板手写画/命中/状态 | 低（复制粘贴） | 单面板快，越多越慢 |
| **自写薄框架** | 抽窗口壳/布局/控件/输入/主题/列表/文字 | **高** | 先 6～10 周，之后每个界面快 |
| **通用 UI 框架（Avalonia）** | 别人写好的完整框架 | 最高 | 1～2 周接入，之后快；+100～200MB |

### 自写薄框架：该写什么、不该写什么

**该写（6～10 周，1 人）**

| 模块 | 内容 | 工期 |
|---|---|---|
| WindowHost / WindowManager | 原生窗口、系统 chrome、最小化/最大化/贴靠/DPI/位置记忆 | 1～2 周 |
| UiElement / 布局 | Stack / Dock / Grid / Scroll；Measure/Arrange；只失效重算 | 1～2 周 |
| 控件 | Button / IconButton / Toggle / Slider / Dropdown / TextBox 外观 / List / Tab / Dialog / Tooltip | 2～3 周 |
| 输入/焦点 | 指针/键盘/捕获/悬停/Tab/Esc/Enter/Popup | 1 周 |
| 列表 | 虚拟化、滚动、多选、拖放、0/1/多/溢出 | 1～2 周 |
| TextEditHost | 原生 EDIT/RichEdit 统一 9 套宿主 | 3～5 天 |
| 主题/模板/自检 | Tokens、组件画廊、截图自检 | 1 周 |

**该复用（不要自己写）**

- 文字编辑/IME/候选窗 → 原生 `EDIT` / `RichEdit`；
- 文件/颜色选择 → 系统对话框；
- 墨迹/湿墨/画布 → 现有 D2D 引擎；
- 图标 → 现有 Fluent SVG / IconAtlas；
- 设置存储 → 现有 `settings.json`；
- 无障碍 → 原生文字控件 + 最小 UIA，不做全量 UIA 引擎。

**不要写（写了就是无底洞）**

- 自研文本编辑器/TSF/输入法；
- 数据绑定/INotifyPropertyChanged 克隆；
- XAML/标记语言/可视化设计器；
- 全量无障碍引擎；
- 跨平台；
- 通用表格/富文本/PDF 查看器（用原生替代）。

### 开发速度与回本点

| 阶段 | 自写薄框架 | Avalonia | WinForms |
|---|---|---|---|
| 框架/接入 | 6～10 周 | 1～2 周 | 0.5～1 天 |
| 设置 | 1～2 周 | 1～2 周 | 1～2 周 |
| 收藏/图形 | 1～2 周 | 1～1.5 周 | 1～2 周 |
| 展台 | 1 周 | 1 周 | 1 周 |
| 白板/PDF 窗口 | 2～3 周 | 2～3 周 | 1～2 周 |
| 触摸/现代打磨 | 1～2 周（自己做） | 3～5 天 | 1～3 周 |
| **第一版合计** | **约 12～20 周** | **约 6～9 周** | **约 4～7 周** |
| 第 10 个界面之后的边际成本 | **最低**（完全贴合） | 低 | 高（owner-draw） |
| 内存 | **最低** | +100～200MB | +10～20MB |
| 与墨迹/覆盖层的贴合 | **最高** | 中（NativeControlHost 空域） | 中（原生子窗） |
| 风险 | 框架自身 bug 影响所有界面 | 框架升级/触屏键盘/装饰 | 观感/触摸/维护模式 |

**回本点**：如果你确定后面有 **10+ 个界面/窗口**、且触摸/DPI/4GB/墨迹贴合是硬指标，
自写薄框架的总成本可能低于长期和框架打架；如果只有 5～6 个界面、要尽快出第一版，
Avalonia/WinForms 更快。

### 自写框架的硬前提（缺一个就会变成第二个 FullUi）

1. **范围封死**：3 类窗口、4 种布局、12 个控件；不做通用控件库；
2. **组件画廊**：每个控件/状态在同一页可见，改主题/DPI 一眼看出问题；
3. **截图自检**：每个界面一条截图 + 一条脚本输入；
4. **单一 Tokens 来源**：颜色/圆角/字号/间距只改一处；
5. **输入路由唯一**：指针/键盘/焦点/IME 只有一套，不允许面板自己处理；
6. **API 稳定**：新界面照模板建，不复制粘贴旧代码；
7. **文档**：窗口模板、面板模板、设置页模板、文字输入模板。

> 一句话：**自己写"薄框架"是最匹配，但先把范围封死、把自检/画廊/模板做出来；
> 否则 6～10 周会变成 6～10 个月，最后还不如 Avalonia。**

## 〇.8 最终建议（综合"现有功能 + 你提到的后续"）

把现有功能（批注覆盖层、工具条、色带、PPT/文档模式、设置、收藏、图形、文字框、AI 菜单……）
和后续（真窗口白板、PDF、视频展台、更多面板、触摸/鼠标、4GB Win10）放在一起看：

| 路线 | 匹配度 | 第一版工期 | 长期 | 风险 | 结论 |
|---|---|---|---|---|---|
| 继续自绘（每个面板手写） | 画布周边高；表单/窗口低 | 中 | 越写越慢 | 焦点/IME/滚动/DPI bug 反复 | **只保留给覆盖层/工具条/画布** |
| 自写薄框架 | **最高**（完全贴合） | **12～20 周** | 边际成本最低 | 框架自身 bug 影响所有界面；小团队维护吃力 | **现在不做**；等 10+ 界面且 Avalonia 撞墙再考虑 |
| **Avalonia** | 高（现代/触摸/多窗口/表单） | **6～9 周** | 低（社区维护） | 触屏键盘、客户区装饰、画布空域、+100～200MB | **推荐（如果 UI 要现代/触摸/统一）** |
| WinForms | 高（标准白/简单表单） | **4～7 周** | 中（维护模式） | 观感旧、触摸/自定义弱 | **备选（如果 UI 就是标准 Windows 白）** |
| 混用 | 低 | 最慢 | 最差 | 三套栈/消息循环/焦点/DPI | **不做** |

### 最终拍板建议

1. **覆盖层、工具条、色带、画布、湿墨：继续原生 D2D 自绘。**
   这是产品最值钱、最独特、框架最难替的部分。
2. **非画布 UI（设置、收藏、图形、展台、白板/PDF 窗口壳）：不要自绘，也不要自写通用框架。**
   二选一：
   - **Avalonia（推荐）**：如果 UI 要现代白/触摸/圆角/动画/多窗口统一，且能接受 +100～200MB；
   - **WinForms（备选）**：如果最终就是标准 Windows 白、简单控件、窗口不多，想最低风险/最低内存。
3. **不要自己写通用 UI 框架。**
   你要写的部分（窗口壳、布局、控件、焦点、IME、滚动、虚拟化、无障碍）
   正是所有成熟框架已经解决、且最容易出 bug 的部分；自写等于把它们重做一遍。
   自写只在"10+ 个界面 + 强定制 + Avalonia 撞墙 + 有 2～3 个月维护预算"时才考虑。
4. **不要混 WinForms + Avalonia + 原生 D2D。**
   覆盖层是特殊形态，必须原生；窗口层只选一个框架。
5. **先做 2 周 Avalonia 试点**（P0）：
   设置页 + 200 条收藏 + 白板窗口嵌原生画布 + 拖放 + 中文 IME/触屏键盘。
   Go 的条件：笔迹延迟不退化、画布无空域、IME/触屏键盘可用、4GB 不换页。
   不达标再退回 WinForms（标准白）或自写薄框架（强定制）。

> **一句话总结：**
> **墨迹继续自绘；窗口/表单/列表用 Avalonia（或标准白用 WinForms）；
> 现在不要自己写通用框架。**

## 〇.9 Avalonia 一定会涨 100～200 MB 吗？有没有轻量用法？

**不是"只要用了就固定涨 100～200 MB"。** 这个数字是社区对"一个完整 Avalonia 应用"
的粗略观感，实际取决于：你是不是第一个窗口、用了多少控件/主题/图片、GPU 缓存多大、
有没有做懒初始化。**没有官方"Avalonia Lite"版本**，但可以把它用得很轻。

### 先拆清楚"涨的是哪部分"

| 部分 | 是否一次性 | 说明 |
|---|---|---|
| .NET 运行时 | 已经在用 | InkTeach 本来就是 .NET 10；这部分不算 Avalonia 的增量 |
| Avalonia 程序集/JIT | 进程级一次 | 第一次初始化时加载；之后复用 |
| Skia / ANGLE / D3D11 | 进程级一次 | 建 GPU 设备/着色器；老核显可能回退软件渲染 |
| 主题/字体/控件模板 | 进程级一次 | FluentTheme + 中文字体回退会占一部分；最小主题更轻 |
| 窗口/视觉树 | 每个窗口 | 一个设置窗通常十几～几十 MB；大列表/图片更多 |
| 图片/缩略图/GPU 纹理 | 按内容 | 收藏缩略图、PDF 页图是大头；懒加载/限制缓存可压 |
| GC 预留/碎片 | 波动 | 大分配/LOH 会推高；池化/流式解码可压 |

### 轻量用法（按性价比）

1. **懒初始化**：覆盖层先跑；第一次打开设置/收藏才初始化 Avalonia。
   不打开就不占这份内存；代价是首开慢（可用预热把成本前移）。
2. **最小主题**：不要整套 FluentTheme；只给用到的 10～12 个控件做 `ControlTheme`，
   去掉大阴影/模糊/多余动画；能省不少资源和首开时间。
3. **少用控件/窗口**：设置/收藏/展台够用即可；不要一上来做通用控件库。
4. **图片/列表**：虚拟化、缩略图懒加载、分批解码、关闭窗口释放位图；
   `MaxGpuResourceSizeBytes` 先给 64～128 MB。
5. **字体**：用系统字体，别塞多套大字体；现有手写字体按需加载。
6. **AOT/裁剪**：Avalonia 12 支持 NativeAOT；能减 JIT/启动，但 XAML/反射要处理，
   不是第一步，等稳定后再评估。
7. **独立进程**：设置/展台这种"用完就关"的窗口可以放独立进程，关掉就还内存；
   代价是 IPC、双进程、拖放/状态同步——收藏（要拖到画布）不适合。
8. **标准白就用 WinForms**：如果 UI 就是标准 Windows 白，WinForms 的增量约 10～20 MB，
   没有 Skia/主题这一套，是最轻的"真窗口"方案。

### 现实预期

- **最小 Avalonia 窗口**（少量控件、系统字体、无大图）：增量常见在 **50～100 MB** 量级；
- **完整主题 + 大列表/图片 + 多个窗口**：到 **100～200 MB** 是可能的；
- **已经在用 Avalonia 后再开一个窗口**：通常只加 **十几～几十 MB**，不是每次 +200；
- **任务管理器里的"内存"是私有工作集**；GPU 纹理/共享内存不一定算在里面，
  但 4 GB 机器上显存和内存是互相挤的，还是要看总压力。

### 结论

- **没有"轻量版 Avalonia"**；但"懒初始化 + 最小主题 + 虚拟化 + 图片懒加载 + 少窗口"
  可以把增量压到可接受；
- 如果 4 GB 是硬指标、UI 又是标准白，**WinForms/原生控件确实更轻**；
- 如果要 Avalonia 的现代/触摸体验，就接受 50～150 MB 的增量，并在 4 GB 真机上量：
  - 不打开任何 Avalonia 窗口时的内存；
  - 打开设置后的增量；
  - 打开收藏（200 条）后的增量；
  - 关闭后的回收情况。
  用数字决定是否值得，而不是用"100～200 MB"这个笼统数字。

## 〇.10 那 WebView 呢？有"轻量模式"是不是更省、更方便？

**没有官方"WebView 轻量模式"。** WebView2 的 Evergreen / Fixed Version 区别是
"用系统 Edge 还是自带运行时"——**省的是磁盘和更新，不是每个实例的内存**。
`--single-process` 之类的参数不受支持、也不安全，不能当产品方案。

### 内存对比（量级，按目标机实测为准）

| 方案 | 增量内存（相对现在的原生应用） | 说明 |
|---|---|---|
| **原生 / WinForms** | **+10～20 MB** | 原生控件，无额外渲染器 |
| **Avalonia（最小主题 + 懒初始化）** | **+50～150 MB** | Skia/ANGLE + 主题/字体 + 视觉树 |
| **WebView2（空白页）** | **+100～200 MB** | 浏览器进程 + GPU/Utility + 渲染器 |
| **WebView2（简单设置页）** | **+150～300 MB** | HTML/CSS/JS + 渲染器 + 缓存 |
| **WebView2（复杂页面/多实例）** | **+300～500 MB+** | 多渲染进程、图片、缓存 |

> 数字是量级，不是承诺；但结论明确：**WebView 不会比 Avalonia 轻，通常更重。**
> 如果 Edge 已经开着，部分二进制/页面缓存是共享的，但每个 WebView2 仍有自己的
> 渲染器/Utility 进程和 JS 堆，不能按"共享"来省。

### 开发速度：HTML/CSS 很方便，但"接进来"不方便

**方便的地方：**

- HTML/CSS 做布局、卡片、表单、动画确实快；生态大、热重载成熟；
- 复杂设置页、帮助页、图表、Markdown 渲染很顺手；
- 前端开发者/资源多。

**不方便的地方（对我们这种原生墨迹应用是硬伤）：**

| 问题 | 表现 |
|---|---|
| **空域** | WebView2 是独立 HWND/视觉层，永远盖在 D2D 内容上；和原生画布/覆盖层叠放会露馅 |
| **焦点/输入** | 浏览器焦点、原生画布焦点、覆盖层不激活，三套焦点/快捷键要桥接 |
| **桥接** | 每个命令/状态都要 `WebMessage`/host object 异步桥接；拖放、选中、撤销要自己同步 |
| **拖放** | 收藏（WebView）拖到原生画布跨两个渲染栈，比 Avalonia 更麻烦 |
| **启动/首开** | WebView2 初始化 + 首帧通常比 Avalonia 更慢；冷启动更明显 |
| **运行时依赖** | Windows 10 老机器可能没装 WebView2 Runtime；安装包要带 Evergreen Bootstrapper 或 Fixed Version |
| **离线/安全** | 本地 HTML 也要处理 CSP、导航拦截、资源路径；不要加载远程内容 |
| **内存** | 如上，比 Avalonia 更重；4 GB 机器更紧张 |

### 什么时候 WebView 才值得

- 你要展示**真正的 Web 内容**（在线帮助、Markdown、图表、地图、第三方网页）；
- 或者团队前端很强、且这个窗口**不需要和原生画布叠放/拖放**；
- 这时可以用 **独立进程/独立窗口** 的 WebView，关掉就还内存；
- 但不要拿它做整个应用的 UI 层。

### 结论

- **想更轻** → **WinForms / 原生控件**（标准白），不是 WebView；
- **想现代/触摸/开发快** → **Avalonia**；
- **WebView** → 只在"确实要 Web 内容"时用，且尽量独立窗口/进程；
- **"WebView 轻量模式更省内存"是个误解**：它省不了每个实例的 Chromium 进程开销，
  还会把空域/焦点/桥接问题带进来。

## 一、边界（先钉死，后面所有设计都按它）

| 层 | 归谁 | 理由 |
|---|---|---|
| 批注覆盖层（透明/置顶/不激活/穿透/湿墨） | **原生 Win32 + D2D** | Avalonia 的 Skia/窗口模型做不了这个形态；这是最值钱的体验 |
| 墨迹画布（WM_POINTER / ID2D1Ink / 分块 / 湿墨） | **原生 D2D** | 延迟、压感、触摸手势、Raw Input 补点都在这条线上 |
| 真窗口外壳（标题栏/最小化/最大化/贴靠/任务栏/DPI） | **Avalonia** | 现成、跨窗口统一、少写 OS 边缘代码 |
| 设置 / 收藏 / 图形 / 展台控件 | **Avalonia** | 控件、布局、键盘、IME、UIA、校验、虚拟化都现成 |
| 画布外的工具条/面板 | **Avalonia**（逐步迁移） | 现有 D2D 工具条先保留，按面板迁移 |
| 画布内的富文本输入 | **原生 RichEdit** | Avalonia 没有免费 RichTextBox；现有实现已稳定 |
| PDF 渲染 | **PDFium**（现有） | Avalonia 的 PDF Viewer 是付费组件 |
| 文本/设置存储 | **现有 settings.json / InkEngine 命令** | 不另起一套状态 |

**一句话：Avalonia 不碰墨迹，引擎不碰窗口。**

## 二、总体架构（推荐：单进程、单 UI 线程）

```
InkTeach.exe（一个进程）
├─ Avalonia 主线程（唯一 UI 线程）
│   ├─ Application / Dispatcher / 主循环（ClassicDesktopStyleApplicationLifetime）
│   ├─ 真窗口：设置 / 收藏 / 图形 / 展台 / 白板 / PDF
│   ├─ 原生画布子窗：NativeControlHost → 现有 D2D 画布
│   └─ 原生覆盖层窗口：同一个线程创建，WndProc 由 Avalonia 消息循环派发
├─ InkEngine（文档 / 输入 / 渲染 / 工具状态）
│   ├─ Doc / 撤销 / 空间索引 / 分块
│   ├─ OverlayWindow（原生、每屏一个）
│   └─ CanvasView（文档窗口里的原生画布）
└─ 自检宿主（InkTeach）：仍走原来的原生 Loop()，不初始化 Avalonia
```

### 2.1 为什么单线程优先

- `NativeControlHost` 创建的是**子 HWND**，子窗必须在父窗线程；父窗是 Avalonia 窗口 → 画布必须在 Avalonia UI 线程；
- 单线程下 `Doc`、撤销、工具状态、输入焦点只有一份，不需要跨线程锁/快照；
- Avalonia 的 `ClassicDesktopStyleApplicationLifetime` 是官方支持的循环；
- 覆盖层窗口在同一个线程创建，消息由 Avalonia 的 `GetMessage/DispatchMessage` 派发，不需要第二个消息泵。

### 2.2 单线程的代价与退路

- **风险**：引擎的 `DwmFlush`/`RenderAll` 会占 UI 线程；Avalonia 动画/输入可能被顶住；
- **试点先量**：湿墨帧耗时、输入→上屏、Avalonia 动画是否掉帧；
- **退路**：把覆盖层移到独立线程（`InkEngine` 渲染线程 + Avalonia UI 线程），
  文档窗口的画布仍留在 UI 线程；两条线程只通过命令队列/状态快照通信。
  这是第二阶段才考虑的，不先上。

### 2.3 不要走的路

- **`SetupWithoutStarting` + 自己的 `PeekMessage` 循环**：Avalonia 12.1.2 在"外部消息泵"
  场景有 open bug（#22234，`Dispatcher.VerifyAccess` NRE）；不要赌。
- **Avalonia 嵌入 WPF/WinForms 壳**：又多一套 WPF/WinForms，违背"减层"。
- **两个进程**：IPC、双任务栏、状态同步、拖放都会变复杂；除非单线程试点失败且双线程也不行。

## 四、启动与生命周期

### 4.1 产品模式

1. `Main` 解析参数；自检模式走原 `App.Run`（原生 Loop，不初始化 Avalonia）；
2. 产品模式：
   - 先创建 `InkEngine`（设备/覆盖层窗口/输入），覆盖层先上屏；
   - 再启动 Avalonia `AppBuilder`；
   - `ShutdownMode = OnExplicitShutdown`（关掉最后一个 Avalonia 窗口不退出，
     覆盖层还在）；
   - 在 `OnFrameworkInitializationCompleted` 里挂 `EngineHost`；
   - Avalonia 主循环接管消息；覆盖层窗口的 WndProc 由同一个循环派发。
3. 退出：
   - 托盘/菜单"退出" → 通知引擎保存 → 关闭所有 Avalonia 窗口 → `Application.Shutdown()`；
   - 覆盖层收到 `WM_QUIT` → 走同一条退出路径。

### 4.2 覆盖层先生效

- 覆盖层创建不依赖 Avalonia；先创建、先上屏；
- Avalonia 初始化（主题/Skia/字体）可能 0.5～1 s，老师在等待期间仍能批注；
- 如果试点发现 Avalonia 初始化抢 CPU 导致笔迹抖，改成"首次打开真窗口再初始化 Avalonia"
  （主线程先跑一个最小消息循环，等待 UI 请求；复杂，试点再定）。

### 4.3 自检

- `--xxx` 自检仍走原生 `Loop()`，不初始化 Avalonia；
- 新窗口自检走 Avalonia headless 或真实窗口截图；
- 一条命令只做相关自检（按项目规则）。

## 五、引擎循环改造

现有 `Loop()`（`Engine.cs:3841`）是"抽消息 → Tick → 需要就 DwmFlush → Render → WaitMessage"。
Avalonia 接管后拆成三块：

| 块 | 内容 | 谁调用 |
|---|---|---|
| `DrainMessages` | 抽/派发消息 | Avalonia 循环负责；产品模式不再手动抽 |
| `Tick()` | 计时、PPT/文档/自动保存、手势、预测、状态推进 | 帧调度器（见下） |
| `RenderFrame()` | `NeedsFrame` 判断 + `DwmFlush` + `RenderAll` | 帧调度器 |

### 5.1 帧调度

- **空闲**：不跑定时器；Avalonia 循环阻塞在 `GetMessage`，覆盖层消息到了自然醒；
- **输入驱动**：覆盖层/画布的 `WM_POINTER` 处理里 `RequestFrame()` →
  `Dispatcher.UIThread.Post(RenderFrame, DispatcherPriority.Render)`；
- **连续动画**（激光、展开、湿墨）：开一个 `DispatcherTimer`（60/120Hz，
  跟随显示器刷新）直到 `!NeedsFrame` 再停；
- **低频任务**（PPT 轮询、自动保存、更新）：250ms `DispatcherTimer`；
- **DwmFlush**：先保留，量它对 Avalonia 动画的影响；如果顶住 UI，
  改成"后台线程等 vblank + Post 渲染"，或去掉它靠 Avalonia 合成节拍。

### 5.2 自检兼容

- `Loop()` 保留给自检/无 UI 模式；
- `Tick()/RenderFrame()` 从 `Loop()` 里抽出来，两边共用同一份顺序，
  避免"自检量出来的结论和产品不一样"（这是项目里踩过的坑）。

## 六、窗口、模式与层序

### 6.1 窗口类型

| 窗口 | Avalonia | Chrome | 任务栏 | 置顶 | 备注 |
|---|---|---|---|---|---|
| 设置 | Window | 系统/客户区装饰 | 可选 | 模态时跟 owner | 分类 + 表单 |
| 收藏/图形 | Window（Palette） | 无边框/客户区装饰 | 否 | 是 | 可拖动/缩放，记忆位置 |
| 展台 | Window | 无边框/客户区装饰 | 否 | 是 | 视频表面 + 控制条 |
| 白板 | Window | 系统/客户区装饰 | 是 | 可选 | 原生画布子窗 |
| PDF/文档 | Window | 系统/客户区装饰 | 是 | 可选 | 原生画布子窗 + PDF 页 |
| 覆盖层 | 原生 | 无边框透明 | 否 | 是 | 不激活、穿透 |

### 6.2 模式与层序（必须先定）

| 模式 | 覆盖层 | 真窗口 | 说明 |
|---|---|---|---|
| 批注 | 显示、置顶、接输入 | 无（或最小化） | 桌面/PPT 批注 |
| 文档 | **隐藏或穿透** | 白板/PDF 置顶或普通 | 覆盖层不能盖住文档窗 |
| 设置 | 隐藏（或穿透） | 设置置顶/模态 | 设置必须在最上 |
| 展台 | 可选 | 展台置顶、小窗 | 视频预览不能被覆盖层盖住 |
| 收藏/图形 | 显示 | 调色板置顶 | 点调色板时它到最上；覆盖层不抢激活 |

规则：

- **文档/设置打开时，覆盖层必须让开**（隐藏或 `WS_EX_TRANSPARENT` + 取消置顶），
  否则它会盖住窗口、抢笔；
- 调色板是"小窗置顶"：点击激活后应在覆盖层之上；如果实测层序不稳，
  打开调色板时临时把覆盖层降为非置顶，关闭后恢复；
- 覆盖层永远不激活（`WS_EX_NOACTIVATE`），所以不参与 Alt+Tab；
- 真窗口的 owner：设置/对话框 owner = 当前文档窗；没有文档时用隐藏 owner，
  **不要** owner = 覆盖层（跨线程/不激活会出怪行为）。

## 七、画布嵌入（最关键的技术点）

### 7.1 `NativeCanvasHost`

- 继承 `NativeControlHost`，在 `CreateNativeControlCore` 里创建原生画布子窗；
- 子窗是 `WS_CHILD`，父 = Avalonia 传进来的 HWND；
- 画布自己画背景/内容/墨迹（D2D/DComp 或 `ID2D1HwndRenderTarget`，按现有 `OverlayWindow` 抽）；
- 尺寸/DPI：Avalonia 的 `Bounds`（DIP）→ 物理像素；`WM_DPICHANGED`/resize 时同步；
- 圆角：画布自己画圆角背景或 `SetWindowRgn`，不要指望 Avalonia 裁剪子窗；
- **不要**在子窗上叠 Avalonia 内容（菜单/提示/色带）——空域会露馅；
  这些用 Avalonia `Popup`（独立顶层窗）或原生小窗。

### 7.2 画布与引擎的关系

- 一个 `CanvasView` = 一个原生子窗 + 一份视图状态（相机/缩放/页）；
- 单线程模式下，`CanvasView` 直接调 `InkEngine` 的渲染/输入；
- 多文档时，`CanvasView` 绑定 `InkDocument`（见 §十）；
- 覆盖层和文档画布可以共用 `InkDocument`/分块缓存，但各自有相机和脏区。

### 7.3 输入/焦点

- 画布子窗收 `WM_POINTER`；Avalonia 控件收自己的指针/键盘；
- 点击画布 → 画布 `SetFocus`；点击工具栏 → Avalonia 焦点；
- 全局快捷键（Ctrl+Alt+…）在窗口级路由：先给引擎，再给 Avalonia；
- 画布上的文字输入继续用现有 RichEdit 宿主（独立小窗），不要用 Avalonia TextBox 叠上去。

## 八、状态、命令与 MVVM

### 8.1 单一事实来源

- `InkEngine` 仍是唯一事实来源：文档、工具、撤销、页、选中；
- Avalonia ViewModel **只读** `UiState` 快照，写只走 `IEngineCommands`；
- 不允许 ViewModel 直接改 `InkDocument`、`Stroke`、`Doc`（和现有架构规则一致）。

### 8.2 `EngineService`

```
EngineService
  ├─ State               只读快照（工具/颜色/粗细/页/撤销深度/文档版本）
  ├─ Commands            IEngineCommands（现有）
  ├─ Changed             状态变化事件（合并到 30～60Hz，避免每点刷新 UI）
  └─ Dispatch(Action)    单线程直接调；双线程时 Post 到 UI
```

- 状态变化用"版本号 + 合并通知"，不要每个笔点都刷新整个 ViewModel；
- 设置项通过 `SettingsService` 读写现有 `settings.json`，保存走引擎的 `SetUiPref/FlushSettings`；
- 撤销/重做/清空/翻页等全部走命令，UI 不缓存可写状态。

### 8.3 ViewModel 边界

- `SettingsViewModel`：分类、行、值、校验、重启提示；
- `LibraryViewModel`：分类、条目、分页/滚动、选择、拖放；
- `ShapesViewModel`：图形目录、预览、最近使用；
- `CameraViewModel`：设备、分辨率、冻结、批注；
- `DocumentViewModel`：文件名、页、缩放、脏标记；
- 每个 ViewModel 只依赖 `EngineService`/`SettingsService`，不依赖 `Window`。

## 九、主题、字体与控件

### 9.1 Tokens → Avalonia 资源

- 颜色（面板底/描边/图标/强调/悬停/选中）、圆角（胶囊/8/4）、字号、间距、动画时长；
- 现有 `Tokens.cs` 是唯一来源，生成/手写 `Tokens.axaml`；
- `FluentTheme` 只做基础，关键控件用自定义 `ControlTheme` 覆盖：
  Button / ToggleButton / Slider / ComboBox / ListBoxItem / TabItem / ScrollBar / ToolTip；
- 暗色主题跟现有 `_dark` 开关；高对比度跟系统；
- 图标继续用现有 Fluent SVG 路径，转成 Avalonia `PathIcon`/`Geometry`。

### 9.2 字体/中文

- 正文用现有 `Microsoft YaHei UI` / 漓雨手书（按场景）；
- Avalonia 12 用 HarfBuzz，字形回退要实测（中文、标点、全角空格）；
- 文本测量用 Avalonia 的 `TextLayout`，界面内不要混用 DWrite 测量。

### 9.3 控件范围

- 先做设置/收藏需要的：Button、Toggle、Slider、ComboBox、TextBox、ListBox、TabControl、
  ScrollViewer、Dialog、ToolTip、InfoBar；
- 不做通用控件库；Avalonia 自带的够用，缺的用 `ControlTheme` 补；
- 白板/PDF 的工具条可以先用 Avalonia 的 `Button/ComboBox`，也可以暂时保留现有 D2D 条。

## 十、文档与多窗口

- **第一阶段：同时只开一个文档**（白板或 PDF），文档窗口只是当前 `Doc` 的一个视图；
- **第二阶段（可选）**：拆 `InkDocument` 与 `DocumentView`，同一 UI 线程上多文档/多视图；
- 现在 `InkEngine.Doc` 是 `readonly` 单例（`Engine.cs:43`），不要用"多开引擎实例"硬凑；
- 文档窗口关闭：自动保存 → 释放页位图/PDF → 回桌面批注页空间；
- 文档窗口标题：文件名 + `*` 脏标记；任务栏图标/缩略图用系统默认。

## 十一、文字输入 / IME / 触屏键盘

| 场景 | 用什么 | 注意 |
|---|---|---|
| 设置/表单文字 | Avalonia `TextBox` | 中文 IME 实测；候选窗跟随 |
| 画布文本框 | 原生 `RICHEDIT50W` | 继续现有 `TextBoxEditing`，只统一宿主 |
| 搜索/重命名 | Avalonia `TextBox` | 单行；Esc 取消/Enter 提交 |
| 触摸键盘 | 手动调 `TabTip` / `ITipInvocation` | Avalonia #10136 不会自动弹；官方虚拟键盘是付费组件 |
| 候选窗 | 系统 IME | 不要自绘候选窗 |

**必测**：微软拼音/搜狗/QQ 拼音、100/150/200% DPI、触摸键盘弹出/收起、候选窗在屏幕边缘翻转。

## 十二、拖放

| 场景 | 方案 |
|---|---|
| 资源管理器 → 窗口（PDF/图片） | Avalonia `DragDrop` / OLE `IDropTarget`；大文件异步 |
| 收藏/图形 → 画布 | **OLE `DoDragDropAsync`** + 原生画布 `IDropTarget`（同线程也能用；跨窗口/跨进程都稳） | 落点高亮；松手换算到画布坐标，调引擎插入 |
| 画布 → 收藏 | 反向：画布提供选中对象快照，Avalonia 接收 | 同上 |
| 同一窗口内的轻量拖动 | 内部指针捕获 | 只在同一 HWND 内用，跨窗口不要用 |
| 触摸拖放 | 长按进入拖拽 | 不要和滚动/手势打架 |
| 取消 | Esc/无效区域：不产生半截对象、不写存档 |

> 跨窗口/跨栈（Avalonia 调色板 → 原生画布）优先用 **OLE 拖放**；
> "内部拖放"只用于同一个窗口里的轻量移动，别拿它硬跨 HWND。

## 十四、P0 试点的 Go / No-Go

### 做

1. 最小 Avalonia 12 应用（设置页 + 10 控件 + 暗色主题）；
2. 200 条收藏虚拟列表（选择/空态/滚动）；
3. 白板窗口：Avalonia 壳 + `NativeControlHost` 嵌现有 D2D 画布（可写）；
4. 画布上浮一个 Avalonia `Popup`（色带/菜单），验证空域；
5. 收藏拖一个图形到画布；
6. 设置 TextBox 中文 IME + 触摸键盘；
7. 4 GB 低端机跑一遍。

### 量

| 指标 | 目标 |
|---|---|
| 笔迹输入→上屏 | 与现在持平（±1 ms） |
| 画布空域 | 缩放/滚动/弹层/圆角无露馅 |
| Avalonia 动画 | 60fps 不掉帧（覆盖层同时书写时） |
| 触屏键盘 | 点 TextBox 能弹/收；输入框不被盖住 |
| 中文 IME | 三种输入法不丢字；候选窗跟随 |
| DPI | 100/150/200%，跨屏不缩不错位 |
| 窗口 | 最小化/最大化/贴靠/任务栏/还原正常 |
| 内存 | 2 个 Avalonia 窗口 ≤ +150 MB |
| 启动 | 覆盖层启动不变；首个窗口 ≤1.5 s |
| 4 GB | 不换页/不卡顿（对比现在） |
| 拖放 | 收藏→画布成功；取消不产生半截对象 |

### Go

- 笔迹延迟不退化；
- 画布无空域问题；
- IME/触屏键盘可用；
- 窗口贴靠/动画可接受；
- 内存 +≤150 MB、4 GB 不换页；
- 设置页开发时间明显下降。

### No-Go

- 单线程下 `DwmFlush`/渲染顶住 Avalonia，动画/输入明显卡；
  → 先试双线程（覆盖层独立线程），仍不行则回退原生窗口层；
- 画布子窗裁剪/DPI 反复出问题；
- 触屏键盘无法稳定调起；
- 4 GB 明显换页。

## 十五、性能与部署

- **渲染模式**：`Win32RenderingMode.AngleEgl`（默认 GPU）+ `Software` 兜底；
  高刷屏可开 `Win32CompositionMode.WinUIComposition`（Win10 17134+，需 AngleEgl）；
- **GPU 缓存**：`SkiaOptions.MaxGpuResourceSizeBytes` 先给 128 MB，低端机再降；
- **列表**：一律虚拟化；不要一次性创建 100+ 容器；
- **动画**：尊重系统"减少动画"；低端机减少阴影/模糊；
- **启动**：覆盖层先上屏；Avalonia 初始化后台化/懒初始化（试点定）；
- **内存**：Avalonia + Skia 预计 +80～150 MB；4 GB 机器实测；
- **发布**：单文件/自包含；Skia 原生库要进包；安装包增大约 20～40 MB；
- **裁剪/AOT**：XAML/绑定对裁剪不友好，先不做 AOT；要做得单独验证；
- **版本**：锁 Avalonia 12.x 具体补丁版本；升级前跑窗口/画布回归。
