# 快速画圆折线：三轮定位的完整记录（含两次错误结论）

日期：2026-10-07　　分支：`opt/d2d-memory`

---

## 零、先回答"点是不是被人为稀疏了"

**不是。** 三条独立证据：

| 证据 | 结论 |
|---|---|
| `Stroke.AddPoint`（`Model.cs:3133`） | **没有任何距离/密度过滤**，调一次加一个点 |
| `ExtendFreehandStroke`（`Engine.cs:3540`）注释 | "指针报什么坐标就存什么坐标：**不做平滑、不做抽稀**" |
| 合并历史（用户的 `[笔画]` 日志） | `12 条消息 → 12 个采样点` —— **historyCount 一直是 1，系统根本没合并可恢复的中间点** |
| **输入捕获率自检**（`--inputtest`，合成注入） | **61 个点 / 593 ms = 103 Hz，1:1 全收下** |

最后一条是决定性的：**同一套代码，喂 103Hz 就收 103Hz。** 所以通路本身能接住高采样率。

**那用户那边为什么只有 12 个点？** 他的日志里还有一条独立佐证：

```
[ 2.9s] fps= 12.3   记录= 0.46  上屏= 0.27
[ 4.1s] fps= 17.3
[ 5.1s] fps= 19.2
```

**fps=12~19 和"一笔只有 12 个点"是同一个数** —— 这个程序每收到一批输入消息渲一帧。
两个独立数字互相印证：**那台机器在"关 Windows Ink"时，输入上报率就是 ~15Hz。**
（ink 开时用户测到 34~43 个点、点距 8~12px，正是"开 ink 上报率更高"。）

**但这不能成为"算法可以不处理稀疏"的理由。** 点稀是设备/驱动的性质，不是我们的 bug；
**而"点稀时不该画出多边形"是我们的 bug** —— 就是下面修的那个。

## 一、三轮定位（两次错误，记下来免得再走）

### ❌ 第一轮：窗口判据按"点数"算，不按弧长（真实 bug，但不是这个）

`MarkCorners` 的窗口判据用 `±CornerWindow 个点` 当窗口。量到的转角 ≈ **2 × (点距/半径)**，
点距超过 0.305×半径 就把正常圆弧判成角。

**修了**（`CornerWindowMaxPx = 24`）。复现器用例⑦（R=150、58.5px 一段）从八边形变光滑 ✅
**但用户实测"两个开关都没反应"** → 这条不是他的问题。

### ❌ 第二轮："和相邻点差 ≤12° 就算光滑"（判据本身是错的）

复现器用例⑧（11 点绕一圈 = 每段 36° > 阈值 35°）复现了多边形，加上"连续性"判据后变光滑。
**但这条判据根上是错的**：锯齿的转角是 `+127 −127 +127`，**相邻差 0°** → 被判成"光滑" →
**角点保护失效**（用 `--cornerdump` 打出来的转角序列才发现）。

### ✅ 第三轮：带符号转角 vs 局部趋势

| 形状 | 带符号转角 | 局部趋势 | 偏离 | 判定 |
|---|---|---|---|---|
| 圆 | +36 +36 +36 | +36 | 0 | 光滑 ✅ |
| 椭圆 | +20…+47…+20 | ~+33 | ~14 | 光滑 ✅ |
| **锯齿** | +127 **−127** +127 | **~0** | 127 | **角 ✅** |
| 直角 | 0 0 **+90** 0 0 | ~0 | 90 | 角 ✅ |

**关键是符号**：取绝对值会把正负交替抹平，一切"幅值比较"式判据都会被锯齿骗过去。
而"偏离趋势"这个口径对**稀采样天然免疫**——圆弧的转角是连续变化的，
再稀也只是趋势的一部分，不会偏离自己。

**为什么固定阈值天生不行**：圆上每顶点转角 = **360°/段数**，与半径无关。
11 点绕一圈就是 36°，只要阈值低于 36°，光滑的圆必然被判成一堆角点。

## 三、新增的工具与开关（都是排查用，产品行为由默认值决定）

| 开关 | 作用 |
|---|---|
| `--geomtrace` | 每一笔报一次几何走了哪条岔路（通道 A/B × 数据源 × 曲线/折线）+ 点数/点距 |
| `--cornerdump` | 打**抽稀后每个顶点的转角序列** + 相邻最大差（定"多松算松"必须看这个分布） |
| `--smoothcornerdeg N` | 旧版连续性容差（第三版已被趋势判据取代，保留做对照） |
| `--notrend` | 关掉趋势判据（回到固定阈值，做"修前/修后"对照） |
| `--cornerdump` 里的 `历时/有效输入 Hz` | `[笔画]` 行新增：**点数 ÷ 历时 = 有效输入频率** |

最后一条是为用户那两个问题加的：**"12 个点"本身说明不了任何事**——
12 个点摊在 0.1 秒上是 120Hz（正常），摊在 0.8 秒上只有 15Hz（异常）。
没有这个分母，讨论"点是不是太稀"都是空谈。

## 四、⚠️ 验证方法上的坑（我踩了两次）

1. **`--smoothshow` 出的 `-off` 是"故意关掉曲线的折线对照组"**，`-on` 才是真实渲染。
   我第一轮裁了两张 `-off` 做"修前/修后"对比，得到"逐像素相同（0）"，
   差点误判成"修改无效"——那两张本来就该都是多边形。
   **修前/修后的对照要用 `--notrend` 显式表达，不能拿 `-off` 当修前。**
2. **诊断本身也会说谎**：`--geomtrace` 第一版用单个标志位去重，
   被"通道 A 总是先建几何"占掉，**通道 B 那行永远打不出来**；
   第二版只打"活笔"那次，把"落笔之后"挡在门外。
   现在按 (阶段 × 通道) 四个组合各打一次。
