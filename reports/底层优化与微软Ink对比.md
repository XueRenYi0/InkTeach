# 底层优化进展 · 与微软 Windows Ink 的对比 · 后续优化空间

日期 2026-09-13。目标：**在不降低教师使用体验的前提下，把底层压到极致**。

---

## 一、本轮最重要的发现：两个内存泄漏

我加了一个"长跑测试"（模拟连续上课：画→擦→撤销→翻页，循环 3 分钟、3458 轮），
跑出来的第一版结果暴露了严重问题：

```
   0s |  98.4M
 180s | 196.4M     ← 笔画数始终只有 20 左右，内存却在翻倍
```

按这个速度，**一节课 45 分钟会涨到 1.5 GB**，在 8 GB 的教室机上就是灾难。

### 泄漏点 1：笔画被移除时没有释放几何缓存

`InkDocument.RemoveStroke()` 忘了调用 `Stroke.Release()`。
于是**每擦一次、每撤销一次，就泄漏一个 Direct2D 几何对象**
（连带它在 GPU 侧的细分数据）。

修复：移除笔画时释放几何。撤销/重做会按需重建，代价很小
（实测重建 1 万笔几何只要 36 ms，而这是极少发生的操作）。

### 泄漏点 2：撤销历史没有上限

原来用无上限的 `Stack` 存撤销动作。长跑里每轮压入约 30 条动作，
3458 轮就是十万条，每条都持有笔画对象（含点列表）。

修复：撤销深度上限 200 步（主流软件都在 100~200 之间），
超过就从最旧的开始丢。

### 修复后

```
  15s | 109.3M
 180s | 111.4M     ← 完全平稳
 提交大小 90.0M → 90.8M，最慢单帧 9.92 ms
```

**结论：一节课 45 分钟的占用稳定在 111 MB 量级，不会随时间劣化。**

## 二、与微软 Windows Ink 的对比

| 维度 | 微软 Windows Ink / InkPresenter | 本原型 |
|---|---|---|
| 平台 | UWP / WinUI 控件（InkCanvas、InkPresenter） | 纯 Win32 + Direct2D + DirectComposition |
| 输入 | 应用把 WM_POINTER 交给 InkPresenter | 全部自己处理 |
| **湿墨**（还没落笔的即时反馈） | **系统级低延迟通道**，由合成器/输入线程渲染 | 每帧重绘活动笔画；可选用 DirectComposition 委托墨迹轨迹 |
| 干墨（已提交笔画） | 系统管理的 InkStroke 集合 + 设备端缓存 | 自研：内容层位图 + 脏区增量补丁 |
| 笔迹平滑 | 系统内置（含预测点） | 自研：1€ 滤波器 + RDP 抽稀 + Schneider 贝塞尔拟合 |
| 橡皮擦 | 笔画级 + 像素级 | 笔画级，自研（线段距离 + 路径插值） |
| 选择 | 套索 / 直线选择（原生） | 框选已完成；套索待做 |
| 形状识别 | `InkAnalyzer`：圆/椭圆/三角形/矩形/菱形… | 无（**可借用**，已实测桌面可用） |
| 延迟 | 湿墨走系统通道，**可以低于一帧** | 约一帧（60 Hz 屏上 ~16 ms） |
| 内存基线 | WinUI 栈 120~250 MB | **96 MB** |
| 可控性 | 低（黑盒，脏区/缓存/每帧画什么都不归你管） | **高**（每一帧都由我们决定，这才有得优化） |

### 核心差异一句话

**微软的路子是"湿墨交给系统、干墨交给系统"，代价是绑 WinUI、内存高、不可控；
我们的路子是"全部自己做"，换来 96 MB 内存和完全的可控性，湿墨延迟得自己扛。**

### 值得借的部分（按价值排序）

1. **`InkAnalyzer` 形状识别**——已实测：普通桌面程序可直接调用，
   手绘圆识别成 `Circle`、三角识别成 `EquilateralTriangle`。识别算法不用自己写。
2. **`InkStroke.PointTransform` 的数据模型思路**——"变换独立于几何"，
   我们已按这个思路设计。
3. **`IDCompositionDelegatedInkTrail`（委托墨迹轨迹）**——见下节。
4. **`ID2D1GeometryRealization`**——微软 Direct2D 官方的细分缓存机制，还没试。

### 委托墨迹轨迹：接口能拿到，但本机验证不了

这是微软自家"笔尖跟手"的关键技术：把正在写的那一小段交给**系统合成器**去画，
应用自己的延迟就不再影响手感。

探测结果（本机 Windows 11 26200）：

| 步骤 | 结果 |
|---|---|
| 从合成设备 QI `IDCompositionInkTrailDevice` | ✅ 成功 |
| `CreateDelegatedInkTrailForSwapChain` | ✅ 成功 |
| `StartNewTrail` / `AddTrailPoints` | ✅ 返回成功（generation id 正常递增） |
| **屏幕上是否出现轨迹** | ❌ **看不到任何渲染结果** |

已排除的原因：

- 不是缺接口（调用全成功）；
- 不是窗口没前台（临时取消 `WS_EX_NOACTIVATE` 并抢前台，仍然看不到）；
- 不是"我们渲染太快没东西可补"（故意每帧睡 100 ms 让它变慢，仍然看不到）。

**剩下最可能的原因：系统只对真实手写笔输入启用这条通道，而我们用的是合成鼠标输入。**
这台机器没有压感笔，无法验证。

因此我把这段代码**默认关掉**（`--inktrail` 才启用）。理由很直接：
一个验证不了的绘制通道，有可能在真笔上留下重影——那反而破坏了体验。
等有压感笔的设备时再打开验证。

## 三、还能优化什么（按性价比排序）

### 已经做掉的一项：几何实现缓存（ID2D1GeometryRealization）

**它是什么。** Direct2D 里的 `ID2D1PathGeometry` 只是一份**数学描述**（一堆直线和曲线）。
每次调用 `FillGeometry` 时，Direct2D 都要现场做一遍**细分（tessellation）**：
把曲线按当前精度折成线段、把填充区域三角化、再交给 GPU 画。
这道工序每次都做，而且它是 CPU 活。

`ID2D1GeometryRealization` 就是把**细分之后的结果**缓存下来的对象：
建一次，之后每帧只是把已经算好的三角形提交给 GPU。

区别可以这样理解：

- 普通几何 = 每次都要重新"把图纸算成施工图"；
- 几何实现 = 施工图算一次存起来，之后直接照着施工。

**实测收益**（1 万笔画，本机）：

| 场景 | 不开缓存 | 开缓存 | 提升 |
|---|---|---|---|
| 整层重画 1 万笔 | 137.2 ms | **19.4 ms** | **7.1 倍** |
| 擦除拖动一步 | 4.29 ms | **1.45 ms** | **3.0 倍** |
| 撤销一步 | 5.61 ms | **2.58 ms** | **2.2 倍** |
| 结束一笔（增量） | 0.71 ms | 0.75 ms | 持平（活动笔画不走缓存） |

**代价与取舍**：

- 每个缓存约 **18 KB**（1 万笔约 +180 MB），所以设了上限
  （`Stroke.MaxRealizations = 4096`），超了就退回"每次重新细分"——
  宁可慢一点，也不能让内存无上限增长。
- 它是**设备相关**的，多显示器时每块屏要各存一份。
- 第一次重画某一笔时要建缓存，会有一次性开销（长跑实测最慢帧 16.66 ms，
  只出现在预热阶段，之后一直稳定）。
- 正在书写的那一笔**不走缓存**：它的几何每帧都在变，建缓存反而更慢。

长跑验证（3 分钟 / 3457 轮，开启缓存）：内存稳定在 **118 MB**，无增长。

标注"体验影响"是为了遵守"不能为了性能降体验"这条红线。

| # | 优化项 | 预期收益 | 体验影响 | 风险/成本 |
|---|---|---|---|---|
| ~~1~~ | ~~`ID2D1GeometryRealization` 缓存细分~~ | **已完成**：整层重画快 7 倍、擦除快 3 倍 | 无 | 已设内存上限 |
| 2 | **4K 屏实测**（现在是 2880×1800） | 摸清像素量翻倍后的余量 | 无 | 低。本机没 4K 屏，可造一张 4K 离屏图层测 |
| 3 | **`GetFrameLatencyWaitableObject` 替代忙等** | 降低绘制时的 CPU | 无 | 低。改 Present 的等待方式 |
| 4 | **离屏内容层分块（tile）** | 省显存；脏区更小 | 无 | 中。实现复杂度 |
| 5 | **笔画几何合并批处理** | 整层重绘从 N 次绘制降到几次 | 无 | 中。适合"长页面"场景 |
| 6 | **像素级部分擦除** | 功能更接近用户预期 | **正向** | 中高。需几何布尔运算或擦除蒙版 |
| 7 | **套索选择（自由选）** | 功能补齐 | **正向** | 中 |

### 明确不建议做的

- **降低笔迹质量换性能**：比如关掉贝塞尔拟合、减少采样点、降低平滑。
  这些正是"字好不好看"的来源，教师一写就知道。性能已经够了，不该动这里。
- **降低刷新率**：比如把激光笔从 60 Hz 降到 30 Hz。省不了多少，手感立刻变差。
- **牺牲压感**：压感线宽是手写笔的核心体验。

## 四、对"低配教室机流畅上一节课"的结论

### 附：4K 与分辨率实测

教室一体机不少是 4K（3840×2160），像素量是当前测试屏（2880×1800）的 1.6 倍。
本机没有 4K 屏，所以用"同样一批笔画渲染到不同尺寸的离屏内容层"来量各操作的
分辨率敏感性（5000 笔，每项取多次平均）：

| 内容层尺寸 | 整层清屏 + 重画 5000 笔 | 20 次脏区补丁 | 每次补丁 |
|---|---|---|---|
| 1920×1080 | 12.3 ms | 18.6 ms | 0.93 ms |
| 2560×1440 | 15.7 ms | 18.9 ms | 0.95 ms |
| 2880×1800（当前屏） | 21.8 ms | 18.7 ms | 0.93 ms |
| **3840×2160（4K）** | 22.5 ms | 13.3 ms | **0.67 ms** |

**结论：我们真正的高频路径——脏区补丁——与分辨率无关。**
因为补丁只处理那一个小方块里的笔画，屏幕多大都一样。整层重画会随分辨率上升
（主要是清屏面积），但那是低频操作（换页、清空、改分辨率）。

4K 真正的代价在内存：离屏内容层从 20.7 MB 涨到 **33.2 MB**（+12.5 MB），
交换链缓冲由 DWM 持有、不计入我们的提交大小。已经单独验证过：
两张 4K 图层提交内存 +64.1 MB，与理论值 66 MB 吻合。

而 DWM 对我们这个全屏图层的合成，因为用的是**脏矩形上屏**，也只更新脏区，
不随屏幕尺寸线性增长。

**所以 4K 的影响主要是 +25 MB 左右内存，性能上几乎没有影响。**

### 附：帧延迟等待对象（GetFrameLatencyWaitableObject）——负面结论

原本的设想是：用 DXGI 的帧延迟等待对象配速，替代 `Present(1)` 在垂直同步上的
阻塞，从而降低绘制时的 CPU。实测结果是**反效果**：

| | 绘制 CPU | 绘制 GPU | 帧率 |
|---|---|---|---|
| 用等待对象 + `Present(0)` | **85.7%** 单核 | **62.9%** | **1726 fps** |
| 用 `Present(1)`（现状） | 16.5% 单核 | 2.9% | 60 fps |

原因：**合成交换链的帧会被 DWM 立刻取走，等待对象几乎不会阻塞**，
于是垂直同步这层配速完全消失，循环跑到 1726 fps、把 CPU 和 GPU 全烧掉。

对这种场景，`Present(1)` 才是正确的节流手段。代码和 `--latencywait` 开关保留，
供将来换设备/换驱动时复测；**默认关闭**。

原型当前状态（2880×1800 @ 192 DPI，Intel Iris Xe 核显）：

| 指标 | 数值 |
|---|---|
| 空闲 | 0.0% CPU、0.0% GPU、96 MB |
| 连续书写 | 约 14% 单核、2.9% GPU，**与画面里已有多少笔无关** |
| 长跑 3 分钟 / 3458 轮 | 内存稳定在 111 MB，无劣化 |
| 每帧绘制开销 | 0.6~1.0 ms（1 万笔时仍是这个量级） |
| 最慢单帧 | 9.92 ms（长跑全程） |

换算到典型教室机（i3-8100 / UHD 630 / 8 GB）：

- GPU：UHD 630 约比 Iris Xe 慢 2~3 倍 → 6~9%，余量充足；
- CPU：4 核机约占全机 3.5%，无积压；
- 内存：长期稳定在 120 MB 上下，8 GB 机器完全无压力。

**结论：已经达到"低配电脑流畅上一节课"的目标，而且是建立在保留
贝塞尔拟合、压感线宽、60 Hz 湿墨这些体验项的前提下。**
