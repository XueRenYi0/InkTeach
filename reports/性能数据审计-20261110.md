# 性能数据审计（2026-11-10）

范围：`InkTeach` 的性能/内存/GC/帧时间相关埋点、自检输出、HUD、控制台日志、README 数字。  
环境：HONOR HGF-WX6-V，i5-12500H / 16GB / Iris Xe / 2520×1680 @192DPI / 90Hz。  
说明：本次是**数据口径修正**，不改渲染策略；临时探针均未保留。相关自检已跑，未跑全量功能套件。

---

## 一、先说三个最重要的“原来不准”

### 1. `--lagtest` 的“写一笔 394 MB”是测量工具自己的分配，不是产品内存

旧输出：

```
[笔画] ... 分配 394014.8 KB / GC 119/119/119
```

- `StrokeAllocBytes` 统计的是**这一笔按下到抬起之间、当前线程累计分配了多少字节**，不是驻留内存，也不是“这一笔占了多少内存”。
- 这个数被 `LagTrailVisibilityProbe` 污染了：它在按住笔的 4 秒里调用 `ScreenProbe.CountMagenta(1000×280)` 360 次；
  旧 `Capture()` 每次 `new byte[w*h*4]` ≈ 1.12 MB，360 次 ≈ **403 MB**，正好对上 394 MB。
- 这些是**大对象（LOH）分配**，所以同时刷出 119 次第 2 代 GC；看起来像“写一笔卡了 119 次”，其实卡的是测试工具。

修正：

- `ScreenProbe.Capture()` / `AvgLuma()` 改成 `ArrayPool<byte>` 复用缓冲；
- `--lagtest` 的 4 秒可见性探针现在最大 **约 2.2 MB / 0 次第 2 代 GC**；普通一笔 20~55 KB；
- 日志文案改成“**整笔会话累计，非驻留**”，避免再被读成内存。

> 真正的产品内存看 HUD/`--memory`/`--longrun`：空载提交约 91 MB，长跑 60 秒约 148 MB 工作集 / 115 MB 提交，不是“一笔几百兆”。

### 2. `--cameratest` 的“不掉帧”之前只看记录时间，漏掉了分块光栅

旧判据：

```csharp
string note = worst < 16.7 ? "不掉帧" : ...
```

`worst` 只来自 `LastRecordMs`（BeginDraw~EndDraw），**不含 `LastRebuildMs`（分块光栅）和 `Present`**。
所以 10k 时明明有一格光栅 18~19ms，它仍然打印“不掉帧”。

修正后：

- 每格统计“工作耗时 = `LastFrameMs` − `LastPresentWaitMs`”；
- 单独列出：每格工作平均、最慢工作、记录平均、光栅平均、最慢光栅、配速等待、超 16.7ms 格数 / 超刷新格数；
- 判据看工作耗时，不再看 `LastRecordMs`。

复测（10k，12 格）：

| 指标 | 修正前输出 | 修正后输出 |
|---|---:|---:|
| 记录平均 | 0.40~0.49ms | 0.43~0.46ms |
| 光栅平均 | 3.6~4.1ms | 3.8~4.0ms |
| 最慢光栅 | 13.8~19.1ms | 17.4~18.1ms |
| 判据 | **“不掉帧”** | **“偶掉 1 格”**（超 16.7ms 1/12，超 90Hz 刷新 1/12） |

### 3. `--longrun` 的“平均上屏 / 最慢帧”也不准

旧代码：

- “平均上屏”其实打印的是 `LastPresentMs`（**最后一帧**，不是平均）；
- “最慢帧”只统计 `LastRecordMs`，漏掉分块光栅、UI 准备、Present；
- 每轮只采样最后一次 `RenderAll`，前面的绘制/擦除帧完全没进统计。

修正后：

- 每次 `RenderAll` 都采样；
- 记录/上屏都做最近 60 帧平均；
- 最慢总帧单独统计；
- 首帧（冷启动）单独报，稳态最慢从 3 秒后算，避免“最慢帧”永远等于启动那一下。

60 秒复测：

| 指标 | 旧输出 | 新输出 |
|---|---:|---:|
| 平均记录 | 0.14~0.17ms | 0.20~0.24ms |
| 平均上屏 | 最后一帧，0.13~16.6ms 乱跳 | 0.13~0.62ms（真平均） |
| 最慢帧 | 0.71~0.93ms（只算记录） | 首帧 61.46ms（冷启动）；稳态最慢总帧 **17.24ms** / 记录 1.20ms |

> 结论没变（长跑很稳），但数字终于能反映“总帧”而不是“只画了多久”。

## 二、逐个指标审计

| 指标 | 原来怎么算 | 问题 | 现在 |
|---|---|---|---|
| `LastFrameMs`（HUD 帧耗时） | RenderAll 墙钟，含 Present 等待 | 本身准确，但和“绘制”并列时容易被误读 | 保留；HUD 仍显示“帧耗时” |
| `LastRecordMs`（绘制） | BeginDraw~EndDraw | 不含分块光栅/UI 准备，单独看会低估 | 保留为“绘制”组件 |
| `LastRebuildMs`（分块光栅） | 只累计 `paint()` 时间 | **漏掉新块纹理创建**（实测 Create 0~1.4ms） | 现在含 Create；`LastPatchMs` 同步修正 |
| `LastPresentMs`（上屏） | 从等待配速前开始计时 | **包含配速等待**，长跑时看起来像上屏很慢 | 现在只算 Present 调用；等待拆到 `LastPresentWaitMs` |
| `LastPresentAreaPercent` | 各脏矩形面积直接相加 | 重叠矩形会算出 **>100%**；触发整屏判断也可能误判 | 先合并重叠/相接矩形，再算面积并 clamp 到 100% |
| `LastPresentRectCount` | 整屏 Present 时置 0 | “0 块 / 100%”很怪，统计也不真实 | 整屏 = 1 块 / 100%，并加 `LastPresentFull` |
| 控制台“总帧” | 原“合计”= `记录+上屏+面板+统计` 之和 | **不含分块光栅/UI 准备**，不是总帧；`统计` 只在部分帧累加，除法则用总帧数 | 改为 `_accFrame` 实际帧耗时平均；另加“光栅”平均 |
| HUD“输入→上屏” | `LastPresentEndQpc` | 到的是 **Present 返回**，不是光子上屏 | 改为“输入→Present”；真实端到端看 `Latency.Report` 的“Present→上屏” |
| HUD“CPU” | 进程 CPU / 逻辑核数 | 是**全机占比**，不是单核占比 | 标成“CPU（全机）” |
| `LastAppendMs` | 字段存在但从未赋值 | 补画路径耗时没有数 | 从 `CanvasTileCache.AppendedMsLastFrame` 真正赋值 |
| `_workingSetMb` / `_privateMb` / `_privateWsMb` | GetProcessMemoryInfo | 三个口径本身正确；`--memory` 在 Trim 后打印 1.8MB 工作集，容易被当成日常 | `--memory` 空闲行只报提交；工作集注明“Trim 后、不代表日常” |
| `Mem.Ws()` / `Mem.Priv()` | `Process.Refresh()` | 读的是工作集/私有提交，正确；但 Trim 后工作集会掉到几 MB | 报告里不再把 Trim 后工作集当日常；结论用提交 |
| `_gpuMb` | DXGI QueryVideoMemoryInfo(Local) | 是 DXGI Local 当前用量；核显/UMA 与任务管理器“GPU 内存”口径不完全一样 | 保留“显存”但知道它是 DXGI Local；报告里写清 |
| `StrokeAllocBytes` | 按下→抬起当前线程分配 | **不是驻留内存**；包含渲染和测试采样；`--lagtest` 被 CountMagenta 污染 | 文案改“整笔会话累计，非驻留”；ScreenProbe 池化；4s 探针从 394MB→2.2MB |
| `StrokeGc0/1/2` | 进程级 GC 次数差 | 进程级，可能包含后台 PDF worker；不是单线程 GC | 保留；报告注明“进程级” |
| `--tiletest` 块大小 | 写死 `const int T=256` | `--tilesize 512/128` 时测试无效（512 曾误报 FAIL） | 改读 `CanvasTileCache.TileSize`；128/512 都实测 PASS |
| `--tiletest` 每块字节 | 写死“256KB” | 换块大小后文案错 | 用 `CanvasTileCache.TileBytes` |
| `--selftest` 汇总 full rebuild | 用激光压测最后一帧的 `LastRebuildMs` | 显示 **0.0ms**，和前面 10k 基准的 227ms 矛盾 | 单独保存 10k 基准值；record/present 标明 last frame |
| `--appendtest` “整体下移”采样点 | 采样 B 的**旧位置** | 实际看到的是 A 移进 B 旧位置，碰巧 PASS，判据不严谨 | 采样 B 的新位置（+260×DPI） |
| `--longrun` 首帧 | 计入“最慢帧” | 冷启动 57~61ms 会永远压住稳态数据 | 首帧单列，稳态从 3 秒后算 |
| `--memory` 一万笔基线 | 清空后没清撤销栈，也不 Trim 显存 | “清空后”仍带着上一轮 10k，数字虚高 | 清撤销栈 + `Gfx.TrimVideoMemory()` 后再测；结论用实测变量 |
| `--memory` 结论 | 写死“200MB / 31MB / 42MB / 26MB” | 旧版本数字，和当前实测不一致 | 改成打印本次实测值；旧版拆分数字删除 |

## 三、复测结果（修正后）

### 3.1 `--lagtest`

- 4 秒可见性探针：**2264 KB / GC 0/0/0**（旧：394014.8 KB / 119/119/119）
- 普通一笔：20~55 KB / GC 0/0/0
- 结论：之前的“几百兆 + 119 次 GC”确认是测试工具分配；不是产品写一笔的内存/GC。

### 3.2 `--cameratest`（256px，10k）

| 指标 | 值 |
|---|---:|
| 每格工作平均 | 5.01~5.23ms |
| 最慢工作 | 18.71~19.40ms |
| 记录平均 | 0.43~0.46ms |
| 光栅平均 | 3.84~3.85ms |
| 最慢光栅 | 17.4~18.1ms |
| 配速等待平均 | 3.41~3.54ms |
| 超 16.7ms / 超刷新 | **1/12 / 1/12** |
| 12 格新光栅块 | 70 |

和上一轮结论一致：根因仍是“滚到新区域时懒建几何 + 第 2 代 GC”，不是分块查询/排序。  
512px 对照：10k 工作平均 3.86ms / 最慢 20.71ms（光栅 2.88 / 19.61ms），平均略好、最慢更差，仍建议保持 256。

### 3.3 `--longrun 60`

- 平均记录 0.20~0.24ms；平均上屏 0.13~0.62ms
- 首帧（冷启动）总 61.46ms / 记录 17.92ms
- 稳态最慢总帧 **17.24ms** / 记录 1.20ms
- 内存：工作集 123→148.5MB，提交 91.5→115.1MB

### 3.4 `--tiletest` 块大小

| 块大小 | 结果 |
|---|---|
| 128 | PASS（去程 80 块 / 回程 0；360 块 / 预算 480） |
| 256 | PASS（去程 20 / 回程 0；90 / 140） |
| 512 | PASS（去程 5 / 回程 0；25 / 50） |

### 3.5 其他

- `--prefetchtest`：PASS（14 拍 / 28 块；再滚一格 0 光栅；预算 112/112）。
- `--appendtest`：8/8 PASS（含修正后的“整体下移”采样）。
- `--scrollflash`：PASS。
- `--ghosttest scroll`：PASS（扣环境噪声后 0 像素残影）。
- `--gclatencytest`：PASS（整笔低延迟档；GC 0/0/0；超时能退回）。
- `--memory`：空闲提交 90.8~91.1MB；10k 按笔画数约 366.9MB；清空+Trim 后 353.8MB（仍高约 263MB，D2D/驱动缓存；不是每笔泄漏，需长跑确认是否随重复写/清增长）。
- `--selftest 5`：10k 单屏 full rebuild 226.9~231.4ms（旧汇总曾显示 0.0ms）。

## 四、还没完全解决/需要知道的边界

1. **`StrokeAllocBytes` 仍然是“整笔会话累计分配”**，不是“这一笔新增的驻留内存”。
   - 它包含这一笔期间的渲染、UI、测试采样；池化只去掉了测试工具的大头。
   - 真正看内存请用 HUD/`--memory`/`--longrun` 的提交/工作集。
2. **GC 次数是进程级**。后台 PDF 渲染线程触发的 GC 也会被算进“这一笔期间”；低延迟档能压住前台 2 代，但后台 2 代仍可能有短停。
3. **`LastFrameMs` 含 Present 配速等待**。HUD“帧耗时”是实际墙钟；`--cameratest` 已用“工作耗时 = 墙钟 − 等待”判掉帧。DiagLog 的 `avgFrameMs` 仍含等待，解读时要区分。
4. **`LastPresentAreaPercent` 是“合并后的上屏矩形面积”**，不是严格的像素并集；角接的矩形可能把中间空隙算进去，但不会再 >100%。
5. **`_gpuMb` 是 DXGI Local 当前用量**；核显/UMA 与任务管理器“GPU 内存”不是同一列，不能直接对比。
6. **4K / 多屏 / 4GB 低端机未实测**；本报告数字只代表这台 2520×1680 / Iris Xe。
7. `--camlag`（手机 120Hz 录像）不在这套软件埋点里，未审计。
